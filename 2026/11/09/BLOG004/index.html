本地文件系统

磁盘可以看作一个巨大的数组。文件系统通过几层抽象，提供了诸如 READ，WRITE 等 API，让我们能够访问，修改磁盘中的数据。

考虑一个 naive 的文件系统，这个 FS 中只有一个巨大的数组，每个数组索引指向一个 block。

对于这个 FS，我们只能通过 block 下标来访问数据。那么当向文件后追加新的 data，撞到了已经存储有其他 data 的 block 该怎么办？想使用人类更容易理解的字符串文件名来访问文件怎么办？文件的读写权限怎么处理？文件系统即通过几层抽象来解决这些问题。

Block Layer

block 是文件系统管理 data 的最小单元，一般来说将一个 block 设置为 4K 大小（当然，这是一种效率与利用率 trade-off，更大的块会导致更多文件内部的空片段）——即使只需要写 1K data，也需要将 4K 的 block 读进来再写回去。一个 4K 的 block 大约为磁盘上 4 个连续的 sector，这层抽象可以将需要管理的 metadata 和索引数量缩小到原来的 4 倍。

super block 放在启动块的后方。这个块中存储了块的大小（即 4K），空闲块的数量，空闲块的 list 以及其他的文件系统元数据。

存储空闲块的方法是 bitmap，用一系列 0/1 bit 来指示每一个块是占用/空闲。

File Layer

一个文件有时候可能对应多个 block，但是我们一般习惯于以文件为单位来访问。只有 block 时我们并不知道哪个 block 属于哪个文件，这里我们使用 inode（index node）来指示这一信息。

inode 中存储了一个文件具体指向哪些块，文件的实际大小，以及其他的元数据。其大小是固定的，一个 inode 对应一个文件。

但是现在又有一个问题——inode 的大小是固定的，导致只用一层 block 索引的话文件的体积上限很小。和虚拟内存中的多级页表一样，这里使用多级 inode 来存储比较大的文件：

4 KiB 块、4 B 块号时 K=1024，单个一级、二级、三级入口分别覆盖 4 MiB、4 GiB、4 TiB。若块号改为 8 B，K=512。六个直接入口、一个一级和一个二级入口，分别覆盖 24 KiB、2 MiB、1 GiB。八个入口在 inode 内只占 64 B。

从 inode 访问文件时给一个 offset ，算出要访问的 block 在 inode 的 block_nums 中的索引即可。

inode Number Layer

inode 只是一个存储文件元数据和块映射的数据结构，但是我们缺少一个名字来指示每一个 inode 实例——因此引入了 inode number layer，赋予每一个 inode 实例一个编号，这样我们可以通过这个编号来访问文件。

在磁盘的数据块之前，再划分一片区域作为 inode table，集中存储 inode。其索引即为每个 inode 的 inode number。

现在放在一起：我们现在通过 inode number 来访问文件。给定要访问的 inode number 和 offset，通过 inode table 基址和 inode 大小找到对应的 inode 位置并返回，然后按照 offset 找到要访问的块。

现在我们在操作文件时，需要一个高效的方法来快速找到空闲的 inode——维护空闲链表和 inode 内部存空闲状态效率较低，和 block 一样维护一个 inode bitmap 就可以了。

inode table 不一定非要存储在数据区之前的连续位置。可以使用分组方法，为每一段连续存储维护一张 inode table，访问时根据 inode number 先确认分组再确认分组内编号；或者维护一张 inode number 与存储位置的映射表，可以更加灵活地安排 inode 和数据区域的位置。

File Name Number

到目前为止，我们可以通过 inode number 来唯一标识一个文件，这对于机器的访问已经足够了。但是对于人来说，需要一个更加容易理解的标识方式——我们更加习惯于用一个字符串来标识一个文件，这个时候就需要一种方法来建立文件名字符串到 inode number 的映射。

维护这个映射的结构为 directory，其本身就是一个文件，文件中则存储这些映射。

找文件的过程就是对文件中存储的映射表做字符串匹配，找到对应的文件并返回其 inode number。

Unix V6 的目录项固定为 16 B。inode 号占 2 B，剩余 14 B 存放文件名。这个限制按编码后的字节数计算。一个 ASCII 字母占 1 B，一个常见的 UTF-8 汉字占 3 B。四个这样的汉字占 12 B，可以放下，五个占 15 B，就超过了上限。

对于字符串匹配的查找过程，线性目录最坏要检查 N 项，成本 O(N)。大目录可以使用 ext4 HTree 等索引，先按名称哈希定位有关块，再比较名称。

Path Name Layer

目录可以进行嵌套，相对路径体现了文件/目录之间的包含关系。如果 path 是一个文件名（如 xx.txt），就去给定的 dir 中找它的 inode number；如果不是（比如 zz/yy/xx.txt），就把路径的最内层（即 zz/）取出来作为下一次搜索的目录，将除去最内层的 path（yy/xx.txt）作为下一次搜索的 path 递归即可。

path 会随着目录的嵌套越变越长，这个时候我们希望给文件一个简短的“别名”，让我们用一个较短的别名来访问文件，这里即需要用到 LINK。

LINK 在当前的上下文下将一个指定 path 的文件链接到一个别名上（即建立一个 Hard Link），UNLINK 则解除掉一个文件名到 inode 的链接。LINK 和 UNLINK 的过程中维护一个 reference count，即指向一个文件的名称数量。当一个文件的 refcnt 减小到 0 时，这个文件被删除。

Absolute Path Name Layer

相对路径以一个目录为 context 来指示一个文件。但是每一个相对路径（包括一个文件名）一定在一个目录的上下文里，一个目录作为一个文件，也一定在另一个目录的上下文中，被一个名字链接到。这样考虑的话会无限向上嵌套，所以需要规定一个没有名字的根目录作为最外层的一个目录，即 root 目录（路径表示为 /）。在 / 的上下文中无论执行 cd 到 .. 还是 . 都会回到 / 中。

Symbolic Link Layer

不同的设备上有不同的 inode 空间，电脑的硬盘和插进来的 U 盘，所持有的 inode X 对应的是两个设备中不同的文件。然而，一个硬链接一般直接指向一个文件，所以在使用硬链接访问时会直接访问本机上对应的 inode，无法跨设备访问。

此时我们需要一个类似于“快捷方式”的方法来访问其他存储设备上的文件，即 Symbolic Link（Soft Link），其通过一个文件直接存储链接文件的绝对路径来进行链接。外部的文件系统一般通过挂载的方式接入本机的文件系统。假设我们有 FS_A 和 FS_B 两个挂载的文件系统：

假设现在要访问 report.txt，用户给出路径 /mnt/data/report.txt，内核顺着路径查找，找到 data 挂载点后，因为其持有文件系统和挂载点的信息，所以知道 report.txt 的 42 是属于文件系统 FS_B 的，因此可以正确完成访问。软链接即通过存储绝对路径名来实现跨存储设备的访问。

实际上可以给软链接赋予一个不存在的文件路径名，访问时沿着路径搜索会发现文件不存在，重新创建文件，软链接就可以搜索到对应的文件。一个软链接文件的大小取决于其存储的绝对路径名的长度，如 “/tmp/abc” 即为 8 个 char，即 8 Byte。

软链接是一个独立的文件，并不会改变一个 inode 的 refcnt，这一点类似于快捷方式——文件删除时，软链接不会消失，而是会提示文件不存在；删除一个软链接，链接的文件的硬链接数量并没有变化。

当我们通过软链接前往一个路径，然后切换到 .. 时，是回到当前目录的上一级，还是回到软链接所在的目录呢？答案是后者：Linux 出于“用户友好”的设计，会保存进入当前上下文之前的路径，以便在使用 .. 时访问，因此实际上会进入之前软链接所在的文件夹而不是相对当前目录的上级文件夹。

文件系统 API

应用通过系统调用访问文件系统。CHDIR 切换当前目录，MKDIR 创建目录，CREAT 创建文件，LINK、UNLINK、RENAME 和 SYMLINK 修改名字与文件之间的关系。MOUNT 和 UNMOUNT 挂载、卸载文件系统。对于 READ，内核会根据路径所属的挂载点，调用对应文件系统提供的实现。

打开文件

考虑 open("/foo/bar", O_RDONLY)。内核沿路径找到 bar 的 inode，还要判断当前用户能否读这个文件。inode 中的 userid 和 groupid 记录文件的所有者和所属组，可以用 chown 修改。mode 分别记录所有者、同组用户和其他用户的读、写、执行权限。

图中最后三个字段记录不同的时间。读文件内容会更新访问时间 atime，写文件内容会更新修改时间 mtime。inode 的状态（如文件大小，block 表等元数据）发生变化时更新 ctime，例如给文件增加一个硬链接，链接计数就会变化。

open() 成功后返回一个整数，叫作文件描述符（fd）。进程把 fd 交给 read()、write() 或 close()，内核就能找到这次打开的文件。这样既省去了每次读写时重新查路径的开销，也把 inode 指针和磁盘块号留在内核里。用户程序只能按打开时取得的权限操作文件。

fd 属于进程。一般情况下，0、1、2 分别对应标准输入、标准输出和标准错误。其他文件的访问操作拿到的 fd 从 3 开始，且规定每一次取新 fd 时都必须取当前最小的空闲 fd。

C 标准库的 fopen() 在 Windows 和 Linux 上都能用，返回的是 FILE *。在 UNIX 上，底层的 open() 返回 fd。用 fopen() 打开的流可以在用户态缓冲数据，多次小写入可以合并成一次系统调用。

fd 和 cursor

两次 read(fd, buf, n) 怎样接着读？内核为每次打开的文件记录一个以字节为单位的 offset，也叫文件游标（file cursor）。读写后游标前移，lseek() 可以直接改变它的位置。

每个进程有一张 fd_table，用 fd 查到系统打开文件表 file_table 的下标。后者的一项记录 inode number、游标，以及有多少个 fd 引用这一项。

图中 A 和 B 分别打开 inode 23，各自拿到 fd 3。A 的 3 指向表项 115，游标在 128，B 的 3 指向表项 116，游标在 240。B 调用 fork() 后，子进程 C 继承了 B 的 fd 3，也指向 116。假设 C 成功读取 8 字节，B 下次就从 248 开始读，A 仍从 128 开始读。父子进程向同一个已打开的输出文件写数据时，会共用这个游标。

OPEN 和 READ

OPEN 先用文件名和当前目录 wd 查 inode number。找不到且设置了创建标志时，就按给定的 mode 创建文件。创建失败或权限检查失败就返回错误。检查通过后在 file_table 中增加一项，再从当前进程的 fd_table 中找一个空位，把新表项的下标填进去。返回给进程的 fd 就是这个空位的编号。

READ 用 fd 找到游标和 inode，再决定能读多少。例如文件有 100 字节，游标在 80，这次请求读 32 字节，实际只能读到剩下的 20 字节。内核根据 offset 查找 data block，从块内对应的位置把数据复制到 buf，遇到块边界就接着读下一块。伪代码第 4 行记录访问时间 atime。读完后游标移到 100，返回 20。此时再请求读数据，就到了文件末尾，UNIX 的 read() 返回 0。

接下来的三次 write() 各写入一个新块。每次先读文件的 inode，读写 data bitmap 以分配一块，写入数据，再把新块号、文件大小和 mtime 写回 inode，共 2 读、3 写。覆盖已有块时可以沿用原块号。WRITE 从当前游标写起，APPEND 则在每次写入时取当时的文件末尾作为起点。

  • 位图 → 数据 → inode（推荐）
    先把块标为已占用，再写入内容，最后更新 inode 的指针和大小。若在更新 inode 前断电，可能留下“已占用但无人引用”的块，造成空间泄漏，可通过 fsck 回收；文件不会引用尚未写好的数据。

  • 位图 → inode → 数据
    若更新 inode 后、写入数据前断电，文件大小和指针已经更新，但新块的内容尚未写好。读取文件新增部分时，可能读到磁盘残留的旧数据。

  • inode → 位图 → 数据（风险最大）
    若更新 inode 后、更新位图前断电，文件已经引用该块，位图却仍将它标为空闲。该块可能被再次分配给其他文件，导致数据相互覆盖；此外，也存在第二种顺序中的旧数据问题。

实际读写会经过 block cache，读过的块可以直接从内存中取，多次修改同一块也可以合并后再写盘（以及同一批次的修改中， atime 这类元数据的值可以只在最后修改一次，而不是每次读写都改）。因此上面两张表中的块访问次数和磁盘实际收到的 I/O 次数可能不同。write() 返回时，改动可能还在缓存里。程序需要等某个文件的数据和元数据写回存储设备时，可以对它的 fd 调用 fsync()。系统范围的 sync() 会安排待写回的文件系统改动一并写出。

关闭与删除

CLOSE 先清除本进程 fd_table 中的条目，再把对应 file_table 表项的引用计数减 1。回到前面的图，C 关闭 fd 3 后，表项 116 仍由 B 使用。B 也关闭它，116 的计数才降到 0，这一项就可以释放。

这里有两个计数。inode 的硬链接计数记录有几个目录项指向这个文件，打开文件表中的计数记录有几个 fd 指向这次打开记录。在 UNIX 上，另一个进程可以在文件打开期间 unlink 它的最后一个名字。原路径随即消失，持有 fd 的进程仍能读写文件。等最后一个打开引用也释放，文件系统才回收 inode 和数据块。

跨目录重命名

看一次同一文件系统内的 mv dir1/from.txt dir2/to.txt。ls -il 输出的第一列是 inode number。操作前，from.txt 是 40978804，已有的 to.txt 是 40978827。操作后 dir1 为空，dir2/to.txt 变成了 40978804。这个过程中先将要覆盖的文件 to.txt （40978827）解除链接，然后将释放出来的名字链接到 from.txt （40978804）上，然后解除旧链接。因此后面打开的 to.txt 实际是指向了原来的 inode 40978804。

编辑器把修改后的内容写入临时文件 .a.txt.swp。保存时用它替换原来的 a.txt，就要让名字 a.txt 指向临时文件的 inode。左边的方案先删目标名，再建立新链接。若第一步刚写盘就断电，原来的 a.txt 已经消失。右边先把目标目录项改为指向源 inode，再移除源目录项。

按右图的顺序，中途断电时 to.txt 仍然存在，但两个名字可能同时指向源 inode。恢复时需要让硬链接计数与实际留下的目录项一致，并在被替换的旧文件没有其他引用时回收它。

Remote Procedure Call

生成网页时，应用服务器需要读一张图片，图片存在另一台文件服务器上。本地的 READ 可以沿着 inode 找到磁盘块，两台机器之间还要多走一趟网络。应用服务器把“读哪张图片”发过去，文件服务器在本机执行 READ，再把图片内容传回来。把这次交互封装成一次函数调用，就是远程过程调用（RPC）。

RPC 可以建立在 socket 之上。直接用 socket 时，每项服务都要写一遍 read()、write() 或 sendmsg()，还得约定对方怎样解释收到的字节。RPC 把这些工作交给封装好的公共代码，应用按函数签名传参、取返回值。调用者不需要知道目标文件系统的 API 实现细节就能使用同一封装的函数访问文件系统。

Stub

考虑给客户端校时。准确的时钟在服务器上，客户端想执行 t ← GET_TIME(SECONDS)，再用 SET_CLOCK(t) 设置本地时间。如果两个函数就在一个进程里，GET_TIME 直接读取 CLOCK，按 units 换算并返回。把它移到服务器以后，跨网络传送的是时间单位和算出的时间，设置时钟仍由客户端完成。

先看手写 socket 的版本。客户端连到 TimeServiceAddr，发送操作名和编码后（不同机器上时间的存储方式不同，如不同系统可能采用大端/小端存储，因此需要 CONVERT2EXTERNAL 来转换）的 SECONDS，等到回复再还原时间。服务端监听端口，接受连接，逐条读取请求。操作名为 "Get time" 且单位为秒或分钟时，服务端返回 "OK" 和换算后的时间，否则返回 "Bad request"。真正与校时有关的只有读取、换算和设置时间，标黄的部分，即与矫时无关，可以复用的过程，就可以用 RPC 封装起来。

把这些通信代码封装起来，就得到两端的 stub（存根）。客户端 stub 提供一个同名的 GET_TIME。调用者传入 units，stub 把参数装进请求，发送后等待回复，再检查状态、解码返回值。这样 SYNC_CLOCK 就可以沿用单机时的写法。

服务端 stub 做相反的工作。它从请求中取出操作名和参数，检查后调用本机的 GET_TIME(arg)，再把结果装进回复。处理网络请求的 TIME_SERVICE 和实际读时钟的 GET_TIME 因此可以分开写。

沿图从左往右看，一次调用经过客户端、客户端 stub、服务端 stub 和服务函数。只有 REQUEST、RESPONSE 两个箭头跨过网络。客户端在请求发出后等待，服务函数返回给服务端 stub 后，经过回程网络回到调用者手里。

请求与回复

socket 上传的是字节。两个 stub 除了要认出参数，还要约定这是什么操作、要调用哪个版本，以及回复该交给谁。图中的 "Get time" 就是一个最简单的操作标识。

以 Sun RPC 的报文为例，请求和回复带有下面这些信息。

报文 主要字段 接收方用它做什么
请求 xid、调用标记、RPC 版本、程序号、程序版本、过程号、认证信息、参数 先检查协议和身份，再用程序号、版本、过程号找到服务函数
回复 原请求的 xid、回复标记、接受或拒绝的状态，以及相应的认证、执行状态或结果 客户端先找到对应调用，再判断能否取出返回值

假设两个线程共用一条连接，线程 1 请求 page.html，线程 2 请求 logo.png。服务端并发处理，图片先读完，先回到客户端的接收缓冲区。此时若线程 1 取走第一条回复，就会把 PNG 当网页，因此需要为请求添加可唯一标识的编号，即 xid。给两个请求分别标上 1、2，服务端在回复中原样带回编号，客户端就能把 2 号回复交给正在等图片的线程。

为什么不为每个 Thread 独立维护一个 buffer 来解决拿错响应的问题？

请求和回复的传递需要通过网卡。网卡上并没有并发控制，会对每一个 buffer 建立一个物理队列。但是实际上网卡的物理资源是很有限的，支持的并发数量有限（量级最多到千级别），因此为了可拓展性和易维护性使用一个公用的 buffer。

参数编码

整数可以按值发送，但发送一个指针会怎样？指针里存的是客户端进程的虚拟地址，服务端有自己的地址空间。若参数里有一个指向字符串的指针，客户端可以把字符串长度和内容装进消息，服务端收到后在本地分配空间，再建立指针。把程序中的值转成约定的字节表示叫作序列化（marshal），从字节还原成值叫作反序列化（unmarshal）。

即使只传一个整数，也要约定字节顺序。同一个参数 0x89abcdef，大端机器从低地址起存为 89 AB CD EF，小端机器则存为 EF CD AB 89。整数宽度、浮点表示、结构体对齐和字符编码也可能不同。比如“中”在 GBK 中占两个字节 D6 D0，在 UTF-8 中占三个字节 E4 B8 AD。另外，不同机器上，相同的数据类型可能占不同的字节数，按照相同的规则进行编解码就会出现对齐问题。

两端可以约定一种独立于语言的格式，例如 Sun RPC 使用的 XDR、ASN.1 的编码规则、JSON、XML 或 Protocol Buffers。用 JSON 表示请求时，查看消息就能读到 xid、call 和 rpc_version，抓包调试很方便，读取对人类友好。XML、YAML、TOML 和 CSV 也使用文本表示。代价是字段名或标签占用空间，数字精度取决于双方的类型约定，任意二进制数据放进 JSON 字符串还要另行编码，例如转成 Base64，如果涉及大模型参数等大量数据的传递时转换和传递的效率很低。

二进制编码

考虑同一条 Person 记录。用户名是 Martin，喜欢的数字是 1337，兴趣是两个字符串。图中最下方的 JSON 去掉空格后共 81 B。Thrift 和 Protobuf 先用接口定义语言（IDL）写下 schema，给三个字段分别分配编号 1、2、3。这样接收端已经知道字段名和声明的类型，发送端可以在消息里用编号表示字段。

Thrift 的 BinaryProtocol 用 1 B 表示字段类型，2 B 表示字段编号，整数采用定长大端编码。看第一行，0b 表示字符串，00 01 表示字段 1，接下来的 4 B 表示长度 6，最后 6 B 才是 Martin，这一项共 13 B。第二项把 1337 存为 8 B 的 i64。第三项还要记录列表的元素类型、元素个数和每个字符串的长度。算上最后的结束标记 00，整条记录为 59 B。

换成 CompactProtocol，相邻字段的编号差很小，可以把差值和字段类型合在一个字节里。整数则用变长编码（varint），每字节的低 7 位装数据，最高位为 1 表示后面还有一个字节。Thrift 先用 ZigZag 把有符号的 1337 映射成 2674，再按低位在前分组，得到 F2 14。图中第二个字段的值从 8 B 降到 2 B，整条记录降到 34 B。

gRPC 常用 Protobuf 编码。同样是字段 2，图中声明的类型为 int64，正数 1337 直接按 varint 编码。因为 1337=10×128+571337=10\times128+571337=10×128+57，低 7 位是 57（0x39），设置最高位得到 B9，剩余的 10 编成 0A。前面的 0x10 是字段 2 和 wire type 0 组成的 tag，因此这一个字段一共占 3 B。

消息从 81 B 缩到 34 B，一次 RPC 就会按同样的比例变快吗？在相同带宽下，少传 47 B 可以缩短这条记录占用链路的时间（网络时间=负载大小/带宽）。一次调用还要花时间编码、解码、等待网络往返和执行函数。网络传输足够快时，这些 CPU 开销可能占去大部分时间。

版本兼容

客户端和服务端往往分批升级。假设旧的 Msg 只有 id，新版增加了 priority。新程序读旧消息时，把缺少的 priority 按约定取为 0，叫作向后兼容。旧程序读新消息时，仍能取出 id，并跳过不认识的 priority，叫作向前兼容。

在 Person 的例子里，字段 1 和 2 保留原来的编号和类型，新加的可选字段 interests 使用编号 3。下图上半部分由新版 reader 读取旧消息，读到结束标记时，字段 3 保持未设置。下半部分的旧版 reader 根据字段类型和长度跳过整个列表，再继续解码。后续版本如果把原有编号改派给含义不同的字段，旧 reader 就可能把新数据当成自己认识的值。

有了接口定义，RPC 编译器可以根据函数编号、参数和返回类型生成两端的 stub，以及配套的序列化代码。调用时，客户端通过服务名或已配置的地址找到服务端，这一步叫作绑定（binding）。服务端框架按过程号分派请求，客户端框架按调用编号唤醒线程或触发回调。收发消息的实现也可以封装在框架内，应用沿用相同的服务接口，底层按框架及硬件支持选择 TCP、UDP 或 RDMA。

超时与重试

调用本地函数时，调用者和被调用者通常处在同一进程里。跨机器以后，客户端可能仍在运行，服务器却已崩溃，或者只有中间的网络出了问题。参数错误可以由服务端直接返回。超时只表示客户端在规定时间内没有收到回复。

第一行中，请求可能在路上丢失，也可能只是排在队列里。第二行中，服务器可能崩溃，也可能正在做垃圾回收，暂停后还能继续执行。第三行中，函数已经执行，丢失或延迟的是回复。六种情况下客户端都可能超时，重发请求的后果却不同（如 Server 已执行未返回则会导致恢复时重复执行；如果服务端 crash 则会只运行一次）。

在 gRPC 示例里，SayHelloAgain 返回 Status。只有 status.ok() 才读取 reply.message()，失败分支读取错误码和错误信息。要不要重试，还得看这个函数多执行一次会发生什么。

执行次数

设 B 的余额原本为 0，客户端发出编号为 7 的请求，要求给 B 转入 100 美元。如果回复丢了，客户端可能重发同一个请求。服务端如何处理第二份请求，决定了这次调用对余额的影响。

  • 至少一次（at-least-once）。客户端持续重传，在通信和服务最终恢复的条件下，请求会执行一次或多次。第一幅图中，两次请求都执行了加款，客户端最终收到成功，余额却是 200 美元。
  • 至多一次（at-most-once）。同一个逻辑调用最多执行一次。第二幅图中，服务端认出编号 7，重发上次的回复，余额为 100 美元。Birrell 和 Nelson 的 RPC 中，成功返回表示执行了一次。如果探测发现服务器已经崩溃，调用者可能只得到 CRASH。第三幅图中，B 的余额可能是 0，也可能是 100，调用者要查询这笔转账的记录才能判断。

什么操作可以直接重试？看下面的 ReadTime。两个客户端各发一次请求，第二个客户端的回复丢失，于是它重试，服务端总共读了三次时钟。第三次读到的时间可能更晚，但多读一次不会修改服务端的状态。

重复执行同一操作，产生的效果与执行一次相同，称为幂等。例如重复执行 i = 1，结果仍为 1。重复执行 i++ 则会多加一次。下图中的 Like() 也是如此，两个用户各点一次赞，一次重试就让计数从预期的 2 变成了 3。投票、入账等操作都需要区分“用户又做了一次”和“上次请求又送到了一次”。

请求去重

客户端为每次新的逻辑操作分配一个调用 ID，重试时带回原 ID。在 Birrell 和 Nelson 的设计中，同一客户端活动依次发起调用，服务端可以按活动保存最近的调用序号。图中 C0 的第 1 次点赞和 C1 的第 1 次点赞来自不同客户端，因此要分别计数。C1 重发的仍是 C1:#1，服务端认出它已经处理过，直接返回已有结果，计数停在 2。如果重复请求在第一次调用还没结束时就到达，服务端也要认出它正在执行，避免两个线程同时进入 counter++。

Sun RPC 的数据报实现可以启用回复缓存。服务端根据调用标识等信息找回原回复，直接发给客户端，随后返回。缓存项被淘汰或随重启丢失后，再来的旧请求就可能重新执行。

要让一次点赞的效果在服务端重启后仍然恰好发生一次（exactly-once），服务端得把“计数加一”和“这条请求已完成、回复是什么”一起持久化。如果先更新计数，还没记录调用 ID 就崩溃，恢复后重试会再加一次。如果只存了“已完成”，计数却没写入，重试又会漏掉这次点赞。在故障最终修复、客户端持续重试的前提下，让业务修改和去重记录一起生效（即作为一个事务），才能同时避免漏做和重复做。

实际的重试策略通常有次数限制。ReadTime 配置的 maxAttempts: 3 包括第一次调用，因此最多再试两次。如果三次请求都没送到，服务端可能一次也没执行。只有遇到 UNAVAILABLE 才按这项策略重试，初始退避为 0.1 秒，之后按 2 倍增长，上限为 1 秒。这样的配置能让一次短暂故障后的读请求再试一次。

分布式文件系统

通过终端登录远程机器、打开网盘选文件都需要显式选择远端资源。换成挂载好的文件系统，程序可以直接调用 open("/home/paul/image.png", O_RDONLY)。程序传入的是普通路径，客户端负责判断数据在哪台机器上，并用 RPC 完成访问。

NFS

Sun 在 1980 年代为工作站设计了 NFS（Network File System）。一台机器可以把自己的目录共享给别的机器，也可以挂载别人的目录。这样，没有本地磁盘的工作站也能访问文件，两端可以使用不同的硬件、操作系统和本地文件系统。

假设服务器 192.168.1.100 要共享 /users/paul。管理员在服务器的 /etc/exports 中配置共享目录和访问范围，客户端执行图中的 mount 命令，把它挂到本机的 /home/paul。

挂载时，客户端向服务器申请访问这个目录，取得目录的文件句柄（file handle，简写为 fh）。内核的虚拟文件系统（VFS）把挂载点关联到远端目录。之后解析路径，一旦走到 /home/paul，剩下的名字就交给 NFS 客户端查询。服务器则通过自己的文件系统查目录、读 inode、访问磁盘。

打开和读取

应用看到的接口和网络上实际发送的请求有些差别。看 OPEN 和 READ 两行，应用使用路径和 fd，服务器收到的是目录句柄、文件名，或文件句柄和偏移。中间的转换由 NFS client 进行。

沿着下图读一次文件 f。

  1. 应用调用 OPEN("f", 0)。NFS 客户端向服务器发送 LOOKUP(dirfh, "f")，取得文件的 fh 和属性，在本地建立打开记录，把 fd 返回给应用。
  2. 应用调用 READ(fd, buf, n)。客户端通过 fd 找到 fh 和当前游标。第一次从偏移 0 开始，网络请求就是 READ(fh, 0, n)。服务器返回数据和属性，客户端将数据复制到本地的 buf，并按实际读取的字节数推进游标。
  3. SEEK 在客户端调整游标。应用关闭这个只读文件时，CLOSE 释放本地打开记录。服务器没有对应的打开记录需要释放。

同样，WRITE 要把待写的字节带上网络，客户端的内存地址 buf 只在本进程中有效。STAT 可以对句柄调用 GETATTR。创建目录、删除名字或重命名时，客户端把路径拆成“父目录句柄和名字”，跨目录的 RENAME 则要带上两组。

为什么由客户端保存游标？假设客户端 A、B 都拿到了 fd 3，但 A 打开的是 f，B 打开的是 g。按图中上半部分的做法，服务器得记住每个客户端的 fd 对应哪个 inode、cursor 在哪里。随着连接的用户增长这张表也会线性增长，增大维护压力。而且一旦 server 崩溃，所有的 API call 都是失败的，维护的 fd table 也会丢失，需要在所有的 client 重新 open 并记录状态。因此这里将由 fd table 的状态分别存在各个用户的 NFS Client 中，这样的服务端就是无状态（与客户端数量无关）的。将状态移动到 client 端，在 Server 崩溃时，用户端会进行 retry，Server 恢复时文件的访问状态不依赖服务端的状态也可以恢复。

在无状态的实现下，客户端每次都发送 fh、offset 和 count，服务器仅凭当前请求和磁盘上的文件就能完成读取。早期 NFS 常用 UDP，客户端超时后可以重新发送请求。遇到重复请求，服务器还可以用 xid 查回复缓存，命中时重发已有结果，避免重复执行。缓存被清空后，这层去重保护也就失效了。

对话接口也可以采用类似的设计。图中客户端每次在 input 里带上前几条消息，服务端便知道这一轮所需的上下文。如果只传 previous_response_id，服务端就得能凭这个 ID 找回上一次的内容。NFS 把句柄和游标带在请求里，也是为了让服务器能从当前请求继续工作。

文件句柄

fd 是 Application 视角使用的标识符，client 会将这个标识符翻译成句柄，用来标识先前打开的是哪个文件。把路径直接存进句柄，会遇到下面的问题。客户端 1 进入 dir1 并打开 f。客户端 2 随后把 dir1 改名为 dir2，再把另一个目录 dir3 改名为 dir1。此时客户端 1 用旧 fd 读文件，应该读到原先打开的对象，也就是现在的 dir2/f。如果重新解析字符串 dir1/f，就会走进另一个目录。

用 inode number 可以避开改名，但 inode number 会复用。下图中客户端 2 打开旧的 f，句柄包含 inode 7、代次 1。客户端 1 删掉 f 后又创建同名文件，新文件恰好也分到 inode 7。这次分配把代次（generation number）增为 2。服务器再收到旧句柄 (7, 1)，检查出代次不同，就返回句柄失效错误。

客户端只需把 fh 原样传回，具体格式由服务器决定。典型句柄能标识所属文件系统、inode number 和该 inode 的分配代次。同一个文件修改内容时仍可沿用句柄，编号被分配给新文件时才需要新代次。本地 UNIX 会为已经打开的 fd 保留被删除的文件。这个 NFS 例子中，服务器没有记录客户端 2 的打开状态，因此旧读请求可能报错，但不会读到新文件。

客户端缓存

读取远端文件时，一次网络往返可能比读数据本身还慢。NFS 客户端会缓存文件数据、文件属性，以及“目录中的名字对应哪个句柄”的查找结果。于是再次执行 READ、GETATTR、LOOKUP、READLINK 或 READDIR 时，有机会直接用本地结果。服务器自己的 block cache 也能减少磁盘访问。对于顺序读取，客户端还可以把下一段提前读进来。例如，客户端一次预读 8 KB，应用随后分几次读取这段数据时，就可以直接从缓存取。

有了两份缓存，客户端 2 什么时候能看到客户端 1 的修改？图中服务器原有 v1。客户端 1 写入 v2 后，新内容暂时只在本地缓存中，这个块被标记为脏块。客户端 2 此时打开并读取文件，仍可能得到 v1。等客户端 1 关闭文件、把脏块写回服务器，客户端 2 再次打开时检查文件属性，发现修改时间已经变化，就丢掉旧缓存并取得 v2。

这种约定叫作 close-to-open consistency。它适合一个程序写完并关闭、另一个程序再打开的用法。若要求两个已打开文件的客户端在每次读写后都看到对方的最新结果，就需要更频繁地验证或协调缓存。客户端还可以给属性缓存设置有效期，如普通文件 3 秒、目录 30 秒，到期后重新检查。

NFSv3 支持 64 位文件大小、大块传输和 COMMIT。例如服务器先接受一批尚未写入稳定存储的数据，客户端随后用 COMMIT 确认写回。也有锁管理器、NVRAM、动态重试和客户端磁盘缓存等配套机制。到了 NFSv4，协议开始维护打开等状态，支持缓存委托、统一的导出命名空间、ACL 和安全机制协商。多个连续操作还可以合成一次 RPC，减少网络往返。

GFS

Google File System 面向网页归档、索引和 MapReduce 等批处理任务。单个文件常有数 GB，许多客户端同时读写。集群里有成千上万台普通机器，某台机器或某块磁盘停机属于系统日常要处理的情况。GFS 把客户端库链接到应用程序，提供创建、删除、打开、关闭和读写等接口，省去了 UNIX 的硬链接、软链接等操作，另外提供快照（snapshot）和记录追加（record append）。

分块与副本

GFS 把一个文件切成固定大小的 chunk，默认 64 MB。每个 chunk 创建时由 master 分配唯一的 64 位 handle，默认在三台 chunkserver 上各存一份。图中 1 TB 文件的第一个块 C0 在节点 1、2、3，第二个块 C1 在节点 2、3、4。master 保存文件到 chunk 的映射，以及各 chunk 当前有哪些副本。chunkserver 把每个 chunk 存成本地 Linux 文件，内部每 64 KB 数据配一个 32 位校验和，用来发现损坏。热门文件还可以增加副本来分担读取。

为什么选 64 MB？本地 ext4 常见的块大小是 4 KB，GFS 的 chunk 却是客户端向 master 查询位置的单位。chunk 越大，同一个文件需要的映射条目越少，顺序读也越容易复用位置和连接。图中要连续读 3 MB，每次读 1 MB。若三个小块分别位于三台机器，客户端需要与三台机器分别握手。若三次读取都落在同一个 64 MB chunk 上，和一台 chunkserver 建立一次 TCP 连接就够了。

使用较大的 chunk，单个 master 就可以在内存中存储查询这些元数据。名称和文件由哪些 chunk 组成的信息保存在操作日志与检查点中。哪台机器现在持有哪些 chunk 则可以在启动时向各台 chunkserver 查询，再根据周期性心跳更新。数据读写直接走 chunkserver，master 不用转发每一个数据块。

读 chunk

客户端先根据文件偏移算出 chunk 下标，把文件名和下标发给 master。master 找到 handle 和副本位置，一并返回。客户端缓存这份元数据，选一个副本，发送 handle 和块内的字节范围。下图第一次读时经过 master，第二次读取同一 chunk 时直接访问 chunkserver。

大文件往往顺序读一遍就换下一个，长期保留客户端数据缓存的收益较小。GFS 客户端主要缓存 chunk 的位置。chunkserver 读取本地文件时仍可利用操作系统的页缓存。

写入冲突

假设两个客户端同时覆盖同一 chunk 的同一段字节，一个写 A，另一个写 B。如果三个副本都按消息到达顺序各自写入，节点 1、2 先收到 A 再收到 B，最终为 B。节点 3 先收到 B 再收到 A，最终为 A。下一次读哪个副本就会得到哪个结果。

GFS 为每个 chunk 指定一个 primary，其余副本叫作 secondary。master 通过租约（lease）授权 primary 为该 chunk 的修改排序，初始租期为 60 秒，可以随心跳续租。一次写入分为两个阶段。

  1. 传数据。 客户端向 master 查询并缓存 primary 和各 secondary 的位置，再把待写字节沿副本链传下去。示例中先到 secondary 1，再到 primary 2，最后到 secondary 3。此时各节点只把数据放进缓冲区，收到数据的顺序不会决定最后的文件内容。data 在沿着链向下传输时，实际上是一次向下发 chunk 的一个小 piece，下一个 piece 过来时同时将上一个 piece 沿着链条传递给下一个 chunkserver。放到一个较大的文件传输过程来看，实际上和只传递到一个 chunkserver 使用的时间差距不大（可以类比 CPU 指令流水线）。

  1. 执行写入。 收齐副本的接收确认后，客户端向 primary 发送写请求。primary 分配序号，在本地执行修改，再通知各 secondary 按同一顺序写入之前缓存的数据。各 secondary 完成后向 primary 确认，primary 再回复客户端。这个阶段传的是写入指令和确认，大块数据已经到位。

回到 A、B 同时覆盖的例子。如果 primary 确定的顺序是先 A 后 B，所有成功执行这两次写入的副本最终都是 B。序号解决本轮写入的先后问题。master 另外维护 chunk 的版本号，用来识别在故障期间错过更新的旧副本。旧副本要退出可读副本集合，再从有效副本补齐。

GFS 常与任务调度器一起部署。一台普通 Linux 机器既运行 chunkserver，也能执行分配来的计算任务。在 Google 早期的集群部署中，单个 GFS 文件系统的容量曾超过 4 PB，读写负载达到 40 GB/s，集群里可以同时运行数百至数千个作业。调度器若把任务安排到保存输入 chunk 的机器，读取时就能少走一段网络。

HDFS

Hadoop 的 HDFS 借鉴了这种分工，同样面向普通硬件上的大数据集、高吞吐和节点故障。对照下图，GFS 的 master 对应 HDFS 的 NameNode，chunkserver 对应 DataNode，chunk 在 HDFS 中叫作 block。NameNode 用 FsImage 保存命名空间快照，用 EditLog 记录后续变更。重启时结合两者恢复文件和块的映射，再根据 DataNode 的块报告得到副本位置。

3FS

DeepSeek 的 Fire-Flyer File System（3FS）服务于 AI 训练和推理。数据准备阶段会产生许多中间文件，训练的 dataloader 要随机读样本，保存 checkpoint 时多个节点又会集中写入。checkpoint 的写入需求可超过每节点 10 GiB/s，推理侧读取 KV cache 的峰值达到 40 GiB/s。

早期 GFS 的一台存储机有两块 80 GB 磁盘和 100 Mbps 以太网。3FS 节点有 16 块 NVMe SSD 和两条 200 Gbps RDMA 链路。按标称速率相加，网络带宽相差 4000 倍。与此同时，访问从大文件上的顺序读，变成了遍布许多文件的 KB 至 MB 级随机读。此时每读一个新块都去问元数据服务，查询本身就可能先成为瓶颈。

元数据与目录

3FS 有四类参与者。客户端替应用打开文件、提交读写。元数据服务处理名称、inode、属性和文件布局。存储服务保存分块及其副本，直接与客户端传输数据。集群管理器通过心跳和租约维护节点状态及配置。沿图中的两条实线看，查名字走元数据服务，读文件内容走存储服务。

3FS 把目录项和 inode 放在 FoundationDB 中。它是一个支持事务的分布式键值存储。元数据服务实例都访问同一份记录，所以可以增减实例，某个实例崩溃后也可以由其他实例继续处理。对照 GFS，单 master 要把全部元数据放在自己的内存里，同时处理所有元数据请求。右侧的 3FS 可以把查询分给多个前端，共享记录的并发修改则由数据库协调。

用前面讲过的跨目录改名来看事务有什么用。假设 /x、/y 的 inode 号分别为 2、5，/x/a.txt 的 inode 号为 7。把目录项和 inode 简写成键值对，键 DENT|2|a.txt 对应值 7，键 INOD|7 则保存文件属性和布局。将文件移到 /y/a.txt，要删除旧键 DENT|2|a.txt，再建立 DENT|5|a.txt → 7。两处修改在同一事务中提交，要么一起生效，要么都不生效。如果另一个服务同时删除源目录项，遇到冲突的一方需要重新读取后再决定怎样处理。

打开文件

一个训练作业启动时，许多 worker 会同时打开样本文件。若每次只读打开都往数据库写一条会话记录，还要在关闭时删除，就会产生大量元数据写入。3FS 只在服务端记录写打开。图中 s0001 是只读样本，清理程序删除它后可以直接回收，原读者后续访问可能失败。ckpt-7 正被 worker 2 写入，删除名字后，数据要等写会话结束再回收。这样写入者不会在文件已经回收后继续留下新的数据块。

定位 chunk

在 GFS 中，客户端换到一个位置尚未缓存的 chunk，通常要向 master 查询。3FS 在打开文件时把布局给客户端，包括 chunk 大小、条带宽度和复制链列表。复制链是一组共同保存副本的存储目标。客户端拿到布局后，就能算出要访问哪条链，再按集群配置找到链上的存储节点。

图中 a.txt 的 inode 号为 7，条带宽度为 3，链列表依次为 1、2、3。给定字节偏移，先除以 chunk 大小取整得到块号 index，余数是块内偏移。chunk ID 由 inode 号和块号组成。图里的简化布局按 chains[index % stripe] 选链，因此第 3 块的 ID 是 (7, 3)，余数 0，对应 chain 1。第 4 块是 (7, 4)，余数 1，对应 chain 2。两次读取都可以直接联系存储服务。

计算与存储分离

MapReduce 通常把计算安排到持有输入块的节点。图左侧要处理 C2，调度器就把 map task 放到保存 C2 的机器。3FS 把 GPU 和 SSD 分别部署在计算节点、存储节点上，GPU 可以通过高带宽 RDMA 网络读取不同节点上的样本。调度训练任务时无需按样本所在磁盘挑 GPU，这就是 locality-oblivious。计算不足时加 GPU，容量不足时加存储，两类资源可以分别扩展。

FUSE 与原生 I/O

普通程序可以挂载 3FS 后直接调用 open()、read()。FUSE（Filesystem in Userspace）让 3FS 的文件系统逻辑运行在用户态。按图中的箭头，应用的读请求先进入内核 VFS，再由 FUSE 放入共享请求队列。用户态的 3FS daemon 取出请求，通过 RDMA 访问存储服务，再把结果经内核交给应用。

当 SSD 和网络都很快，小块读的成本就可能主要花在本机。多个线程进出 FUSE 队列要竞争自旋锁，数据在应用、内核和 daemon 之间也要复制，造成大量的 I/O 读写。

需要更高吞吐的程序可以先经 FUSE 打开文件，再走原生异步 I/O 接口。图中的 Ior 是共享内存中的请求环，记录要读写哪个文件、哪个位置。Iov 是共享数据缓冲区，保存实际字节。应用把请求放入环，daemon 取出后访问远端存储，并把完成状态交回应用。这种方式借鉴了 io_uring，每次读写都能绕过 FUSE 的内核请求队列，省去了这条路径上的数据复制。

经典 NFS 客户端把文件句柄和偏移发给导出目录的服务器。GFS 客户端向 master 询问副本位置，再到 chunkserver 读指定范围。3FS 客户端在打开时取得布局，后续随机读取直接算出目标复制链。

一致性模型

Alice 在群里发了一份 Chap_01.pdf，随后引用它问“是这个文件吗？”。Bob 先看到了这句话，点开引用却提示“引用内容不存在”，过了一会儿文件才出现。图中两个人最终收到了同样的两条消息，但在 Bob 点开引用的那一刻，他看到的聊天记录里还没有文件。

把聊天记录看成一个列表，发送文本或文件就是向列表追加一项，记作 Update。打开聊天窗口查看当前列表，记作 Read。一致性模型约定不同用户以什么顺序看到这些更新，以及每次读允许返回什么结果。前面 NFS 的 close-to-open consistency 也是这样的约定，写入者关闭文件之后，另一个客户端再打开它，就应当看到已经写回的内容。

中心化服务器

先把整个群的聊天记录放在一台服务器上。客户端通过 RPC 发送消息，服务器把消息追加到列表末尾再回复 ACK。读聊天记录时，服务器返回当前列表。如果 Alice 等文件的 ACK 到达后才发引用，那么她发出第二个请求时，文件已经在服务器的列表里了。Bob 向这台服务器读取历史，可以暂时只读到文件，也可以同时读到文件和引用。

这种实现有两个地方要等。写入时，即使消息只有“收到”两个字，发送者也要等一次网络往返。读取时，如果每次打开窗口都传回整份历史，聊天越久，要传的数据就越多。下图的例子里，历史增至原来的四倍，按相同速率传输，传数据的时间也从 ttt 增至约 4t4t4t。

手机断网后，连自己刚发过的消息都要等重新联网才能查。服务器一旦停机，所有人的读写都要等它恢复。给每台设备保留一份聊天记录，可以让本地读写继续进行，但接下来要决定各份记录怎样同步。

副本与同步

假设手机、服务器和平板各有一个副本。手机发出“你好”后，可以先追加到自己的列表。什么时候向用户显示“发送成功”，取决于要等哪些副本确认。

读操作可以直接取本地列表。比如平板断网时，手机又发了“谢谢”和“再见”，平板这段时间仍能打开聊天，只看到原有的“你好”。它可以定期向服务器拉取缺少的消息，也可以收到推送通知后批量同步。设定一定间隔的心跳，平板恢复连接，下一次同步就补上两条消息。

同步解决了消息能否送到，但是要处理到达顺序。回到开头的例子，手机先发文件，再发引用。文件传得慢，服务器先收到短小的引用并转给平板。平板此时读到的就是一条指向缺失文件的消息。即使文件随后送到，若每个副本都只往末尾追加，手机上的顺序仍是“文件、引用”，平板上却是“引用、文件”。

两个副本也可能在同一份历史上分别写入。假设两边原来都是 [你好, 谢谢]，手机追加“好的”，平板追加“收到”。此时任选一份完整列表去覆盖另一份，都会丢掉一条消息。同步时要交换各自新增的操作，按消息 ID 去重，保留这两条更新。至于“好的”和“收到”谁在前面，无论最终选哪一种顺序，至少一边已经显示过的列表要调整。

最终一致性

聊天应用可以允许设备离线时照常读写，等到恢复通信后再补齐历史。系统在后台传播更新。这个列表按同一规则合并后，拥有同一组更新的副本应得到相同状态。如果没有新的写入，经过同步，各副本最终会返回相同的列表。这就是最终一致性（eventual consistency）。

图中的 0 RTT 表示用户提交本地更新时无需等网络往返。后台可以由设备之间互相传消息，也可以通过服务器中转。使用至少一次 RPC 重试时，同一条消息可能收到多次，所以副本需要凭更新 ID 识别重传。

对于这个列表，一种做法是保留更新日志。副本 1 的到达顺序为 [X, Y]，副本 2 为 [Y, X]。两边收齐更新后，用同一个规则排序，再从相同的初始列表按序重放。如果两端都排成 [X, Y]，重放后就得到相同结果。这里能保证的是最后收敛，用户在同步完成前读到的结果仍可能不同。

最终一致性对同步过程中的可见顺序约束较少。若应用还要求“先看到文件，才能看到引用”，就要进一步约束读操作。图中从左到右列出的模型对容错和易用性有不同要求。

给更新排序

先尝试用设备时间作为排序键。两个设备调用 getTimeOfDay()，都可能取得 1755419200.123。只比较时间，两个键相等，保留原有到达顺序就可能让两个副本各排各的。图中改用 (时间, 节点 ID)，时间相同再比较 R1 和 R2，两边都把 X 排在 Y 前。若同一设备也能在一个时钟刻度内发出多条更新，还可以用本地递增序号把它们区分开。

能把任意两个不同事件排出先后，称为全序。先按节点 ID 再按本地序号也能得到全序，但这样会把同一节点的消息排在一起，连问答都可能前后颠倒。即使用时间作第一排序键，两台机器的时钟也有偏差。机器通过计算振荡器周期来计时，经过的时间约为周期数除以频率。各台设备独立计数，晶振的实际频率还会受温度等因素影响。

看下面两个具体的时间戳。R1 在本机时间 1755419200.123 发出 file_a。R2 收到文件后才引用它，但 R2 的时钟偏慢，给引用标上了 1755419199.987。按数值从小到大排，两台机器最终都把引用排在文件前面。它们达成了一致，却把“先收到文件，后发出引用”这个已知顺序排反了。

因果与逻辑时钟

用 X→YX \to YX→Y 表示事件 X 在因果上先于 Y（happened-before）。在同一个单线程执行流中，先执行的事件在前。跨节点时，一条消息的发送在它的接收之前。这个关系还可以传递。图中 R1 发文件是 X，R2 收到文件后发引用是 Z，之后又发“看完了”是 Y。消息建立了 X→ZX \to ZX→Z，R2 的本地顺序给出 Z→YZ \to YZ→Y，因此 X→YX \to YX→Y。

Lamport 时钟用一个整数记录这种先后关系。每个节点维护一个计数器 TTT，每发生一个本地事件或发送事件就递增，发送消息时带上当前值。收到时间戳为 T′T'T′ 的消息时，用 T←max⁡(T,T′)+1T \leftarrow \max(T,T')+1T←max(T,T′)+1 给接收事件编号。这样接收既晚于本机的上一事件，又晚于这条消息的发送。如果本地计数已经为本次接收加过一，接下来只需把它与 T′+1T'+1T′+1 取最大值。

见下图如果没有使用逻辑时钟，假如 R2 收到 <file_a, 10> 的时候立即按照本设备时间戳发出 <ref, 9>，就会导致另一台设备同步后，引用跑到了文件前。

图中 R1 给文件标上 10，R2 收到时本地计数为 9，于是接收事件取 11。随后 R2 发引用，再加一得到 12。各端按“逻辑时间、节点 ID”排序，文件 10 就会排在引用 12 前。这些数字表示事件顺序，实际经过的秒数要用物理时钟计量。

节点 1 上的事件 e1e_1e1​ 和节点 2 上的事件 e2e_2e2​ 的 Lamport 时间戳分别为 3 和 7。根据 3<73<73<7，下列判断哪些成立？

  1. “事件 1 在物理时间上一定更早”——不成立。 假设节点 2 先独立执行到第 7 个事件，过了一秒，节点 1 才执行到第 3 个事件。此时仍有 3<73<73<7，物理时间上却是事件 2 先发生。
  2. “两个节点一定通信过”——不成立。 上面的例子中，两台机器各自递增本地计数器就能得到 3 和 7，全程可以没有消息往来。
  3. “若事件 1 已同步到节点 2，事件 1 就一定更早”——不一定成立。 Lamport 时钟可以保证在两台设备之间有同步的情况下，有因果关系事件之间的先后顺序。但是在并发时并不能确保没有因果关系的时间的物理时间戳顺序是可信的。

对有因果依赖的更新，因果一致性要求读者看见后续更新时，也已经能看到它依赖的更新。若引用先到、文件还在路上，要满足这一要求，接收端就得暂缓展示引用，等文件补齐。只在最后按 Lamport 时间排好列表，仍可能让同步期间打开窗口的人碰到缺失的引用。

接龙与向量时钟

假设群接龙已排到第 17 人。Alice 和 Bob 都读到同一份名单，分别在本地填上自己是第 18 人。这两次报名之间没有消息依赖，称为并发。用“Lamport 时间、节点 ID”可以选定其中一个排在前面。如果第 18 名有奖，按节点 ID 打破平局的结果却不能说明谁先按下按钮。

应用也可以把两条报名标为冲突，请参与者重新确认。这要求系统能区分 X 先于 Y、Y 先于 X，以及两者在因果上不可比这三种情况。允许有些事件不可比的关系叫作偏序。Lamport 时间能保留已经存在的因果先后，但是并不能反映真实的时间戳顺序。要从时间戳本身识别并发，可以用向量时钟（vector clock）。

每个节点维护一个向量，每一项对应一个节点。本地发生事件时只增加自己的分量，发消息时附上整个向量。收到消息后，先把两个向量的对应分量分别取最大值，再增加自己的分量。以 R1、R2 各占一项为例，按下图推一遍。

  1. 两端从 [0, 0] 出发。R1 独立产生 X，时间戳为 [1, 0]。R2 独立产生 Y，时间戳为 [0, 1]。第一项 X 大，第二项 Y 大，所以两者不可比（因此此处同步时会产生冲突，需要一个逻辑来处理二者的先后顺序）。
  2. R1 收到 Y，先将 [1, 0] 和 [0, 1] 逐项取最大值得到 [1, 1]。接收也是 R1 上的一个事件，第一项再加一，得到 [2, 1]。
  3. R1 随后引用 Y，时间戳为 [3, 1]。拿 Y 的 [0, 1] 和它比较，Y 的每项都小于或等于引用的对应项，且第一项严格更小，因此 Y→ref(Y)Y \to \mathrm{ref}(Y)Y→ref(Y)。

严格一致性

对于同一份接龙名单，要求对于几个并发的事件，实际最终都会暴露出来一个确定的事件先后顺序。不同的场景对于并发的时间最终排出的先后顺序会有不同的要求，因此有不同的一致性模型。

严格一致性（strict consistency）要求操作按真实的发起时间排序。假设 Alice 先按按钮，Bob 后按，即使 Bob 的请求先到服务器，名单也应当先记 Alice。服务器由于网络的传输延迟等因素，光看到达顺序无法判断是谁先发，客户端附上本机时间又会遇到时钟偏差。

严格一致性是定义的最强的一致性。但是实际上由于不同的设备之间即使有同步，也不能确保事件和物理时间是完全一致的，所以严格一致性可以认为是无法实现的。

线性一致性

线性一致性（linearizability）给每次操作留出了从发起到返回的一段区间。只要能在各自区间内为每个操作选一个生效点，使所有返回值都符合这一个串行顺序，就满足要求。若 A 已经返回，B 才发起，A 就必须排在 B 前面。 两个区间有重叠时，可以选择其中任一顺序，前提是它能解释实际返回的结果。

图中 Alice 先发起 A，Bob 稍后发起 B，但两次更新有重叠，服务器先追加了 B，再追加 A。最后一次读取发生在两次更新都返回之后，因此它读到 [B, A] 符合线性一致性。只要收到了 server 完成的消息，那么做下一步操作一定可以看到在 ACK 消息之前完成的任务。

一种实现是给每个对象指定主副本（primary），由它决定这个对象的读写顺序。客户端可以联系任意副本，备副本收到请求后转给主副本。图中的 P0 收到 Write(x, 1) 后，先把更新转给 P1，待 P1 更新并确认，再完成本地写入并回复客户端。读请求也经过主副本，按已确定的顺序读取，备副本尚未完成协调的状态不会提前 返回给读者。

只有主副本决定顺序还不够，这个顺序得随写请求一起到达备副本。下图中，P0 先写 1 再写 2。如果 P1 按消息到达顺序执行，收到 2 再收到 1，最终就会停在 1。解决办法与前面 GFS 的 primary 类似。P0 给每个写分配递增的序号 seq，P1 只能按号执行。先收到 seq=2 就暂存，等到 seq=1 完成，再执行 2。

这种简化方案每次写都要多等主备之间的一轮通信。主副本失效后需要安全地选出接替者。若规定所有备副本都必须 ACK，任何一台备副本失联也会挡住写入。复制解决了数据有多份的问题，故障时由谁继续决定顺序，还需要单独的协议。

顺序一致性

能不能让每个副本直接用本地值回答读请求，省掉读操作的转发？看 x 从 1 改成 2 的例子。写请求还没返回，P1 已经更新为 2，第一个读在 P1 得到 2。这个读完成之后，另一个客户端才在尚未更新的 P0 发起第二个读，得到 1。期间只有这一次写。

若第一个读能看到 2，串行历史中写 2 就必须排在它前面。实时先后又要求第二个读排在第一个读之后，因此第二个读也应看到 2。实际返回的 1 与这个要求矛盾，这段执行无法满足线性一致性。

顺序一致性（sequential consistency） 也要求存在一个能解释所有返回值的全局串行顺序，同时必须保留每个进程自己的程序顺序。它允许不同进程的操作在这个序列中的先后与实际时间不同。假设这一次写和两次读分别来自三个进程，每个进程各发出一个操作，那么“读到 1 → 写入 2 → 读到 2”就能解释这些结果。如果两个读来自同一个进程，并且它先读到 2、再读到 1，就不能把两次读取互换位置。允许本地读能省去往返，要对所有执行保证顺序一致性，实现还须维护每个进程的操作顺序。

回到聊天和接龙，同样是往列表里追加一项，用户依赖的保证却不同。离线发一条普通消息，可以先在本地显示，等设备联网后再合并。引用一份文件，需要保留文件与引用的因果顺序。发放唯一名额时，还可以由一个权威服务按处理顺序原子地登记，登记成功后再向用户确认。若业务坚持比较两人按按钮的物理时刻，线性一致性本身也不能替它裁决重叠的两次报名。

原子性与故障恢复

假设账户 a、b 的余额都是 10，要从 a 向 b 转 10。程序先扣款，再入账。如果系统里只有转账操作，那么无论执行多少次，两个账户的余额之和都应当保持为 20。这个在每笔交易前后都要成立的条件，称为不变量（invariant）。

先只看一台服务器，假设它依次处理请求。即使两笔转账完全不并发，一笔转账自身也要写两个位置。假设断电时整台机器一起停止，内存随之丢失，重启后只能看到已经持久化的内容。这是本节使用的 fail-stop 故障模型。

一次未完成的转账

把账户存在文件 bank 里，通过 mmap 映射到内存。下面两次赋值先改到页缓存（page cache），fsync 再要求系统把修改写回磁盘。程序等 fsync 成功返回，才通知用户转账完成。

如果在 fsync 执行到一半时断电，会留下什么？

按图从左到右看，两个账户分属不同的页。开始时磁盘上是 (10, 10)，内存改完后变成 (0, 20)。假设此前还没有后台写回，若此时就断电，重启后仍是旧余额。接下来系统先写回 a 所在的页，还没来得及写 b 就断电，磁盘上留下的却是 (0, 10)。用户没有收到成功通知，钱已经少了 10。

这里需要的保证叫作全有或全无原子性（all-or-nothing atomicity）。恢复结束后，这笔转账只能保留旧余额 (10, 10)，或完成转账得到 (0, 20)。这个要求允许磁盘在写入途中暂时处于中间状态，前提是系统知道怎样从那里恢复。

影子副本

可以把修改放在另一个文件里。先把 bank 复制成 bank_temp，在副本上完成扣款和入账，再用 fsync(bank_temp) 持久化副本，最后用 rename(bank_temp, bank) 替换原文件。

在 fcopy 或同步临时文件时崩溃，应该用哪个文件？如果崩溃发生在 rename 中间呢？

复制或同步期间，名字 bank 仍然指向完整的旧文件，重启后可以丢弃未发布的临时副本。进入 rename 时，新文件的数据也已经准备好。现在需要保证的是，文件系统能把名字和 inode 一起恢复到一次完整替换之前或之后。若应用还要确认替换后的名字已经持久化，在常见 UNIX 文件系统上还要同步相应的父目录。

图中原先 bank → 12，bank_temp → 13，两个 inode 的硬链接数均为 1。替换时，先把 bank 改指向 13，此时两个名字都指向 13。再给 inode 13 的链接数加一，把 inode 12 的链接数减一，最后删除临时名字并扣掉它对 13 的引用。完成后只剩 bank → 13，inode 13 的链接数为 1。

如果刚改完 bank 的目录项就断电，inode 13 有两个名字，磁盘上的链接数却仍为 1。这时直接删除 bank_temp 就可能把计数减为 0，回收仍被 bank 引用的 inode。与此同时，inode 12 已经没有名字，旧计数却仍为 1。即使余额文件本身完整，文件系统的元数据也已经出错。文件系统需要自行恢复目录项与计数的对应关系，应用可能永远不会再启动，无法指望它来清理。

文件系统日志

文件系统可以在磁盘上留一片区域作为 journal。修改原位置之前，先把这次操作要改哪些块、各块应变成什么写进 journal。所有记录持久化后，再写入提交标记 COMMITTED。有了这份完整记录，文件系统才开始修改原位置。等原位置也全部写稳，就可以回收这段 journal。

仍看 rename。看图右侧的黄色区域，恢复后应当满足以下条件。bank 指向 13，删除临时名字，inode 12 的计数为 0，inode 13 的计数为 1。提交标记把这几项归作一次修改。

用了 journal 之后，如果仍在“目录项已改、引用计数还没改”的位置断电，重启时怎么办？

先查提交标记。若 journal 还没完整提交，原位置应当还保留旧状态，可以忽略这批记录。下图的故障发生在提交之后，原位置只写了一部分，右侧却还保存着完整的新值。

恢复程序按 journal 把目标块重新写一遍，这叫重做（redo）。已经写过的字段会再次得到同一个值，漏掉的字段也会补齐。下图中，临时名字已删除，两个引用计数分别为 0、1。只有此时确认目标块已落盘，才可回收这批记录。

追加一个块

给 inode 13 的文件追加一块也涉及多个磁盘位置。原文件占用块 6、7、8，准备追加块 9。文件系统需要把 data bitmap 的第 9 位设为已占用，写入块 9 的数据，把 ptr[3] 指向 9，并更新文件大小。图中以块为单位表示大小，因此从 3 变为 4。

如果连文件内容都记入 journal，新数据要先写日志，再写回文件所在的块。以图中 231 GB 的游戏安装为例，若全部内容都走这条路径，仅这两份数据写入就约为 462 GB，还没算元数据。文件系统因此可以只记录位图、inode 等元数据，再单独安排文件内容的写入顺序。

ext4 的三种数据模式可以用同一次追加来区分。看下面三张图时，先找到黄色的 COMMIT，再看块 9 的新内容此时在哪里。

  • data=writeback 只记录元数据，允许数据块稍后写回。若在图中断电，重放后 inode 会指向块 9，文件大小也是 4 块，但新数据可能还没写进去。元数据结构正确，新增部分的内容却可能是旧的。

  • data=ordered 也只记录元数据，但要求这次追加的数据先写到块 9，再提交使它可见的元数据。若恢复后文件已有第 4 块，块里也已有本次追加的内容。这个顺序保证针对新块的发布，不能把任意多次应用写入自动组合成一笔事务。

  • data=journal 把块 9 的新内容也放进日志。提交前，恢复程序可以忽略这一批。提交后，数据和元数据都能通过重放补齐。代价是块 9 的内容要写两遍。

如果连 COMMITTED 自己都只写了一半，恢复程序凭什么相信它？

假设设备对一个扇区提供原子写，例如设备可以用电容储备的电量完成正在进行的扇区写入。小的提交标记可以放进这个原子写单位。整个事务可以横跨多个扇区。先写齐日志内容并确保其持久化，最后才发布提交标记。恢复时检查记录边界、长度和校验和，只有内容完整且提交有效时才重放。校验和帮助识别残缺记录，写入顺序则保证提交标记不会抢在它要证明的内容之前落盘。

并发修改副本

即使 rename 本身已经原子化，两个客户端同时用影子副本转账，仍可能出错。图中四个账户原来各有 100。客户端 0 从 a 向 b 转 100，客户端 1 从 c 向 d 转 100。两笔转账涉及的账户没有重叠，代码却都在替换整份 bank。

客户端 0 只把 a 改成 0 就被切走，此时 b 仍为 100。客户端 1 在同一份临时内容上完成自己的转账，同步后执行替换。于是正式文件成了 (0, 100, 0, 200)，总额从 400 变成 300。即使两个客户端各用不同的临时文件，从同一旧版本出发再各自替换整份文件，也可能让后一次替换覆盖前一次转账。

要安全地更新同一份文件，还得串行化复制到替换的过程，或在发布前检查版本冲突。跨多个文件时，一次 rename 只能切换一个名字，通常还要用一个共同的目录或根指针来发布整批变更。即使只改两个余额，按这种整文件复制法也要复制整份账本。日志可以把代价缩小到本次真正修改的数据。

事务与提交点

首先需要区分 journal 和 log。journal 是 all-or-nothing 的，保证的是文件系统中的任何一个 API 操作的原子性，而 log 则在应用层进一步区分哪些操作需要保证原子性，哪些操作不需要严格原子性，记录可能影响数据正确性的点。

把扣款和入账放进同一个事务（transaction），用 TX.begin() 和 TX.commit() 标出边界。事务日志按顺序追加修改。一旦有足够的持久信息保证重启后能完成整笔事务，就越过了提交点（commit point），此后才可以向用户确认成功。

只重做日志

先看 redo-only。程序先用局部变量 new_a、new_b 算出两个新余额。事务提交前，这些变量只在进程内存中，共享的 records 还保留旧值，操作系统即使写回文件页，也不会把半笔转账写进账本。

提交时，把两个新余额装进同一个条目，执行 log.append(entry).sync()。条目要有边界和校验和。若追加时断电，只留下前半条记录，恢复程序就跳过它。完整有效的事务条目一旦持久化，即已提交。sync() 成功返回后，应用能确认已经过了这个点。如果磁盘已经写完、回复却还没返回就断电，恢复程序仍以磁盘上的记录为准。

还要立即调用 fsync(bank)，才能向用户报告成功吗？

这里可以稍后再同步账本。提交点已有完整的新值，即使 records[a] 已落盘、records[b] 还在页缓存中，也能在重启后把两者都重做到目标值。前提是保留这条日志，直到账本本身已写稳。

图中前三笔事务的日志分别是 (8,12)、(5,15)、(3,17)，第四笔只写到 a=2，缺少完整的 b 和有效校验。重启后从前向后重放前三笔，跳过残缺的第四笔，恢复结果为 (3,17)。

记值还是记操作

恢复程序重放到一半又断电。下一次启动时，从头再做一遍，会不会多转一次钱？

若日志记的是 a=3, b=17，赋值执行几次，最后都是 (3,17)。若记的是 transfer(a, b, 7)，从 (10,10) 执行一次得到 (3,17)，再执行一次就成了 (-4,24)。操作日志要另行识别哪些操作已生效，才能避免重复扣款。

记录结果也能避免重新求值。例如重放 UPDATE t SET id = UUID() 会生成新的 UUID，用行值复制则可以直接记录当时生成的结果。值日志可能更大。例如，ext3 使用块日志时，即使只修改一位，也可能要记录整个块。

撤销与重做

redo-only 的提交可以集中为一次顺序追加，但长事务要把全部未提交修改留在私有内存中。如果转而直接修改 records，操作系统便可以在内存紧张时把脏页写回磁盘。此时即使事务最终没有提交，磁盘上也可能已经出现新余额。

允许提前写回，就需要能够撤销（undo）。下面左边是 (10,10)，右边是 (3,17)。日志同时保留旧值和新值，恢复程序可以用旧值撤回未提交的修改，也可以用新值补齐已提交的修改。

先看只记旧值的版本。每次修改共享页之前，先把位置和旧值追加到日志并同步。这样哪怕新余额随后被刷到磁盘，也有办法找回旧余额。

有了旧值，为什么还要记录新值？

如果只记旧值（undo-only），可以撤销未提交的事务，但一笔已经确认的转账若还缺一个新余额，日志无法重建它。因此提交前必须等这笔事务修改的所有数据页写稳。两个账户可能分散在不同磁盘位置，这些写入会拖长提交时间。

undo-redo 则在一条更新记录中同时写下旧值与新值，最后追加并同步事务的提交记录。这样数据页可以较早写出，也可以晚于提交写出。图中两次更新各有对应的日志，末行的 <TX 1 commit> 表示整笔事务提交。

redo-only 把一笔事务合在一个 entry 里。undo-redo 每次更新追加一条 record。不同事务的记录可以交错。下图的 1, 2, 1, 2, 1 是各条记录所属的事务编号，恢复时要把属于同一事务的记录关联起来。

每条记录带事务 ID、同一事务上一条记录的位置，以及本次改动的文件、偏移和新旧值。图中的 TID=1 表示事务 1，PTR=80 指向它的前一条记录，old 3000 new 2000 说明该位置可以恢复成哪两个值。

这里有两条落盘顺序。第一，修改后的数据页写回原位置之前，对应的更新日志必须已经持久化，这就是预写日志（write-ahead logging，WAL）。第二，事务的更新日志完整之后，才能持久化它的提交记录并确认成功。图中黄色的 C 是其中一笔事务的提交标记，其他事务的日志即使排在它前面，也要按各自的事务 ID 查提交状态。

崩溃后怎样恢复

在 undo-redo 算法中，先从有效日志末尾向前查提交记录。对崩溃时还没有提交的事务，按更新的逆序恢复旧值。例如余额曾从 10 改到 8、又从 8 改到 3，撤销要先把 3 改回 8，再把 8 改回 10。对已提交的事务，则从前向后重做，使同一位置最终保留最后一次有效写入。

图中事务 T1 已经提交，把 (10,10) 改成 (8,12)。T2 接着把 a 从 8 改成 3，却没有提交。恢复时先撤销 T2 对 a 的修改，再重做 T1。最终磁盘上应为 (8,12)，既保住了已确认的转账，也消除了未完成的扣款。

检查点

如果一直追加日志，恢复程序每次都要从开头读起，哪怕大部分更新早已写回账本，且会占用大量的磁盘空间。检查点（checkpoint）把某个边界之前的结果持久保存下来，同时丢弃这个 cehckpoint 之前的 log。重启时可以从这个结果继续，只处理还没被它覆盖的日志。训练时保存模型参数、暂停进程时保存内存与执行状态，以及给聊天更新日志保存已重放的列表，都用到了同一种做法。

先考虑没有活跃事务的情况。图中共享页里的余额已经是 (3,17)。把这些脏页写稳，再持久记录检查点覆盖到哪里，就可以回收相应的旧日志。若同时又有新事务提交，它在边界之后追加的日志要保留到下一次检查点。

T4 正打算把 (3,17) 改为 (1,19)，检查点能直接刷页并清掉旧日志吗？

在 redo-only 中，T4 提交前的两个新值是私有变量。检查点刷到磁盘的仍是 (3,17)，只回收边界内已经覆盖的日志。图中 T4 随后提交，把 (1,19) 作为新条目留在日志中。此时即使账本还没再写回，恢复时也能重做 T4。

undo-redo 会允许提前写数据。假设 T4 只执行了第一步，已把共享页中的 a 从 3 改成 1，b 仍是 17。检查点刷出的是 (1,17)。如果此时保存 ckpt 并把 a: 3 → 1 的日志也删掉，T4 提交前再发生故障，恢复程序就无法撤回扣款，总额只剩 18。

一种办法是暂停接收新事务，等已开始的事务全部提交或撤销，再刷页并截断日志。图中的 T4、T5 既要等 T2、T3 结束，还要等检查点写完。只要有一笔长事务，其他请求就可能等很久。

另一种办法是保留活跃事务的恢复记录，在一次短操作完成的边界协调检查点，把还在运行的事务及其所需日志保存到 CKPT 记录中。等数据页和 CKPT 都可靠落盘，才截断已覆盖的旧日志。这样 T4 可以跨过检查点继续执行。若它随后崩溃，恢复程序仍能从 CKPT 取出 a: 3 → 1，把磁盘上的 1 改回 3。

并发控制与两阶段锁

前面的日志能在断电后把一笔转账完整地恢复或撤销。现在假设机器始终正常，只让两个客户端同时向银行发请求。即使两笔事务最后都提交，执行顺序也可能让一笔存款消失，或让查账的人看到一个从未在任何一笔交易结束时出现过的余额。

为什么要并发

假设银行只有一个服务线程，收到 RPC 后逐个处理。若处理一次请求平均需要 SSS 秒，一个始终有请求可做的线程每秒至多完成 μ=1/S\mu=1/Sμ=1/S 个请求。用户关心的是自己的请求多久能回来，但只要前面有人排队，这个时间就取决于服务器每秒能处理多少请求。

用户等待的时间等于排队时间加上实际处理时间。设每秒平均到达 λ\lambdaλ 个请求。当 λ>μ\lambda>\muλ>μ 时，连续运行 ttt 秒后，积压的请求约增加 (λ−μ)t(\lambda-\mu)t(λ−μ)t 个。例如每秒到达 1200 个、最多完成 1000 个，持续一分钟就会多出约 12000 个待处理请求。

2004 年前后，靠提高单核频率增加吞吐量的速度放缓了。可以在一台机器上用多个核和线程处理请求（scale up），也可以把工作分给多台机器（scale out）。两个请求在同一段时间内都有进展，就可能发生交错，即使线程只是在一个 CPU 上轮流执行，也要考虑下面的问题。

如果请求全程都要经过同一把锁，即使增加了 CPU 核心，持锁的那段工作也只能逐笔完成。增加执行资源能否提高吞吐量，取决于请求中有多少工作能真正同时进行。

丢失的存款

Alice 初始余额为 0，两个线程各向她的账户存 10，正确结果应为 20。代码只写了一行 bank[acct] += amt。按下图的指令展开，线程要先把余额读进寄存器，在寄存器里加 10，再把结果写回。即使单次读和单次写各自都是原子的，这一整段仍可被另一个线程插入。

如果 T0 读到 0 后被切走，T1 也会读到 0。两个线程各自在寄存器里算出 10，随后各自写回 10，最终余额只有 10。另一个合法的调度是先让 T0 写完，再让 T1 开始读。此时 T1 读到 10，最后写回 20。同样的输入得到不同结果，只取决于哪一步先执行，这就是竞态条件（race condition）导致的丢失更新。

这里竞争的是同一个内存位置，两个线程都要写它，而且从读到写的这段时间没有同步保护。如果两个线程只是读取同一份余额，那么交换这两次读的顺序不会造成丢失更新。

并发程序要在每一种允许的调度下都正确。有问题的顺序可能很少出现，一条调试输出或一次断点就足以改变时机，问题随之消失，这类现象常叫作 Heisenbug。确定性多线程（DMT）让相同输入按同一调度执行，记录与重放（record and replay）则保存一次执行的顺序供事后复现。前者要限制调度，后者要捕捉影响执行的事件，两者都有成本。

竞态的实际影响

有些竞态首先表现为界面显示的先后顺序异常，底层记录仍然正确。判断影响时，要分清用户看到了什么，以及系统实际保存或执行了什么。

判断竞态的影响时，可以先确定要维持的业务条件。对于存款，这个条件是每笔款项都要计入余额。对于消息界面，如果异常只影响展示顺序，底层消息及其内容都保存正确，这类情况称为良性竞态（benign race）。

Therac-25 是一台放射治疗设备。看下图的三幅束流示意图。左图是电子模式（E），设备用较低电流的电子束扫描治疗区域，金属靶移出束路。中图是 X 射线模式（X），设备把较高电流的电子束打在金属靶上，产生治疗用的 X 射线。右图红框里，束流仍按 X 模式设置，金属靶却已经移开，高电流电子束可能直接照射患者，造成严重过量照射。

模式只有一个变量，为什么束流和金属靶会采用两种不同的设置？

在这个简化模型中，键盘处理程序负责把所选模式写入共享变量 mode。另外两段代码分别读取它。设置程序根据读到的值配置束流和磁铁，位置控制程序根据读到的值移动金属部件。两次读取发生在不同的时刻，改写 mode 也不会自动撤销已经开始的硬件配置。

下图从左往右读，蓝色表示 X，绿色表示 E。开始时两段程序都读到 X，金属靶就位，设置程序开始按 X 模式调整磁铁。这项调整约需 8 秒。在它完成之前，操作员把模式改成 E。位置控制程序读到了新值，移开金属靶。设置程序却继续按先前读到的 X 完成工作。时间线末尾的 still X 表示束流设置仍是 X，此时共享变量 mode 的值已经是 E。

两次读取各自都读到了当时的值，危险来自系统把旧的束流设置和新的部件位置一起当成了可用配置。即使给每一次 mode 的读写单独加锁，上述顺序仍然可能发生。需要协调的是整次模式切换。设置过程中若选择发生变化，就让旧配置失效，等各部件的实际状态与同一次选择相符后，才允许出束。

竞态也可能跨越多台服务器。2025 年 10 月，AWS 美国东部区域的一次 DynamoDB 故障影响了依赖它的服务。客户端通常先通过 DNS 查服务端点的 IP。图中的 DNS Planner 根据可用服务器生成不同版本的地址列表，三个可用区中的 DNS Enactor 负责将计划应用到 DNS。即使数据库内的数据仍然完好，端点的地址记录被清空后，需要重新解析的客户端也无法建立连接。

沿着简化时序看，两个执行器都在第 7 版基础上决定更新。第一个执行器的写入延迟，第二个先发布了第 12 版。随后延迟的第 8 版才生效，而清理程序按第 12 版的进度删除旧计划，第 8 版也在清理范围内。结果是当前正在使用的地址记录被清空。检查版本、发布计划、清理旧版本分别都能执行成功，组合起来却破坏了“正在使用的计划必须保留”这个条件。这次 DNS 故障的主要影响持续了约两个半小时。AWS 在事后报告中说明，当时已停用相关自动化，并计划修复竞态、增加错误计划的拦截检查。

这次故障涉及 2025 年 10 月 20 日的 DynamoDB 区域端点 dynamodb.us-east-1.amazonaws.com。部署多个 Enactor 本来是为了让一个可用区出故障时仍有人能更新地址，但它们最终修改的是同一个 Route 53 记录。“读出当前版本”“写入较新版”“清理旧版”是分开的远程操作。第一次比较版本的结果，到了实际写入时就可能已经失效。AWS 在全球范围暂停了这套 Planner 和 Enactor 自动化。

隔离的单位

前面的一致性模型把一次 Read 或 Write 看成一个操作。即使每个操作都可线性化，一笔存款中的“读余额、加款、写回”仍可能和另一笔存款交错。看下图的方框。上半部分给单次读写排序，下半部分把同一项业务的几次读写放进一个方框，要求把整个方框放到串行顺序里的同一个位置。

这种保证称为 before-or-after atomicity。对调用者来说，两笔并发事务的效果可以解释为一笔完整地发生在另一笔之前或之后。数据库把事务之间互相看见哪些修改称为隔离（isolation），这里要求的隔离强度是可串行化。上一节的日志解决崩溃后应保留哪些修改，本节要解决的是正常运行时其他事务能够读到哪些值。

把前面的例子连起来看，主备复制可以让应用观察到一份逻辑数据，事务日志可以在崩溃后恢复整笔转账。现在即使只有这一个逻辑账户、也没有任何故障，还须让并发调用者观察到某个完整的事务顺序，否则两次存款仍会相互覆盖。

从全局锁到记录锁

互斥锁在同一时刻只允许一个线程持有。acquire(lock) 取得锁，遇到占用就等待，release(lock) 释放锁，例如 POSIX 线程的 mutex。先用一把全局锁包住整段存款代码。图中的 L、U 分别是加锁和解锁，中间是临界区。T1 在 T0 释放锁后才能读余额，因此一定能读到 T0 已写回的 10，最后得到 20。

若 T0 给 Alice 存款、T1 给 Bob 存款，两笔操作本来可以并行。共用一把全局锁后，T1 仍然要等 T0，额外还要付出申请锁、唤醒线程的成本。把锁本身实现得更快可以减少这部分开销，却不会让两个持有同一互斥锁的临界区同时运行。

临界区可以缩小到哪里？

对单账户存款，需要一起保护的是同一余额从读到写的全过程。可以让每个账户各有一把锁，调用 Deposit 时只取 locks[acct]。Alice 和 Bob 各自的余额仍有互斥保护，两笔存款则可以同时执行。线程的局部计算和其他不访问这份共享状态的工作可以放在锁外。

转账和审计

记录锁的粒度合适，还要看何时释放。让 a 和 b 初始各有 10，Transfer 从 a 向 b 转 10。按图中的代码，它先锁住 b、给 b 入账、解锁，再对 a 扣款。Audit 逐个锁住账户，读余额并累加。转账前后银行总额都是 20，所以无论串行时哪一笔先做，审计都应输出 20。

图中的账户最终余额是否正确？审计打印的总额又是多少？

转账先把 b 从 10 加到 20 并解锁。审计趁这时读出 b=20，又赶在扣款前读出 a=10，于是打印 30。随后转账把 a 改成 0，账户最终为 (0,20)，余额正确。问题出在第一次释放 b 的锁时。转账已经向别人公开了入账，却还没扣款。每次单独访问都有锁，审计依然看到了半笔转账。

静态加锁

一种做法是在事务开始前拿齐所有需要的锁，事务结束后一起释放，称为静态加锁。图中的 acquire_all 表示先取得 a 和 b 的锁再访问数据。审计即使先尝试读 b，也只能等转账完成，最后读到 b=20, a=0，打印 20。

代价是要预先知道事务会访问哪些记录。转账起初就知道两个账号。如果审计要边扫描边发现账户，静态做法就得提前确定全部账号，或保护整个扫描范围。图中的转账最后才访问 a，却从第 0 步就持有它的锁。两把锁各占 6 个时间格，加起来是 12 个“锁 × 时间”格。

这里的“拿齐”还有一个实现细节。如果采用一次申请整组锁的方式，只要有一把被占用，就先等待整组可用。若改用多个普通的 acquire 逐一取得，则还要统一申请顺序，才能避免拿着一把锁等另一把锁的情况。

但是静态加锁的问题在于，如果说需要访问的数据依赖于执行时线程取得的数据，就没法提前拿到要访问的数据的锁。

两阶段锁

两阶段锁（two-phase locking，2PL）仍然可以每条记录一把锁。事务访问记录前先取得相应的锁，可以用到时再申请。额外的限制是，一旦释放第一把锁，这笔事务就不能再申请任何新锁。因此加锁集中在增长阶段，解锁集中在收缩阶段。已经拿在手里的锁可以继续使用。

下图把一笔转账和一笔给 a 存款的事务放在一起。静态加锁时，转账先取得两把锁，存款要等到它结束。换成 2PL，转账可以先持有 b 的锁，存款趁这段时间把 a 从 10 加到 20。转账随后取得 a 的锁，再释放 b 的锁，并从 a 的新余额 20 中扣去 10。这个顺序的效果等价于先存款、再转账。

事务取得最后一把锁的时刻叫作锁点（lock point）。图中的 2PL 在这个位置短暂同时持有两把锁。按每一步持锁数量相加，得到 1+1+1+2+1+1=71+1+1+2+1+1=71+1+1+2+1+1=7 格，其中 b 占 4 格、a 占 3 格。与前面的 12 格相比，其他事务就能更早取得转账尚未使用或已经用完的锁。

判断一段执行是否遵守 2PL，可以先圈出第一次解锁，再向右检查有没有成功取得新锁。例如转账取得 a 后再释放 b 属于合法的阶段转换。反过来，先放掉 b 才去申请 a，就会重新出现审计读到 30 的窗口。

可串行化

怎样验证一张交错执行的时序图等价于串行执行？先确定每笔事务自己要做什么。下面两笔事务操作初值均为 0 的 x、y。T1 读 x，再读 y 并给它加 10。T2 把 x 写成 20、把 y 写成 30。把一次执行中所有读写的先后排列出来，称为一个调度（schedule）。调度必须保留每笔事务内部的程序顺序。

只有两笔事务，所以只有两种串行调度。T1 先执行时，它读到两个 0，把 y 写成 10，随后 T2 覆盖为 30。T2 先执行时，T1 读到 20 和 30，再把 y 写成 40。检查并发调度时，要同时对照这些读值和最后的写入。

对照三种调度

图中的调度 A 允许两笔事务重叠，但 T2 写完 x 后 T1 才读 x，T2 写完 y 后 T1 才读并更新 y。T1 因而读到 20 和 30，最终状态为 (20,40)，和串行的 T2 → T1 相同。调度 B 中，T1 先读到 y=0，T2 把它写成 30，T1 再用早先读到的 0 加 10 写回，最终为 (20,10)。两种串行顺序都得不到这个结果。

调度 C 最终也是 (20,40)，能否说它等价于 T2 → T1？

不能。T1 读到 x=0，要求它排在 T2 写 x 之前。T1 随后又读到 T2 写入的 y=30，要求它排在 T2 之后。两个条件无法同时成立。即使最后的余额碰巧相同，T1 已经读到了一组在串行执行中不可能同时读到的值。

视图与冲突

视图等价（view equivalence）比较每次读从哪里取得值，以及最后一次写由谁完成。对于相同的一组事务，若要把调度 S 换成 S′，读初值的操作在 S′ 中也要读初值，读到某笔事务写入值的操作仍要从同一笔写入取值，每个数据项的最后写者也要相同。若能找到一个与 S 视图等价的串行调度，就称 S 为视图可串行化。事务多起来，逐个尝试可能的串行排列代价很高，一般情形下判定视图可串行化是 NP 完全问题。

对照视图时要给读值标上来源。例如 T1 和 T2 都曾把 x 写成 10，某次读在两个调度中都返回 10，仍须检查它读到的是哪一笔写。若有 nnn 笔事务，直接枚举串行顺序最多要考虑 n!n!n! 种排列，这也是下面改用冲突图判定的动机。

另一种判据是冲突可串行化。两个操作访问同一数据项、来自不同事务，而且至少一个是写，它们就发生冲突。例如，两个事务同读 x 可以交换次序。各事务内部仍遵守程序顺序，跨事务则检查读写、写读和写写三类冲突。把这些冲突操作原有的顺序都保留下来，如果仍能把各事务排成串行顺序，就找到了与原调度冲突等价的串行执行。

画冲突图时，每笔事务是一个节点。若 T2 的一个操作先于 T1 的某个冲突操作（二者之中至有一个是写，因为仅读操作没有 race），就连 T2 → T1。调度 A 的三对冲突分别是T2 写 x 与 T1 读 x，T2 写 y 与 T1 读 y，以及 T2 写 y 与 T1 写 y。三对都要求 T2 在前，图中只需一条 T2 → T1 的边。

再看调度 C，T1 先读 x，T2 后写 x，得到 T1 → T2。对 y 则有 T2 → T1，两条边闭合成环。一般地，图无环时，沿边做拓扑排序就能得到满足全部冲突顺序的串行历史。有环时，环上的事务会被要求排在自己前面。冲突图无环，当且仅当调度冲突可串行化。

同样的方法也能检查调度 B。T1 读取 y=0 早于 T2 写 y=30，产生 T1 → T2。随后 T1 又把 y=10 写回，T2 的写在它前面，产生 T2 → T1。仅检查 y 就找到了环。

两种判据的范围

图中四个操作依次是 T1 读 x、T2 写 x、T1 写 x、T3 写 x。T1 先读初值，要求 T1 → T2；T2 的写排在 T1 的写之前，又要求 T2 → T1。因此这个调度不满足冲突可串行化。

但看视图，整个调度只有 T1 的一次读，它读的是初值，最终写 x 的是 T3。串行执行 T1 → T2 → T3 也满足这两点。T2 不读取 x 就写入，T3 最后又覆盖它，中间两次写的相对次序在本例中没有被任何读观察到。因此这一调度是视图可串行化的。

既然这种执行也能解释为串行结果，系统为什么常用冲突可串行化？

冲突可串行化覆盖的范围更小，但可以通过图的环检测高效判定，也可以用 2PL 在运行中直接保证。冲突可串行化是可见可串行化的一个子集，保留所有冲突次序，自然也保留了每次读的来源和每个数据项的最后写者。View 串行化的搜索空间更大，调度可以更加灵活；Conflict 更快，但是也更加严格，其没有可行的串行方法不代表不存在最终结果一致的串行方法。

2PL 的证明

假设这是一个 2PL 过程，且存在一个冲突的环。冲突图里有一条 T1 → T2 的边，来自它们对同一记录的冲突访问。T2 取得这把锁之前，T1 必须先释放它。再看各自的锁点，T1 释放任何锁之前已经取得了最后一把锁。T2 的锁点则在它取得这把锁时或之后。于是 T1 的锁点严格早于 T2 的锁点。

沿着冲突图中的每一条边，都能推出同方向的锁点先后。若存在 T1 → T2 → … → Tk → T1 这样的环，沿环推一遍就会得到“T1 在释放锁之后拿了锁”，这不是一个 2PL 过程。因此 2PL 生成的调度一定冲突可串行化。原图用交锁过程表达同一个矛盾。走完一圈，T1 就得在已经释放一把锁后，又成功取得新锁，这违反了两阶段规则。

具体看图中的 T2。它可以先拿着 x2 等 x1，也可以先拿 x1 再拿 x2。两种顺序都满足同一个条件。T2 成功取得 x1 一定早于它释放 x2。沿假设的环串起来，T1 先释放 x1，T2 才能取得 x1，随后 T2 才能释放 x2。一直传到 Tk 释放最后一把争用的锁，T1 才能取得它。这就要求 T1 在第一次解锁之后再加锁，与 2PL 矛盾。

可串行化保证的是整笔事务之间的执行效果。应用本身还得写对。图中的第二段转账代码给 b 加上 2 × amt，却只从 a 扣去 amt，单线程执行一次也会多出钱。若初态满足余额总和不变，并且每笔事务单独执行都维持这个不变量，那么按任意串行顺序执行后，不变量仍成立。可串行化才把这个推理推广到并发执行。

CiC_iCi​ 表示满足业务不变量的状态。从 C0C_0C0​ 开始，第一笔交易保住总额，便得到满足同一条件的 C1C_1C1​。再对下一笔交易用一次同样的推理，就能一直推到 CnC_nCn​。可串行化提供了一个可以这样逐笔检查的顺序。

死锁

2PL 在访问记录前先申请锁，遇到冲突就等待，因此属于悲观并发控制。下图里 Transfer 先取得 b 的锁，Audit 也从 b 开始，就在第一步等着。转账还能继续取得 a 的锁，做完扣款后放行审计。这里发生了等待，但最后两笔事务都能结束，审计得到 20。

如果审计先拿到了 a 的锁，转账先拿到了 b 的锁，两边还能完成吗？

往后各走一步就能看出区别。转账需要 a，只好等审计。审计需要 b，只好等转账。谁都无法走到释放锁的那一步，于是形成死锁。这里的等待图把边从等待者连到持锁者，作用是找出当前谁被谁挡住。前面的冲突图记录已经发生的操作顺序，用于判断可串行化。遵守 2PL 能排除冲突图中的环，仍可能在运行中遇到等待图中的环。

OCC、HTM 与 MVCC

两阶段锁要求事务先取得锁再访问记录。若不同事务通常操作不同账户，一笔存款从计算到写回都持有锁，可能大部分时间都在为很少发生的冲突付费。乐观并发控制（optimistic concurrency control，OCC）允许事务先用自己读到的数据计算，等准备提交时，再检查这次计算的依据是否仍然成立。OCC 于 1981 年提出，后来也用于数据库和在线服务。

OCC 的三个阶段

  1. 本地执行。 tx.begin() 为本次事务建立读集和写集。读集记录“我根据哪些记录的哪个版本做了计算”，写集记录“提交时准备把哪些记录改成什么值”。调用 tx.write(A) 时先把新值放进私有写集，其他事务仍读已提交的数据。本事务随后再读 A，应先检查自己的写集，以便读到刚写的新值。
  2. 验证。 在 tx.commit() 时遍历读集，把先前记录的版本与共享记录的当前版本比较。若某项发生了冲突，就丢弃这次计算和私有写集，重新读取并计算。
  3. 写回。 验证通过才把写集中的新值安装到共享记录中，并更新版本。验证和写回要受到同一套同步机制保护，否则刚查过的记录就可能在写回之前发生变化。

第一阶段可以在没有长时间持锁的情况下执行，为什么读一条记录时仍要把值和版本配成一对？

假设 A 的值为 100，版本为 7。T1 刚读出 100，T2 就把 A 改成 110 并将版本增为 8。如果 T1 随后读到 8，便会把旧值 100 误记为第 8 版。到提交时版本仍是 8，验证也发现不了它用错了值。读记录的一种方式是先读版本，再复制数据，最后复查版本和锁状态。只有两次版本相同、期间没有写者使这次读取失效，才保留这份数据。读集要记住读取时的依据，写集里的暂存值则可以由本事务继续修改。

验证与写回

设 A、B 起初都是 1，T1 和 T2 都执行 A += 1; B += 1。如果两笔事务均先读到 (1,1)，都在对方写回之前完成验证，它们就都会算出 (2,2)，也都会把它写回。串行执行两次本应得到 (3,3)。图中的两个 V 都检查成功，问题出在检查通过后，两个事务都以为自己有权按旧值提交。

最直接的实现是给 validate_and_commit() 加一把全局锁。图中 T1 先拿锁，验证后写回 2，释放锁。T2 这才开始验证，发现自己读过的 A 已经变了，于是中止。它重试时读到 2，才有机会把结果写为 3。锁只包住提交阶段，两个事务前面的读取和业务计算仍可并发执行。中止路径需要释放已持有的锁。

数值与版本

验证时重新比较数值，和比较每次写入都会递增的版本号，会拒绝相同的调度吗？

图中第一种做法保存读到的值，第二种保存读到的版本号。区别出现在一项数据被修改后又恢复原值时，这就是 ABA 问题。

以 A 初值为 1 为例。T1 读出 1 后暂停。T2 也读 1，执行加一并提交，A 变成 2。T3 再把 A 写回 1。轮到 T1 验证时，比较数值会得到 1 == 1，于是它也把自己算好的 2 写回。按版本验证则会发现，T1 手里的 1 和此时的 1 来自两次不同的写入。只要版本号在这段时间内不会复用，就能识别中间的修改。看图下方的两条冲突边。T1 先读、T2 后写要求 T1 在前，T2 先读、T1 后写又要求 T2 在前。

缩小提交锁的范围

全局锁让两个修改完全不同账户的事务也要排队提交。可以改用记录锁。第一种写法边扫描读集边加锁验证，再锁住要写的记录。两笔事务若分别拿着对方需要的锁，就可能死锁。第二种写法先把读集和写集取并集、去重，按统一顺序拿齐记录锁，再验证和写回。这样，不相交的事务可以同时提交，相交的事务也按同一个顺序申请锁。

可以进一步只锁写集吗？如果读集只比较版本号，会漏掉哪一种冲突？

设初值 A=B=1，T1 做 A += B，T2 做 B += A。两笔事务都读到 (1,1)，T1 锁 A，T2 锁 B。此时双方虽已拿到写锁，却都还没修改对应的版本。T1 检查 B、T2 检查 A，都能通过，然后各自写回 2。最终得到 (2,2)。若 T1 先串行执行，结果应为 (2,3)，若 T2 先执行，则应为 (3,2)。两种串行结果都解释不了实际结果。

修正后的协议先按固定顺序拿齐写集的锁，然后逐条检查读集。记录要保持原来的版本，也不能正被其他事务锁住准备写入。若 T2 已经取得 B 的锁，T1 会看到 B 上的写锁，或在 T2 已提交后看到 B 的新版本，因此不能带着旧读值通过验证。若 T1 先完成验证，T2 则会在 A 上发现冲突。若一条记录同时在自己的读集和写集里，应识别出自己的锁，并照常比较读到的版本。成功时安装全部新值和新版本再解锁，失败时释放已持有的锁、丢弃写集。实现还须让版本和锁状态的检查与写入协议配合，使读者能识别提交中的记录。

加锁的成本

只考虑事务读取一条记录，且本次没有中止。OCC 执行时读取数据，提交时再读取版本和锁状态，读者通常不必修改共享的锁标志。用互斥锁的 2PL 则要先取得锁、读取数据、再写锁标志释放锁。这些操作的代价，在多个核心同时访问同一条缓存行时尤其不同。

设一把锁用 flag=0 表示可用。若加锁分成普通的“读出 0”和“写入 1”，两个线程就可能同时读出 0，又都以为自己拿到了锁。硬件提供比较并交换（CAS），把读旧值、比较和条件写入合为一个原子操作。图中的函数返回实际读到的旧值，仅在旧值等于 expected 时才写入 new。SPARC 称之为 compare-and-swap，x86 可用带 lock 前缀的 cmpxchg 对内存执行原子比较交换。

自旋锁让线程反复尝试把 flag 从 0 改成 1。返回 0 的线程取得锁，返回 1 的继续等。释放锁时，持有者只需用具有释放语义的原子写把标志设回 0，无需再次比较。下图保留了标志初始化、加锁循环和解锁的完整示意代码。

图中的一次 L1 缓存读取约 1 ns，一对 mutex 加锁、解锁约 17 ns。数值随处理器和争用情况变化。在低争用时，即使共读一条记录，读者也能各自读取缓存，省去争夺同一个锁标志的工作。

为什么会误中止

初值 A=B=100。T1 读 A、B，准备写 B=A+B=200。T2 只读 A，准备写 A=A×1.1=110。T2 先验证，此时 A 仍为 100，因此它可以提交。T1 随后验证，发现 A 的版本已经变化，于是放弃暂存的 200。数据库此时为 A=110, B=100。

如果单看两笔业务，其实可以按 T1 → T2 排列。T1 用旧 A 算出 B 为 200，T2 再把 A 改为 110。T2 没有读 B，两者之间只有 T1 读 A 在 T2 写 A 之前这一条依赖，图中没有环。这里的 OCC 按验证提交的顺序来解释执行，无法利用另一个合法顺序，所以中止了一笔本可串行化的事务，称为误中止（false abort）。

事务执行越久、读集越大，验证时遇到某条记录被修改的机会就越多。即使每一条记录都很少发生冲突，一次扫描上千条记录也可能白做。高争用时，同一笔事务还可能一直重试却无法提交，形成活锁。下图横轴是并发事务数，纵轴是每秒成功提交的事务数。图中 OCC 在低争用时省下了加锁开销，争用增大后，大量重试反而使它的吞吐低于等待锁的 2PL。

硬件事务内存

硬件事务内存（HTM）让 CPU 直接跟踪一段内存访问。Intel 在 Haswell 一代引入的 RTM（Restricted Transactional Memory）和 ARM 的 TME 都属于这一类。对于支持 RTM 的处理器，程序用 XBEGIN 标记开始，用 XEND 尝试提交。成功时，这段代码的内存修改作为一个整体对其他核心可见。程序也可以主动执行 XABORT 中止。

下图使用对应的编程接口。若 _xbegin() 返回 _XBEGIN_STARTED，就进入事务区执行普通的内存读写。中止会丢弃这次尝试的暂存修改，把控制交回开始处指定的回退路径，并提供中止状态。

CPU 0 在事务里读过 x，此时 CPU 1 在事务外执行普通写 x=1，会发生什么？

在图中的交错顺序里，x 已经进入 CPU 0 的读集。CPU 1 的写入与它冲突，硬件中止 CPU 0 的事务。CPU 1 的普通写可以完成，内存中的 x 变为 1，CPU 0 则转入回退路径。此前事务区里尚未提交的写入不会留给其他核心。

重试与回退

上半段代码中止后就跳回 beginning。若中止原因一直存在，每次重试还会在同一处失败。实际实现通常限制重试次数，再走一条能完成工作的路径，例如取得全局锁，执行同一段业务代码，最后释放锁。

为什么硬件事务里面还要检查 lock.held()？因为另一个核心可能已经走了加锁回退路径。若锁已被持有，事务应主动中止。若刚读到锁空闲，锁标志所在的缓存行就已经进入事务读集，别的核心随后取锁会使硬件检测到冲突。这样两条路径才按同一把锁协调。

硬件怎样验证

RTM 可以看成由硬件执行的乐观并发控制。图中 CPU 0 读 x，缓存记录这条缓存行属于事务读集。CPU 1 要写同一行，需要通过缓存一致性协议取得独占权限。CPU 0 收到失效请求时发现这条行带有读集标记，于是中止事务。写集里的暂存修改也由硬件管理，软件省去了为每个变量显式构建集合的步骤。硬件按缓存行跟踪，同一行里两个不同变量也可能互相干扰。

这种做法受缓存容量和地址分布限制。在图示 Intel 实现中，写集依赖 L1 容量，读集可以利用更大的缓存层级。小图里的测试标出写集约 31 KB、读集约 4 MB 的容量边界。写集更容易先装不下，具体上限要看处理器和访问模式。

事务运行越久，遇到定时器中断、调度或其他外部事件的机会也越大。网络 I/O 等操作通常要移到事务区外。图中一次实验里，中止率随着执行时间上升，测得的最长执行时间约为 3.9 ms。程序不能据此假设所有短于 3.9 ms 的事务都会成功。

SmallBank 和 TPC-C 展示了同一机制在不同工作量下的表现。图中黑线是 HTM，绿线是软件 OCC 系统 Silo。SmallBank 的短转账和审计事务上，黑线随线程数增加得更快。TPC-C 的订单事务要处理多条订单明细并更新多条库存记录，读写范围更大，图中 Silo 的吞吐随线程数上升，直接用 HTM 包住整笔事务的收益很小。硬件事务适合能在缓存中完成的短临界区，容量中止和回退成本都要计入执行时间。

事务的保证

下单时，程序先判断库存是否大于 0，再扣减库存并把商品加入购物车。若两个买家同时读到最后一件库存，两人都可能通过检查。开发者需要把“检查、扣减、加入”定为一次业务操作，再由系统约束并发和故障时可以留下哪些结果。

银行转账也是如此。客户收到转账成功的答复，就应能在故障恢复后查到一笔同时包含扣款和入账的记录。金融应用用事务把这两个动作绑定，并明确何时可以向客户确认成功。下图的余额显示争议说明用户关心的是恢复后账目是否一致，仅凭界面截图无法判断底层原因。

文件系统里，一次创建文件会修改目录项、inode 和分配位图，同样可以构成一个事务。TxOS（SOSP 2009）允许把支持的系统调用放进事务。TxFS（USENIX ATC 2018）利用 ext4 的 journal 实现文件事务。前面介绍的 3FS 则把事务用于元数据服务，例如 lookup、listdir 可使用只读事务，create、unlink、rename 等修改放进 FoundationDB 的读写事务，发生冲突后重试。

ACID

事务划定一组应该一起处理的操作，ACID 描述系统为它们提供的保证。以一次训练 checkpoint 为例，保存会生成多份文件，恢复需要使用同一轮保存的完整结果。图中虚线是提交点，越过它之后，即使故障打断后续工作，恢复机制也要能完成已经承诺的修改。

多版本并发控制

用户可以不断浏览商品，却只偶尔购买一件。后台的报表或审计事务也可能读很多条记录才结束。对这种长读事务，2PL 要申请并持有许多锁，可能挡住写者。单版本 OCC 虽然能在执行阶段直接读取，但读集越大，就越容易在最后发现某个版本已经改变。图中的绿色线表示系统优化的目标：在增加并发时维持的吞吐趋势。

读同一个快照

T1 想打印 A+B，T2 要将 A、B 一起改成新值。下面第一幅时序图中，T1 先读完旧 A 和旧 B，随后 T2 提交。原先的 OCC 验证会让 T1 中止，但它读到的本来就是完整旧状态，把它排在 T2 之前就可以解释结果。第二幅图中，T1 先读旧 A，等 T2 更新后再读新 B。两次读分别来自更新前后，求出的和可能从来没有在任何一个已提交状态中出现过。

若写者保留旧版本，T1 即使在 T2 提交后才去读 B，也仍可取回旧 B，与先前读到的旧 A 配成一份快照。多版本并发控制（MVCC）采用这个办法。每次更新创建一个带版本号的新值，读事务按自己开始时选定的快照读完整笔事务。

图左边的一条记录只有值和锁。右边把值换成版本列表，其中每一项包含数据和版本号。读取时可以从新到旧查找可见的版本。只读事务的工作由此变成“读取某个已经确定的状态”，即使其他事务提交了更新，也无需因为这些新版本而重新验证整个读集。

快照时间

一个简单实现用全局计数器发时间戳。事务开始和提交时都通过原子的 fetch-and-add（FAA）取得编号，分别记为 start_ts 和 commit_ts。开始时间决定可以看见哪一轮提交，提交时间标记本事务写出的全部版本。若 T1 完成后 T2 才开始，T1 的提交时间就小于 T2 的开始时间。对于重叠执行的事务，时间戳规定可见性，是否可串行化还取决于冲突检测。

读取一条记录时，找满足 version <= start_ts 的最大版本号。第一版伪代码先按这个规则选读值，将写入暂存在写集。提交时先锁住写集，取一个提交时间戳，再给各记录依次安装同一时间戳的新版本。单看编号，每条记录都像是来自正确的快照，但还有一个时间窗口。

图中 T2 先取得提交时间 1，已经安装 B1，还没安装 A1。T1 随后取得开始时间 2，按编号应当能看到整笔 T2。如果读者忽略写锁，此时只能找到 A0，却已经能找到 B1。两者都满足版本号不大于 2，放在一起仍然只有半笔提交。为多个值标上同一个编号，还要保证读者确实能取得属于这个编号的完整结果。

写入可见性

改进的协议要求写者在取得提交时间前持有整个写集的锁。安装某条记录的新版本后才释放其锁。读者若遇到正在写入的记录，就等它解锁，然后按自己的开始时间选版本。图中 T1 想读 A 时 A 仍锁着，等到 T2 安装 A1，T1 便能读出 A1, B1。实现时，读者对锁状态与版本链的观察也要同步，例如在读取期间复查版本和锁，确保一次读不会跨过未发现的更新。

能先取提交时间，再去锁住写集吗？

按这里的读取协议，顺序不能交换。假设 T2 先取到时间 1，还没锁 A、B。T1 此时以时间 2 开始，见 A 未锁就读出 A0。接下来 T2 取得锁并安装新版本，T1 再读 B 就会得到 B1。先拿齐锁再领号，才能保证任何有资格看到 T2 的读者遇到的记录，要么已经安装好，要么还由 T2 持锁保护。

防止丢失更新

快照解决了跨记录读取的问题，写者之间还须检查是否同时修改了同一项。图中两笔事务都做 A += 1。T1、T2 的开始时间分别为 1、2，都看到 A0=0。T1 提交得到时间 3，写入 A3=1。如果 T2 也可以在时间 4 直接安装自己算的 A4=1，版本链虽有两次写，余额却只加了一次。

提交时应在持有写锁的条件下，对写集逐项检查当前最新的已提交版本。如果其中一项的提交时间晚于本事务的开始时间，说明本事务开始后已有其他事务改过自己也要写的记录，应中止重试。这里 T2 发现 3 > 2，重试时会读到 1，随后才能正确写出 2。其他事务只改了无关记录，不影响这项检查。

写偏斜

只验证写集还会漏掉一种冲突。图中 T1 读 X、写 Y，T2 读 Y、写 X，两笔事务都在对方提交前开始。T1 读到 X0，T2 读到 Y0。两人的写集分别是 Y 和 X，因此都可以通过写写冲突检查，先后发布 Y3 和 X4。然而，T1 读旧 X 要求 T1 排在 T2 前面，T2 读旧 Y 又要求 T2 排在 T1 前面，冲突图有环。这叫作写偏斜（write skew）。

什么业务会因为这样的调度出错？

假设 X、Y 分别表示甲、乙两名医生是否值班，规定至少留一人。初始两人都在岗。乙查到甲在岗，于是把自己的 Y 改成休息。与此同时，甲查到乙在岗，把自己的 X 也改成休息。两人改的是不同记录，两笔事务都提交后却无人值班。按任意串行顺序，第二个人都会看到第一人已离岗，只能留下。

这种“从同一已提交快照读，提交时排除并发写同一记录”的隔离级别叫作快照隔离（SI）。允许它的系统就可能出现上面的写偏斜。如果业务要求可串行化，一种实现是让读写事务在提交时也验证读集，并让验证和发布按 OCC 的规则协调。医生的出勤状态已经被另一人改过，后验证的一方就要重试。只读事务仍可以读完选定的快照。MVCC 是保留和选择版本的机制，也可以和 2PL 或 OCC 结合。具体的隔离保证取决于读者选择哪个版本、写者在提交前检查哪些冲突。

两阶段提交与复制状态机

假设银行按姓名分片，Alice 的账户在 A–M 服务器，Zack 的账户在 N–Z 服务器。一次发工资要给两人都入账，协调者（coordinator）通过 RPC 分别调用两个服务器上的 deposit。如果 Alice 已经入账，另一台服务器却在 Zack 入账前崩溃，单独恢复两个本地事务，就可能得到“一笔提交、一笔中止”的结果。

与单机断电不同，这里可能只有一台机器停止，其他节点还在处理请求。网络也可能只阻断部分节点之间的消息，称为部分故障（partial failure）。跨机器的原子性需要让所有参与者对同一笔事务采用共同的最终决定。

两阶段提交

参与这笔发工资事务的两个服务器叫作参与者（participant，也称 worker）。协调者负责收集各参与者的准备结果，再决定整笔事务提交还是中止。参与者可以在本地执行计算、暂存更新，但对整笔事务的提交要经过协调。

两阶段提交（two-phase commit，2PC）把提交过程分成两个阶段。第一阶段是准备，协调者问所有参与者“你是否已经具备提交这笔事务的条件”，参与者回答 YES 或 NO。只有全部 YES，协调者才能决定 COMMIT。任一参与者回答 NO，就决定 ABORT。第二阶段是把这个共同决定通知所有参与者，各自执行并确认。

图中编号 1 是客户端请求提交，编号 2、3 才是协议的两个阶段。阴影内的入账操作已经执行到可准备提交的位置。橙色的提交点位于协调者收齐准备结果之后，还要满足下面的持久化条件。

从本地提交到全局提交

回想单机的 redo-only 事务。两个新余额 a=8, b=12 先留在内存，一条完整有效的日志持久化后，就可以据此恢复整笔事务。账本数据页可以稍后写回。若日志没有完整写成，事务就没有留下有效的提交依据。

直接把这套恢复规则搬到每个参与者，会遇到一个问题。看下图，两台机器完成了日志写，但是还没有提交。coordinator 向两台 server 发送确认消息后收到 yes 并决定提交，但其中一台在收到最终决定前重启。这个时候进行 commit 时，下面一台机器由于重启，前面没有 commit 仍然留在内存中的 log 丢失了，收到 commit 之后仍然处在最初的状态；而上面一台机器则收到 commit 消息而提交了上面一半日志，因此导致只完成了一半的提交。

因此，参与者在回复 YES 之前，必须先持久保存 PREPARED、事务 ID，以及恢复本地修改所需的信息。这个状态表示它承诺保留提交能力，接下来等待共同决定。它重启后也要认出这份承诺。

协调者收齐 YES 后，先将 COMMIT 决定写稳，再通知参与者。这个写入才是全局提交点。参与者收到决定，记录并完成本地提交，随后回复确认。最终结果已决定为 ABORT 时，也要保存相应的决定，按协议让所有参与者完成中止。

消息丢失与崩溃

这里所有请求都带同一笔事务的 ID。重发 prepare 或 commit 时，接收者按已经记录的状态答复，避免把一次重传当成第二次发工资。

准备阶段

第一种情况是 prepare 在网络中丢失。协调者迟迟收不到该参与者的回答，可以超时后重发。如果一直没有得到全部 YES，它也可以选择中止，此时还没有越过全局提交点。

再看下图，一台参与者在保存准备记录之前崩溃，另一台已经 PREPARED。协调者在等待期间没有收齐 YES，于是持久保存 ABORT，并通知仍在线的参与者中止。崩溃的节点重启后看到自己没有准备承诺，可以清理这笔尚未准备好的本地事务。两边最终都中止，整次发工资的原子性得到保留。

如果参与者已写稳 PREPARED，但 YES 回复丢了，它能在等待超时后自己撤销吗？

它必须继续保留准备状态，并向协调者查询。站在它的角度，协调者既可能因为缺票决定 ABORT，也可能已经从一次重发中收齐 YES、决定 COMMIT。它单凭超时无法区分这两种情况。允许在超时后选择中止的是尚未作出最终决定的协调者，已经投出 YES 的参与者须服从最终决定。

提交阶段

COMMIT 已落到协调者的日志里，但发给 A–M 服务器的通知丢了。N–Z 服务器可以先完成提交，A–M 仍停在 PREPARED。协调者超时后重发相同决定，A–M 收到才继续完成。两台机器完成的物理时刻可以不同，它们最终执行的决定必须相同。未完成一侧需要继续保护相关数据，使其他事务不会利用这笔事务的半成品。

若参与者直接在提交阶段崩溃，重启后先查本地日志。已有有效 COMMITTED 记录，就按本地恢复规则补齐修改。若只查到 PREPARED，则恢复为等待决定的状态，带事务 ID 向协调者查询。图中协调者已有 COMMIT，便从记录中重新发送，参与者据此完成提交。

协调者崩溃

协调者崩溃的位置决定了恢复后还能做什么。

下图中，它还没有把任何最终决定写入日志。两个参与者都已准备好，只能等待协调者恢复。协调者恢复并检查完整的持久状态，确认没有最终决定后，可以记录 ABORT 再通知所有参与者。参与者在等待期间不能替协调者猜一个决定。

如果协调者已写稳 COMMIT，恢复后就必须继续发送 COMMIT。图中 A–M 已经提交，N–Z 还在等待。协调者重启后从日志中找到决定并重发，N–Z 也提交。把后半笔撤销会和前半笔已经生效的工资冲突。

与并发控制配合

本地事务的锁和验证要持续到全局决定生效。使用持锁到提交的 2PL 时，参与者准备好以后仍保留相关锁，收到 COMMIT 后完成本地修改再释放，收到 ABORT 后撤销再释放。否则其他事务可能读到一笔最终被全局中止的工资。

使用 OCC 时，参与者在准备阶段验证读集、锁住需要保护的记录，并在投 YES 后保持保护。协调者收集的是这些本地验证与准备结果，再统一决定是否提交。若参与者一投 YES 就释放写锁，等协调者回来时，它先前验证过的依据可能已被其他事务改变。

检查点也要识别 PREPARED。即使更新页已写回，仍要保留事务身份、准备状态和恢复所需的日志。可以把这些信息完整移入持久的检查点记录，再回收旧日志段。只有最终决定明确、相关结果也有可靠的持久依据后，才能按协议清理未决事务的恢复信息。

网络分区与 CAP

2PC 允许协调者故障后恢复正确结果，但等待可能很长。若两个区域之间的网络断开，各区域内部的机器却仍能互相通信，就形成了网络分区。看下面的商店，美国区和欧洲区各保存一份库存副本，内容都是“剩 1 件”。这个 1 指的是同一件商品。

分区可以来自交换机故障、维护或链路损坏。下图的 fat-tree 网络中，交换机分为 Core、Aggregation、Edge 三层，底部每个 pod 里还有多台服务器。被叉掉的链路和交换节点使两组机器之间失去通信路径，各组内部仍可继续运行。

跨地域连接还依赖长距离光缆。下面的照片用鲨鱼接触水下电缆的场景说明，线路也有物理损坏的可能。协议需要能够处理通信中断，并判断中断时哪些请求仍有足够的信息可以完成。

CAP 定理讨论这种分区期间的取舍。这里 C 指线性一致性，即操作看起来作用于一份数据，并保持已完成操作先于后来发起操作的实时顺序。A 指每个到达正常节点的请求最终都能得到符合接口约定的完成结果。P 指系统要把节点间可能长期无法通信纳入故障模型。发生分区后，系统无法对所有请求同时兑现前两项保证。

工程服务还会给请求规定时限，这通常写进 SLO（服务等级目标）。正式的 CAP 可用性只要求最终响应，实际业务还要求响应在可接受的时间内到达。下图两次请求都最终有回复，但右边超过了 deadline，用户可能已经离开。把延迟落在 SLO 内的有效完成请求计入吞吐量，称为 goodput。

最后一件商品

美国用户先买下商品，美国区返回成功，库存改为 0。复制消息却被分区挡住，欧洲区仍看到 1。接下来欧洲用户下单，欧洲区若直接按本地值返回购买成功，同一件商品就卖出了两次。若先等另一边确认，则可能一直等到请求超时。

不能通过一律回答“售罄”来同时获得两种保证。欧洲区此时无法区分美国区已经卖出和美国区根本没有订单这两种情况，必须遵守库存与购买接口的语义。返回“服务暂不可用”则明确表示这次购买尚未得到正常处理。

下图左侧让两边都按本地库存继续确认，在这个执行中出现超卖。右侧把销售权保留在能够安全决策的一边，另一边暂停处理，守住单份库存的结果。它牺牲的是被暂停一侧的可用性。

在前面的事务系统里，2PC 通过让 PREPARED 参与者等待共同决定，优先保住全局提交的安全性。要让整个服务同时具备线性一致性，还须配合本地隔离和正确的读写协议。即使完全没有网络分区，一台协调者宕机也足以阻塞事务，因此还需要想办法让协调服务能够被接替。

复制状态机

复制可以让其他机器在某个节点故障后接管，也可以分担读取并缩短访问距离。GFS 副本和聊天记录缓存都用了复制，但它们对更新时间和结果可见性的要求不同。2PC 协调者的最终决定一旦发布就不能随意更改，因此接替者需要继承已经确定的决定和操作顺序。

先看一个反例。C1 发出 write(x=1)，C2 发出 write(x=2)。两台服务器收到的请求集合相同，到达顺序却相反，于是一台最终为 1，另一台为 2。后台再合并的乐观复制适合允许暂时不同的状态。协调事务决定时，则要在对外确认前把相关顺序和决定协调好。

复制状态机（replicated state machine，RSM）把每个副本看成按输入更新状态的程序。各副本从相同状态出发，按相同顺序执行相同的确定性操作，就会得到相同结果。图中初值都是 5，依次执行 x += 1、x *= 2，每台机器都会走过 5、6、12。若交换这两个操作，结果会变成 11，因此顺序也是输入的一部分。

主备复制让主节点（primary）接收请求、选择顺序并分配序号，再把输入发给备节点（backup）。按协议取得足够的复制确认后，主节点才向客户端确认成功。备节点必须按序号执行，先到的后续序号要等缺失记录补齐。读请求也要采用与这一顺序相符的读取规则。若某个操作要用 random() 或 time()，主节点应把选定的随机数或时间作为输入一起复制，各副本据此执行。需要替换失效备机时，还要先把已提交状态传给新成员。

主节点故障

小规模服务可以由管理员决定何时切主。要自动处理，就可以让监控程序接收心跳。下图中客户端平时直接访问 S1，监控器 M 只负责观察。S1 的心跳消失后，M 让 S2 接任，客户端查询 M 得到新地址，再把请求发给 S2。

多放几个监控器，各自发现超时就选一个新主，能提高可靠性吗？

若它们独立决策，可能造成脑裂（split brain）。图中 M1 还能收到 S1 的心跳，M2 却因分区收不到，于是 M2 让 S2 接任。原主 S1 继续给一个客户端写入 3，新主 S2 给另一个客户端写入 2，两边都觉得自己有权确认请求。超时能说明消息没按时到达，但无法仅凭这一点确认旧主已停止服务。

View Server

可以让一个 view server（VS）统一维护配置序列。每个 view 包含单调递增的编号、主节点和备节点列表，客户端查询后缓存当前主节点。图中 view 1 是主 S1、备 S2。S1 失效后，view 2 把 S2 提升为主。S3 补齐状态后，在 view 3 成为 S2 的备机。随后 S2 失效，view 4 再把 S3 提升为主，让已恢复并追上状态的 S1 充当备机。

不过，只有一个 VS 仍然可能有两台机器同时认为自己是主。下图中 VS 与 S1 之间断开，VS 发布 view 2 并通知 S2 接任，S1 却还保留 view 1。协议需要保证旧主此时无法继续向客户端确认新的操作。

拒绝旧 view

在这个主备示例中，主节点处理请求时必须取得备节点接受。转发请求带上 view 编号，备节点只接受当前 view 中正确主节点发来的请求，其他角色也按自己的 view 拒绝不匹配的客户端操作。

客户端 C 缓存着旧主 S1 的地址，发来一个写请求。S1 按 view 1 转发给 S2，S2 此时已经进入 view 2，因 view 不匹配而拒绝。S1 得不到必要确认，就无法把这次写作为成功操作返回。客户端收到错误后重新查询 VS，再向 view 2 中的主节点 S2 重试。对读请求也要有同样的有效主身份检查，例如转发给备机确认，防止旧主单独返回陈旧数据。

可以把接管边界分为两个时段来理解。

S2 的状态 S1 收到旧客户端请求时 客户端已经得知 view 2 时
S2 仍在 view 1 S2 仍是备机，可以按 view 1 接受 S1 的转发 S2 尚未安装新 view，会拒绝把自己当作 view 2 主节点的请求
S2 安装了 view 2 S2 拒绝 S1 的旧 view 转发，S1 无法取得确认 S2 可以按新配置接收请求

对这次交接，关键时刻是 S2 安装 view 2，开始拒绝旧 view。实际接管还须确保它已经取得旧 view 中所有必须保留的状态。新主确定后恢复日志并同步新备机，再开放服务，才把“谁能决定顺序”和“已有顺序从哪里接着执行”连接起来。旧主也须遵守 VS 发布的备机列表，不能因为等不到 ACK 就自行删去备机、独自确认。否则原先用于阻止旧 view 的检查会被绕过。

哪个副本可以接管

等待所有备机确认，一台慢机或失联节点就能卡住写入。能否少等几台？看下面的例子，S1、S2、S3 起初都保存 x=1。S1 写入 x=2，只收到 S2 的确认便向客户端返回成功，S3 还停在 1。随后 S1 崩溃，VS 恰好选 S3 为新主。客户端在成功写入之后才发起读，却读到 1，已经确认的写入丢了。

接管前先问“谁的日志最新”，就足够了吗？

还要看问了哪些节点。下图只有 S3 回答，VS 没有询问持有新记录的 S2，就直接让 S3 接管。它在已收到的回复里确实最新，却仍遗漏了客户端已经成功提交的第 2 条写。先前确认过写入的集合，必须和接管时实际查询的集合有交集。

那么这两个集合必有共同节点。证明可以反过来看，如果它们完全不重叠，合起来就至少需要 Qr+QwQ_r+Q_wQr​+Qw​ 个不同副本，超过系统总数 N，因此不可能。共同节点会把先前已确认的写带进查询结果。

在单写者已确定版本顺序的前提下，可以比较这些节点返回的版本。恢复时还要保留完整的日志前缀，按提交规则完成未决操作，防止只有最新编号、却缺少中间的修改。正常读取也要与尚未完成的写入协调，按协议返回已确认可见的状态。交集保证解决的是能否接触到持有记录的节点，版本顺序、提交规则和 view 切换共同决定整套服务的行为。

表里统计的是数据副本总数，主节点持久保存的那份也可以计入写集合。如果说“主节点还要等 W 台备机”，就要先换算为同一套总副本计数，再应用交集条件。例如总共 3 个副本，主节点加 1 台备机确认等于写 quorum 为 2，接管查询也至少需要覆盖 2 个副本。若只剩一台机器能够回答，它可能正是没有收到已确认写入的那一台，此时继续等待才能避免丢数据。

如果我们的机器比较稳定，不会频繁出现 primary 挂掉的情况，那么可以将 w 设置为一个较小的值——这样同步会很快，但是当 primary 挂掉的时候，较大的 r 会导致较长的切换时间；反过来如果 primary 可能频繁地挂掉，则可以调大 w 的值，让较小的 r 在 primary 出问题时可以快速切换。

接管时恢复日志

把前面的要求合起来，一次主备切换需要按顺序完成以下工作。

  1. 当前主节点为请求分配序号，复制相应日志，取得写 quorum 的确认后再向客户端确认。
  2. VS 确定新 view，协议阻止旧 view 再确认操作。新配置按规定从旧配置中收集足够的状态，使恢复集合覆盖已确认的写入。
  3. 从收集到的日志中恢复完整前缀，补齐所缺记录。选择接替者时比较日志及其已确认状态，不能只看哪个节点回复得快。
  4. 把恢复的状态同步到新配置的备机，建立新的复制关系，然后从这个共同状态继续提供服务。

图中给出的恢复耗时约为 30 ms，体现的是快速故障恢复的目标或特定部署的结果。恢复量和网络速度会影响同步时间，心跳多久才判为失联也会影响客户端实际等待多久。备机一直追踪日志，接管时需要补的内容就可能很少。若要承受机器重启后丢失内存，还须把需要保留的日志持久化，或依赖足够多仍存活的副本。

最后，VS 本身也可能失效。若当前主备仍能安全工作，它们可以继续处理已有 view 的请求，但需要改选主节点或增加备机时，就缺少新的权威配置。要让 VS 也有可接替的副本，必须让这些副本对 view 的先后和内容达成一致。Paxos、Raft 等共识协议用来解决这类复制决定的问题，也能用于复制 2PC 协调者的最终决定。

Paxos 与 Raft

前面的 View Server 决定哪台机器是主节点。若 VS 自身也有多个副本，它们就要对“下一届 view 是什么”作出共同决定。一台说 S1 是主，另一台说 S2 是主，主备协议就失去了共同依据。共识协议解决的正是这个问题。Paxos 先让一组节点选定一个值，再扩展为一串决定。Raft 直接组织一份可复制、可换主的日志。

先决定一个值

Lamport 用 Paxos 岛议会讲解这个问题。议员可以中途离场，信使也可能丢失消息，但每位议员都保存自己的账本。对于第 37 号法令，已经通过的内容需要一直保留。若每个人只把最先听到的提议记下来，S1 可能写 x，S2 写 y，S3 写 z，这样就得不到共同的法令。

把议员换成服务器，法令内容换成待决定的值 V，账本换成磁盘，多数议员换成 quorum，就得到单值共识的模型。允许不同客户端向不同节点提出不同候选值，协议最终为这一个实例选定一个值，称为 Single-Decree Paxos。Paxos 以及前面使用的逻辑时钟都出自 Lamport 的分布式系统研究。

这里考虑节点崩溃后可重启、消息可丢失或延迟、网络可分区的情况。安全性要求同一实例一旦选定 V，后续就始终保留 V。离线节点可以稍后追上，投票时必须保留影响后续决定的持久状态。要继续取得进展，则需要一个可通信的多数派，以及足够稳定的提议者和消息传递。三台服务器中，两台能继续协作时，第三台可以暂时离线。

多数派与提案号

如果有一个永远可用的写者，让它选择 V 就很简单。一个初步办法是先申请写入资格。图中 S1 获得 S1、S2 的同意，它们随后拒绝把同一份资格再授给 S3，因此 S3 只有一票。S1 写出 V1 后，另一个多数派查询也会碰到保存 V1 的节点，因为三个节点里的两个多数派必然相交。

如果拿到资格的 S1 在写值之前崩溃，其他节点怎样继续？

给每次申请附一个更大的提案号。接受过编号 1 的承诺，并不妨碍节点以后对编号 2 作出新承诺。图中 S1 在取得编号 1 的授权后退出，S3 用编号 2 从 S2、S3 获得多数同意，就可以继续推动协议。已经承诺编号 2 的节点会拒绝迟到的编号 1 写入。

一个节点可以同时承担 proposer、acceptor、learner 三种角色。proposer 发起提案并驱动两轮交互，acceptor 保存承诺和已经接受的提案，learner 得知共同决定后，将它交给上层服务执行。在图中 S1 负责处理当前请求，但 S2、S3 也具有成为提议者的能力。

Prepare 与 Accept

第一轮是 Prepare。提议者选择编号 N，向 acceptor 发送申请。acceptor 记录自己承诺过的最大编号 Nh。新申请的 N 至少达到当前承诺时，它才更新并持久化 Nh，然后返回 promise。这个承诺的含义是，以后拒绝编号小于 N 的 Accept。

提议者收到多数派对同一编号 N 的承诺，才进入第二轮 Accept，发出 (N,V)。acceptor 再次检查 N 是否低于当前 Nh，因为两轮之间可能已有更高编号的申请。检查通过后，持久保存已接受的编号和值，再回复 accept-ok。当同一提案被多数派接受，V 就被选定。提议者收集到多数确认后，可以向 learner 广播 decide，让上层得知结果。

不过，只有“更大编号优先”还不够。假设 S1、S2 已经接受了 (1,V1)，V1 因而被选定。随后 S3 用编号 2 从 S2、S3 取得承诺。如果它可以随意写自己的 V2，S2、S3 又会形成一个接受 V2 的多数派。同一个实例先选定 V1、再选定 V2，安全性就被破坏了。

继承已有提案

每个 acceptor 除了 Nh，还保存最高的已接受提案号 Na 和对应值 Va。回复 Prepare 时，把 (Na,Va) 一起返回。提议者收齐一组多数派回复后，找出其中最大的 Na，采用它对应的 Va。只有这些回复全部表示从未接受过值，提议者才能自由选择本轮 V。

Nh 和 Na 可以不同。收到更高编号 Prepare 时只提高承诺，旧的已接受提案仍保留。于是图中节点可以同时保存 Nh=2 与 Na=1, Va=V1，表示“今后只接受编号至少为 2 的提案，但我上次真正接受的是编号 1 的 V1”。

S1 已经提议 foo 后崩溃，S3 想写 bar，第 2 轮可以改写成 bar 吗？

图中 S1、S2 已接受 (1,foo)。S3 发出编号 2 的 Prepare，收到自己的空记录以及 S2 的 (1,foo)。这组回复中，最高的已接受编号是 1，所以 S3 必须把本轮值改为 foo。它新提出的是 (2,foo)，本轮成功后 S2、S3 都保存 Na=2, Va=foo。

多数派的交集让后来的 Prepare 能遇到至少一个保存过已选定值的节点。但交集节点也可能已经接受过更高编号的提案，因此协议取的是回复中最高 Na 的值。按提案号归纳，若较低编号的 V 已被选定，后续合法提案就都要继承 V，更高编号只能继续确认这个共同值。

Multi-Paxos

单值 Paxos 可以实现一个持续换主的 View Server 吗？

先回顾一下 paxos 的协议：对于一个 paxos 实例，可能会有不同的 propose 先后抵达。但是在每一次提出 propose 之后，proposer 会看到写集和读集交集中的最新 Na 和 Va。paxos 要求如果看到的 Va 非空，就必须把 V 设置成当前的最新 Va。因此可以得知，如果已经选定了一个值，就无法再进行更改了。但是实际作为 view server 工作时，view 随时会因为 primary 机器挂掉而更新，选定之后即不能修改的单个 paxos 实例不能满足这个要求。

一个实例可以决定一届 view。例如实例 1 决定主 A、备 B 和 C。A 故障后，实例 2 再决定主 B、备 C。已经选定的实例 1 保留原值，新的配置写进新的实例。图中 view 编号与 Paxos 实例号一一对应，记作一串历史。

把每个实例看成复制日志中的一个位置，就得到 Multi-Paxos。实例 0 决定 add，实例 1 决定 cmp，实例 2 决定后续命令。状态机按位置从小到大执行各实例已经选定的值，因而可以复制任意确定性计算。

日志位置冲突

最直接的实现是让 S1 先选一个位置，再针对它运行单值 Paxos。图中前面已有位置 0、1、2，客户端新命令是 yyy，S1 选择位置 3。若 Prepare 的多数回复都为空，S1 可以提议 yyy，再由多数 Accept 选定。

若 S2、S3 已经为位置 3 接受过 zzz，S1 重新申请时就必须按回复继承 zzz。它完成这一轮，选定的是该位置已有的候选值，自己的命令 yyy 还没放进去。

S1 随后选位置 4，再运行协议，才把 yyy 放进下一格。多个节点都在抢同一格时，可能要反复换位置。这与同一个位置内提案号互相抢占是两个层面的冲突。

稳定 leader

即使没有竞争，每项命令都单独 Prepare、Accept，取得决定也要两轮 RPC 往返。下图中固定由 S1 发起，位置 2、3 仍各自走一遍完整流程。

可以让 S1 的一次 Prepare 覆盖从位置 2 开始的后续位置，acceptor 对这些位置承诺同一个编号 S1:19。在承诺有效期间，后续新命令只需为相应位置发送 Accept，常态成本降为每项一轮往返。新 leader 接手时，仍要收集并继承被覆盖位置中已经接受的值，按编号恢复各位置的决定。

Multi-Paxos 必须永远只有一个 proposer 吗？

安全规则允许多个 proposer 同时尝试，但它们可能争抢提案号、争抢日志位置并反复重试。固定 leader 让客户端集中提交，由它安排位置，主要是在稳定运行期间减少这些冲突。leader 更替仍由底层 Paxos 承诺和选值规则保护。

真正实现一个复制服务，还要补上故障检测、leader 选举、状态恢复和日志推进。Paxos 的单值规则已经定义得很清楚，Multi-Paxos 的工程方案则需要明确这些机制怎样衔接。Raft 的作者和 Chubby 的实现者都讨论过，从单值协议到完整系统之间存在这些实现工作。

看下图，位置 3 的 yyy 已经出现，位置 2 却还是空的。状态机需要按顺序执行，所以不能越过 2 直接执行 3。恢复者要先对位置 2 运行 Paxos，若存在必须继承的值就补回它，若可以自由选值则可以用不改变状态的 no-op 填空。这个 no-op 也要经由共识选定。

Raft 的复制日志

Raft 直接定义复制日志服务，把问题分成 leader 选举、日志复制和提交安全性。每台服务器有自己的日志和状态机，客户端命令先进入日志，共识模块决定哪些位置已提交，状态机再按序执行。短期内某个 follower 可以少几项，但已经提交并执行的历史必须一致。

Raft 把节点状态和两个主要 RPC 的处理规则放在一起，便于按完整协议实现。etcd 使用 Raft 复制元数据，Kubernetes 的控制面依赖 etcd 保存状态，TiDB、CockroachDB 等系统也将共识复制用于各自的数据分片。

角色与任期

Raft 节点在任一时刻处于 follower、candidate、leader 三种状态之一。follower 平时响应 leader 的日志请求及 candidate 的投票请求。它长时间收不到有效的 leader 消息，就成为 candidate 发起选举。获得多数票才成为 leader，随后接收客户端命令并向其他节点复制。看到更高任期时，原 leader 或 candidate 更新自己的任期并退回 follower。

任期（term）是递增的逻辑编号，每个节点记录自己看到的 currentTerm。一次新选举会进入更高任期，可能选出一个 leader，也可能因分票而没有赢家。图中 term 3 只有选举，下一轮 term 4 才产生 S3。任期并非固定长度的时间段，各节点知道最新任期的时刻也可以不同。安全要求是同一 term 最多选出一个 leader。

leader 定期发送心跳。follower 在选举超时内没有收到可接受的 leader 消息，就自己成为 candidate 并发起新一轮选举。常见的教学示例把超时设在 100–500 ms 一类范围，实际数值要结合网络往返和调度延迟选择。节点通常只在收到有效的 leader 请求，或按协议授出票时重置选举计时器，避免过期消息持续推迟选举。

投票规则

candidate 先递增 currentTerm、投自己一票，并持久保存本轮状态，然后向其他节点发送 RequestVote。收齐包括自己在内的多数票，就当选。若它先收到当前任期合法 leader 的消息，就返回 follower。若收到更高 term 的请求或回复，则先更新任期。

每个节点在一个 term 内最多投给一个 candidate。五台机器中，一个候选者拿到三票后，其他候选者最多拿到剩余两票。多数派相交配合“每任期一票”，就排除了同一任期的两个赢家。对同一 candidate 的重复投票请求可以重发原来的答复。

多个 candidate 也可能同时开始，假如有三台机器，一个 leader 挂掉之后剩下两个 candidate 几乎同时开始投票并各自投给自己一票，这种情况下就会导致无法选出 leader，且会一直在这种情况下重试。Raft 给各节点使用独立随机的选举超时，例如在 [T, 2T] 内重新取值。下一轮更早超时的节点就有机会在其他节点开始竞争前收齐多数票。它减少持续碰撞，进展仍需要一个能够通信的多数派。

复制与修复日志

一条日志由 index、term 和 command 标识。index 是它在日志中的位置，term 是创建它的 leader 所在的任期。两者作用不同。例如下图 index 4 属于 term 2，index 5 至 8 都属于 term 3。每个节点把日志持久保存，重启后才能继续参与协议。提交表示该项已经得到协议保护，此后的合法 leader 都必须保留它。

客户端把命令 xxx 交给 S1，S1 在自己的日志末尾追加，向 follower 发送 AppendEntries。follower 检查并持久保存后回复。若它是当前任期的条目，并满足后面介绍的选举与提交规则，leader 获得多数确认就可以推进 commitIndex，按序把命令交给状态机执行，再回复客户端。

commitIndex 表示已提交的最大连续位置。leader 会把它随 AppendEntries 或心跳带给 follower，follower 据此执行已经收到的已提交条目。三节点集群中，leader 自己和一个 follower 已经能组成多数，第三台慢机可以继续追赶。图中画出了全部回复的过程，关键条件是达到多数派。RPC 可以重发，follower 依靠 index 和 term 识别已经有的条目。

日志为什么会分叉

旧 leader S1 被网络分区隔在一边，尚不知道另一边已经选出 term 2 的 S3。客户端 A 仍能联系 S1，于是 S1 在 index 3 本地追加 term 1 的 xxx。另一边 S3 追加 term 2 的 shi、ret，并复制给 S2。S1 的本地追加尚未获得多数，不能据此向客户端确认已经提交。网络恢复后，这段未提交的后缀需要按新 leader 的历史修复。

Raft 维持日志匹配性质。如果两个节点在同一个 index 上有相同 term 的条目，它们在这一项中保存相同命令，之前的全部日志也相同。图中两台机器的 index 5 都是 term 3 的 jmp，所以前 5 项一致。index 6 的任期不同，可以属于尚未协调的后缀。

检查前一项

leader 发送一批新条目时，还附上它们之前一项的 prevLogIndex 和 prevLogTerm。follower 只有在相同位置找到相同 term，才接受后续追加。图上半部分的前一项都是 index 4、term 2 的 mov，因此可接上 term 3 的 jmp。下半部分 follower 在 index 4 保存的是 term 1 的 shl，前缀对不上，就先拒绝。

这也说明了日志匹配性质怎样逐步维持。开始时日志为空，公共前缀一致。一次成功追加先确认前一项，通过已有的前缀一致性，再把同一 leader 发来的条目接上去。同一 term 只有一个 leader，而 leader 对自己的同一日志位置只写一条命令，因此新增的相同 index、term 也对应同一命令。

leader 为每个 follower 保存 nextIndex，表示准备从哪个位置继续发送。下面第一次想发 index 5，先检查 prevLogIndex=4，遭到拒绝。leader 将该 follower 的 nextIndex 退到 4，改用 index 3 作前一项，成功后补上 index 4 的 mov，再补 index 5 的 jmp。

如果分叉更长，简单实现会逐次后退，直到找到匹配位置。下图两个 follower 各有自己的 nextIndex，修复进度可以不同。遇到相同 index、不同 term 的冲突条目时，才删除该冲突位置及其后的旧后缀，再安装 leader 的新条目。

下面的 AppendEntries 伪代码省略了一些返回与状态更新。处理旧 term 请求时，拒绝后应立即返回。看到更高 term，则更新任期并退回 follower。前一项缺失或任期不匹配时也立即拒绝。只有前缀检查通过，才处理随消息到来的新条目。已经匹配的条目保留，空心跳也沿用前缀检查，不能无条件截掉 follower 的所有后缀。持久写好新增日志后再答复成功，并按 leader 的提交位置推进本地执行。

Raft 何时能提交

恢复日志会覆盖未提交的冲突条目，所以“某项已经写入磁盘”和“这项已经提交”还要分开判断。安全要求是，leader 一旦决定提交某项，以后所有合法 leader 的日志都必须包含它。新 leader 在自己的日志末尾追加命令，再用这份历史修复 follower。

index 4 已经复制到 S1、S2、S3，五个节点中有三个保存了它，就能确定它永远不会被覆盖吗？

先看只按任期和一票规则选举、尚未限制候选日志的错误版本。term 2 的 S1 已把 index 4 复制给 S2、S3，随后崩溃。S5 的日志只有前两项，如果它仍能在 term 3 拿到多数票，就会在 index 3 写入自己的新命令，并用这份更短的历史覆盖其他副本的冲突后缀。index 4 因此丢失。

候选日志的比较

选举时要把 lastLogTerm 和 lastLogIndex 一起带进 RequestVote。投票者比较候选者和自己的日志末项。先比最后一项的 term，较大的更新。term 相同时再比 index，较长的更新。候选者的这两个字段至少与投票者一样新，才具备拿到这一票的条件。

下图上半部分留下的问题是，S1 故障后，该让谁继承 index 4？如果 S4 或 S5 的最后一项落后于 S2、S3，它们就会被这些节点拒绝，拿不到三票。下半部分给了两个具体比较。

  • Case A 中 S1 的任期序列是 [1,1,2,2,2]，S2 是 [1,1,2,2]。最后 term 同为 2，S1 的最后 index 为 5，比 S2 的 4 大，因此 S1 更新。
  • Case B 中 S2 的任期序列变成 [1,1,2,3]。它最后 term 为 3，高于 S1 的 2，因此 S2 更新，尽管它只有 4 项。

加上这条投票条件，原例中的 S4、S5 无法取代持有已确认条目的节点。S2 或 S3 可以当选，随后把 index 4 带进新任期。多数派接受与多数派选举之间的交集，结合日志匹配性质，使提交过的当前任期条目持续留在后续 leader 中。

这里的多数派一律按全部服务器计数，leader 自己的持久副本也算一份。五台服务器的多数是三台，不能把“多数 follower”和“多数服务器”混用。

旧任期条目的反例

还要检查该条目属于哪个任期。下面 S1 当前处于 term 4，正在把 index 3 上的 term 2 条目补到多数派。它自己的 index 4 已有一条 term 4 日志，但目前只有 S1 保存了这一项。S5 则保存着另一条分支，末尾三项的 term 都是 3。

按时间顺序看，下图发生了这些变化。

  1. term 2 时，index 3 的旧条目仅到达 S1、S2，尚未获得五台机器中的多数确认。
  2. 之后的分区中，S5 在 term 3 当选，并在自己的日志中追加 term 3 条目，但这些条目也尚未形成提交。
  3. S1 恢复联系后，在 term 4 当选。它在本地追加 term 4 的 index 4，并将旧的 term 2、index 3 补给 S3。至此 S1、S2、S3 都有 index 3 的旧值。
  4. 若 S1 此时再次崩溃，其他节点都还没拿到它的 term 4 条目。S5 发起 term 5 选举，日志末项的 term 3 比 S2、S3 的 term 2 新，仍有机会取得多数票。它接任后就会用自己的 term 3 条目覆盖 index 3。

因此，新 leader 不能仅凭旧条目现在到了多数派，就直接认定它提交。要让日志中的旧前缀也获得提交保护，可以继续复制当前任期的一条后续条目。图中 S1 把 index 4、term 4 也复制到 S1、S2、S3。这时，S5 仅有 term 3 的末项，无法再从这些节点取得选票。index 4 一旦提交，日志匹配性质也保护了它之前的 index 3。

完整的计数规则是，leader 找到一个位置 N，确认包括自己在内的多数服务器已持久保存至少到 N 的匹配日志，并且 log[N].term == currentTerm，才凭这次多数确认将 commitIndex 推进到 N。随后按序执行直到 N 的所有条目。如果新任期暂时没有客户端命令，leader 也可以追加一条本任期的 no-op，让旧前缀通过同样的规则获得确认。

要判断的事情 所需条件
Paxos 某个值已选定 同一实例中的同一提案 (N,V) 已被多数 acceptor 持久接受
Raft 某节点当选 本轮取得包括自己在内的多数票，投票者每任期只投一个候选者，并检查其日志足够新
Raft leader 按副本数推进提交 匹配日志已到多数服务器，推进到的 N 属于 leader 当前任期
Raft 旧任期条目获得提交保护 它位于一条已按规则提交的后续日志之前，随同连续前缀一起提交

Paxos 把“这一格选择哪个值”的规则用于连续日志位置，Raft 把任期、选举、前缀修复和提交条件结合起来维护复制日志。两者都需要把参与下一轮判断的状态可靠保存，并在决定命令之后按同一顺序驱动状态机。
