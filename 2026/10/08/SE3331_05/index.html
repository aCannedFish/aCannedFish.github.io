并发读写

多个用户同时读写数据时，系统需要规定操作的顺序，以及每次读取能看到哪些更新。数据有多个副本后，更新还要经过网络传播；消息延迟、节点故障和本地缓存都可能影响读取结果。

例如，两台手机各保存一份聊天记录。一台先发文件、再发引用，另一台可能先收到引用。两个人也可能各自看到接龙已有 17 人，同时把自己加在第 18 位。要解释这些结果，需要先了解读写、副本和消息传递，再讨论系统怎样安排顺序。

读写基础

程序保存在系统中的数据称为状态。聊天应用的状态可以是一份消息列表：[你好] 表示已有一条消息，[你好,谢谢] 表示已有两条。Write 或 Update 是写入、修改状态的操作；Read 是读取当前状态的操作。

状态机用“当前状态与操作决定下一状态”描述执行。例如列表先追加 X、再追加 Y，得到 [X,Y]。读取可以保持状态不变，但返回值取决于它在这些更新之间的位置：第一次追加后读取得到 [X]，两次追加后读取得到 [X,Y]。

副本是同一份数据在另一位置保存的拷贝。手机、平板和服务器都可以保存聊天记录。缓存通常用于加快访问，副本还可以用于故障后继续服务；两者都需要处理内容更新。

程序的一次运行实例称为进程。进程可以依次执行多次操作，也可以与其他进程共同访问数据。客户端是发出请求的一方，服务器是接收请求、处理数据并返回结果的一方。一台电脑上可以同时运行多个客户端或服务器进程。

串行执行是做完一个操作后，再做下一个。并发执行时，多个操作的运行时间有重叠。例如 Alice 的消息还在等待回复，Bob 就已经发送了另一条消息。网络和服务器处理可能让这些操作以不同顺序完成。

内存保存正在使用的数据，程序可以快速访问；磁盘、SSD 等设备用于长期保存。断电后要保留的数据需要写入相应的稳定存储。下面每次提到“写入完成”，都要结合当时规定的确认条件理解。

图示读法

时序图中的每条横线或竖线代表一个参与者，例如客户端、服务器或某个副本。时间沿标有 time 的方向推进。箭头表示请求、回复或同步消息：箭头起点是发送，终点是接收，两者之间可能有网络等待。

ACK 是确认回复，Done 表示这次调用已按协议完成。RPC 是远程过程调用，客户端把函数参数发给服务器，由服务器执行并返回结果。RTT 是一次网络往返的时间，即请求发出后等到回复返回所用的网络时间。

图中的 x=1、f=v1 或 [你好] 都表示某一时刻的数据状态。沿时间方向逐步看每个箭头，再更新各条线上的状态，就能判断一次读取会得到什么。

文件共享

文件系统把文件内容和管理记录一起保存。内容是文件里的字节；管理记录包括名称、大小、权限和数据位置。inode 是一份文件管理记录，inode 号用于找到它。文件句柄把服务器需要的对象标识交给客户端，后续请求带回句柄，就能继续访问相应文件。

NFS 是 Network File System，中文叫网络文件系统。应用挂载远端目录后，通过普通文件接口访问内容，客户端把操作转换成 LOOKUP、READ、WRITE 等 RPC。

经典 NFSv2/v3 由客户端保存打开状态和读写位置。每次请求带上文件句柄、偏移和长度，服务器据此找文件。句柄中的 inode 号标识对象，generation number 记录编号的使用代次，用来识别 inode 重新分配后留下的旧句柄。客户端还会缓存数据，减少远端读取。

在单服务器模型中，文件容量受这台服务器的磁盘容量限制。服务器失效期间，客户端需要等待服务恢复。超时后可以重试，执行结果还要结合回复记录和具体文件操作确认。

GFS 是 Google File System。它把大文件切成多个 chunk，经典块大小为 64 MB，每块通常保存三份副本。master 记录文件包含哪些块、每块在哪些 chunkserver 上；客户端取得位置后直接读写 chunkserver。

图中的 C0 位于节点 1、2、3，C1 位于节点 2、3、4。一个文件可以跨多台机器保存；一台 chunkserver 失效后，客户端可改读其他副本。master 管理的两类映射让客户端从文件名找到块，再找到存储节点。

训练文件

训练样本是供模型学习的一条输入，例如一段文本或一张图片。模型通过训练调整参数，检查点保存这些参数和训练进度。数据准备会把原始资料转换成适合训练的文件，dataloader 再按训练顺序取出样本。许多任务同时进行时，存储系统需要及时接收写入、提供读取。

3FS（Fire-Flyer File System）用于 AI 训练与推理。训练程序反复随机读取样本，定期保存模型，推理程序还会读写已有计算结果，形成下面四类文件访问：

用途 文件访问
数据准备 写入并读取大量中间文件
dataloader 随机读取训练样本，每次可能为几 KB 至几 MB
检查点 集中写入模型状态，图示负载超过每节点 10 GiB/s
KV cache 读取推理中保存的注意力键和值，图示负载的峰值为 40 GiB/s

检查点用于恢复训练进度；dataloader 把样本交给训练程序；KV cache 保存已有 token 的部分计算结果，供后续生成使用。这里的吞吐数字对应图示负载，1 GiB 等于 2302^{30}230 字节。

3FS 分为客户端、元数据服务、存储服务和集群管理器四类组件。心跳是定期发送的存活消息，租约是有有效期的授权，用于规定某个节点在这段时间承担的职责。文件布局记录文件怎样分块，以及怎样找到这些块。

思考题：3FS 的目录和 inode 元数据由谁可靠保存？多个元数据服务怎样在共享事务存储上处理请求？

解答：

权威目录项、inode 属性和布局保存在 FoundationDB 中，由事务键值存储可靠管理。元数据服务把文件操作转换成读取、检查和修改键的事务。多个实例访问同一份记录，按存储提供的冲突检测与提交规则协调修改，因此可以由其他实例继续读取和处理请求。

客户端接收文件操作，元数据服务查询和修改目录、inode 及文件布局，存储服务保存数据块。集群管理器通过心跳了解节点状态，并管理成员和租约。文件内容由客户端与存储服务传输，文件管理信息保存在共享的键值存储中。

这些设计延续了前面介绍的分块、副本、心跳和文件接口。每类服务负责哪些状态，需要分别看它的工作：元数据服务从共享存储取得记录，存储服务持有数据块，写打开的会话也需要记录。

硬件和调度

SSD 是使用闪存保存数据的设备，NVMe 是访问这类设备的一种协议。GPU 执行适合大量并行处理的计算，网卡负责收发网络数据。Mbps、Gbps 分别表示每秒百万、十亿 bit；每 8 bit 为 1 B。图中的设备数量和链路速度共同决定一台节点能持续处理多少数据。

思考题：GFS 与 3FS 的硬件和文件访问方式发生了哪些变化？locality-oblivious 怎样影响任务位置、网络需求和扩容方式？

图中给出两组存储节点配置：GFS 节点使用两块 80 GB 磁盘和 100 Mbps 网络；3FS 节点使用 16 块 NVMe SSD 和两条 200 Gbps RDMA 链路。按名义带宽计算，400 Gbps/0.1 Gbps=4000400\ \text{Gbps}/0.1\ \text{Gbps}=4000400 Gbps/0.1 Gbps=4000。

RDMA 是远程直接内存访问，网卡可以读写对端预先注册的内存缓冲区。这些硬件变化使远端小块读取更有实用价值，软件队列、内存复制和 CPU 处理也更容易影响总速度。

左图把处理 C2 的 MapReduce 任务安排到保存 C2 的机器，减少网络传输。右图的 GPU 与存储分开部署，GPU 节点通过 RDMA 读取所需数据。

locality-oblivious 表示任务调度主要依据计算资源，数据位置由存储系统处理。图中的 full bisection 表示网络设计要为两组节点之间提供足够的总带宽。在相应带宽条件下，计算节点和存储节点可以分别扩容，任务也有更大的调度余地。

元数据事务

键用于查找一条记录，值是记录内容，例如 文件名 → inode 号。元数据描述文件的属性和位置，键值存储让服务按键取得这些记录。事务提交是把一组准备好的修改一起确认：改名后，读取应看到源目录项已经移除、目标目录项已经建立；恢复时也按完整的事务记录处理。

3FS 把 inode 和目录项表示成键值对，保存在 FoundationDB 中。键值存储提供 get(key)、set(key,value) 等接口；事务把几次相关读写一起提交，使它们全部完成或全部撤销。

思考题：目录 inode 2 中的 a.txt 移到目录 inode 5，文件 inode 仍为 7，事务需要修改哪些键？同一时刻另一个服务 unlink 源名称，会发生什么？为什么多服务共享事务存储有助于处理这种情况？

解答：

事务读取并检查源、目标记录，删除 DENT|2|a.txt，建立 DENT|5|a.txt → 7，两项修改共同提交。inode 7 和文件内容继续代表同一对象。并发 unlink 访问相关目录项时，读写冲突使其中一方重新读取并重试。各服务使用同一事务存储，能够依据共同记录协调这个冲突。

图中 /x 的 inode 为 2，/y 为 5，文件为 inode 7。DENT|2|a.txt 表示目录 2 中的 a.txt，值为 7；INOD|7 保存这个文件的属性和布局。

把 /x/a.txt 改名为 /y/a.txt 时，简化步骤如下：

  1. 开始事务，读取并检查相关目录项。
  2. 删除 DENT|2|a.txt。
  3. 写入 DENT|5|a.txt → 7。
  4. 提交这两次修改。

若另一个元数据服务同时删除源目录项，事务存储会检查读写冲突，让其中一方重新读取并重试。权限检查、目标覆盖和目录环检查也要放进实际操作中。

GFS 的单 master 在内存中保存元数据，文件数和查询量增加时，内存容量与处理速度会影响扩展。图中标出的历史实现约处理每秒几千次元数据操作。3FS 让多个元数据服务访问同一份事务存储；图中一个服务失效后，其他实例仍可读取这些记录。请求重试与事务结果确认由相应协议处理，共享存储本身也需要故障恢复能力。

打开记录

打开文件后，操作系统为当前进程建立记录，并返回文件描述符 fd，后续读写通过这个编号找到文件。服务器端的会话则记录哪个客户端以何种方式使用文件。只读表示查看内容，写打开表示客户端可能修改内容；回收文件时需要考虑这些正在进行的操作。

思考题：哪些打开文件需要服务器端会话记录？只记录写打开怎样减少大量样本打开的工作，删除时又需要考虑什么？

解答：

服务器跟踪写打开的会话，只读 fd 与布局由客户端保存。大量样本打开时，省去只读会话的写入、维护与清理。删除没有写会话的样本时可进行回收，已打开读者的后续远端读取可能失败；正在写的检查点要等写会话关闭或失联记录清理后再回收。

3FS 在服务器端记录写打开的文件会话。训练启动时会打开大量样本，省去只读会话的记录写入，可以减少启动时的元数据工作。

图中 worker 0、1 打开了样本 s0001、s0002，这些只读打开记录被划去；worker 2 写入 ckpt-7，W 会话保留。

清理任务删除 s0001 时，可以立即处理删除，已经打开的读者随后可能遇到读取失败。删除 ckpt-7 时，要等写会话关闭，或等失联会话被清理后回收。这让服务器能协调正在进行的写入和删除。客户端仍保存自己的 fd 与文件布局。

文件接口

内核管理进程、内存和设备访问，用户态运行普通应用。read() 是程序请求读取文件的接口，调用后由文件系统实现完成读取。共享队列保存待处理请求，多线程取放时用锁协调；共享内存让两个进程访问同一份缓冲区，减少把数据反复复制到不同位置的工作。

FUSE 是 Filesystem in Userspace，中文常称用户态文件系统。应用照常调用文件接口，内核把请求交给用户态文件系统程序，再由它访问存储服务。

思考题：FUSE 怎样把普通文件调用交给用户态程序？一次读取经过哪些步骤？

解答：

应用调用 read，内核 VFS 将文件操作交给 FUSE 模块，请求进入共享队列。用户态文件系统程序取出请求并访问存储服务，再把数据经返回路径交给应用。多个线程的队列访问需要同步，数据还会在用户态程序、内核和应用之间复制。

沿图中的 read() 路径看：应用进入虚拟文件系统 VFS，FUSE 模块把请求放进共享队列，用户态程序取出请求，再访问存储。结果经内核返回应用。队列需要线程间同步，数据传递还会消耗内存带宽。用户态程序便于开发和维护，应用也能继续使用已有文件 API。

图示实现的测试中，这条 FUSE 路径每秒约处理 40 万次 4 KiB 读取。SSD 和网络更快后，队列竞争及数据复制可能限制总性能。

思考题：FUSE 队列和复制在快速 SSD、RDMA 环境中会带来什么成本？共享请求环与数据缓冲区怎样改变这条 I/O 路径？

解答：

较快硬件使共享队列的锁竞争、调度和数据复制更容易影响总耗时。Ior 传递请求描述，Iov 保存读写数据。打开和注册完成后，应用与客户端通过共享内存提交并批量处理 I/O，减少逐次进入 FUSE 队列及复制内容的工作；初始化和共享结构同步仍按接口安排。

3FS 还提供 native client。应用先通过 FUSE 打开文件，后续 I/O 使用共享内存：

结构 作用
Iov 数据缓冲区，保存待写数据或读取结果
Ior 请求环，记录待处理的异步 I/O 请求

应用把请求放进 Ior，客户端批量处理，并通过 RDMA 访问存储；数据进入共享的 Iov。图中的绿色路径减少了每次经过内核 FUSE 队列和复制数据的工作。这种异步提交方式参考了 io_uring。缓冲区注册、文件打开和多线程同步仍要按客户端接口安排。

缓存读取

v1、v2 表示同一个文件先后两个版本。例如 v1 的内容是 hello，写入方改成 hello, world 后得到 v2。修改先留在客户端时，服务器仍保存 v1；等写回完成后，服务器才具备返回 v2 的内容。读取方也要检查自己保留的缓存是否仍有效。

一个文件在服务器和多个客户端缓存中都有内容时，写入传播时间会影响读取。

图中最初 f=v1：

  1. 客户端 1 写入 v2，新内容先保存在本地缓存。
  2. 客户端 2 打开并读取文件，服务器仍返回 v1。
  3. 客户端 1 关闭文件，将 v2 写回服务器。
  4. 客户端 2 再次打开，检查文件属性后读到 v2。

这称为 close-to-open consistency：关闭文件时完成相应写回，打开文件时检查缓存。两个程序长期保持文件打开时，还需要安排读写同步。写回进入稳定存储的时机由具体版本和配置规定。

副本写入

这里的 write(A)、write(B) 表示把同一片数据改成 A 或 B。先写 A 再写 B，后一次覆盖前一次，最终为 B。因此，每个副本要记录相同的操作顺序，才能得到相同结果。消息到达时间、开始处理时间和完成写入时间都可能影响这个顺序。

两个客户端分别写 A、B，消息可能以不同顺序到达三个 GFS 副本。某些节点先写 A 再写 B，最终保存 B；另一些节点先写 B 再写 A，最终保存 A。

GFS 选一个副本作为 primary（主副本），由它决定同一 chunk 上的修改顺序。图中数据 A、B 先进入各副本的缓冲区，primary 再规定顺序为 A、B，secondary（次副本）依次执行，最终都保存 B。

参与写入的副本执行并返回结果后，primary 才能报告成功。某个副本执行出错时，primary 向客户端报告失败，客户端再按协议重试和恢复。

思考题：GFS 已统一写入顺序，若某次写入只在部分副本完成并报告失败，两个客户端随后从不同副本读取，会得到什么？写入顺序与读取可见性各需要什么规则？

解答：

图中初始都为 A，写 B 只在节点 1、2 完成，节点 3 保留 A。客户端 1 可读到 B，随后客户端 2 从节点 3 读到 A。统一写入顺序规定副本怎样执行修改；读取规则还要明确失败或未确认修改是否可见、哪些副本可读。若要求统一的已确认读取状态，需要额外确认、验证或修复等待。

初始值都是 A。写 B 时，节点 1、2 完成更新，节点 3 的写入消息丢失，整个写请求返回失败。此时一个客户端从节点 1 读到 B，随后另一个客户端从节点 3 读到 A。

GFS 客户端通常从某个合适的副本直接读取，常会选择网络距离近的副本。失败写入可能留下部分修改，因此统一成功写入的顺序后，还需要规定失败期间允许怎样读取。一致性模型用来规定这些情况下允许返回的结果。

聊天记录

列表是一组有排列顺序的项。追加表示把新项放到末尾，[file,ref] 表示先有文件项，再有引用项。引用保存目标消息的标识，用户点击后，程序按这个标识寻找原消息和文件。目标消息还没到当前设备时，程序就需要等待取得它，才能显示引用内容。

聊天记录可以表示成一个列表，每项可以是文字或文件。更新操作 Update(msg/file) 向列表加入内容，读取操作 Read(history) 返回已有记录。

思考题：Alice 先发文件，再发引用它的消息，Bob 却先看到引用并提示“引用内容不存在”。哪些发送、同步和显示顺序可能产生这个结果？

解答：

Alice 本地产生文件，再产生引用，顺序为 file、ref。文件同步先启动，但传输较慢，引用先到服务器和 Bob；若按到达顺序立即显示，就先出现 ref，此时找不到目标。文件后来到达才补齐内容。要保留引用依赖，可记录目标消息 ID，并等目标可见后再展示引用。

Alice 先发 Chap_01.pdf，再问“是这个文件吗？”，第二条消息引用了第一条文件。Bob 的设备先显示引用，点击时得到“引用内容不存在”，文件随后才到达。

这里要分清三件事：用户创建更新的顺序、网络传递更新的顺序，以及设备显示更新的顺序。例子中 Alice 看到“文件、引用”，Bob 一度看到“引用、文件”。系统的一致性规则要说明这种情况是否允许，以及后来怎样处理。

这里用一个简化的传播过程解释这种可观察结果。实际“引用内容不存在”还可能与目标删除、权限或附件获取失败有关，需要记录消息与附件状态才能定位原因。分析一致性时，先明确假定哪些操作已发生、哪些消息已经到达，再检查允许的观察。

集中保存

在集中保存的实现里，服务器持有用于回答请求的列表。更新函数先修改列表，再返回确认；读取函数在安排好的位置取得当前列表。比如服务器已按顺序追加 A、B，读取就返回 [A,B]。同一台服务器有多个处理线程时，也要安排它们怎样共同访问这份列表。

先考虑一种简单实现：一台服务器保存完整聊天列表，所有更新和读取都通过 RPC。

思考题：由一台服务器统一追加消息，并让用户等待上次 ACK 后再发下一次请求，是否能保留这个用户的操作顺序？两项条件分别起什么作用？

解答：

在给定条件下，可以保留同一用户的顺序。服务器把上一条更新加入列表后才返回 ACK，用户收到它才发下一条，所以文件已加入后才可能发出引用。统一安排追加让读取取得同一份列表。重叠的其他用户请求则按服务器规定的合法顺序处理。

服务器收到 Update(file) 后追加文件，返回 ACK；用户收到回复后再发送 Update(ref file)，服务器继续追加引用。随后读取就得到 [file,ref]。

这个例子的顺序成立需要两个条件：服务器统一安排追加顺序；每个用户收到上次调用的回复后再发下一次调用。服务器还应协调并发线程，保证每次追加和读取符合列表的操作规则。

这种实现有四项成本：

情况 对用户的影响
每次更新等待服务器回复 发消息要等待一次网络往返和服务器处理
每次读取返回全部历史 历史越长，需要传输的数据越多
设备离线 获取历史依赖服务器，本地也没有自己发过的完整记录
服务器失效 所有用户的远端更新和读取都要等待恢复

图中后一次历史量约为前一次的四倍，在相同带宽等简化条件下，传输时间由 t 增长到约 4t。按页加载、增量读取和本地缓存可以减少每次读取的数据量。

本地副本

一条新消息可以先写入当前设备，再发送给服务器或其他设备。当前设备立刻具备显示这条消息的内容，其他设备只有收到它之后才能显示。界面可以分别记录“已在本地保存”“已发送”“对方已收到”，让这些不同阶段有明确含义。

让手机、另一台设备和服务器各保存一份聊天列表，可以在设备上读取已有内容，也可以先保存自己刚发的消息。

图中三个副本最初都有 [你好]。服务器失效后，副本 1 在本地加入“谢谢”，副本 3 仍能读到“你好”。设备恢复联系后再同步缺少的更新。

本地读写减少了等待：写入可以先完成本地处理，读取直接使用已保存的历史。离线时也能查看已有记录和暂存新消息。消息是否已经送达他人、是否已在远端保存，需要另外记录状态。

本地保存可以通过 SQLite 等本地数据库或日志实现，把消息 ID、内容、发送状态和待同步记录一起保存。进程退出或设备重启后，再从这些记录继续发送。界面上的“已显示”可以先于远端确认，应用需要按自己的语义标记当前阶段。

更新确认

确认是接收方按约定返回一条回复。例如一组确认条件要求本机和服务器都保存记录，这两方完成后即可报告成功，第三台设备稍后补齐。要求全部副本确认时，每一方的等待都计入这次请求；要求部分副本确认时，其他副本可能暂时缺少新记录。

只修改本地副本后，其他副本暂时还保留旧状态。系统需要传播更新，并规定在什么条件下向调用方报告完成。

思考题：只更新本地副本后，各设备会处于什么状态？一次写入要等多少个副本确认才返回？全部确认和部分确认分别影响哪些等待与故障情况？

解答：

只改本地时，一个副本已有新内容，其他副本仍保留旧内容。确认数量由协议规定：全部确认要等最慢的一方，失联节点会阻塞或使请求超时；部分确认在指定参与者完成后返回，其他节点后台补齐。成功回复所表示的保存和可见性程度，也必须与这些确认条件一起定义。

第一种做法要求每个副本都返回 ACK。所有副本完成后，调用方再收到成功回复。等待时间取决于最慢的一方；某个节点或链路失效时，写入可能一直等待或超时。

第二种做法先联系若干副本，例如本地设备和服务器，满足确认条件后返回。暂时失联的副本在后台补齐更新。

确认条件决定了这次成功所提供的保存与可见性保证。需要说明哪些节点已保存更新、哪些读取可能仍返回旧内容，以及后续如何补齐数据。

周期同步

同步交换设备已经收到的更新。设备可以保存上次同步位置或已知更新 ID，只请求缺少的记录。新消息到达、网络恢复或定时检查，都可以触发同步。一次同步可能带回多条消息，再逐条合并到本地列表。

读取本地副本时，返回的是这台设备已经收到的内容。其他设备刚产生的消息可能还在传输中。

思考题：读本地副本可以立即取得哪些消息？其他设备刚产生的更新何时能读到？周期同步与推送通知怎样补齐缺少的内容？

解答：

本地读取返回该设备已经收到的记录。新消息在传播完成前可能尚不可见，联网后通过同步补齐。周期检查定时交换缺少的更新，推送通知提醒设备有新内容并触发获取。图中的 10 s 是一次同步触发示例，实际可见时间还包含网络恢复、传输和处理等待。

图中副本 1 先后产生“谢谢”和“再见”，副本 3 暂时失联，只能读取 [你好]。网络恢复后，同步带来两条更新，列表变成 [你好,谢谢,再见]。

可以每 10 秒通过心跳检查并同步，也可以使用 Apple Push Notification 等推送服务通知设备有新消息，再批量取得更新。同步间隔会影响更新多久可见；网络断开时，设备等待恢复后再继续交换记录。

推送通知可以触发一次增量获取，消息正文与附件还要按协议取得。一次同步可以合并多条更新，降低逐条往返的成本；重试重复带来的记录则按稳定 ID 检查。离线时间较长时，可以从服务器保留的日志或有效快照补齐状态。

到达顺序

把收到的更新立即追加到列表尾部，可能让同一批更新在各设备上排列不同。

副本 1 先加入文件，再加入引用，本地为 [file,ref]。文件的同步先启动，但传输延迟；引用先到副本 2。副本 3 从服务器同步时也先收到引用，因此出现“引用内容不存在”。文件最后到达，按到达顺序追加就得到 [ref,file]。

两条更新最终都到了，显示顺序还需要由共同规则确定。系统要保存更新标识、依赖和排序信息，才能在不同到达顺序下得到约定的结果。

合并更新

合并要保留不同设备产生的新记录，并识别重复发送的同一记录。例如 R1:#8 是 R1 创建的第八条更新，重试时仍用这个 ID；接收方收到三次，也只加入一次。另一条内容相同、ID 为 R1:#9 的消息可以作为新的记录保留。

两台设备也可能从同一份历史开始，各自加入不同消息。

开始时都有 [你好,谢谢]。副本 1 加入“好的”，副本 3 加入“收到”。两份列表各自包含新更新，同步需要保留这两条消息。

若把收到的新消息追加在已有内容之后，副本 1 会得到 [你好,谢谢,好的,收到]，副本 3 会得到 [你好,谢谢,收到,好的]。去重只能解决同一更新出现多次的问题，排列顺序还需要统一。

思考题：副本 1 先显示“好的”，副本 3 先显示“收到”。合并后若统一排列，能同时保留两边已经显示的顺序吗？应用要怎样处理消息移动？

解答：

统一后选“收到、好的”时，副本 1 原先显示的“好的”会向后移；选“好的、收到”时，副本 3 的显示会调整。因此，两边各自优先的临时观察需要由共同规则重新解释。聊天可标记待同步并合并更新；涉及业务名次时，应等确认或明确处理冲突。

图中最终选定“收到、好的”，副本 1 原先显示的“好的”向后移动。若选定“好的、收到”，副本 3 的已有顺序就会变化。应用需要决定能否接受同步后的重新排列；聊天和按名次发奖的接龙可能有不同要求。

一致性模型

规定模型时，需要写出可检查的读取结果。比如 x 初始为 1，一次更新把它改为 2，随后另一个进程读取。模型要说明这次读能否返回 1、是否必须返回 2、需要等待什么条件。这样的规则让应用开发者知道可以依据哪次确认继续做下一步。

思考题：应用怎样通过一致性模型判断读取结果，而无需了解每条同步消息？应先确定哪些业务要求，再选择可实现的保证？

解答：

一致性模型规定允许的操作顺序和读取结果，开发者据此判断已确认更新是否应可见、引用是否需等待目标，以及是否允许临时旧值。选择前应确定离线操作、名次变化和冲突处理等业务要求，再检查实现的同步、排序和恢复机制能否提供相应保证。

一致性模型规定更新的可见性和操作的顺序，也就是每次读取可以返回哪些结果。它适用于数据副本、缓存、多核或多机并发，以及故障恢复中的读写。

观察到不同数值，需要结合操作历史判断。例如 x 从 1 改到 2，较早读取返回 1、较晚读取返回 2，本来就可以符合规则。若写入已确认后另一读取仍返回 1，是否允许取决于所选模型及确认条件。

检查一段历史时，可以记录操作的发起、返回、输入与结果，寻找符合对象规则的解释。业务还可以有额外条件：转账保持总额、引用指向存在的目标、名次按确认规则分配。这些条件需要与一致性模型共同满足。

模型 主要要求
最终一致性 更新停止并完成传播后，各副本收敛到相同状态
因果一致性 有依赖的更新按因果顺序可见
顺序一致性 所有操作可解释为一个共同的串行顺序，并保留每个进程的程序顺序
线性一致性 在合法串行顺序中，保留操作完成到后续操作发起的实时先后关系
严格一致性 按全局实际发起时间规定操作顺序

模型对结果的要求越多，实现就需要满足更多协调条件。图中的性能和容错箭头概括了常见设计选择，实际速度还取决于算法、负载、网络和硬件。具有相同一致性保证的系统也可以采用不同架构。

选择模型时，先写清楚应用要求：消息是否允许延迟出现，引用是否要等目标内容到齐，接龙的名次是否允许同步后变化。再判断实现提供的保证能否满足这些要求。

最终一致性

收敛表示各副本经过同步后，内容和约定的排列变得相同。假设 x 最初都是 1，R1 改成 2，R2 在更新到达前仍读到 1；收到更新后，R2 改成 2。若之后没有新修改，持续同步会让相关副本都保留 2。这种保证允许传播期间存在暂时不同的读取结果。

思考题：聊天应用怎样在设备能继续读写已有状态的同时，让多台设备最终取得相同历史？最终收敛需要哪些传播和故障恢复条件？

解答：

设备先保存自己的更新并读取已有状态，后台持续传播记录，接收方按 ID 去重并按共同规则合并。更新记录需能在故障后恢复，相关副本重新通信后继续补齐。写入停止、更新最终送达、各副本从一致的基础状态按相同规则处理后，历史收敛为相同结果。

聊天例子的两个目标是：设备能继续读取已有内容、保存新消息；恢复通信后，各设备最终得到相同历史。

最终一致性要求，在更新停止、相关副本恢复通信并持续传播更新后，读取最终返回相同状态。同时，持有相同更新集合的副本，需要按共同规则产生相同结果。

图中本地 Update(file) 标为 0 RTT，表示这一步完成前可以省去网络往返。随后同步通过服务器转发，也可以在设备之间进行。本地持久化所需的磁盘操作仍按保存要求执行。

一种实现流程是：

  1. 为每条更新分配稳定标识，保存内容和排序信息。
  2. 写入本地记录，向用户显示处理结果。
  3. 后台向其他副本传播，失败后继续重试。
  4. 接收方按标识去重，合并收到的更新。
  5. 按共同规则计算列表状态。

至少一次 RPC 可能把同一条更新发送多次，稳定标识用于避免重复追加。长期断开的副本要在重新连接后补齐记录，持续同步是最终收敛的前提。网络长期中断时，单个副本可以继续提供本地操作，跨设备的新内容则等待通信恢复。

统一日志顺序是聊天列表的一种收敛方法。其他数据也可以使用共同的合并规则。例如一个计数器分别收到“加 1”和“加 2”，假设每项更新恰好应用一次，两种执行次序都得到 3；列表追加 X、Y 则会产生不同排列，需要进一步规定顺序。

最终一致性关注相应条件下的收敛，具体传播速度、数据保留与离线操作由实现确定。可交换操作和可合并状态也是实现方向，相关形式化方法见 CRDT 研究报告。

日志排序

日志按条保存发生过的操作，例如 追加X、追加Y。重放表示从一个已知初始状态开始，重新依次执行这些操作。空列表先追加 X、再追加 Y，就得到 [X,Y]；相同的初始列表和相同操作序列会得到相同结果。日志还需要保存 ID，重复传输的同一操作只执行一次。

两个设备分别产生 X 和 Y，本地开始时为 [X]、[Y]。同步后，若只按到达顺序追加，就会得到 [X,Y] 和 [Y,X]。

思考题：R1 先保存 X，R2 先保存 Y，交换后分别得到 X、Y 与 Y、X。怎样用确定的日志排序和重放，让相同更新集合产生相同列表？

解答：

保存完整更新记录与稳定 ID，交换缺少的记录并去重；双方对相同集合使用同一唯一排序规则，从共同初始状态或检查点重放。例如双方都约定 X 在 Y 前，重放后都得到 [X,Y]。到达顺序可以不同，计算结果由相同日志顺序确定。

一种便于分析的实现是：保存所有更新日志，对相同更新集合使用相同的排序规则，从共同初始状态重新执行更新。两台机器把日志都排成 X、Y，重新执行后就都得到 [X,Y]。

这里需要三个条件：各副本最终取得相同更新；排序规则确定；相同初始状态和相同操作顺序产生相同结果。实际系统可以用检查点和增量计算减少重放工作，同时保留这些条件。

操作标识还用于去重。同步与重放期间，更新保留创建时的标识和时间戳，接收方单独维护自己的当前时钟。

迟到更新

假设当前日志有 〈1,X〉、〈3,Z〉，列表显示 [X,Z]，后来收到 〈2,Y〉。共同规则规定键 2 在键 3 前，完整列表就要变成 [X,Y,Z]；直接在末尾追加 Y 会得到另一种顺序。

因此，可以重新排序并从已知状态重放，也可以采用能正确处理插入的增量结构。建立检查点后，还要明确它覆盖哪些更新；迟到更新若属于更早位置，需要保留足够的信息处理，才能继续满足合并规则。

重放使用已经记录的内容和决策。例如消息带着创建时的 ID、正文和排序标签，所有副本按同样规则处理它们。重放期间若重新生成随机标识、当前时间或其他不同值，也可能让结果变化。

时间排序

时间戳是附在事件上的一个数值，用于记录事件的时间信息。排序键是程序拿来比较先后的字段组合。字典序按各项依次比较：〈10,R2〉 排在 〈11,R1〉 前面，因为第一项 10 更小；〈10,R1〉 与 〈10,R2〉 第一项相同，再比较节点编号。

最直接的排序键是本机时间，例如 getTimeOfDay()。但不同更新可能取得相同读数。

思考题：两个更新的 getTimeOfDay() 都是 1755419200.123，仅用 T 排序能确定二者先后吗？怎样增加字段，避免两边继续保留不同的并列顺序？

解答：

两个相同的 T 留下并列，仅按 T 排序时，双方可能保留各自原有的 X、Y 或 Y、X。可以按 〈T,node ID,sequence〉 依次比较：时间相同后比节点编号，再用节点内序号区分同节点的更新。若 R1 编号小于 R2，两条给定记录都排为 X、Y。

图中 X、Y 都带 1755419200.123。副本 1 原先按 X、Y 保存，副本 2 原先按 Y、X 保存。仅按这个时间值排序时，两个相等键可以继续保留不同的原始顺序。

全序要求任意两个不同更新都能确定谁排在前面。可以用复合键，并按字典序比较：

K(e)=(T(e),node_id(e),sequence(e))K(e)=(T(e),\mathrm{node\_id}(e),\mathrm{sequence}(e)) K(e)=(T(e),node_id(e),sequence(e))

先比较时间，再比较节点编号，仍相同时比较节点内序号。节点内序号用于区分同一设备在同一时刻产生的多个更新。

本地物理时钟的分辨率有限，连续两次读取可以得到同一数值，校时也可能改变读数。递增序号帮助识别不同更新；重启后的运行代次与已有记录还需要按身份规则管理，避免把新更新与旧更新混在一起。

图中的两个更新分别来自 R1、R2，用 〈T,node ID〉 已能区分。假设 R1 的编号较小，X 就排在 Y 前面，两台设备都得到 X、Y。

也可以采用 〈node ID,T,sequence〉，先按节点编号排序。这同样能给出确定顺序，但会把同一节点的更新排在一起。排序规则还需要符合消息之间的依赖关系。

时钟偏差

各设备的时钟独立运行。硬件通过振荡器的周期计数估计时间，频率和温度等因素会带来偏差；校时也可能调整读数。

操作系统把选定计时源的计数按换算参数转换为时间单位，并可以通过 NTP 等协议校准。不同机器仍有残余偏差，排序时需要考虑这些误差及消息依赖。Linux 的计时源与换算机制见内核时间文档。

思考题：按 〈T,node ID〉 排序后，各副本能否仍得到 [ref(file_a),file_a]？给节点加唯一编号能解决哪些问题，文件与引用的依赖又需要怎样保留？

解答：

仍可能出现该结果。图中 file_a 的时间为 1755419200.123，引用在另一节点上取得更小的 1755419199.987，按时间优先就把引用排在前面。节点编号解决时间并列，依赖需要逻辑时钟等关系记录；传播途中还要在目标消息未到齐时暂存引用，待依赖可见后显示。

图中 R1 创建 file_a，时间为 1755419200.123。文件同步到 R2 后，R2 已经看到了它，再创建引用，自己的时间却为 1755419199.987。

按 〈T,node ID〉 排序时，引用的时间数值更小，结果成了 [ref,file_a]。两台机器可以得到完全相同的列表，但这个顺序把引用放到了目标文件前面。

文件创建、收到文件、创建引用之间存在依赖。排序键需要记录这种关系，设备的独立时钟读数只提供本机的时间信息。

因果关系

事件是系统中一次需要记录的动作，例如创建文件、接收消息、创建引用。某个动作读取了先前收到的信息，后续动作就可能依赖这份信息。沿进程执行顺序和消息箭头连出一条向前的路径，就能确定一组这样的先后关系。

思考题：一个节点收到文件后再创建引用，消息传递怎样建立文件到引用的先后关系？能否利用这些依赖来调整各节点的事件时间戳？

解答：

创建文件先于发送它，发送先于对方接收，接收又先于创建引用，所以形成文件到引用的因果路径。接收带 T′ 的消息时，用 T=max(T,T′)+1 推进本地时钟，创建引用再递增。文件为 10、接收后为 11、引用为 12，就保留了这条先后关系。

用 X→YX\to YX→Y 表示 X 先发生，并且 Y 可以受到 X 的影响。这种关系称为 happens-before，由三条规则定义：

  1. 同一进程中，按程序顺序先执行 X、再执行 Y，则 X→YX\to YX→Y。
  2. 一条消息的发送先于该消息的接收。
  3. 若 X→ZX\to ZX→Z 且 Z→YZ\to YZ→Y，则 X→YX\to YX→Y。

图中 X 是 R1 创建文件。文件消息到达 R2 后，R2 创建引用 Z，随后发出“看完了”Y。消息传递给出 X→ZX\to ZX→Z，R2 的本地顺序给出 Z→YZ\to YZ→Y，合起来得到 X→YX\to YX→Y。

因此，展示引用前应先有文件，展示“看完了”前应先有引用。若两个事件之间找不到这样的程序顺序或消息依赖，它们在这个关系中称为并发事件。并发描述的是缺少因果先后关系，两事件在物理时间上也可能隔着一段时间。

逻辑时钟

逻辑时钟保存一个整数计数器。每产生一个需要记录的事件，计数就向前推进。max(a,b) 表示取 a、b 中较大的数。接收消息时先比较两边计数，再加一，能让当前事件的编号同时大于本地已有编号和消息携带的编号。公式里的 ⇒ 读作“推出”，表示箭头左边条件成立时，右边条件也成立。

Lamport 时钟为事件分配递增的整数时间戳。它的目标是：

X→Y⟹L(X)<L(Y)X\to Y\quad\Longrightarrow\quad L(X)<L(Y) X→Y⟹L(X)<L(Y)

每个进程保存计数器 T。创建一个事件并将它发出可以合为一次逻辑事件；后续重传继续携带原事件的时间戳。按事件递增的常见写法如下：

事件 时钟更新
本地事件 T = T + 1，把新 T 作为事件时间戳
创建并发送事件 推进 T，把新时间戳附在事件消息中
接收带 T′T'T′ 的消息 T = max(T,T') + 1

同一进程的每次事件获得更大的时间戳。收到消息后，当前时钟也大于发送方的时间戳，所以后续事件保留消息带来的先后关系。

取最大值保留了两边已经知道的进度。例如当前 T 为 20，收到时间戳 10，接收事件取得 21；收到时间戳 30，则取得 31。这样本地后续事件继续前进，同时也排在收到消息的发送事件之后。

计数器需要满足两项要求：一个进程的后续事件取得更大的计数；接收消息的事件取得比发送事件更大的计数。上表的取最大值、再加一同时满足这两项要求。

沿图中的消息传递过程计算：

  1. R1 创建文件，时间戳为 〈10,R1〉。
  2. R2 的当前计数为 9，收到文件后推进为 max(9,10)+1=11。
  3. R2 创建引用，再推进为 12，引用时间戳为 〈12,R2〉。
  4. 两台设备按时间戳排序，文件 10 排在引用 12 前面。

逻辑计数器按事件推进，也可以在本地计时推进的基础上做消息调整；需要保持上述时钟条件。节点编号和节点内序号可以补齐排序键，区分并发事件产生的相同计数。

排序记录用于重建列表。要在传播途中也满足因果可见性，接收方还需要检查依赖：引用先到、文件未到时，先暂存引用，等文件内容到齐后再展示。

文件更新原来的标签为 〈10,R1〉，收到它的事件令 R2 当前时钟变为 11；保存文件更新时仍沿用原标签。R2 创建引用取得 12，这条新更新才使用 〈12,R2〉。同一更新在各副本中的身份与标签因此保持一致。

思考题：引用消息带有时间戳 12，依赖的文件带有时间戳 10，但引用先到达。仅知道 10 比 12 小，能否立即显示完整引用？还缺什么？

解答：

时间戳帮助规定顺序，文件内容仍需要实际到达。接收方可以按目标消息 ID 检查依赖，缺少文件时暂存引用或显示待获取状态，再请求或等待文件。

若要持续交付一个确定的全序，还需要判断是否有更早更新尚在路上。日志排序与完整更新集合可以用于最终重建，传播中的交付时机则由额外同步、确认与依赖规则决定。

时钟判断

逻辑时间 3、7 是按事件推进的编号。一个节点已经处理较多事件，可能较早取得编号 7；另一个节点后来才处理到编号 3。判断实际发生时间还需要发送和接收记录，例如明确知道一个节点先收到某条消息，再创建下一事件，就建立了实际的先后路径。

判断题：节点 1 的事件时间戳为 3，节点 2 的事件时间戳为 7。图中的 TS 表示事件时间戳，记为 L(e)L(e)L(e)。判断下面三项，并说明理由。

  1. 仅凭 L(e1)<L(e2)L(e_1)<L(e_2)L(e1​)<L(e2​)，可以确定事件 1 在实际时间上更早。
  2. 仅凭这两个时间戳，可以确定两个节点一定交换过消息。
  3. 节点 2 在事件 2 之前，已经收到事件 1 的同步消息，因此事件 1 在实际时间上更早。

解答：

  1. 错。逻辑计数大小不足以证明实际发生时间；节点 2 可以先发生编号 7 的事件，节点 1 后来才发生编号 3 的事件。
  2. 错。两个节点也可以独立执行各自事件，分别取得 3 和 7，时间戳本身没有提供通信记录。
  3. 对。题目补充了事件 1 的消息在事件 2 前已到达，发送、接收、后续事件形成因果路径，所以事件 1 实际更早。

L(X)<L(Y)L(X)<L(Y)L(X)<L(Y) 时，可能有 X→YX\to YX→Y，也可能是两个并发事件恰好获得了大小不同的计数。要判断哪种情况，需要知道消息依赖，或使用记录更多信息的时钟。

练习：两个互不通信的节点分别产生事件 e1、e2，逻辑时间为 3、7。e1 在实际时间上更早、更晚或与 e2 同时发生，三种情况能否出现？

解答：

三种都可以出现。两个节点各自推进计数，较小的计数既可以较早产生，也可以较晚产生，还可以恰好在同一个参考时刻产生。数值 3、7 只说明这两个事件的逻辑标签。

如果另外知道 e2 → e1，时钟条件就要求 L(e2)<L(e1)，与题中数值不符；如果知道 e1 → e2，则符合 3 小于 7。通信记录提供的关系与标签大小要分别检查。

接龙名次

名次是列表中的位置。每个副本都有 17 项时，本地追加自然取得第 18 位；其他设备也可以基于自己的 17 项做同样计算。应用可以先保存报名请求，待系统确定序号后再公布名次，也可以把并发情况交给用户处理。

聊天列表最终重新排列，用户通常还能继续阅读。接龙若规定“第一个报名的人获得奖金”，名次变化就会影响实际结果。

思考题：两份接龙到第 17 位相同，两个人都在本地追加自己，会不会同时显示为第 18 位？若按名次发奖，应选择临时排序、报告冲突还是等待确认？

解答：

会。两边都在各自的 17 项后追加自己，本地位置都为 18；合并确定顺序后，它们分别为 18、19。临时位置可以用于显示待确认状态，奖金应按明确的最终确认规则结算。可以等待系统给出序号，也可以识别并发后报告冲突，让业务或用户重新处理。

两人都读取到前 17 位，各自在自己的副本上报名，于是都显示为第 18 位。稍后同步可以把两条报名排成第 18、19 位，但其中一人的已有名次会改变。

应用需要明确怎样处理同时报名：可以报告冲突，让用户重新提交；也可以等待系统确认唯一的报名顺序，再公布名次。

给并发事件加上 〈Lamport 时间,node ID〉 能决定展示顺序。奖金规则若按这个顺序执行，结果可能由节点编号等排序规则决定。若需要识别“这两次报名缺少因果先后”，时间戳就需要保留不可比较的情况。

全序和偏序

例如三个更新 A、B、C，确定 A在B前，B在C前 后，就得到 A、B、C 的全序。若只知道 A 在 C 前、B 在 C 前，A 和 B 的关系仍可保留为不可比较。这组关系构成偏序；应用可以共同确认两者都应在 C 前，再单独处理 A、B 之间的顺序。

思考题：两个报名缺少因果先后关系时，强行规定一个全序与保留不可比较的关系，分别向应用提供什么信息？

解答：

全序给所有不同事件一个确定位置，能直接决定列表排列，但独立报名的顺序可能由节点编号等规则决定。偏序保留已经知道的因果先后，并将缺少关系的事件标为不可比较。应用于是知道这里存在并发，可按业务规则合并、重试或仲裁。

全序可以对任意两个不同元素确定先后。〈逻辑时间,node ID,sequence〉 就能让所有更新排成一条确定序列。

因果关系是偏序。对两个事件，允许三种结果：

  • X→YX\to YX→Y：X 先于 Y。
  • Y→XY\to XY→X：Y 先于 X。
  • X∥YX\parallel YX∥Y：二者并发，缺少因果先后关系。

应用可以利用第三种结果报告冲突。先完整记录偏序，再由业务决定怎样处理并发更新，能保留更多信息。

向量时钟

向量在这里是一排整数，长度等于参与计数的节点数量。每个事件保留创建时的向量，表示当时已经知道的各节点事件进度。例如 [3,1] 记录已知 R1 到第 3 个事件、R2 到第 1 个事件。比较两个向量时，需要逐项检查它们记录的进度。同一更新在不同副本上的拷贝沿用相同 ID 和创建向量，下面的先后比较针对不同事件。

向量时钟为每个节点保留一个分量。两个节点时，第一项记录已知的 R1 事件计数，第二项记录已知的 R2 事件计数。R1、R2 都从 [0,0] 开始；R1 的事件推进第一项，R2 的事件推进第二项。收到其他节点的消息后，也会更新相应分量。

R1 创建 X，得到 [1,0]；R2 独立创建 Y，得到 [0,1]。第一项中 X 较大，第二项中 Y 较大，所以两向量不可比较。它们分别记录了自己看到的事件，没有记录对方的新事件。

公式中的 V(X)kV(X)_kV(X)k​ 表示事件 X 的向量在第 k 项的数值；∀k\forall k∀k 表示每一项都满足条件；∃j\exists j∃j 表示至少存在一项；∧\land∧ 表示两个条件同时成立。向量先后关系写为：

V(X)<V(Y)⟺(∀k, V(X)k≤V(Y)k)∧(∃j, V(X)j<V(Y)j)V(X)<V(Y)\quad\Longleftrightarrow\quad \left(\forall k,\ V(X)_k\leq V(Y)_k\right) \land \left(\exists j,\ V(X)_j<V(Y)_j\right)V(X)<V(Y)⟺(∀k, V(X)k​≤V(Y)k​)∧(∃j, V(X)j​<V(Y)j​)

也就是 X 的每个分量都小于等于 Y，且至少一项更小。若两个方向都无法满足这个条件，两个事件并发。

向量更新

下面按“创建更新”“接收更新”计数。创建更新时，推进自己的分量，将新向量保存在更新记录里；同步发送这条记录时，沿用它的向量。接收方逐项合并这条记录带来的进度，再为自己的接收事件推进一项。记录创建时的向量与当前节点继续推进的向量分别保存。

接收方在自己的第 i 个分量上计数，逐项合并和推进可以写为：

Vi[k]←max⁡(Vi[k],Vmsg[k])对每个 kV_i[k]\leftarrow\max(V_i[k],V_{\mathrm{msg}}[k])\quad\text{对每个 }k Vi​[k]←max(Vi​[k],Vmsg​[k])对每个 k

Vi[i]←Vi[i]+1V_i[i]\leftarrow V_i[i]+1 Vi​[i]←Vi​[i]+1

逐项最大值把收到消息所包含的历史合进来；增加自己的分量记录本次接收事件。

例题：R1、R2 从 [0,0] 开始，R1 创建 X 得到 [1,0]，R2 创建 Y 得到 [0,1]。R1 随后收到 Y，再创建 ref(Y)。

  1. X 与 Y 是否有因果先后？
  2. R1 收到 Y 后，逐项最大值和计入接收事件后的向量各是多少？
  3. ref(Y) 的向量是多少，怎样判断 Y→ref(Y)Y\to ref(Y)Y→ref(Y)？

解答：

  1. X 的 [1,0] 和 Y 的 [0,1] 各有一项较大，互不覆盖，因此 X、Y 并发。
  2. R1 合并时逐项取最大值，得到 [1,1]；再把自己的第一项加一，计入接收事件，得到 [2,1]。
  3. 创建 ref(Y) 再推进第一项，得到 [3,1]。Y 的 [0,1] 每项都小于等于 [3,1]，且第一项严格更小，因此 Y→ref(Y)Y\to ref(Y)Y→ref(Y)。

图中的计算为：

  1. R1 创建 X 后保存 [1,0]。
  2. R2 创建 Y 后保存 [0,1]，发送给 R1。
  3. R1 逐项取最大值，得到 [1,1]。
  4. 接收事件推进 R1 的第一项，得到 [2,1]。
  5. R1 创建 ref(Y)，再推进第一项，得到 [3,1]。

比较 Y 的 [0,1] 和引用的 [3,1]，满足向量先后条件，因此 Y→ref(Y)Y\to ref(Y)Y→ref(Y)。X 与 Y 原来并发的关系也保留在它们各自的时间戳中。

向量长度随节点数增加，系统需要保存和传递更多信息。它适合识别更新之间的依赖和冲突，冲突发生后仍由应用选择合并、重试或其他处理规则。

串行观察

逻辑对象指对外提供的一份数据及其操作规则。例如三个节点各保存一个聊天列表，但所有读取都能解释为对同一份列表进行操作，应用就可以按这份列表的规则判断结果。判断时要把已经返回的操作和结果列出来，寻找一个共同顺序来解释它们。

接龙还有另一种处理办法：先由系统确认操作顺序，用户读取确认后的名次。

思考题：多个物理副本对外表现为一个逻辑对象，需要让哪些操作和结果对应到共同的串行执行？仅有共同顺序时，还要说明哪些时间约束？

解答：

需要找到一个共同的合法串行顺序，解释所有调用与返回结果。例如列表追加把项放到末尾，读取返回该位置之前加入的内容。还要声明保留哪些时间关系：顺序一致性保留每个进程的程序顺序，线性一致性还保留完成到后续发起的实时关系，严格顺序则要求全局实际发起顺序。

底层仍可以有多个物理副本。对外提供的结果可以解释为对一个逻辑对象依次执行操作：先写一次，再写一次，最后读取。

每种数据结构都有自己的操作规则。列表追加应把新项放在末尾，寄存器读取应返回对应顺序中最近一次写入的值。判断一致性时，需要找出一个符合这些规则的共同顺序，再检查这个顺序满足哪些时间约束。

严格顺序

一次调用有几个不同的时刻：客户端发起请求，服务器收到请求，服务器执行，客户端收到回复。发起时间位于客户端，请求到达时间位于服务器。网络传输耗时不同，会让这些时刻之间隔着不同长度的等待。

严格一致性要求按全局实际发起时间安排操作。接龙中，发起时间可以理解为用户按下按钮的时刻。若 Alice 更早按下，理想顺序就把 Alice 放在 Bob 前面。

即使使用单台服务器，请求到达顺序也可能变化：Alice 先发 A，网络延迟较大；Bob 后发 B，B 却先到服务器。

思考题：Alice 发起 A 的实际时间更早，Bob 的 B 却先到服务器。怎样知道应先处理 A？即使携带精确时间戳，B 的时间为 7、A 为 5，服务器应等待多久、等待多少条更早请求？

解答：

客户端各自的时间存在偏差时，时间戳不足以可靠恢复全局发起顺序。即使时钟精确，B=7 先到后仍可能有 A=5 在路上。在消息延迟无已知上界、消息可能丢失的模型中，服务器无法确定等待上限或更早请求数量；额外的同步与延迟条件需要另行规定。

给请求附上本机时间会遇到时钟偏差。假设时钟已精确同步，服务器收到时间戳 7 的 B 后，还要确认是否有更早的请求正在路上。图中 A 的时间戳为 5，服务器等待它才能按 5、7 执行。

在消息延迟没有已知上界、消息还可能丢失的环境中，服务器难以确定要等待多久，以及是否还有更早请求。实际系统通常通过请求完成和后续发起的关系来规定顺序。

线性一致性

操作的调用区间从发起开始，到返回结束。例如 Write(x,2) 在 10:00:00 发起，10:00:01 返回，这一秒是它的区间。Read(x) 在 10:00:02 发起时，写入已经返回；若其间没有其他写入，读取需要得到 2。两次调用的区间重叠时，系统则依据对象规则确定它们的生效顺序。

线性一致性，英文为 linearizability，要求所有操作可解释为一个合法串行顺序，并保留实时的先后关系：

return⁡(A)<invoke⁡(B)⟹A 在串行顺序中先于 B\operatorname{return}(A)<\operatorname{invoke}(B) \quad\Longrightarrow\quad A\text{ 在串行顺序中先于 }Breturn(A)<invoke(B)⟹A 在串行顺序中先于 B

invoke 是发起调用，return 是返回结果。如果 A 已返回，随后才发起 B，B 的结果就需要符合 A 已生效后的对象状态。

另一种等价理解是：每次操作在发起和返回之间存在一个生效时刻，称为线性化点。把操作按这些点排列，可以解释所有读取结果。

思考题：集中服务器实际按什么顺序处理重叠请求？B 已完成后才发起的读取必须包含什么？为什么完成到后续发起的关系可以作为线性一致性的判断条件？

解答：

图中 B 先到服务器，示例处理顺序为 B、A，列表变为 [B,A]。B 已完成后才发起的读必须保留 B 的加入；图中 A 也已完成，所以返回 [B,A]。完成说明操作已经生效，后来发起的调用区间在它之后，合法线性化顺序就必须保留这项实时关系。

图中 A、B 的调用区间重叠，服务器先收到 B，依次处理 B、A，得到 [B,A]。读取在 B 完成后发起，需要看到 B；图中读取也发生在 A 完成后，因此返回 [B,A]。

两次调用重叠时，线性一致性允许按对象规则选择其中一个先执行。两次调用分开时，已经完成的操作排在后来发起的操作之前。报名应用可以按系统确认的序号发奖，并在确认前显示“处理中”。线性一致性原论文

主副本

primary 保存本对象的排序职责，backup 保存相应副本。调用方可以向不同入口发请求，入口将请求送到 primary，由它分配位置并等待复制完成。已确认的写入记录用于恢复；更换 primary 时，新节点需要取得这些记录，并确保之后的更新继续按共同顺序安排。

一种实现线性一致性的方法，是对每个对象指定一个 primary，统一安排读写顺序，其他副本按这个顺序执行。

思考题：各副本先本地写入并立即返回，再于同步时重新排列，能否让所有已完成操作保留线性一致性的顺序？primary-backup 方法怎样安排读写与确认？

解答：

这种做法一般无法保证线性一致性：一个节点已确认的写入，另一节点还可能读旧值，事后重排也改变不了已返回的结果。primary-backup 对每个对象统一安排操作，给写入排序，备份按序应用并确认，满足条件后才返回完成；读取按相应顺序取得已确认状态。

图中 P0 是 primary，P1 是 backup。初始 x 为旧值，写入 x=1 时：

  1. 请求到达 P0，由 P0 安排位置。
  2. P0 把更新转发给 P1。
  3. P1 写入本地副本并返回 ACK。
  4. P0 按协议完成自己的写入，确认这次操作完成。
  5. P0 向调用方返回 Done。

发到 P1 的 Write(x,2) 也被转交 P0。读取同样经过统一安排。在这个逐次处理请求的实现中，后续读取在相应写入确认后返回，从而看到正确的已完成状态。

统一排序可以按对象分工，不同对象由不同 primary 负责。任期标识一段主节点授权，选出新主后需要更新相应任期。故障恢复要取得已确认的操作记录，再安排后续读写；旧任期的节点恢复连接后也按授权规则处理请求。

写入序号

序号表示第几条更新，数据值表示写了什么。例如 〈seq=1,value=1〉 和 〈seq=2,value=2〉 分别是第一、第二次写入。接收方维护 next_seq：期待 1 时先执行 1，再把期待值改为 2。即使值恰好等于序号，这两个字段也各自承担不同职责。

primary 发出两次更新，也要让所有副本按它规定的顺序应用。

思考题：primary 安排先写 1、再写 2，backup 却先收到写 2。仅按到达顺序执行会得到什么结果？附上 seq=1、seq=2 后，backup 应怎样等待与应用？

解答：

按到达顺序执行时，primary 先写 1 再写 2，最终为 2；backup 先写 2 再写 1，最终为 1。附上序号后，backup 收到 seq=2 时先缓冲并等待 seq=1，执行 1 后再执行 2，两边都得到 2。缺失更新按协议补传，重复更新按已执行记录处理。

P0 先安排 Write(x,1)，再安排 Write(x,2)。P1 若先收到第二条消息，并直接执行，就会先写 2、再写 1。最终 P0 为 2，P1 为 1。

为每个更新分配递增序号，可以明确记录 primary 的顺序。

P0 为两条更新分配 seq=1、seq=2。P1 收到 2 时，先放进等待区；收到并执行 1 后，再执行 2，最终两边都是 2。

可以用 next_seq 记录下一条应执行的序号。序号较大时等待前面的更新，重复消息按序号和请求标识检查处理记录，缺失消息通过重传补齐。顺序由序号保存，网络到达时间只影响等待多久。

复制成本

这套 primary-backup 实现增加了转发和确认。写入需要经过 primary，并等待 backup 返回；读取也要进入统一安排，primary 的处理量和网络往返会影响性能。

思考题：要求 primary 排序、全部 backup 确认时，多出哪些等待？primary 失效或某个 backup 失联，分别会影响哪些操作？

解答：

写入多出转发与等待备份确认的时间，要求全部确认时由最慢备份影响完成时间。primary 失效会使统一读写入口暂停，需要确定新主并恢复已确认记录；backup 失联会阻塞要求全确认的写入。若读也排在这个未完成写入之后，它会被连带等待。

primary 失效后，其他节点需要确认新的负责者；若写入要求全部 backup 确认，一个 backup 失联也会阻塞写入。这套简化实现需要等待故障节点恢复，或通过额外协议重新确定参与写入的节点。

要在部分节点失效后继续工作，需要选出负责排序的节点，恢复已确认的记录，并重新确定哪些副本能够参加确认。参与节点数和确认条件决定了需要交换多少消息、等待多少回复。

顺序一致性

程序顺序是单个进程自己依次执行操作的顺序。例如进程 A 先写 2、再读，解释结果的共同串行顺序也要把它的写放在它的读前面。不同进程之间的操作，要结合模型规定的关系安排。下面的例子让两次读取由不同进程执行，以检查它们可被排列成怎样的顺序。

让读取直接使用本地副本，可以减少一次向 primary 请求数据的等待。下面检查这种读法会返回什么结果。

思考题：初始 x=1，写请求与两次读取分别由不同进程发起。P1 收到写 2 并读到 2，这次读完成后，P0 的读者才开始读取，却仍返回 1。

  1. 这段历史满足线性一致性吗？
  2. 怎样排列这三次操作，可以解释为合法串行结果？
  3. 解释为顺序一致性时，还要检查每个进程的什么条件？

解答：

  1. 违反线性一致性。先一次读取已经得到 2，随后发起的读取又得到 1，中间没有其他写入，无法保留完成到后续发起的实时关系。
  2. 可按 P0读1、写2、P1读2 排列，解释为合法的单对象串行结果。
  3. 顺序一致性还要求保留每个进程自己的完整程序顺序。题中三次操作由不同进程发起，给出的排列没有颠倒任何进程内部顺序；若同一进程先写后读，还要保留它的写先于读。

初始 x=1。P0 发出 Write(x,2)，P1 先执行更新，返回给 P0 的 ACK 还在路上。P1 的读者读到 2；这个读取完成后，P0 上的另一个读者发起读取，本地仍为 1，返回 1。

图中的 P0、P1 表示所在节点，每个节点可以运行多个调用进程。下面将写请求和两次读取分别看作三个进程的操作，检查它们能否形成共同的串行顺序。

若这段历史满足线性一致性，读到 2 说明写 2 已经生效。后一次读取又发生在第一次读取完成后，中间没有其他写入，因此也应返回 2。图中的实际结果违反了这项实时顺序要求。

顺序一致性要求存在共同的合法串行顺序，并保留每个进程自己的程序顺序。两个读取属于不同进程时，可以尝试以下顺序：

串行位置 操作
1 P0 的读者读取，返回 1
2 写入 x=2
3 P1 的读者读取，返回 2

这个顺序能解释两次读取的数值。它把两个不同进程的读取排列为旧值在前、新值在后。线性一致性还要保留实际的“第一次读取完成、第二次读取发起”关系，所以对同一段历史提出了更多要求。

实现顺序一致性时，还需要检查每个进程的完整调用序列。例如，一个进程先写入、再读取，或连续执行两次读取，都要在共同串行顺序中保留它们的程序顺序。系统应按这个条件安排会话与副本读取。

模型选择

思考题：最终一致性适合每一种应用吗？普通聊天与按名次发奖的接龙，需要怎样规定临时结果、冲突和最终确认？

解答：

最终一致性适合可以接受临时缺少消息、之后同步合并的用法。聊天可以先显示本地记录并标记发送状态，引用还需等待目标消息可见。按名次发奖的接龙应先确认名次，或检测并处理并发报名，再按奖项规则结算；直接把未确认的本地位置作为最终结果，会使名次在同步后变化。

图中的雷达图用于概括设计倾向，轴上没有测量单位和实验数值。最终一致性的本地操作减少了协调等待，应用要处理延迟可见、顺序调整和冲突。线性一致性让程序按对象的串行规则判断结果，实现则需要安排确认、排序和故障恢复。

聊天记录可以先显示本地消息，后台持续同步，并保留引用依赖。按名次发奖的接龙需要明确确认顺序，或在并发时报告冲突。存储文件、修改目录、递增计数等操作，也要结合各自的业务规则选择保证。

分析一个并发系统时，可以依次检查四件事：数据状态是什么，操作怎样修改或读取状态，事件之间有哪些依赖，以及读取结果要保留哪种先后关系。时钟帮助记录事件关系，读写和同步协议负责实现一致性要求。
