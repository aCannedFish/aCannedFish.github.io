计算机系统工程-05：一致性模型与逻辑时钟

发表于2026-10-08|更新于2026-11-02|Note计算机系统工程
|浏览量:

理解状态

并发读写

两个用户同时修改数据，系统需要规定每次读取能看到什么。有多个副本时，更新还要经过网络，消息迟到、节点失效和缓存都会改变观察结果。

聊天中，Alice 先发文件再发引用，Bob 却可能先收到引用。接龙中，两个人各看到 17 项，都把自己放在第 18 位。判断这些情况是否错误，要先写清操作与业务要求，再选择一致性模型。

读写基础

状态是程序当前保存的数据，例如 [你好] 是一条消息的列表。Update 改变状态，Read 读取状态。状态机用“原状态加一次操作得到新状态”描述执行：先追加 X 再追加 Y，列表成为 [X,Y]。

副本是同一数据在另一位置的拷贝，缓存用于加快部分访问，二者都要处理更新。客户端发请求，服务器执行并回复；一个进程中可以运行多条线程，一台机器也能运行多个进程。

串行表示一个操作结束后才执行下一个，并发表示执行区间重叠。断电后保留的内容还需进入稳定存储。因此，图中的“写入完成”应按该例的确认条件理解。

图示读法

每条时间线表示一个参与者，沿 time 箭头向前看。请求、回复和同步消息的箭头从发送指向接收，两端之间有传输时间。ACK 是确认，Done 表示调用按协议完成，RTT 表示一次网络往返。

读图时先记下各节点初始值，再按箭头到达顺序更新各自状态。遇到 Read，就检查该节点此刻能看到哪些更新。不要因为另一条线上已经写完，就直接把它当成所有节点都已经收到。

文件读取

NFS 的 close-to-open 在关闭写回和重新打开验证时协调缓存，长期同时打开的读者可能仍持有旧内容。GFS 即使统一成功写入的次序，一次失败写入也可能只改变部分副本。

图中初始都是 A，写 B 只在节点 1、2 完成，节点 3 仍为 A。两个客户端分别读取不同副本，便可能先读 B、后读 A。系统还需要规定哪些副本可读、失败修改是否可见，以及何时等待或修复。排序规则与读取可见性需要配合。

GFS 已统一写入顺序，若某次写入只在部分副本完成并报告失败，两个客户端随后从不同副本读取，会得到什么？写入顺序与读取可见性各需要什么规则？

解答：

图中初始都为 A，写 B 只在节点 1、2 完成，节点 3 保留 A。客户端 1 可读到 B，随后客户端 2 从节点 3 读到 A。统一写入顺序规定副本怎样执行修改；读取规则还要明确失败或未确认修改是否可见、哪些副本可读。若要求统一的已确认读取状态，需要额外确认、验证或修复等待。

聊天记录

把聊天表示为有序列表，文字、文件和引用都是列表项。引用保存目标消息 ID，只有取得目标，才能显示相应内容。

图中 Alice 先产生 Chap_01.pdf，再产生“是这个文件吗”的引用。文件传输较慢，引用先到 Bob，便暂时找不到目标。创建顺序、网络到达顺序和界面显示顺序是三件事，应用可以按依赖暂存引用，等目标可见后再显示。

截图本身也可能受目标删除、权限或附件失败影响。这里固定“文件先创建、引用先到达”的执行，用它分析消息依赖。

Alice 先发文件，再发引用它的消息，Bob 却先看到引用并提示“引用内容不存在”。哪些发送、同步和显示顺序可能产生这个结果？

解答：

Alice 本地产生文件，再产生引用，顺序为 file、ref。文件同步先启动，但传输较慢，引用先到服务器和 Bob；若按到达顺序立即显示，就先出现 ref，此时找不到目标。文件后来到达才补齐内容。要保留引用依赖，可记录目标消息 ID，并等目标可见后再展示引用。

复制历史

集中保存

先用一台服务器保存完整聊天列表，所有追加和读取都通过 RPC。服务器按确定顺序处理列表，更新完成后回复 ACK，读取返回对应位置的列表内容。

如果同一用户等上次 ACK 再发下一条，文件必定先加入，引用才会发送。其他用户重叠的请求则按服务器安排执行。服务端内部多线程也要保护列表操作。

这种实现容易理解，但每次访问要等待网络，完整历史越长传输越多，离线设备无法取得未保留的历史，服务器失效也会阻断访问。图中历史量增加四倍，在相同带宽的简化条件下，读取时间从 t 增到约 4t。分页、增量读取和本地副本可以减少这部分成本。

由一台服务器统一追加消息，并让用户等待上次 ACK 后再发下一次请求，是否能保留这个用户的操作顺序？两项条件分别起什么作用？

解答：

在给定条件下，可以保留同一用户的顺序。服务器把上一条更新加入列表后才返回 ACK，用户收到它才发下一条，所以文件已加入后才可能发出引用。统一安排追加让读取取得同一份列表。重叠的其他用户请求则按服务器规定的合法顺序处理。

情况 对用户的影响
每次更新等待服务器回复 发消息要等待一次网络往返和服务器处理
每次读取返回全部历史 历史越长，需要传输的数据越多
设备离线 获取历史依赖服务器，本地也没有自己发过的完整记录
服务器失效 所有用户的远端更新和读取都要等待恢复

本地副本

设备先保存新消息，再向服务器和其他设备传播，可以立即显示本地内容，离线也能查看已有历史。图中服务器失效后，一个设备加入“谢谢”，另一个仍只能读取原有“你好”。

界面需要分别记录本地保存、已发送和对方收到。SQLite 或本地日志可以一起保存消息 ID、内容、发送状态与待同步记录，进程退出后再继续发送。显示成功与远端可靠保存不是同一阶段。

更新确认

一次写入在哪个时刻返回，由确认条件决定。要求全部副本 ACK，就要等待最慢副本，失联者可能使写入超时；要求指定部分确认，则可在它们完成后返回，其他副本以后补齐。

两张图分别展示这两种等待范围。协议还必须说明成功代表哪些节点已保存、哪些读取可能仍返回旧值，以及怎样恢复缺少的更新。只给出确认数量，不能自动确定全部读取语义。

只更新本地副本后，各设备会处于什么状态？一次写入要等多少个副本确认才返回？全部确认和部分确认分别影响哪些等待与故障情况？

解答：

只改本地时，一个副本已有新内容，其他副本仍保留旧内容。确认数量由协议规定：全部确认要等最慢的一方，失联节点会阻塞或使请求超时；部分确认在指定参与者完成后返回，其他节点后台补齐。成功回复所表示的保存和可见性程度，也必须与这些确认条件一起定义。

周期同步

同步让设备取得缺少的记录。可以保存上次同步位置或已知 ID，只交换增量，再去重合并。定时检查、新消息通知或网络恢复都可以触发同步。

图中离线设备只有“你好”，恢复后取得“谢谢”“再见”，列表才完整。每 10 s 检查是一个触发周期示例，实际可见时间还包括联网、传输与处理。Apple Push Notification 等推送可以提醒设备获取内容，消息和附件仍需另行传输。

一次同步可批量取得多条更新。离线太久时，需要服务器保留的日志或有效快照作为补齐来源。

读本地副本可以立即取得哪些消息？其他设备刚产生的更新何时能读到？周期同步与推送通知怎样补齐缺少的内容？

解答：

本地读取返回该设备已经收到的记录。新消息在传播完成前可能尚不可见，联网后通过同步补齐。周期检查定时交换缺少的更新，推送通知提醒设备有新内容并触发获取。图中的 10 s 是一次同步触发示例，实际可见时间还包含网络恢复、传输和处理等待。

到达顺序

若每次收到消息就追加到尾部，同一组消息可以形成不同列表。Alice 本地先有 file 再有 ref，服务器却先收到 ref，后来追加 file，就得到 [ref,file]。

最终都收到并不等于排列相同。系统还要保存更新身份、依赖与排序依据，让各节点按共同规则生成结果。

合并更新

合并需要保留不同设备的新记录，同时识别同一记录的重传。例如 R1:#8 重传三次仍只加入一次，内容相同但 ID 为 R1:#9 的消息则是另一条记录。

图中两个副本分别在 [你好,谢谢] 后加入“好的”和“收到”。各自先保留本地消息，再追加远端消息，会得到相反次序。要最终统一，一方已经显示的位置就可能调整。普通聊天可接受待确认和重排，按名次发奖的业务则需要明确何时确认名次。

副本 1 先显示“好的”，副本 3 先显示“收到”。合并后若统一排列，能同时保留两边已经显示的顺序吗？应用要怎样处理消息移动？

解答：

统一后选“收到、好的”时，副本 1 原先显示的“好的”会向后移；选“好的、收到”时，副本 3 的显示会调整。因此，两边各自优先的临时观察需要由共同规则重新解释。聊天可标记待同步并合并更新；涉及业务名次时，应等确认或明确处理冲突。

约定结果

一致性模型

一致性模型用允许的操作顺序和返回值描述服务。例如 x 从 1 改为 2，写入确认后再读能否返回 1，应由接口明确，应用才能决定下一步是否需要等待。

模型适用于副本、缓存和多核或多机读写。数值不同本身不表示违反一致性，较早读 1、较晚读 2 可能完全合法。判断要结合调用顺序、确认条件和所选模型。

应用还可能要求余额守恒、引用目标存在、报名名次稳定。系统的读取保证与这些业务条件需要一起检查。下表列出最终、因果、顺序、线性与严格一致性的约束，性能取决于实现怎样完成相应协调。

应用怎样通过一致性模型判断读取结果，而无需了解每条同步消息？应先确定哪些业务要求，再选择可实现的保证？

解答：

一致性模型规定允许的操作顺序和读取结果，开发者据此判断已确认更新是否应可见、引用是否需等待目标，以及是否允许临时旧值。选择前应确定离线操作、名次变化和冲突处理等业务要求，再检查实现的同步、排序和恢复机制能否提供相应保证。

模型 主要要求
最终一致性 更新停止并完成传播后，各副本收敛到相同状态
因果一致性 有依赖的更新按因果顺序可见
顺序一致性 所有操作可解释为一个共同的串行顺序，并保留每个进程的程序顺序
线性一致性 在合法串行顺序中，保留操作完成到后续操作发起的实时先后关系
严格一致性 按全局实际发起时间规定操作顺序

最终一致性

最终一致性要求更新停止、所需更新最终送达并按共同规则处理后，各副本收敛。传播期间，一个节点已经是 2，另一个仍读到 1，可以符合这个模型。

聊天设备可以先保存本地更新，再持续传播。接收方按稳定 ID 去重，合并记录，并用共同规则生成列表。图中的 0 RTT 只表示本地完成无需先等网络往返，本地可靠保存仍有相应成本。

操作可交换时，合并较简单：加 1 和加 2 各应用一次，无论顺序都加 3。列表追加 X、Y 则产生不同排列，需要额外顺序规则。CRDT 研究可合并状态与可交换操作的形式化条件。断网期间本地仍可工作，跨设备更新需要等通信恢复。

聊天应用怎样在设备能继续读写已有状态的同时，让多台设备最终取得相同历史？最终收敛需要哪些传播和故障恢复条件？

解答：

设备先保存自己的更新并读取已有状态，后台持续传播记录，接收方按 ID 去重并按共同规则合并。更新记录需能在故障后恢复，相关副本重新通信后继续补齐。写入停止、更新最终送达、各副本从一致的基础状态按相同规则处理后，历史收敛为相同结果。

排列更新

日志排序

日志保存更新的 ID、内容与顺序依据。两设备各自先有 X、Y，交换后按同一确定规则排成 X、Y，再从相同初始状态重放，就都得到 [X,Y]。

收敛依赖三项条件：取得相同更新集合，采用相同排序，确定操作在相同初态上产生相同结果。ID 用于去重，时间标签沿用创建时的值，接收节点自己的当前时钟则另外推进。

实际可以用检查点和增量计算减少重复重放，但仍需维持同一结果。

R1 先保存 X，R2 先保存 Y，交换后分别得到 X、Y 与 Y、X。怎样用确定的日志排序和重放，让相同更新集合产生相同列表？

解答：

保存完整更新记录与稳定 ID，交换缺少的记录并去重；双方对相同集合使用同一唯一排序规则，从共同初始状态或检查点重放。例如双方都约定 X 在 Y 前，重放后都得到 [X,Y]。到达顺序可以不同，计算结果由相同日志顺序确定。

迟到更新

当前日志为〈1,X〉、〈3,Z〉，后来到达〈2,Y〉，正确排序是 X、Y、Z。直接追加成 X、Z、Y 会违反共同规则。

可以重新排序重放，也可用支持中间插入的结构。检查点需要说明覆盖哪些更新，迟到的早期记录可能要求保留额外历史。重放必须使用已记录的 ID、正文和决策，若重新生成随机值或当前时间，不同副本可能再次分叉。

时间排序

物理时间可以作为排序键，但两条更新可能取得相同读数。图中 X、Y 都是 1755419200.123，单按时间比较留下并列，各副本可能继续保持自己的先后。

复合键按字典序比较：先比时间，相同时比 node ID，再比节点内 sequence。这样，同一时刻来自不同节点或同一节点的多条更新也能区分。重启代次和序号复用还需保证身份唯一。

也可以把 node ID 放在首位，得到确定顺序，但会将同节点的消息聚在一起。确定顺序只解决排序一致，是否保留依赖还需另外检查。

两个更新的 getTimeOfDay() 都是 1755419200.123，仅用 T 排序能确定二者先后吗？怎样增加字段，避免两边继续保留不同的并列顺序？

解答：

两个相同的 T 留下并列，仅按 T 排序时，双方可能保留各自原有的 X、Y 或 Y、X。可以按 〈T,node ID,sequence〉 依次比较：时间相同后比节点编号，再用节点内序号区分同节点的更新。若 R1 编号小于 R2，两条给定记录都排为 X、Y。

K(e)=(T(e),node_id(e),sequence(e))K(e)=(T(e),\mathrm{node\_id}(e),\mathrm{sequence}(e)) K(e)=(T(e),node_id(e),sequence(e))

时钟偏差

各机器按本地计时源估计时间，振荡频率、温度和校准会影响读数。操作系统用换算参数把计数转换成时间，NTP 等服务帮助校准，仍有残余误差。

图中 R1 的文件时间为 1755419200.123，R2 收到后再创建引用，本机却读到较小的 1755419199.987。按时间排序，两边可能一致地把引用放在文件前。节点编号只能打破并列，不能修正这种依赖倒置。

按 〈T,node ID〉 排序后，各副本能否仍得到 [ref(file_a),file_a]？给节点加唯一编号能解决哪些问题，文件与引用的依赖又需要怎样保留？

解答：

仍可能出现该结果。图中 file_a 的时间为 1755419200.123，引用在另一节点上取得更小的 1755419199.987，按时间优先就把引用排在前面。节点编号解决时间并列，依赖需要逻辑时钟等关系记录；传播途中还要在目标消息未到齐时暂存引用，待依赖可见后显示。

记录因果

因果关系

事件是一次创建、发送、接收或其他要分析的动作。若同一进程先做 X 再做 Y，或 X 发送的消息在 Y 接收，就建立先后。这个关系还具有传递性：X→Z、Z→Y，就有 X→Y，称为 happens-before。

图中文件 X 传到另一节点后，才产生引用 Z，随后又发“看完了”Y，因此 X→Z→Y。显示这些依赖时，应先有目标，再显示依赖它的更新。

两个事件若两个方向都没有这种路径，就称为并发。它们在真实时间上可以相隔很久，并发在这里表示缺少因果先后关系。

一个节点收到文件后再创建引用，消息传递怎样建立文件到引用的先后关系？能否利用这些依赖来调整各节点的事件时间戳？

解答：

创建文件先于发送它，发送先于对方接收，接收又先于创建引用，所以形成文件到引用的因果路径。接收带 T′ 的消息时，用 T=max(T,T′)+1 推进本地时钟，创建引用再递增。文件为 10、接收后为 11、引用为 12，就保留了这条先后关系。

逻辑时钟

Lamport 时钟用一个整数 T 编号。每次本地事件先加一，发送时携带事件编号；接收带 T′ 的消息时，取两者最大值再加一。

这样，同一进程后续事件编号更大，接收事件也比发送事件编号大。沿因果路径连接，便得到 X→Y 时 L(X)<L(Y)。本地 T=20 收到 10 后变为 21，收到 30 则变为 31。

图中 R1 文件标签为〈10,R1〉，R2 原计数 9，接收后变 11，再创建引用得 12。文件记录仍保留原标签 10，只有 R2 当前时钟变为 11，新引用才用 12。

时间戳规定排序，不会替代缺失内容。引用 12 先到、文件 10 未到时，仍需按目标 ID 等待或获取文件。持续交付确定全序还要知道是否有更早消息在路上，这需要额外确认与同步规则。

时钟判断

L(X)<L(Y) 不能反推 X→Y。两个不通信的节点可以分别取得 3、7，编号大的事件甚至可能在现实时间上更早发生，因为它所在节点此前处理过更多事件。

若另外知道节点 2 在事件 2 前收到事件 1 的消息，才有发送、接收和后续事件组成的因果路径。下列判断题分别检查仅有编号与已知消息关系的差别。

节点 1 的事件时间戳为 3，节点 2 的事件时间戳为 7。图中的 TS 表示事件时间戳，记为 L(e)L(e)L(e)。判断下面三项，并说明理由。

  1. 仅凭 L(e1)<L(e2)L(e_1)<L(e_2)L(e1​)<L(e2​)，可以确定事件 1 在实际时间上更早。
  2. 仅凭这两个时间戳，可以确定两个节点一定交换过消息。
  3. 节点 2 在事件 2 之前，已经收到事件 1 的同步消息，因此事件 1 在实际时间上更早。

解答：

  1. 错。逻辑计数大小不足以证明实际发生时间；节点 2 可以先发生编号 7 的事件，节点 1 后来才发生编号 3 的事件。
  2. 错。两个节点也可以独立执行各自事件，分别取得 3 和 7，时间戳本身没有提供通信记录。
  3. 对。题目补充了事件 1 的消息在事件 2 前已到达，发送、接收、后续事件形成因果路径，所以事件 1 实际更早。

两个互不通信的节点分别产生事件 e1、e2，逻辑时间为 3、7。e1 在实际时间上更早、更晚或与 e2 同时发生，三种情况能否出现？

解答：

三种都可以出现。两个节点各自推进计数，较小的计数既可以较早产生，也可以较晚产生，还可以恰好在同一个参考时刻产生。数值 3、7 只说明这两个事件的逻辑标签。

如果另外知道 e2 → e1，时钟条件就要求 L(e2)<L(e1)，与题中数值不符；如果知道 e1 → e2，则符合 3 小于 7。通信记录提供的关系与标签大小要分别检查。

识别并发

接龙名次

两台设备都保存 17 项，各自在本地追加，都会先显示第 18 位。同步可以决定最终第 18、19 位，却可能改变已经显示的位置。

用〈Lamport 时间,node ID〉可以确定展示次序，但独立报名的先后可能由节点编号决定。按名次发奖时，应把临时位置标为待确认，或识别并发后按业务仲裁。若需要保留“二者没有因果先后”这一事实，就不能只依赖强行排出的全序。

两份接龙到第 17 位相同，两个人都在本地追加自己，会不会同时显示为第 18 位？若按名次发奖，应选择临时排序、报告冲突还是等待确认？

解答：

会，各自的本地追加都先占第 18 位，合并后才能确定 18、19 的共同顺序。临时名次应标为待确认；按名次发奖时，需等待确认或明确处理并发冲突。

全序和偏序

全序要求任意两个不同元素都能比较。例如 A 在 B 前、B 在 C 前，得到 A、B、C。偏序允许不确定某些对之间的先后：只知道 A、B 都在 C 前时，可以保留 A 与 B 不可比较。

因果关系属于偏序。两个事件可能 X→Y、Y→X，或 X∥Y。第三种结果向应用提供并发信息，可以据此合并、重试或仲裁。之后再加确定规则排列表，与一开始就把独立事件误当成已有先后不同。

两个报名缺少因果先后关系时，强行规定一个全序与保留不可比较的关系，分别向应用提供什么信息？

解答：

全序给所有不同事件一个确定位置，能直接决定列表排列，但独立报名的顺序可能由节点编号等规则决定。偏序保留已经知道的因果先后，并将缺少关系的事件标为不可比较。应用于是知道这里存在并发，可按业务规则合并、重试或仲裁。

向量时钟

向量为每个参与节点保存一个分量，表示已知的事件进度。两个节点时，[3,1] 表示知道 R1 到第 3 个事件、R2 到第 1 个事件。创建记录时保存向量，传播副本继续使用同一 ID 和创建向量。

图中 X=[1,0]、Y=[0,1]，两者各有一项更大，互不包含对方历史，因此并发。比较 X<Y 时，要求 X 每项不大于 Y，并至少一项严格更小。公式中的 ∀ 表示每一项，∃ 表示至少一项，∧ 表示两条件同时成立。

例如 [0,1]<[3,1]、[2,1]<[3,1]。比较的是不同事件的向量，不能把同一记录的两份拷贝当作两个并发事件。

向量更新

创建本地事件时，只增加自己的分量并保存新向量。接收消息时，先逐项取最大值，将消息带来的历史合入当前状态，再增加自己的分量记录接收事件。

R1 创建 X 得 [1,0]，R2 独立创建 Y 得 [0,1]。R1 收到 Y，合并为 [1,1]，计入接收后为 [2,1]，再创建 ref(Y) 得 [3,1]。Y 的 [0,1] 小于 [3,1]，因此 Y 先于引用。

向量长度随节点数增长，存储与传输成本也增加。它记录依赖和冲突，不负责替应用决定冲突结果。

版本冲突

Dynamo 为同一键的版本保存向量上下文。两个版本互不包含时，读取可以返回分支，让应用合并，再提交包含双方历史的新版本。

购物车的两个节点从空车出发，一个加苹果得 [1,0]，另一个加牛奶得 [0,1]。只保留一边会丢另一项，应用可按规则保留两者。删除、改数量等操作仍要明确含义，向量本身不会替应用算出商品清单。

完整向量若每项 8 B，1000 节点需要约 8000 B，尚未计标识和协议头。稀疏表示可以减少记录，但截断历史会影响判断，需要结合冲突识别要求选择。

购物车的两个并发版本分别为“苹果”和“牛奶”，向量是 [1,0]、[0,1]。只保留第一个版本会丢失什么？向量时钟能直接决定合并后的商品吗？

解答：

只保留第一个版本会丢失加入牛奶的更新。两个向量互不覆盖，系统可以识别存在分支并保留两份结果。合并后的商品由应用规则决定；在本例中可以同时保留苹果和牛奶，再提交包含两个分支历史的新版本。

统一观察

串行观察

多个副本可以对外表现为一个逻辑对象。验证时列出全部调用与返回值，尝试排成对同一对象依次操作的顺序。列表追加应在尾部增加项，寄存器读取应返回这个顺序中最近的写入。

找到合法顺序后，还要检查它保留哪些时间约束：进程自己的程序顺序、完成到后续发起的实时顺序，或者更强的全局发起顺序。下面分别讨论这些要求。

多个物理副本对外表现为一个逻辑对象，需要让哪些操作和结果对应到共同的串行执行？仅有共同顺序时，还要说明哪些时间约束？

解答：

需要找到一个共同的合法串行顺序，解释所有调用与返回结果。例如列表追加把项放到末尾，读取返回该位置之前加入的内容。还要声明保留哪些时间关系：顺序一致性保留每个进程的程序顺序，线性一致性还保留完成到后续发起的实时关系，严格顺序则要求全局实际发起顺序。

严格顺序

一次调用有客户端发起、服务器接收、执行与客户端收到回复几个时刻。网络延迟不同，会让较早发出的 A 比较晚发出的 B 更迟到达。

若要求按全局真实发起时间执行，服务器即使收到精确时间戳，也要知道是否还有更早请求在路上。图中 B=7 已到，A=5 仍未到，服务器应该等多久？消息延迟没有已知上界、还可能丢失时，仅凭现有消息无法确定。实际协议因此通常围绕可观察的调用完成关系建立保证。

Alice 发起 A 的实际时间更早，Bob 的 B 却先到服务器。怎样知道应先处理 A？即使携带精确时间戳，B 的时间为 7、A 为 5，服务器应等待多久、等待多少条更早请求？

解答：

客户端各自的时间存在偏差时，时间戳不足以可靠恢复全局发起顺序。即使时钟精确，B=7 先到后仍可能有 A=5 在路上。在消息延迟无已知上界、消息可能丢失的模型中，服务器无法确定等待上限或更早请求数量；额外的同步与延迟条件需要另行规定。

线性一致性

每次操作从发起到返回构成调用区间。线性一致性要求在每个区间内选择一个生效点，使全部操作形成合法顺序，并保留已经完成操作到后来发起操作的先后。

写 x=2 已经返回，之后才开始读，中间无其他写入时必须读到 2。写与读区间重叠，则可以按结果解释为读在写前或写后。一个操作的生效点可以早于回复到达，客户端收到成功只是取得完成的证据。

图中 A、B 重叠，服务器先处理 B 再处理 A，随后读返回 [B,A]。不同设备之间也受同一实时约束，不能用各自独立的排列解释互相矛盾的结果。

集中服务器实际按什么顺序处理重叠请求？B 已完成后才发起的读取必须包含什么？为什么完成到后续发起的关系可以作为线性一致性的判断条件？

解答：

图中 B 先到服务器，示例处理顺序为 B、A，列表变为 [B,A]。B 已完成后才发起的读必须保留 B 的加入；图中 A 也已完成，所以返回 [B,A]。完成说明操作已经生效，后来发起的调用区间在它之后，合法线性化顺序就必须保留这项实时关系。

初始 x=1。A 写入 x=2，服务器执行后，回复在网络中停留了一秒。B 在这一秒内发起读取。另一次读取则在 A 收到成功回复后才发起，两次读取分别允许返回什么？

解答：

第一次读取与写入的调用区间重叠。若没有其他写入，合法线性化可以把它排在写入之前或之后，分别返回 1 或 2；具体实现可以给出更强的保证。

第二次读取在写入完成后发起，必须排在写入之后并返回 2。这一条件跨客户端成立。判断时使用调用和返回的历史，服务器内部执行时刻可以帮助理解实现。

主副本

一种实现方式是为每个对象指定 primary，统一排序读写，backup 按序保存。请求可以从不同入口进入，但最终交给这个对象的 primary。

图中 P0 排序更新，转发给 P1，等相应确认后再完成自己的提交并向客户端返回 Done。发到 P1 的写也转交 P0。读取需要按规定取得已确认状态。

不同对象可以由不同 primary 负责。列表 A、B、C 分别由 P0、P1、P2 排序，便能分担不同列表的请求。线性一致性可按独立对象组合，但跨对象共同修改还需事务。单个热点列表仍可能限制一台主节点。

切换主节点需要保留已确认记录，并让旧任期授权失效。超时只能触发怀疑，不能靠“选新节点加一个序号”自动完成全部安全条件。

各副本先本地写入并立即返回，再于同步时重新排列，能否让所有已完成操作保留线性一致性的顺序？primary-backup 方法怎样安排读写与确认？

解答：

这种做法一般无法保证线性一致性：一个节点已确认的写入，另一节点还可能读旧值，事后重排也改变不了已返回的结果。primary-backup 对每个对象统一安排操作，给写入排序，备份按序应用并确认，满足条件后才返回完成；读取按相应顺序取得已确认状态。

写入序号

主副本给更新分配序号，备份便能按这个顺序处理，而不是按网络到达顺序。seq 表示位置，value 表示内容，即使都是 1、2 也不能混为一项。

图中写 2 先到备份，直接执行后再写 1 会使最终值变成 1，与主副本不同。带序号后，备份将 seq=2 暂存，等 seq=1 完成才继续。next_seq 记录下一项，缺项补传、重复项检查已处理状态。

primary 安排先写 1、再写 2，backup 却先收到写 2。仅按到达顺序执行会得到什么结果？附上 seq=1、seq=2 后，backup 应怎样等待与应用？

解答：

只按到达顺序，primary 最终为 2，backup 可能为 1。序号把原顺序带给接收方：先到的 seq=2 暂存，seq=1 执行完再应用 2；缺失与重复消息按协议补传和去重。

复制成本

统一排序增加转发与确认等待。要求全部备份确认时，最慢或失联备份会阻碍写入，排在该写入后面的读取也可能等待。

主节点失效后，要选出有效的新负责者并恢复历史。若希望部分节点失效时继续工作，还需改变参与确认的条件或配置，同时保持安全。消息数量和等待长度由这些协议条件共同决定。

要求 primary 排序、全部 backup 确认时，多出哪些等待？primary 失效或某个 backup 失联，分别会影响哪些操作？

解答：

写入多出转发与等待备份确认的时间，要求全部确认时由最慢备份影响完成时间。primary 失效会使统一读写入口暂停，需要确定新主并恢复已确认记录；backup 失联会阻塞要求全确认的写入。若读也排在这个未完成写入之后，它会被连带等待。

顺序一致性

顺序一致性要求一个共同的合法串行顺序，并保留每个进程的程序顺序。它不额外要求所有跨进程的“前一调用结束、后一调用开始”都按实时顺序排列。

图中写请求与两次读取分别属于不同进程。P1 先读到新值 2，之后 P0 仍读到 1。这违反线性一致性，却可以按“P0 读 1、写 2、P1 读 2”解释为顺序一致的结果。

若两次读属于同一进程，先读 2 再读 1，就不能交换它们来解释，因为程序顺序必须保留。因此，随意读本地副本也不能自动保证顺序一致性，需要会话或进度规则配合。备份若经过协调，确认已提交位置并追上它，也可以提供线性读取。

初始 x=1，写请求与两次读取分别由不同进程发起。P1 收到写 2 并读到 2，这次读完成后，P0 的读者才开始读取，却仍返回 1。

  1. 这段历史满足线性一致性吗？
  2. 怎样排列这三次操作，可以解释为合法串行结果？
  3. 解释为顺序一致性时，还要检查每个进程的什么条件？

解答：

  1. 违反线性一致性。先一次读取已经得到 2，随后发起的读取又得到 1，中间没有其他写入，无法保留完成到后续发起的实时关系。
  2. 可按 P0读1、写2、P1读2 排列，解释为合法的单对象串行结果。
  3. 顺序一致性还要求保留每个进程自己的完整程序顺序。题中三次操作由不同进程发起，给出的排列没有颠倒任何进程内部顺序；若同一进程先写后读，还要保留它的写先于读。

2 写入 x=2
3 P1 的读者读取，返回 2

只有一次把 x 从 1 改为 2 的写入。同一个进程连续两次读取，先得到 2、后得到 1。能否用“读 1、写 2、读 2”解释为顺序一致性？

解答：

这个排列颠倒了该进程的两次读取，违反程序顺序。保留读 2 在读 1 前面时，又找不到符合这两次数值的合法寄存器顺序。因此这段历史违反顺序一致性。前面图中的两次读取属于不同进程，才能使用给出的排列。

内存顺序

多核也有可见性问题。一个核的写还在缓冲，另一个核可能尚未看到，编译器和处理器也可按允许规则调整访问。锁、原子操作和内存屏障为指定访问建立顺序。

例如，写线程先准备内容再发布“已就绪”标记，读线程需要配套同步，才能在看到标记后正确使用内容。TSO 与顺序一致性并不相同，TSO 允许某些先前写仍在缓冲时执行后续读取。程序需要同时遵守语言与硬件模型。

模型选择

图中的雷达图概括设计倾向，不是带有单位的实验结果。最终一致性的本地操作减少协调，应用需要处理迟到、重排与冲突；线性一致性便于按一个对象的串行行为推理，实现需要完成排序与确认。

聊天可以先显示本地消息，按状态标记并在后台补齐，引用仍需目标可见。按名次发奖则应等待确认或处理并发仲裁。分析具体应用时，先写出状态与操作，再列依赖和允许结果，最后检查协议是否满足它们。

最终一致性适合每一种应用吗？普通聊天与按名次发奖的接龙，需要怎样规定临时结果、冲突和最终确认？

解答：

最终一致性适合可以接受临时缺少消息、之后同步合并的用法。聊天可以先显示本地记录并标记发送状态，引用还需等待目标消息可见。按名次发奖的接龙应先确认名次，或检测并处理并发报名，再按奖项规则结算；直接把未确认的本地位置作为最终结果，会使名次在同步后变化。
