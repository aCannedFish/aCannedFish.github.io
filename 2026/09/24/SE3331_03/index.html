计算机系统工程-03：RPC

发表于2026-09-24|更新于2026-11-02|Note计算机系统工程
|浏览量:

跨机调用

远程调用

调用 Add(2,3) 时，程序把两个参数交给函数，取得返回值 5。函数放到另一台机器后，参数与结果需要通过网络传递。发起请求的一方称为客户端，执行函数的一方称为服务器。

RPC 是 Remote Procedure Call，即远程过程调用。应用仍按函数接口使用服务，RPC 库负责把调用变成请求消息，再把回复还原成返回值。例如，应用可以调用文件服务器的 Read、Write，而无需在每处业务代码中手工收发报文。

直接使用 Socket 时，还要约定消息格式、编码参数、划分消息边界，以及把回复交给正确的调用。RPC 集中处理这些公共工作。1976 年的 RFC 707 已讨论远端调用，Birrell 与 Nelson 在 1984 年介绍了实现；Sun RPC 用于 NFS，gRPC、Thrift 和面向对象的 RMI 也是相关系统。

跨机器后还会出现超时。重试 Read 可能读到更新后的内容，重试 Append 可能追加第二份。接口必须同时说明正常返回与失败后的行为。

模块接口

文件服务可以先实现本地读写，再让服务端存根接收远端参数、调用这些函数并编码结果。存根 stub 是业务函数与通信代码之间的适配层，负责格式转换和消息收发。

接口明确输入、输出与错误，业务实现就可以复用。例如二十台机器从共同网络工作区读取一个已编译程序，仍需检查架构、运行环境与版本发布，但不必每台手工复制一份。分层也便于分别检查文件操作和 RPC，最后再检查参数、错误和完成条件能否贯通。

时钟服务

假设服务器有准确时钟，客户端要取得秒数，再设置自己的本地时钟。业务代码先调用 GET_TIME(SECONDS)，拿到 t 后调用本地 SET_CLOCK(t)。服务端真正的 GET_TIME 只负责读取时钟并换算单位。

图中两条存根线位于业务与网络之间。客户端存根编码单位并发送请求，服务端存根解码、找到 GET_TIME 并调用。时间值沿回复返回，由客户端存根解码并交给原调用方。连接复用或异步等待可以改变实现，业务仍需处理调用失败。

沿图的时间方向追踪时，要区分请求已经发出、函数正在执行和结果已经返回。后面讨论故障时，这些阶段会有不同的恢复含义。

只有服务器具有准确时钟和 GET_TIME(units) 的实现，客户端怎样调用它并设置自己的时钟？客户端存根和服务端存根各负责什么？

解答：

客户端通过存根发送 GET_TIME 的参数，服务端存根解码并调用时间函数，再把结果沿回复返回。客户端据此调用 SET_CLOCK；精确校时还需估计网络传输误差。下图给出完整调用路径。

客户端 SYNC_CLOCK() 调用 t = GET_TIME(SECONDS)，再执行本地 SET_CLOCK(t)
服务端 GET_TIME(units) 读取 CLOCK，按秒或分钟等约定单位换算后返回

校时误差

每台机器独立计时，频率偏差会累积成时钟偏差。服务器返回 t，也不表示客户端收到回复时仍是 t：回复在网络上走了 d 秒，参考时间已经约为 t+d。

双方可以约定 Unix 时间戳，以 1970 年 1 月 1 日 UTC 为起点，并明确秒等单位。若测得往返为 20 ms，且两方向近似对称，可先估算回程为 10 ms。路径不对称时，这个估计会产生误差。

NTP 一次交换记录四个时刻：T1 客户端发送，T2 服务器接收，T3 服务器发送，T4 客户端接收。下面第一个公式用两方向时间差估计服务器相对客户端的偏差，第二个从总往返中扣除服务端处理时间。系统通过多次测量、筛选与持续校准减少误差。

识别请求

请求和回复

请求必须说明“哪一次调用、调用哪个过程、输入是什么”。调用标识 xid 关联请求与回复，程序号和过程号选择函数，版本字段确定协议与接口，认证信息说明凭证，参数字段保存业务输入。

服务端在回复中带回同一个 xid，并报告请求是否被接受、过程是否成功执行。RPC 版本错误、认证失败、找不到过程和参数解析失败属于不同错误。函数已经正常执行，也可能返回“余额不足”这样的业务结果。

Sun RPC 的 xid 通常为 32 位。客户端让仍在等待的调用使用不同标识，服务端判断重复时还需结合客户端身份和方法。这里的调用 ID 与银行整笔事务的 ID 不同，一笔业务可以包含多次 RPC。

RPC 请求消息中要放哪些内容，才能让服务器选中正确函数、读出参数，并让客户端识别回复？

解答：

请求要包含调用标识 xid、消息方向、RPC 版本、程序号与版本、过程号、认证信息和编码后的参数。服务器按程序和过程标识选择函数，再解码参数。回复带回同一 xid、处理状态与结果，客户端据此查找等待中的调用。

xid 关联一次请求与回复
CALL/REPLY 标记 区分消息方向
RPC 版本 确定报文协议
程序号、程序版本、过程号 选择服务器上的程序与过程
认证信息 按所用认证机制提供凭证与校验信息
参数 过程的输入

匹配回复

同一进程可以有多个线程，同时请求不同内容。假设线程 1 请求 page.html，线程 2 请求 logo.png，共用连接。图片先完成时，第一条到达的回复应交给线程 2，不能按发起次序直接分配。

客户端维护 xid 到等待者的表，例如 1 对应线程 1、2 对应线程 2。图中服务器把请求交给不同工作线程，回复携带原 xid，客户端据此唤醒正确等待者。完成顺序受文件大小、缓存和排队影响。

标识分配与等待表也需要并发协调。可以组合线程编号和线程内序号，再结合客户端身份与运行代次。16 bit 序号只有 65536 个值，回绕时不能与仍有效的旧调用混淆。重启可能复用线程编号，因此需要代次等额外信息。同一请求重传沿用 ID，新操作取得新 ID。

本地调用靠调用栈和返回地址恢复控制流，进程号无法区分进程内的多次调用。RPC 跨过这些本地结构，需要显式记录等待关系。

线程 1 请求 page.html，线程 2 请求 logo.png，二者共用连接，图片先完成。收到回复时怎样找到对应线程？为什么请求需要 xid？

解答：

客户端保存 xid=1 → 线程1、xid=2 → 线程2 的对应关系。图片先完成时，收到 xid=2 的回复就交给线程 2；随后收到 xid=1，再交给线程 1。xid 将每条回复与它所属的请求关联，完成顺序变化也能正确分发。

连接复用

为每个线程建立连接，可以简化部分分发，但会增加连接状态和缓冲。多个逻辑调用共用连接时，用调用标识区分回复即可。

连接由协议栈管理，多个连接仍可能共享网卡队列。RSS 等分发机制再把流量交给处理核心。C10K 讨论单机处理约一万个并发连接的资源问题，涉及线程、事件、内存和 I/O。连接数、硬件队列数、同时处理的 RPC 数需要分别统计。

传递参数

参数编码

通信双方最终交换的是字节。一个字节有 8 bit，可表示 0–255，两位十六进制数正好表示一个字节。例如 0x89abcdef 是四个字节组成的整数。

发送指针数值不会把对象送到远端。地址 0x1000 只在发送方进程中解释，接收方需要得到姓名、年龄等内容，再创建自己的对象。如果要返回修改，应在回复中编码修改结果；持续引用远端对象，则需要双方认可的对象 ID 与操作协议。

把对象变成线上字节称为序列化或 marshal，反向称为反序列化或 unmarshal。XDR、ASN.1、JSON、XML Schema、Thrift、Protobuf 都规定了相关表示。Java Serializable、Python pickle 依赖各自语言的对象体系，跨语言或长期兼容需额外处理。

图中大端按 89 ab cd ef 排列，小端按 ef cd ab 89 排列。双方还需约定整数宽度、符号、浮点格式和字符编码。“中”的 GBK 为 d6 d0，UTF-8 为 e4 b8 ad，相同字符可以有不同字节表示。

参数按值传递和按引用传递，跨机器时各需要怎样处理？整数 0x89abcdef 在大端、小端机器上各怎样排列？字符串、整数宽度和内存对齐还需要哪些共同约定？

解答：

按值传递把数据内容编码成字节。跨机器传对象引用时，需要编码对象内容和对象间关系，在接收方重建本地对象。需要修改调用方对象时，应把修改结果放进回复，再由调用方更新；若要持续访问远端对象，则需共同识别的对象 ID 和相应协议。普通内存地址属于所在进程的地址空间。
0x89abcdef 的大端排列为 89 ab cd ef，小端为 ef cd ab 89。两端还要约定整数宽度与符号、浮点表示、字符编码及字段布局，按统一格式读取。

字段布局

结构体的字段之间可能有对齐填充。一个 uint8_t 与一个 uint64_t 的值合计 9 B，如果后者要求 8 B 对齐，前面补 7 B，整个结构体就可能占 16 B。直接发送本机 sizeof 个字节，会把这种布局假设也带给对方。

协议可以独立规定字段类型与顺序，让两端各自构造本地对象。浮点数也要明确格式：float16、bfloat16、float32、float64 的范围、精度和大小不同，12.3 还可能只能近似表示。

链表等对象包含引用关系，编码时要保存节点内容及连接方式。遇到环，可以给对象编号并记录已经访问的对象，接收方再恢复引用。编号和引用的含义必须写进协议。

填充 1 至 7 满足本例的对齐要求
b 8 至 15 八字节数值

编码格式

字符串、整数、布尔值和数组表示不同类型的数据。JSON 用字段名和值描述对象，二进制格式可以用字段编号。选择格式时，需要同时检查能否正确还原、跨语言是否兼容、消息有多大，以及编解码需要多少计算。

JSON 容易查看，但每次都传字段名。二进制图片常先转为 Base64，每 3 B 变为 4 个字符，体积约增加三分之一。数字还受接收程序的数据类型限制：若使用 binary64，通常只有 −(2^53−1) 到 2^53−1 的整数范围能保证逐整数区分，64 位业务 ID 需要单独约定。

大量浮点数组还会产生数字文本、分隔符和解析工作。Thrift、Protobuf 可以减少传输字节，但也需要 CPU、内存分配和复制。YAML、TOML、CSV 同样需要字段、类型与版本约定，不能只凭“文本”或“二进制”判断总耗时。

Java 客户端与 Python 服务器怎样交换对象？使用语言专用对象格式会遇到什么兼容问题？JSON 这类文本格式怎样传输图片等二进制内容？

解答：

双方可以采用共同的消息定义和跨语言编码，例如通过 IDL 生成各自的消息类、编码器和存根。Java Serializable、Python pickle 等依赖各自语言的对象模型，跨语言和升级兼容需另行安排。JSON 可把二进制数据转成 Base64 文字；每 3 B 通常变为 4 个编码字符，总长度约增加三分之一。

格式 特点 需要另外约定的内容
JSON、XML 等文本格式 易于阅读与调试，多语言支持较广 数字类型与精度、二进制表示、版本规则
Thrift、Protobuf 等二进制格式 利用字段编号和类型描述，通常较紧凑 schema、生成代码及兼容规则

消息采用二进制格式后，RPC 总耗时是否一定减少？网络变快时，还需要测量哪些成本？

解答：

是否减少取决于整个调用的成本。二进制格式可以减少字段名、长度和数值的传输字节，但也需要编码、解码、分配内存和处理请求。网络变快后，传输所占时间可能变小，CPU 与内存工作占比上升。因此应测量相同消息从编码到业务处理、回复解码的完整耗时。

接口定义

IDL 是接口定义语言，用一份声明说明消息字段和可调用方法。schema 指数据结构定义。Thrift 使用自己的 IDL，Protobuf 使用 .proto，gRPC 还在其中声明服务。

在 Person 中，string user_name=1 的 1 是字段编号；int64 favorite_number=2 的 2 也是编号，与运行时填写的 1337 无关。repeated string interests=3 表示可包含多个字符串。

rpc GetTime(TimeRequest) returns (TimeResponse) 指定方法、输入与输出类型。protoc 生成消息类和编解码代码，gRPC 插件生成服务相关代码，开发者填写实际业务。Python 客户端与 C++ 服务端可以由同一份定义生成各自接口，重试与去重语义仍需应用设计。

一份跨语言、可升级的消息定义，应怎样说明字段身份、类型和可以调用的方法？生成工具能替开发者完成哪些代码？

解答：

消息定义应给字段稳定编号、类型和含义，并约定缺少字段时的默认值与未知字段的跳过规则；方法声明写明名称、请求类型和回复类型。生成工具可以输出各语言的消息类、序列化与反序列化代码、客户端和服务端存根。业务函数及业务层的重试、去重规则仍需开发者实现。

声明 含义
message Person 定义消息类型
string user_name = 1; 字符串字段，编号 1
int64 favorite_number = 2; 64 位整数类型的字段，编号 2
repeated string interests = 3; 可包含多个字符串的字段，编号 3

读懂编码

Thrift 编码

下面固定同一个 Person 对象：Martin、1337，以及 daydreaming、hacking 两项兴趣。无空格 JSON 为 81 B。比较时只数对象编码，完整 RPC 还要加请求头。

BinaryProtocol 的字段头包含 1 B 类型与 2 B 编号，字符串再带 4 B 长度，i64 使用 8 B。图中姓名为 13 B，整数为 11 B，列表头为 8 B，两字符串各为 15、11 B，结束标记为 1 B，合计 59 B。13、24、32、47、59 表示累计位置，相邻数相减就是对应片段长度。

CompactProtocol 在合适时把字段编号增量和类型合为一个字节，并使用变长整数与长度。1337 先经 ZigZag 映射成 2674，再得到 f2 14。姓名、整数、列表头、两字符串及 STOP 分别为 8、3、2、12、8、1 B，合计 34 B。

ZigZag 按 0→0、−1→1、1→2、−2→3 排列，正 x 映射到 2x，负 x 映射到 −2x−1。去掉 f2 14 的最高位，得到 114 和 20，恢复为 114+20×128=2674，再解映射得到 1337。减少的是字段描述与数值表示，字符串本身仍完整保留。

userName="Martin"、favoriteNumber=1337、interests=["daydreaming","hacking"]。按图中的 BinaryProtocol 和 CompactProtocol 格式，逐段计算字段头、长度、整数和字符串占用的字节，再求对象总大小。

解答：

  1. BinaryProtocol：姓名的类型、编号、长度、内容共 1+2+4+6=131+2+4+6=131+2+4+6=13 B；整数为 1+2+8=111+2+8=111+2+8=11 B；列表的字段头、元素类型和数量共 8 B，两个字符串分别为 4+11=154+11=154+11=15 B、4+7=114+7=114+7=11 B，STOP 为 1 B。合计 13+11+8+15+11+1=5913+11+8+15+11+1=5913+11+8+15+11+1=59 B。
  2. CompactProtocol：姓名为 1+1+6=81+1+6=81+1+6=8 B；整数 1337 经 ZigZag 得到 2674，Varint 为 f2 14，加字段头共 3 B；列表头 2 B，字符串为 1+11=121+11=121+11=12 B、1+7=81+7=81+7=8 B，STOP 为 1 B。合计 8+3+2+12+8+1=348+3+2+12+8+1=348+3+2+12+8+1=34 B。

Protobuf 编码

每个 Protobuf 字段前有 Tag，保存字段编号和 wire_type。字段编号左移三位，相当于乘 8，最低三位留给 wire_type，两者按位或组合。Tag 自己也按 Varint 发送。

wire_type 说明后续字节怎样读取：0 为 Varint，1 为固定 8 B，2 为长度加内容，5 为固定 4 B。旧 group 的开始、结束类型 3、4 已弃用。接收方凭这些信息可以读取已知字段，也能跳过未知字段。

Tag=(field_number≪3)∣wire_type\mathrm{Tag}=(\mathrm{field\_number}\ll3)\mathbin{\vert}\mathrm{wire\_type} Tag=(field_number≪3)∣wire_type

wire_type 编码方式 常见类型
0 Varint，按继续位确定结束 int32、int64、bool、enum
1 固定 8 B fixed64、double
2 先读长度，再读相应字节 string、bytes、嵌套消息
5 固定 4 B fixed32、float

变长整数

Varint 每字节的低七位保存数值，最高位指示是否继续。1 表示还有下一字节，0 表示结束；数值块按低位在前，基数为 128。

128 分成低位 0、高位 1，加继续位后得到 80 01。恢复时计算 0+1×128=128。1337 分为 57 和 10，编码为 b9 0a。字段 2 的 int64 使用 wire_type 0，Tag 为 2×8=16，即 10，所以整段为 10 b9 0a。

字符串 Martin 属于字段 1，wire_type=2，Tag=10，即 0a；长度 06 后接六个字符 4d 61 72 74 69 6e，合计 8 B。读图时先确定 Tag，再按类型读取长度和内容。

字段声明为 int64 favorite_number = 2;，实际值为 1337。计算 Tag、Varint 和完整字节串，并说明接收方怎样还原它。

解答：

字段编号为 2，int64 使用 wire_type=0，所以 Tag 为 2×8+0=162\times8+0=162×8+0=16，十六进制是 10。编号 2 的二进制 00000010 左移三位得到 00010000，低三位 000 表示类型 0。16 小于 128，Tag 占一个字节。

将 1337=10×128+571337=10\times128+571337=10×128+57 拆成低位块 57、高位块 10：

第一字节 0111001，即 57 1 10111001，即 b9
第二字节 0001010，即 10 0 00001010，即 0a

完整字节串为 10 b9 0a，共 3 B。接收方从首字节 16 计算 16 >> 3 = 2 和 16 & 7 = 0，知道字段号为 2、后面按 Varint 读取；去掉 b9 0a 的继续位，取得 57、10，还原 57+10×128=133757+10\times128=133757+10×128=1337。

字段编号和类型决定 Tag，实际数值决定后面的整数编码。字段名字来自消息定义。int64 规定整数范围，Varint 按值决定长度；sint64 还会先使用 ZigZag。

版本兼容

服务升级往往是分批完成的，新旧程序会同时通信。新程序读旧消息称为向后兼容，旧程序处理新消息称为向前兼容。兼容需要稳定字段身份、可缺省的新字段，以及跳过未知字段的方法。

图中旧 writer 只发送 1、2，新 reader 读到 Thrift STOP 后结束，字段 3 保持未设置或采用默认值。反过来，新 writer 发 1、2、3，旧 reader 按类型与长度跳过字段 3，再继续解析。

已有编号和含义不应随意改变，Protobuf 删除字段后应保留编号，避免赋予新含义。解析成功也不等于业务一定兼容，还要检查默认值和行为约定。直接把短旧消息当成长新结构体，会越界或读到未定义值，解码必须检查实际边界。

旧消息定义只有 id，新定义增加 priority，约定缺省值为 0。

  1. 旧程序写出 {id:7}，新程序应怎样读取？
  2. 新程序写出 {id:7,priority:1}，旧程序应怎样处理？
  3. 这些行为对字段编号、可缺省规则和未知字段处理有什么要求？

解答：

  1. 新程序读取旧消息，得到 id=7，并为缺少的 priority 使用约定值 0。
  2. 旧程序读取新消息，识别 id=7，按编码规则跳过新增 priority 字段，继续解析。
  3. 格式要支持字段身份识别和未知字段跳过，已有编号与含义保持稳定，新增字段允许缺省并有明确默认值。直接改变内存结构还需要相应编码协议提供这些兼容规则。

计算开销

调用成本

把一次按阶段完成的调用拆开，可以分别计算编码、网络、排队、业务处理和解码。这些项目包含请求与回复两方向的相关工作，下面公式给出总和。

S 字节经过可用速率 B 的链路，理想纯发送时间为 S/B。传播、协议头、最小帧和排队会继续增加耗时。59 B 缩到 34 B，减少 25 B，约为原对象的 42%，但总调用节省比例不会自动也是 42%。

在 1 Gbit/s 链路上，25 B 只对应 0.2 μs；若紧凑编码多花 1 μs，总体反而多 0.8 μs。假设速率为 100 GB/s，也就是 800 Gbit/s，4 KiB 的纯发送时间约 0.041 μs，编解码和分配工作就更值得测量。这个速度是算例假设，不是所有网络的实际吞吐。

TRPC≈T编码+T网络+T业务+T排队+T解码T_{\mathrm{RPC}}\approx T_{\text{编码}}+T_{\text{网络}}+ T_{\text{业务}}+T_{\text{排队}}+T_{\text{解码}} TRPC​≈T编码​+T网络​+T业务​+T排队​+T解码​

只按有效字节计算，1 Gbit/s 链路传输 59 B 与 34 B 的时间差是多少？若更紧凑的编码额外花费 1 μs，其他成本相同，净变化是多少？

解答：

1 Gbit/s 等于 109/8=1.25×10810^9/8=1.25\times10^8109/8=1.25×108 B/s，25 B 的理想发送时间差为 25/(1.25×108)=0.225/(1.25\times10^8)=0.225/(1.25×108)=0.2 μs。编码增加 1 μs 后，合计多花约 0.8 μs。

实际报文还有头部、最小帧和传输时延等条件。这个计算只用来说明，节省字节与增加编码工作要一起计入。

远端映射

受控环境可以采用另一种数据传递方式。Dmerge 的生产者先生成对象，消费者随后使用它。RMMAP 将生产者相关内存映射到消费者地址空间，消费者访问对象及内部指针时，由操作系统取得远端页面。

RDMA 允许网卡按注册范围与权限访问远端缓冲区，可以用于页面传输。注册、地址映射与对象访问仍需要操作系统、网络、分配器和语言运行时配合，还要处理地址冲突、生命周期与隔离。

论文示例中，一个 3.2 MB pandas dataframe 含约 40 万子对象，序列化约需 10 ms。这说明对象数量和结构也影响成本。比较远端映射与普通编码时，要把页面读取、预取、映射和对象保留一起计入。

处理失败

网络故障

超时只表示客户端等待超过期限。例如 1 秒后还没回复，请求可能丢了，也可能仍在路上，服务器可能崩溃或暂停，也可能已经执行而回复丢失，或者回复只是迟到。这六种情况无法仅凭一次计时区分。

两张故障图分别把红叉放在请求与回复路径上。请求丢失时没有 run，重试提供首次执行机会；回复丢失时 run 已完成，再次执行 AddBalance(100) 可能多加 100。

服务器队列、线程暂停和业务内部部分执行也会造成不同状态。客户端需要稳定调用身份和可靠结果记录，服务器需要事务与恢复机制处理已执行的部分，然后才能决定重试怎样继续。

客户端一直收不到回复并发生超时，服务器可能处于哪些状态？怎样区分请求丢失、服务器停顿与已经执行但回复丢失？

解答：

可能是请求丢失、请求仍在路上、服务器崩溃、服务器暂时停顿、过程已完成但回复丢失，或回复仍在路上。一次超时只记录等待超出期限，无法据此选定一种情况。需要用稳定调用 ID 查询执行记录和业务结果，再按协议重试；缺少可靠记录时，结果仍可能不确定。

执行次数

用户的一次逻辑请求、网络上的发送次数、服务端过程执行次数和最终业务修改次数，需要分别理解。用户只点了一次加款，客户端重发两次，并不代表希望加款三次。

至少一次方法在未成功时继续重试，过程可能重复，最终完成还依赖故障恢复和持续尝试。至多一次通过稳定 ID 抑制重复，但失败时可能执行零次或一次，客户端未必知道是哪种。恰好一次业务效果需要把请求身份、结果与业务修改共同可靠提交，再通过重试或查询确认。

Birrell 模型中，成功回复说明过程已完成一次，CRASH 则可能对应零次或一次。成功效果与调用者知道成功的时刻仍然不同。

应用开发者通常希望一次调用产生怎样的执行效果？系统实现至多一次、至少一次或恰好一次效果时，分别需要记录和处理什么？

解答：

应用通常希望一次逻辑调用只产生一次已确认的业务修改。至少一次方法在未获成功回复时重试，允许过程重复执行，完成依赖通信和服务最终恢复。至多一次需要稳定 ID 与去重记录，重复请求等待已有执行或取已有结果，失败时可能执行零次或一次。恰好一次效果需要把业务修改、请求 ID 和结果一起可靠提交，重试沿用 ID，恢复后按记录确认结果。

名称 处理方法 可能结果
至少一次 未获成功回复时重试 可能重复执行；完成依赖故障最终恢复、持续重试等前提
至多一次 固定调用 ID，检测并抑制重复 失败时可能执行零次或一次，调用方未必知道是哪种
恰好一次效果 持久去重记录与业务修改原子提交 故障恢复后按记录确认结果，客户端持续重试直至完成

回复缓存

回复缓存保存请求 ID 与已完成结果。编号 7 的加款使余额从 0 变为 100，同时保存 7→100；回复丢失后，再收到编号 7，就返回原结果，不再加款。改成编号 8 会被视为新请求。

跨重启去重需要可靠保存这些记录，并让它们与余额修改共同生效。只保存余额，恢复后可能再加一次；只保存完成标记，可能返回一个没有实际入账的结果。Sun RPC 的近期回复缓存仅在记录仍有效时提供保护，淘汰或重启丢失后需要另外的业务保证。

图中的 CRASH 表示调用者结果不明。只有一笔加款时，余额 0 或 100 可以帮助理解两种结果；真实系统还要按具体操作身份核对，不能仅看余额是否符合某个数值。

账户 B 初始为 0，只有一次 Transfer(100)。服务器报告 CRASH，调用方无法确认过程是否执行。B 可能是多少？重试前应怎样确认结果？

解答：

按这次转账已经完成或尚未完成的两种情况，B 可能为 100，也可能为 0。应查询这笔操作的可靠业务记录或请求完成记录，保持原操作 ID，再由协议处理继续执行或返回已完成结果。在这个只有一笔加款的例子中，余额可帮助检查；实际确认仍需与具体操作身份对应。

服务器重启后仍要识别重复请求，需要可靠保存哪些信息？若业务修改与完成记录只有一份保存成功，会产生什么问题？

解答：

需要保存稳定请求 ID、执行或提交状态，以及已完成调用的结果，并将完成记录与业务修改一起可靠提交。只保存业务修改时，恢复后可能再次执行；只保存完成记录时，可能返回一个实际未完成的结果。事务或相应日志恢复协议要让两类记录共同生效，并在重试时检查它们。

正在执行

重复请求可能在第一次尚未完成时到达。例如第一次需要 100 ms，客户端在 50 ms 超时，此时完成缓存还没有结果。

服务器可先登记“正在执行”，重复请求等待同一次执行或收到处理中状态，原执行完成后再取得相同结果。登记与查询必须并发协调，防止两个线程都认为自己处理的是首次请求。

缓存回收

每秒 1000 次调用、每条记录 100 B，不回收一天会增加 8.64 GB，还未计入索引与大回复。因此要规定会话期限、客户端确认和序号边界。

删除具体回复前，需要知道旧调用后来到达时怎样识别。可以保留完成边界或其他防重记录。编号 7 已执行后若全部记录丢掉，再将旧 7 当新请求，就会重复加款。重试期限、重启身份和编号复用必须一起设计。

编号 7 的加款已经完成，回复记录因容量限制被删除。很久以后编号 7 又到达，直接当新请求执行会怎样？

解答：

可能再次加款，产生第二次业务修改。服务器需要依据仍有效的调用身份、完成边界或业务记录判断；超出协议允许的重试范围时，可以要求查询业务状态或返回相应错误。

去重保证需要说明记录保留时间、客户端重启后的身份规则，以及故障恢复条件。删除记录与编号复用要按这些规则共同安排。

重复执行

幂等描述状态效果：同一个操作重复执行与执行一次相同，记为 f(f(x))=f(x)。连续设置 i=1 是例子，连续 i++ 则会累加。

清扫图将地面简化为 dirty 与 clean，在没有新增污物时，扫一次或三次最终都是 clean。电梯按钮图中，未完成的一次呼叫重复按下仍是同一请求，复位后再按才是新呼叫。两图都需要先明确“同一个操作”对应的范围。

ReadTime 重试得到较新的时间，通常没有累计修改状态，可以按接口再次读取。Like 重试却可能把两次点赞计成三次，需要稳定请求 ID；每人每轮一票时，还可用用户 ID 与轮次识别业务身份，改票则需要独立更新规则。

幂等也要结合并发。旧请求设置 1，随后另一请求设置 2，再执行旧请求仍会覆盖新结果。因此，旧请求能否继续应用，还可能需要版本和顺序检查。

两个用户各请求一次 ReadTime，回复丢失引起重试，服务器实际运行三次。这个结果是否可以接受？什么情况下至少一次重试适用？

解答：

按图中的“取得当前时间”语义，可以接受：第三次读取取得新的当前时间，服务端没有因此累计修改业务状态。返回值会随时钟变化。至少一次重试适用于这样的查询、幂等更新，或具备可靠重复检测的业务；校时程序还需处理读取时刻和网络等待造成的误差。

两个点赞请求因重试实际执行三次，计数从预期的 2 变成 3，应怎样处理？投票请求需要依据什么业务身份或操作标识识别重复？

解答：

点赞重复执行会多加一次计数，因此要为每次逻辑点赞分配稳定 ID，重试沿用这个 ID。服务器把 ID 检查、计数更新和完成记录一起提交，重复请求返回已有结果。每人每轮只能投一次时，可按“用户 ID、投票轮次”记录投票；允许改票时，还要定义改票操作，并协调原票与新票的更新。

组成服务

RPC 组成

一套 RPC 包含消息格式、编解码库、存根生成器、服务端分发、客户端等待匹配、重试与去重，以及服务绑定或发现。业务从客户端存根进入，服务端找到函数执行，结果再沿回复返回。

服务地址可以来自配置或注册服务。TCP 提供有序字节流，RPC 仍要划分消息；UDP 提供数据报，需要按协议处理丢失与重排；RDMA 使用相应网卡与注册内存访问缓冲区。框架支持哪些方式，要结合硬件、消息和故障要求选择。

前面的字段编码、回复缓存和重试都是整条调用路径的一部分，单独选好编码格式不能代替其他组件。

客户端怎样找到服务端地址？RPC 可以怎样选择 TCP、UDP 或 RDMA 作为传输方式？

解答：

服务地址可来自配置，或通过服务名向注册、发现服务查询。TCP 提供可靠有序字节流，RPC 格式负责划分消息；UDP 发送独立数据报，RPC 框架按协议处理丢失、重排和重试。RDMA 在相应网卡与注册内存条件下访问远端缓冲区。应按硬件、消息大小、等待成本和故障处理要求选择框架支持的传输。

超时重试

退避是在两次尝试间等待，减少故障或过载时连续重发。示例 maxAttempts=3 包含第一次，因此最多再试两次。基础等待分别为 0.1 s、0.2 s，随后受倍率、上限和调用截止时间限制，实际框架还可加入随机调整。

只对指定状态考虑重试，例如 UNAVAILABLE。ReadTime 可以重新读取，Like 则需要应用去重。达到次数或时间上限后，应明确返回失败还是结果未确认，再由应用查询。

永久故障下，有限或无限重发都不能凭空完成操作。次数约束与结果保证要分别写清，不能把“配置了重试”当成恰好一次效果。

项目 示例值 含义
maxAttempts 3 包含首次调用，最多再试两次
initialBackoff 0.1 s 初始退避
maxBackoff 1 s 退避上限
backoffMultiplier 2 基础等待时间逐次增加
retryableStatusCodes UNAVAILABLE 仅对选定状态考虑重试
