发表于2026-09-24|更新于2026-10-02|Note计算机系统工程

从磁盘到文件

大型现代互联网平台为了支撑海量业务，通常需要将文件存储服务器、关系型数据库、内存缓存集群、负载均衡器、CDN 与消息队列等组件紧密组合在一起。然而，这些庞大复杂的分布式系统，其最底层的基石依然建立在单台计算机的单机操作系统与基础抽象之上。

在单机存储中，最核心的基础设施就是文件系统（File System）：

  • 底层的物理磁盘与驱动程序只认识按数字顺序排列的物理扇区（Sectors）；
  • 上层应用程序希望操作的却是有名字、可动态伸缩长度、具有严格访问权限控制、且在系统断电或崩溃后仍然完整保存的文件。

因此，**文件（File）**可以看作是对物理存储的一种高层抽象：它是一串长度任意、可动态增长的线性字节数组。持久性（Durability）与人类可读的命名（Naming），是文件区别于一段普通易失内存数组的关键属性。

磁盘驱动抽象 vs 文件系统抽象

物理磁盘驱动程序提供给内核的接口极其原始，可以高度抽象为两个基础操作：

  • Read(sector_idx)：读取指定编号扇区的数据；
  • Write(sector_idx, data)：向指定编号扇区写入数据。

底层硬件的最小读写粒度通常是扇区，历史上以 512 字节为主，现代高级格式化磁盘则多为 4096 字节（4 KiB）。然而，一个真实应用文件往往跨越成千上万个扇区，并且需要按目录层级组织、支持随机读写与权限控制。文件系统在底层硬件驱动与上层应用之间构建起多层映射：对上提供统一易用的系统调用接口，对下将应用请求精准翻译为具体的物理存储块编号。

对比两者的接口抽象差异：

  • 驱动程序只接受面向硬件的指令：“读取第 bbb 个扇区”；
  • 文件系统面向应用程序提供面向人类的接口：“读取名称为 a.txt 的文件，从文件内偏移量 ooo 处连续读取 nnn 个字节”。

当应用发起读取时，文件系统首先通过路径名逐级寻找到对应的文件元数据结构（inode），再将文件内部的相对偏移量 ooo 换算为文件内部的逻辑块号与块内偏移，进而通过索引表查出该数据块在物理磁盘上的具体块号。若应用请求的长度跨越了多个块，文件系统还会负责将多个物理块的数据拼接成连续的内存缓冲区返回给应用。

核心系统调用接口

在典型的 UNIX 文件系统中，操作接口涵盖了数据读写、元数据管理与全局命名空间维度的全生命周期：

接口分类 典型系统调用 核心职责
生命周期与数据访问 open, read, write, append, seek, close 建立文件打开会话、读取或修改字节序列、移动内部读写游标，并在关闭时释放会话状态
持久性与同步 fsync, sync 强制将操作系统内核缓冲区中的脏数据及相关元数据立即刷盘写入物理持久介质

命名与链接关系 rename, link, unlink, symlink 建立或移除目录项映射、创建硬链接与符号链接、协调源目录与目标目录以实现重命名
目录与命名空间 mkdir, rmdir, chdir, chroot, mount, umount 创建/删除子目录、改变当前工作目录、隔离全局根目录，以及将外部文件系统挂载接入现有命名树

从应用发起一次系统调用到硬件磁盘执行 I/O，整个系统结构可以清晰地划分为三层协同：

  1. 用户态（User Space）：运行应用程序，应用通过 POSIX API 发起 read("report.txt", offset=5000, size=100)；
  2. 内核态（Kernel Space）：
    • 文件系统模块：解析文件名找到文件元数据，将第 5000 字节换算为文件内逻辑块，再通过索引映射表查出目标磁盘块号；
    • 块设备驱动程序：接收文件系统发出的物理块 I/O 指令，调度设备控制器命令队列；
  3. 硬件层（Hardware）：物理磁盘控制器根据指令完成磁头移动、寻道或闪存阵列读取，将底层数据搬运至物理内存。

连续存储方案为何失效

为了对比理解基于索引的文件系统，先考察一种最朴素的设计思路：连续分配（Contiguous Allocation）。在该方案中，系统要求每个文件必须在物理磁盘上占据一段连续的扇区，直接用文件的“起始扇区编号”作为该文件的唯一代号。

观察这种朴素方案在动态场景下的表现：

  • 红色标示已被其他文件占用的物理扇区。假设系统中有三个文件，分别从扇区 101、107、113 开始存放；
  • 文件 107 当前占用了 107 与 108 两个扇区。此时 109 至 112 扇区尚为空闲，文件 107 尚可向后追加；
  • 然而，一旦文件 107 继续增长到第 113 号扇区时，便会直接与下一个文件的起始位置发生碰撞！即使磁盘在扇区 200 以后还有数以万计的空闲扇区，由于连续性限制，文件 107 必须被迫将全部已有数据整体迁移搬迁到另一片足够大的空闲区域。

这一严重缺陷揭示了连续分配的核心痛点：

  1. 严重的磁盘碎片与空闲查找代价：磁盘在使用一段时间后会产生大量碎片区间，分配新文件前必须进行昂贵的全盘扫描；
  2. 文件动态扩容极度脆弱：一旦后续扇区被占用，必须整体重分配并物理搬迁整个文件；
  3. 文件身份与物理位置紧密耦合：将起始扇区号（如 107）作为文件代号，一旦文件扩容发生物理迁移，其名字与标识便彻底失效；
  4. 缺乏独立的元数据管理：无法优雅地存储文件权限、时间戳及人类可读的文件名字。

为了彻底摆脱连续存储的桎梏，UNIX 诞生了以 inode（Index Node，索引节点） 为核心的经典文件系统架构。

UNIX 文件系统的七层命名结构

以经典的 UNIX Version 6 为代表，文件系统将从物理磁盘块到完整绝对路径的转换抽象为严谨优雅的七层软件架构：

七层结构严密定义了每一层的输入、输出与转换职责：

层级 名称 输入 输出 核心职责与抽象转换
L1 块层 (Block Layer) 块号 (Block Number) 磁盘物理块数据 将磁盘抽象为统一编号的定长块阵列，屏蔽底层柱面/磁头/扇区物理差异
L2 文件层 (File Layer) inode 与文件内部偏移量 文件内容所在的磁盘块 通过直接与间接索引结构，将离散的物理块组织为可动态扩缩的连续文件
L3 inode 编号层 (inode Number Layer) inode 号 具体的 inode 元数据对象 在磁盘固定区域维护 inode 表，为每个文件分配全局唯一且位置独立的数字身份
L4 文件名层 (File Name Layer) 目录 inode 与单级文件名 目标文件的 inode 号 引入目录文件，建立人类可读的字符串名称与底层 inode 数字编号的映射
L5 路径名层 (Path Name Layer) 当前工作目录 inode 与相对路径 最终目标文件的 inode 号 递归解析多级目录（/ 分隔），支持跨级路径导航并支持硬链接与引用计数
L6 绝对路径名层 (Absolute Path Layer) 全局根目录 / 与绝对路径 目标文件的 inode 号 确立全局统一的起始锚点（通常为根 inode），使所有进程拥有统一的全局视图
L7 符号链接层 (Symbolic Link Layer) 符号链接中的目标路径字符串 新的目标路径名 独立记录目标路径文本作为别名，支持跨磁盘、跨文件系统与跨挂载点的弹性重定向

整个命名体系的分水岭在于：

  • L1 至 L3 属于机器导向命名（Machine-oriented Names）：使用无含义的整数编号（块号、inode 号），追求定位效率与机器处理速度；
  • L4 至 L7 属于用户导向命名（User-oriented Names）：引入多级字符串路径与别名，为人类用户提供层级化、语义化的组织方式。

自底向上看：驱动识别块；inode 将分散的块聚合成文件；inode 表为元数据提供统一数字代号；目录项将字符串名字绑定至 inode 号；路径解析实现跨层级导航；根目录收敛全局入口；符号链接提供灵活别名。当应用读取一个绝对路径时，系统正是沿这条调用链自顶向下逐层解析，最终精准锁定对应的物理磁盘块。

块与超级块

块层 (L1: Block Layer)

在现代文件系统中，块（Block） 是操作系统进行空间分配与 I/O 管理的基本逻辑单元。一个文件系统块的大小始终是物理设备扇区大小的整数倍（例如将 8 个 512 B 扇区组合为一个 4096 B / 4 KiB 的逻辑块）。

增大块大小能够在管理相同容量的文件时将索引所需的指针数量减少为几分之一，减少寻道与元数据开销；但对于只有几个字节的小文件，即使数据再小也会独占整个逻辑块，从而导致块内出现大量未使用的碎片空间（内部碎片 / Internal Fragmentation）。因此，4 KiB 成为了多数现代通用文件系统兼顾 I/O 效率与空间利用率的标准折中选择。

在逻辑抽象上，块号到内容的映射可以简洁地表达为：

BLOCK_NUMBER_TO_BLOCK(b)→devices[b]\text{BLOCK\_NUMBER\_TO\_BLOCK}(b) \rightarrow \text{devices}[b] BLOCK_NUMBER_TO_BLOCK(b)→devices[b]

底层驱动程序负责将逻辑块号 bbb 乘以每块扇区数换算为具体的起始 LBA 物理扇区编号，并提交硬件执行 DMA 传输。

超级块与空闲位图

为了能够正确挂载并解释磁盘上的数据，文件系统必须在磁盘固定位置持久化记录其自身的全局元数据。这一核心区域被称为超级块（Superblock）。操作系统在挂载文件系统时最先读取的正是超级块。

经典的磁盘物理布局划分如下：

  1. 引导块（Boot Block）：位于磁盘前 1 KiB（扇区 0 等），存放计算机开机启动代码，文件系统本身不直接修改该区域；
  2. 超级块（Superblock）：记录文件系统的魔数（Magic Number，用于验证格式）、块大小、总块数、空闲块数、inode 总数与空闲 inode 数，以及 inode 表与位图的起始物理位置；
  3. 空闲块位图（Free Block Bitmap）：利用二进制位（Bit）跟踪磁盘每个数据块的空闲与分配状态；
  4. inode 表（inode Table）：在磁盘连续区域连续分配的一组结构体，每个槽位存放一个文件的完整 inode 元数据；
  5. 数据块区（Data Blocks）：占据磁盘绝大部分空间，存放普通文件的实际内容和目录文件的目录项。

空闲位图的压缩效率极高：每一个二进制位严格对应一个物理数据块（0 表示空闲，1 表示已分配）。一个字节可记录 8 个块；对于一个包含 2302^{30}230 个 4 KiB 块（总容量为 4 TiB）的大磁盘，其对应的完整位图仅需：

230 bits8 bits/byte=128 MiB\frac{2^{30} \text{ bits}}{8 \text{ bits/byte}} = 128 \text{ MiB} 8 bits/byte230 bits​=128 MiB

这相比于 4 TiB 的物理总容量微乎其微。当创建新文件分配块时，系统扫描位图找到为 0 的空闲位，置 1 并返回块号；释放文件时，必须先确保该块的引用完全解除，再将对应位置 0，以防止出现两个文件指向同一块物理介质的严重数据损坏。

inode 与多级索引

文件层 (L2: File Layer)

在文件层中，每个文件由一个唯一的 inode（Index Node） 结构体进行刻画。inode 是文件所有元数据的物理载体，通常包含以下字段：

  • 文件大小（Size，以字节为单位）；
  • 文件类型（Type，普通文件、目录、符号链接、设备文件等）；
  • 访问权限（Permissions / Mode，读写执行掩码）；
  • 拥有者与组 ID（Owner UID / GID）；
  • 时间戳（访问时间 atime、修改时间 mtime、元数据变更时间 ctime）；
  • 引用计数（Link Count，指向该 inode 的硬链接总数）；
  • 数据块索引数组（Block Pointers）。

特别需要强调的是：文件名本身绝对不在 inode 内部保存！

当应用发起对文件偏移量 offsetoffsetoffset 处的读写时，文件层将其转换为文件内逻辑块索引 qqq 与块内字节偏移 rrr：

q=⌊offsetBLOCKSIZE⌋,r=offset mod BLOCKSIZEq = \left\lfloor \frac{offset}{\text{BLOCKSIZE}} \right\rfloor, \qquad r = offset \bmod \text{BLOCKSIZE} q=⌊BLOCKSIZEoffset​⌋,r=offsetmodBLOCKSIZE

随后，系统通过 inode 内维护的索引结构将逻辑块号 qqq 映射为真实的物理磁盘块号 bbb：

INODE_TO_BLOCK(offset,i)→BLOCK_NUMBER_TO_BLOCK(INDEX_TO_BLOCK_NUMBER(i,q))\text{INODE\_TO\_BLOCK}(offset, i) \rightarrow \text{BLOCK\_NUMBER\_TO\_BLOCK}(\text{INDEX\_TO\_BLOCK\_NUMBER}(i, q)) INODE_TO_BLOCK(offset,i)→BLOCK_NUMBER_TO_BLOCK(INDEX_TO_BLOCK_NUMBER(i,q))

直接索引与多级间接索引

如果 inode 内部只保存一个固定大小的物理块号数组（例如 10 个指针），那么在 4 KiB 块大小下，文件最大只能支持 10×4 KiB=40 KiB10 \times 4 \text{ KiB} = 40 \text{ KiB}10×4 KiB=40 KiB，这显然无法满足现实需求。为了既能极速访问小文件，又能无缝扩展以容纳巨型文件，UNIX 采用了多级间接块索引机制：

经典的 inode 块指针数组由四部分构成：

  1. 直接块指针（Direct Pointers）：通常包含 10 到 12 个指针，每个指针直接存放一个物理数据块编号。由于绝大多数小文件都在数十 KB 以内，这些文件仅需 1 次磁盘寻道即可直接命中数据；
  2. 一级间接指针（Single Indirect Pointer）：指向一个专门存放块指针的“索引块”（Indirect Block）。若块大小为 4 KiB、每个磁盘块号占 4 字节，则一个索引块可容纳：

    K=4096 B4 B=1024 个块指针K = \frac{4096 \text{ B}}{4 \text{ B}} = 1024 \text{ 个块指针} K=4 B4096 B​=1024 个块指针

    单单一级间接指针即可额外支持 1024×4 KiB=4 MiB1024 \times 4 \text{ KiB} = 4 \text{ MiB}1024×4 KiB=4 MiB 的文件容量；
  3. 二级间接指针（Double Indirect Pointer）：指向一个一级索引块，其中包含 1024 个指针，每个指针各自再指向一个二级索引块，最终指向数据块。二级间接指针可支持：

    K2=1024×1024=1,048,576 个数据块≈4 GiBK^2 = 1024 \times 1024 = 1,048,576 \text{ 个数据块} \approx 4 \text{ GiB} K2=1024×1024=1,048,576 个数据块≈4 GiB

  4. 三级间接指针（Triple Indirect Pointer）：经过三层索引树状展开，可支持 K3≈109K^3 \approx 10^9K3≈109 个数据块，最高支持 4 TiB 级巨型文件。

多级索引的优势在于按需分配：对于几 KB 的小文件，系统仅需分配直接块，间接索引指针为 NULL，零额外开销；只有当文件体积突破上限时，内核才动态分配间接索引块。代价则是对于落在深层间接区的大文件随机读写，在索引块未命中内存缓存时，可能需要经历多次磁盘 I/O 逐级读取索引。

inode 编号层 (L3: inode Number Layer)

在物理磁盘上，所有 inode 结构体整齐紧凑地排列在连续的 inode 表区域。inode 号本质上就是该 inode 在磁盘 inode 表中的数组下标：

INODE_NUMBER_TO_INODE(num)→inode_table[num]\text{INODE\_NUMBER\_TO\_INODE}(num) \rightarrow \text{inode\_table}[num] INODE_NUMBER_TO_INODE(num)→inode_table[num]

结合前三层，系统已能够根据 (inode_number, offset) 准确定位并读取任意文件的任何字节。然而，纯数字编号对人类用户而言是极其反直觉的。人类需要更友好、更具语义的字符串名字。

目录与路径解析

文件名层 (L4: File Name Layer)

UNIX 系统中一个极其优雅的核心设计哲学是：目录本身也是一个普通文件。

目录也是由一个 inode 表示（其类型字段为 DIRECTORY），其对应的数据块中存放的不是用户的文本或二进制字节，而是一组结构化的目录项（Directory Entries / dirent）。每一个目录项的核心职责，就是建立一个从单级字符串文件名到目标 inode 号的映射：

LOOKUP(dir_inode,filename)→inode_number\text{LOOKUP}(dir\_inode, filename) \rightarrow inode\_number LOOKUP(dir_inode,filename)→inode_number

观察目录的解析过程：

  • 假设某目录的数据块中包含两条目录项记录："helloworld.txt" -> 12 和 "cse2021.md" -> 73；
  • 当在当前目录下查找 "cse2021.md" 时，系统首先确认当前目录的 inode 类型确为目录，然后读取其数据块并执行字符串匹配；
  • 成功匹配后，直接返回对应的数字编号 73。下一层再拿着 73 去检索磁盘 inode 表，进而取得文件大小与块索引。

在早期 UNIX Version 6 中，目录项采用极简的固定 16 字节设计：前 2 字节为 inode 号，后 14 字节为固定文件名字段。这导致早期 UNIX 文件的最大文件名长度被严格限制在 14 字节。在现代现代文件系统（如 Linux ext4）中，目录项采用了变长编码，并引入了哈希 B 树（HTree）索引，以支持超长文件名并在包含数十万文件的巨型目录中实现近常数级的查询性能。

  1. 0d 01 73 00：按照 x86 小端序（Little-Endian）解析，十六进制数值为 0x0073010d，换算为十进制即为 inode 编号 4194573，与 ls -ai 中当前目录 . 的编号完全吻合；
  2. 0c 00：十六进制为 0x000c，表示当前目录项总共占据 12 字节；
  3. 01：文件名真实长度为 1 个字符；
  4. 02：文件类型代码为 0x2，严格代表该条目是一个目录（Directory）；
  5. 2e：ASCII 字符为 .；后续的 00 00 00 为 4 字节边界对齐填充。

跳过 12 字节后进入第二个目录项，起始为 01 01 73 00（inode 4194561），类型同样为 0x2，名称为 ..（父目录）。目录项长度 dir_entry_length 记录的是跳往下一个记录的物理步长，而 file_name_length 记录的是文件名字节长度，两者解耦使得目录能够在删除文件时直接通过合并跳步长度实现常数级的就地空间回收。

路径名层与绝对路径 (L5 & L6)

单级目录只能查找同级文件，路径名层（Path Name Layer） 与 绝对路径层（Absolute Path Layer） 则通过递归展开建立全局层级命名：

  • 相对路径：从进程的当前工作目录（CWD / Current Working Directory）对应的 inode 开始逐级向下解析；
  • 绝对路径：必须从全局唯一的根目录 / 开始解析。根目录的 inode 编号在文件系统格式化时已固定确立（在 UNIX V6 中为 inode 1，在 Linux ext4 中通常固定为 inode 2）。

经典案例解析：检索 /programs/pong.c 的完整数据块

考察系统从输入绝对路径 /programs/pong.c 到最终定位物理数据块的完整遍历时序：

系统解析全过程严格遵循以下 9 个步骤：

  1. 定位根目录：系统直接以预先约定的根目录 inode 编号（假设为 1）作为起点；
  2. 读取根目录元数据：在磁盘 inode 表的第 1 号槽位取出根 inode；
  3. 读取根目录内容：根据根 inode 中的直接块指针，读取根目录的数据块；
  4. 线性匹配第一级路径：扫描根目录数据块中的目录项，查找名为 "programs" 的条目，成功获取其 inode 编号为 7；
  5. 读取二级目录元数据：根据编号 7，在 inode 表中取出 /programs 的 inode，检查其权限并确认其类型为目录；
  6. 读取二级目录内容：读取 inode 7 对应的数据块；
  7. 匹配第二级路径：扫描目录项，查找名为 "pong.c" 的条目，成功获取其 inode 编号为 9；
  8. 读取目标文件元数据：在 inode 表中取出 inode 9，获取文件真实大小、权限以及数据块指针数组；
  9. 检索真实数据块：在 inode 9 的直接块指针中，查得该文件由物理块 61、44、15 构成。

当应用要求读取文件第 5000 字节（假设逻辑块长为 4096 B）时：

  • 逻辑块号为 q=⌊5000/4096⌋=1q = \lfloor 5000 / 4096 \rfloor = 1q=⌊5000/4096⌋=1（即第 2 个数据块）；
  • 块内偏移为 r=5000−4096=904r = 5000 - 4096 = 904r=5000−4096=904 字节；
  • 系统索引定位到物理块号 44，指令驱动程序直接从物理磁盘第 44 块的第 904 字节处读取数据返回应用。

整个过程生动体现了分层解耦的精妙：文件在物理磁盘上的分布可以高度碎片化（块 61, 44, 15 彼此不相邻），但对应用呈现的却始终是连续统一的流式体验。

硬链接与重命名机制

硬链接 (Hard Links)

在 UNIX 文件系统中，执行 link("a.txt", "b.txt") 并不会创建新的文件，而仅仅是在目录中增加了一个全新的目录项，指向既有的 inode 编号。

硬链接的核心语义如下：

  • a.txt 与 b.txt 具有完全对等的地位，不存在所谓的“主文件”与“快捷方式”之分，它们是同一文件的两个平权别名；
  • inode 结构体内记录了 link_count（硬链接计数），每执行一次 link 计数加 1；
  • 调用 unlink("a.txt") 只是删除了 "a.txt" 这个目录项，并将 inode 内部的 link_count 减 1；只要 link_count > 0，或者依然有进程持有该文件的打开句柄，底层的数据块和 inode 就绝不会被释放；
  • 只有当 link_count 降为 0 且所有引用进程均已 close 时，文件系统才会真正回收 inode 并在空闲位图中将数据块标记为空闲。

为什么绝对禁止普通用户为“目录”创建硬链接？
因为硬链接将原本纯粹的层级树状结构变成了有向图。如果允许为目录创建硬链接，用户便可以构造出目录循环引用（Cycle）：

观察成环后的严重后果：

  1. 初始时刻，根目录可以正常到达子目录 a，inode 25 的引用计数为 1；
  2. 若允许在子目录内部创建硬链接指向父级目录 a，则形成了一个闭环，inode 25 的计数上升为 2；
  3. 当用户从根目录执行 rm -r a 删除了对 a 的顶层引用时，link_count 仅仅从 2 降为 1；
  4. 此时，由于闭环内部互相引用，整个孤岛的链接计数永远无法归零，但从根目录出发又没有任何合法路径能够再次遍历到达该孤岛。这会导致磁盘空间发生永久性泄漏，文件系统一致性检查（fsck）将彻底陷入死循环。因此，现代操作系统严格禁止用户对目录创建硬链接。

崩溃安全的重命名 (Crash-Consistent Rename)

在日常使用文本编辑器（如 Vim）保存文件时，编辑器为了防止保存中途断电导致源文件损坏，通常采用“写临时文件，然后重命名替换”的机制：

  1. 编辑内容先完整写入隐藏临时文件 .a.txt.swp；
  2. 将临时文件正式重命名覆盖目标文件 a.txt。

若采用简单的 API 组合模拟该过程，分析不同实现顺序在系统突然断电时的行为：

方案 A（存在安全空窗）：

  • 步骤 1：unlink("a.txt") 删除目标旧文件；
  • 步骤 2：link(".a.txt.swp", "a.txt") 建立新绑定；
  • 步骤 3：unlink(".a.txt.swp") 删除临时别名。
  • 致命缺陷：若系统恰好在步骤 1 完成后、步骤 2 尚未执行时突然断电崩溃，重启后用户会震惊地发现原有的 a.txt 彻底凭空消失！对于关键应用，这种数据中途不可见是绝不可接受的。

方案 B（顺序优化）：

  • 步骤 1：先让目标名字 a.txt 指向新临时文件的 inode；
  • 步骤 2：再删除源临时名字 .a.txt.swp。
  • 该方案消除了旧文件被提前删除的空窗期，即便两步之间发生崩溃，新旧数据至少有一种依然可见，恢复程序能够根据引用计数进行平滑对齐。

现代 POSIX rename(oldpath, newpath) 系统调用在内核底层由文件系统日志（Journaling）保证其严格原子性：无论何时遭遇断电崩溃，系统恢复后观察到的要么是完整的重命名后状态，要么是完全未执行的原状态，绝不存在半途撕裂。

符号链接 (L7: Symbolic Link Layer)

符号链接（Symbolic Link / 软链接） 是最高层次的命名抽象。符号链接本身是一个具有独立 inode 的特殊实体文件，但其数据块中存放的内容非常特殊：它保存的是另一个目标文件的路径名字符串。

对比硬链接与符号链接的本质特征：

关键维度 硬链接 (Hard Link) 符号链接 (Symbolic Link / Soft Link)
指向机制 目录项直接指向目标文件的 inode 编号 拥有独立 inode，内部存储目标路径字符串
跨文件系统 绝不可跨越（每个独立分区的 inode 编号是局部自治的） 完全支持（字符串路径可通过根命名空间挂载点自由跨越）
指向目录 严格禁止（防止目录环） 允许指向目录（内核通过遍历深度限制 MAXSYMLINKS 防止死循环）
目标被删除 文件不受影响，其余硬链接继续合法读写 软链接立即可变成为悬空链接（Dangling Link）
文件大小属性 与目标文件完全一致 严格等于其保存的路径名字符串字节长度

总结：文件系统的本质

回顾 UNIX 文件系统的七层结构，可以提炼出贯穿存储系统的核心设计精髓：

  1. 文件名是目录的数据，而非文件的属性：inode 刻画了文件的物理存在与存储布局，但文件叫什么名字完全由引用它的目录项决定；
  2. 多层命名映射实现高层解耦：从面向物理硬件的“扇区号 →\rightarrow→ 逻辑块号”，到面向操作系统的“inode 号”，再到面向人类的“相对路径 →\rightarrow→ 绝对路径 →\rightarrow→ 别名”，每一层软件仅负责一层映射，极大增强了系统的灵活性与可维护性；
  3. 元数据管理决定系统成败：无论是超级块的全局协调、位图的高效空间追踪、多级间接指针的平滑扩缩，还是硬链接与重命名中的原子性保障，文件系统设计的核心工作，正是通过严谨精妙的元数据协议，在脆弱易失的物理磁盘之上构筑出坚不可摧的持久化虚拟抽象。
