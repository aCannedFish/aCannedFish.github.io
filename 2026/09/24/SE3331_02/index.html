使用文件

先把磁盘结构放在一边。假设文件里有 100 个字节，应用想读取第 11 到第 20 个字节：它需要先打开文件，再指定从偏移 10 开始读取 10 字节。偏移从 0 计数，所以“第 11 个字节”对应数值 10。下面先建立这种应用视角，之后再追踪内核怎样找到这些字节。

磁盘和文件

计算机中的所有数据在底层均以二进制位（bit）表示，8 个 bit 组成 1 个字节（Byte，记为 B）。文本、图片、音视频和可执行程序，最终在存储介质上都表现为一串字节序列。在容量计量中，计算机系统通常使用以 2 为底的二进制单位：1 KiB=1024 B1\text{ KiB} = 1024\text{ B}1 KiB=1024 B，1 MiB=1024 KiB1\text{ MiB} = 1024\text{ KiB}1 MiB=1024 KiB，1 GiB=1024 MiB1\text{ GiB} = 1024\text{ MiB}1 GiB=1024 MiB。

操作系统管理内存、处理器和存储设备，为应用提供相应接口。磁盘和 SSD 常通过逻辑块地址（LBA，Logical Block Addressing）访问固定大小的数据单元，例如 512 B 或 4 KiB；逻辑地址还会由设备映射到实际介质。文件系统在这些块之上组织文件与目录，负责命名、查找、空间分配、持久保存和权限控制，使应用可以按路径与字节偏移操作数据。

文件需要具备哪些基本特征？文件名、字节内容和长期保存分别由什么记录和设备支撑？

解答：

文件的基本特征可以概括为：具有人类可读的字符串名称、支持按字节偏移量随机或顺序访问，以及具备跨越机器关机或重启的持久保存能力。支撑这三项特性的机制分别如下：

  1. 文件名：保存在文件系统的目录项（Directory Entry）中，负责将字符串名称映射到文件系统的内部管理结构——inode 编号。
  2. 字节内容：由数据块（Data Block）承载，并通过 inode 中记录的元数据（文件大小、类型、权限、时间戳）以及数据块指针索引进行定位。
  3. 长期保存：物理数据与元数据最终持久化存储在机械硬盘或 SSD 等非易失性介质上；操作系统在内存中维护的打开文件记录、虚拟文件系统（VFS）结构和页缓存（Page Cache），则用于加速运行时的读写访问。

在现代互联网架构中，后端的 Web 应用服务器需要与分布式文件存储、关系型数据库、内存缓存、负载均衡器以及内容分发网络（CDN）紧密协同。理解单机操作系统如何组织与管理本地文件系统，是深入掌握大规模分布式存储系统（如 GFS、HDFS、NFS）的基石。

对普通文件而言，应用看到的是可按字节位置访问的有序序列，可以读取某个区间、追加或修改内容，以及查询属性。文件名保存在目录中，同一文件可以有多个名称。文件系统负责将路径与字节偏移映射到设备块，并维护空闲空间和访问权限，应用无需自行管理扇区编号。

持久化需要落实到具体写入协议。写入可能先停留在标准库的用户态缓冲区，或进入内核页缓存，尚未保存到设备时断电仍可能丢失。程序需要按接口要求刷新相关缓冲、执行 fsync 等同步并检查错误；文件系统还要保存目录、inode 和空间分配记录，重启后才能找回完整名称与内容。

读写接口

应用按字节位置访问文件。文件偏移量（File Offset）从 0 开始：offset=0 指第一个字节，offset=100 跳过前 100 个字节，指向第 101 个字节。size 表示希望访问的长度。

应用可以只读取其中一段。文件系统根据偏移与长度找到对应块，跨块时再把结果按文件顺序组合起来。

磁盘驱动按扇区编号读写，应用按文件名和偏移读取，二者之间需要完成哪些转换？

解答：

系统从上至下需要完成两级关键转换：

  1. 名称到文件对象的转换（路径解析）：从根目录或当前工作目录出发，逐级读取并解析目录项，比对字符串路径中的各级组件，最终获取目标文件的 inode 编号并载入其 inode 元数据。
  2. 字节偏移到物理地址的转换（块索引映射）：根据文件系统定义的逻辑块大小 CCC，将文件字节偏移量 ooo 拆分为逻辑块索引 q=⌊o/C⌋q = \lfloor o / C \rfloorq=⌊o/C⌋ 和块内偏移量 r=o mod Cr = o \bmod Cr=omodC。接着，通过 inode 中的直接指针或多级间接索引表，将逻辑块号 qqq 转换为设备物理块号 bbb。最后，驱动程序将块号换算为具体的物理扇区号并发起硬件 I/O。如果读取请求跨越了多个块，文件系统还需要按顺序调度多次物理块读取，并将取出的数据拼接还原为连续的字节流返回给应用。

底层块设备接口可以简化为 Read(sector_idx) 与 Write(sector_idx, data)，表示按逻辑扇区编号读写。512 B 和 4 KiB 是常见单位，但传输单位与断电下的原子写入保证需要分别确认。文件通常跨越多个扇区，并通过字符串路径组织，因此文件系统还要完成上层文件接口与块设备接口之间的转换。

读取接口可以抽象为 READ(name, offset, size)：找到 name 对应的文件，从 offset 开始取 size 个字节。POSIX 接口把打开与读取分开：先调用 open(path, flags) 得到文件描述符 fd，再调用 read(fd, buf, count)。

read 使用并推进打开记录中的游标。需要指定位置而不改变该游标时，可以使用 pread。

读取调用从应用进入内核后，VFS 根据打开记录选择具体文件系统；文件系统利用 inode 和块映射定位内容。命中页缓存时可以直接返回，否则由块层与驱动发起设备 I/O，完成后将所需字节交给应用。路径通常在 open 阶段解析，后续 read 使用 fd 对应的打开记录；跨块请求需要组合多块内容，设备完成通知方式由实现决定。

库函数

在编写应用程序时，开发者通常有两种接口选择：C 标准库接口与 POSIX 原生系统调用接口。C 标准库使用 fopen 打开字节流，返回一个指向结构体的指针 FILE *，常与 fread、fwrite、fclose 配套使用；POSIX 系统调用则通过 open 返回整数型文件描述符 fd，常与 read、write、close 配套使用。

两类接口主要在抽象与缓冲层次上不同。read、write 等系统调用进入内核，fread、fwrite 等标准 I/O 函数还管理用户态流缓冲。例如，fwrite 可能先将内容放入 C 库缓冲区，之后因缓冲区填满、调用 fflush 或其他刷新条件而交给底层 write；内核页缓存再按规则写回。需要持久性时，还要协调库缓冲与 fsync 等接口，并检查错误。fopen 手册说明了流接口及相关行为。

常用操作

应用通过 API 请求文件操作。open 返回的 fd 是一个小整数，用来索引当前进程的文件描述符表。内核由此找到打开文件记录（Open File Description），其中保存文件引用、访问方式和当前游标。

read 从游标位置读取并推进游标，lseek 只调整位置而不读取内容，close 释放这个描述符的引用。后面的打开记录图会说明多个 fd 何时共享同一个游标。

文件描述符的分配遵循 POSIX 严格规定的最小未用非负整数规则。在进程启动时，操作系统默认预先分配前三个标准文件描述符：

  • 0：标准输入（stdin）
  • 1：标准输出（stdout）
  • 2：标准错误（stderr）

如果这三个描述符均处于占用状态，随后首次调用 open 通常会分配到描述符 3。如果程序主动关闭了 0 并再次打开一个新文件，内核会严格按照“选择最小可用编号”的原则，重新将 0 分配给新打开的文件。这一确定性的分配规则正是 Unix 命令行中实现标准输入输出重定向（如利用 dup2）的底层原理。open 手册明确记录了这项分配规范。

组织磁盘

设备可以按编号读写存储单元，却不知道哪个单元属于哪个文件。文件系统因此需要保存两类内容：文件本身的字节，以及描述名称、位置和分配情况的元数据。先试一个连续存放方案，观察它在文件增长时哪里出问题，再引入目录和 inode，便能理解这些结构为什么需要存在。

连续分配

在探索现代文件系统的内部结构之前，先考察一种最直观的物理布局思路——连续分配（Contiguous Allocation）。存储介质在逻辑上被划分为按序号排列的扇区数组。连续分配方案规定：每个文件在磁盘上必须占用一段物理扇区号严格连续的存储区间，系统只需记录文件的“起始扇区号”与“总长度”，即可定位整个文件。

一种极简的设想甚至可以直接将文件的起始扇区编号用作该文件的标识。

用起始扇区编号作为文件名，并让每个文件占连续扇区，怎样找到空闲空间？文件增长、字符串命名和权限检查还会遇到哪些问题？

解答：

  1. 空闲空间查找：系统必须维护空闲扇区位图（Bitmap）或空闲区间链表（Free Extent List）。为了分配一个新文件，系统必须遍历查找一段长度大于或等于该文件需求的连续空闲区间。
  2. 文件扩容受限：当一个已分配的文件需要追加内容而扩容时，如果其相邻的下一个物理扇区已经被其他文件占用，该文件就无法直接向后延伸。系统必须在磁盘其他区域重新寻找一个足够大的连续空闲段，将全部旧数据完整搬迁过去，并释放原有空间。这不仅会带来昂贵的拷贝开销，还会导致其逻辑标识（起始扇区号）发生变动。
  3. 命名与权限缺失：人类用户需要层级化的可读字符串名称（如 /home/user/code.c），而不是生硬的扇区物理编号；多用户系统还需要追踪记录文件拥有者、读写执行权限、时间戳等元数据，这些信息无法直接从裸扇区号中表达，必须引入专门的元数据管理结构。

  • 中间的文件起始于 107，当前已占用扇区 107 和 108。在其后方，扇区 109 至 112 恰好处于空闲状态（共 4 个可用扇区）。

空闲空间总量足够、却缺少所需长度的连续区间，称为外部碎片（External Fragmentation）。通过目录项、inode 与块映射分离名称和数据位置，可以允许一个文件使用不连续的块。文件增长或块位置改变时，更新相应索引即可继续通过原名称访问；目录与分配记录仍需正确维护。

七层命名

在现代操作系统中，从用户给出的高层路径字符串（如 /programs/pong.c）到最终驱动程序向存储硬件发出的扇区读写命令，中间跨越了巨大的语义鸿沟。计算机系统工程通过分层抽象（Layering）将这一复杂过程逐级解耦。在此处，“层”代表一次确定性的地址或命名转换契约。

下图用经典 Unix 的七层命名模型解释名称转换。它是理解文件访问的一种分层方式，具体系统可以合并或调整这些层：

层级编号与名称 输入参数 输出结果 核心设计职责与工程意义
L1 块层 (Block Layer) 块号（Block Number） 对应块的裸数据（Raw Block Data） 屏蔽硬件底层寻址差异，提供统一的基本块读写接口
L2 文件层 (File Layer) inode 元数据、文件字节偏移量 对应的数据块号及块内偏移 将离散分布的物理块按逻辑顺序组装为线性的连续字节序列
L3 inode 编号层 (Inode Number Layer) inode 编号（Inode Number） 具体的 inode 数据结构实例 为系统内所有文件元数据记录提供扁平化、唯一的数字索引
L4 文件名层 (Directory / File Name Layer) 父目录 inode、单级子项字符串名称 该子项对应的 inode 编号 在单个目录文件的数据块内，完成名称字符串到 inode 编号的映射查找
L5 路径层 (Path Name Layer) 起始工作目录、相对路径字符串 目标文件的 inode 编号 沿着多级目录层次结构，连续迭代解析各级路径组件
L6 绝对路径层 (Absolute Path Layer) 根目录 (/)、绝对路径字符串 目标文件的 inode 编号 确定全局路径解析的唯一起点，屏蔽当前进程工作目录的差异
L7 符号链接层 (Symbolic Link Layer) 软链接中的目标路径字符串 被重定向的新目标路径 提供间接路径别名能力，将访问请求引导至新的路径上下文中重新解析

在这套七层转换模型中，越靠近底层（L1–L3），系统越依赖高效率的数字编号（物理块号、inode 编号）；越靠近上层（L4–L7），系统越面向人类用户友好的字符串标识（文件名、绝对路径）。当应用程序请求读取 /programs/pong.c 时：

  1. L6 / L7：检测到首字符为 /，确定从系统的根目录 inode 开始解析；
  2. L5 / L4：在根目录数据中查找 programs，获取其目录 inode 编号；再进入 programs 目录的数据中搜索 pong.c，获取其文件 inode 编号；
  3. L3：根据该 inode 编号，在磁盘的 inode 表中精确定位并读出文件元数据；
  4. L2：根据应用程序指定的读写偏移量，查阅 inode 的索引指针，换算得出目标数据究竟落在哪个物理块中；
  5. L1：驱动程序根据物理块号发出底层存储总线指令，读取该块的实际数据。

值得注意的是，inode 编号通常仅在它所属的具体文件系统分区内部具有唯一性。若要跨越不同的物理分区，操作系统还需借助挂载点（Mount Point）机制将不同分区的局部层次结构拼接成统一的全局命名空间。

块和超级块

文件系统通常按块（Block）管理存储，例如一个 4 KiB 块可以对应一个或多个设备逻辑扇区（Sector）。这种安排减少了需要维护的地址数量，也会影响 I/O 与空间利用率。超级块（Superblock）保存块大小、总块数、inode 数量等全局参数，其他管理区域的位置可以直接记录，也可以通过块组描述符等结构取得。挂载时，内核先按格式读取这些布局信息，才能正确解释后续记录。

为什么文件系统还要用“块”管理扇区？假设 4 KiB 块包含四个 1 KiB 扇区，同样的数据需要记录多少个块号？选择更大的块时，空间利用率又会怎样变化？

解答：

  1. 管理开销对比：若每个块包含四个扇区，管理相同容量数据所需的块编号数量直接减少为原先扇区编号数量的四分之一（1/41/41/4）。由于需要存储的指针数量大幅缩减，描述文件所需的索引元数据（如 inode 间接块）尺寸得以显著减小，内核扫描和缓存块地址表的内存开销也相应降低。
  2. 空间利用率折中（内部碎片）：文件系统为文件分配存储空间时是以完整的数据块为最小粒度的。如果选用更大的块，虽然能提高顺序读取性能并减少元数据，但对于小型文件而言，其末尾未占满的部分会导致更多的空间浪费。这种在分配单元内部产生且无法分配给其他文件使用的闲置空间称为内部碎片（Internal Fragmentation）。例如，一个仅有 1 KiB 内容的小文件若被分配到一个 4 KiB 的块中，剩余的 3 KiB 空间将无法被利用，此时该块的有效空间利用率仅为 1/4=25%1/4 = 25\%1/4=25%。

文件偏移

inode 应保存在哪里？如果 inode 的块号数组只能容纳固定数量的入口，文件继续增长会遇到什么限制？

解答：

  1. 保存位置：inode 自身也是一种结构化元数据，在格式化时由文件系统规划在专用的 inode 表区域（位于非易失性介质上），并由超级块记录其全局起始物理位置。
  2. 增长限制：如果 inode 内部仅设计了一个容量固定为 NNN 的直接物理块号数组，且每个逻辑块大小为 CCC，那么该文件能够寻址的最大物理尺寸将被硬性限制在 N×CN \times CN×C。例如，若设计中仅包含 10 个直接块号且块大小为 4 KiB，则单个文件哪怕磁盘仍有空余，其容量上限也只有 10×4 KiB=40 KiB10 \times 4\text{ KiB} = 40\text{ KiB}10×4 KiB=40 KiB。为了突破这一寻址天花板，现代文件系统必须引入间接索引块（Indirect Blocks），通过分层的树状指针结构来扩展对大容量文件的描述能力。

inode（Index Node，索引节点）是文件系统中最核心的文件管理结构体。在现代 Unix 体系中，目录中记录的只是文件名与对应 inode 编号的映射关系，而文件的所有核心元数据——包括文件类型（普通文件、目录、符号链接等）、文件真实字节大小、访问权限掩码、拥有者 UID、所属组 GID、硬链接计数、各类时间戳以及数据块索引指针——全部保存在对应的 inode 实例中。

例如，若 inode 9 中记录的物理块指针数组为 [61, 44, 15]，这表明该文件逻辑上的第 0、1、2 个块，分别保存在底层的第 61、44 和 15 号物理数据块中。在此，“逻辑块号”描述的是文件内部从 0 起算的连续数据段，而“设备块号”描述的是物理存储硬件上的实际落盘位置。

当应用程序给出文件字节偏移量 ooo 时，文件系统如何确定该字节落在哪个物理块呢？设逻辑块大小为 CCC，计算公式如下：

q=⌊oC⌋,r=o mod Cq = \left\lfloor \frac{o}{C} \right\rfloor, \qquad r = o \bmod C q=⌊Co​⌋,r=omodC

其中：

  • qqq 为逻辑块索引（第几个数据块，从 0 开始）；
  • rrr 为块内字节偏移量（在该数据块内的第几个字节，范围为 0≤r<C0 \le r < C0≤r<C）。

系统首先在 inode 中查出第 qqq 个逻辑块所对应的物理块号 bbb，再驱动硬件读取物理块 bbb 中的第 rrr 个字节。在此过程中，系统还需检查该偏移量是否超出了文件的真实长度限制、该逻辑块是否已被分配，以及底层 I/O 是否触发异常。

文件长度与分配空间分别计数。在本节按完整块分配的例子中，5000 B 的普通文件需要两个 4096 B 块，共分配 8192 B。第一块保存前 4096 B，第二块保存剩下的 5000−4096=9045000-4096=9045000−4096=904 B。

第二块剩余的 3192 B 属于内部碎片。文件长度仍为 5000 B，应用不会因为分配了两块就多读出这些尾部空间。

此外，对于使用 lseek 跳过大片空白区域直接写入形成的稀疏文件（Sparse File），中间未曾写入过的逻辑块在 inode 中会被标记为 NULL 指针，并不占用实际的物理磁盘块；当应用程序尝试读取这些空白区域时，系统会自动填充全 0 字节返回。

  1. 直接指针（Direct Pointers）：inode 直接保存数据块编号，对应右侧 Data 块。这条路径无需先读取额外的间接索引块，适合索引范围内的小文件。

inode 编号

在存储架构的物理实现中，inode 表（Inode Table）通常表现为一个连续的定长结构体数组。只要知道了 inode 表在磁盘上的起始物理偏移地址，以及单个 inode 结构体的固定字节长度 SSS（例如常见为 128 B 或 256 B），就可以根据给定的 inode 编号直接通过简单的代数公式计算出其在磁盘上的精确物理字节位置。

假设 inode 编号从 0 开始计数，每条记录占用 128 B，则编号为 9 的 inode 距离 inode 表起点的相对偏移量即为：

Offset=9×128 B=1152 B\text{Offset} = 9 \times 128\text{ B} = 1152\text{ B} Offset=9×128 B=1152 B

这种数组查找模型高度抽象为映射函数：INODE_NUMBER_TO_INODE(num) → inode_table[num]。操作系统同时需要借助前面介绍的 inode 位图来追踪记录哪些 inode 编号已被分配使用。

对于预先分配固定 inode 数量的文件系统，可创建对象的数量也受 inode 资源限制。大量小文件乃至 0 字节文件都需要 inode，因此即使还剩数十或数百 GiB 数据空间，也可能因 inode 耗尽而报告“No space left on device”。这一限制取决于具体文件系统，不能从块空间剩余量单独判断是否还能创建文件。

  • df -i：检查全系统 inode 编号资源的使用率与剩余数量。

inode 的具体字节大小由文件系统的格式化参数决定。以 Linux ext4 为例，其超级块记录了 inode 的大小，生产环境中通常被格式化为 256 B，以容纳扩展属性、纳秒级时间戳以及内联数据特性。ext4 inode 文档详细列举了各字段的物理排布细节。

解答：

寻址算法如下：设每个块组分配固定数量 GGG 条 inode，则对于给定的全局编号 numnumnum：

  1. 所属块组号：group_idx=⌊num/G⌋\text{group\_idx} = \lfloor num / G \rfloorgroup_idx=⌊num/G⌋；
  2. 组内局部编号：local_idx=num mod G\text{local\_idx} = num \bmod Glocal_idx=nummodG。

Address=GroupInodeTableBase+local_idx×S\text{Address} = \text{GroupInodeTableBase} + \text{local\_idx} \times S Address=GroupInodeTableBase+local_idx×S

每个块组内部均拥有独立的局部 inode 位图，负责自治管理本组内的可用 inode 编号。

目录查找

在前述的底层机制中，系统已经具备了通过 inode 编号和字节偏移量访问任意文件的能力。然而人类用户只能记忆并理解具有语义的字符串名称（如 programs、notes.txt）。目录（Directory）的诞生正是为了建立字符串名称与内部 inode 编号之间的纽带。

在 Unix 哲学中，“一切皆文件”，目录本身也是一个文件。它的特殊之处仅仅在于其 inode 元数据中的文件类型被标记为 DIRECTORY。目录文件的数据块中存储的不再是普通文本或二进制数据，而是由一系列目录项（Directory Entry，简称 dentry）组成的列表。每个目录项最核心的内容，就是一个名称字符串以及其对应的目标 inode 编号。

文件名到 inode 号的对应表可以保存在哪里？系统怎样用普通块存储机制读取目录内容？

解答：

映射关系直接作为普通数据存放在目录自身占用的数据块中。当系统需要读取目录内容时，像读取普通文件一样根据目录的 inode 找到其对应的数据块，将磁盘块数据载入内核内存，然后按照预定的目录项格式（如定长或变长结构体）逐字节解码出其中的条目，比对每个条目中的字符串与目标文件名；一旦匹配成功，便提取出该条目中记录的 inode 编号。

上图清晰地展示了某单一目录内部的数据块结构：

  • 在该目录所拥有的数据块中，整齐记录着多条映射条目：例如字符串名称 helloworld.txt 映射到 inode 编号 12，而名称 cse2021.md 映射到 inode 编号 73。
  • 当系统在该目录下查找文件 cse2021.md 时，内核首先校验当前目录 inode 的操作权限，接着调取其数据块展开扫描，依次比对各条目的名称字符串。
  • 检索命中后，系统提取出目标 inode 编号 73，随后便可以查询 inode 表以获取该文件真实的数据块指针，进而展开实体内容的读写。
  • 文件名保存在父目录的目录项中，同一 inode 可以通过不同名称访问。新增硬链接会增加目录项和链接计数，内容仍是同一份，因此需要区分内容不变与元数据变化。

Unix V6 的文件名最多占 14 B，这个限制由什么布局决定？按字节计数有什么含义？目录中有很多文件时，逐项扫描会出现什么问题？

解答：

  1. 历史限制起因：Unix V6 采用了结构极简的定长目录项设计，每个目录项强制固定为 16 个字节。其中前 2 个字节用来存储 16 位的 inode 编号，剩下的 16−2=1416 - 2 = 1416−2=14 个字节全部留给文件名，因此文件名物理上限严格被锁死在 14 个字节以内。
  2. 按字节计数的含义：长度限制指的是字符编码后的物理字节数（Bytes），而非字符视觉个数。在 ASCII 编码下 1 个英文字母占 1 字节；但若在现代 UTF-8 编码下，一个标准汉字通常占用 3 个字节。若在 14 字节限制下，4 个汉字占用 12 字节尚可存下，而 5 个汉字将占用 15 字节，就会发生溢出截断。
  3. 大目录的查找成本：线性目录中，最坏需要比较 N 条目录项，成本为 O(N)O(N)O(N)。数万或数百万个名称会增加读取与字符串比较。ext4 可以使用 HTree 按名称哈希定位有关目录块，再查找匹配项，减少扫描范围；实际成本仍受树结构、哈希冲突、缓存和磁盘访问影响，不能统一视为严格 O(1)O(1)O(1)。

目录大小

目录文件大小主要取决于目录项数量、名称长度、索引和空间分配方式，子文件内容不会直接计入父目录的字节大小。它因此与目录树下全部文件占用的空间是不同统计量。

一个目录里有十个 1 GiB 文件，另一个目录里有六千个空文件，哪个目录自身可能更大？文件名变长会怎样影响目录？

解答：

  1. 目录大小对比：包含六千个空文件的目录，其自身占用的磁盘空间会显著大于包含十个 1 GiB 文件的目录。原因在于，那十个 1 GiB 大文件的巨额内容数据存放在各自独立的数据块中，父目录仅需保存 10 条微小的目录项记录；而六千个空文件无论其内容多小，都必须在父目录内创建 6000 个目录项条目，这必须消耗父目录的多个数据块来容纳。
  2. 变长名称的影响：在现代变长目录项格式下，文件名越长，单条目录项所占用的实际字节数就越多。这会导致单个目录数据块所能容纳的条目数减少，迫使目录文件提前分配更多的数据块来承载目录项，使得目录文件自身的体积膨胀。

在现代 Linux ext4 文件系统中，单个文件名的长度上限通常为 255 个字节。需要牢记的是，该限制依然是以 UTF-8 物理字节计算的。

目录转储

为了透彻理解目录项在磁盘底层的真实存储格式，我们需要借助十六进制和字节序的基础工具。

十六进制用 0–9 和 a–f 表示数字，前缀 0x 标明这种记法。两位十六进制数对应一个 8 bit 字节。

路径解析

在文件系统的树状组织中，路径是由斜杠 / 分隔的一系列目录组件名称构成的序列。

  • /：单独出现于路径开头时，代表整个文件系统的根目录（Root Directory）。
  • .：代表当前目录自身。
  • ..：代表当前目录的父目录。
  • 绝对路径：必须以 / 开头，其解析过程无条件从根目录作为起点向下展开（如 /programs/pong.c）。
  • 相对路径：不以 / 开头，其解析过程默认以当前调用进程的当前工作目录（Current Working Directory，CWD）作为基准起点展开。

在系统初始化时，文件系统标准明确规定了根目录的入口坐标。例如在 Unix 经典设计中根目录的 inode 编号被固定为 1，而在 Linux ext4 中根目录 inode 编号通常被标准化为 2。无论从磁盘的何处发起解析，开头的 / 均会引导内核直接定位到该固定的根目录入口。

管理名称

文件已经打开后，程序通过打开记录访问对象。此时另一个程序给它改名，改变的是目录中的名称关系。硬链接、重命名和符号链接都围绕名称展开，但它们保存的内容不同：硬链接直接指向 inode，符号链接保存一段需要再次解析的路径。

硬链接

硬链接（Hard Link）是在目录中新增一个指向已有 inode 的名称。它继续使用原文件对象，不复制内容，也不建立一种需要逐次转发的新文件类型。多个名称都可以用于访问同一文件。

调用 link("a.txt", "b.txt") 后，目录新增 b.txt，它与 a.txt 指向同一个 inode，没有复制文件内容。通过任一名称修改的都是同一对象；读取何时看到这些修改，还需遵守相关缓存和并发接口规则。

为了安全管理这种多对一的映射，inode 内部设立了一个关键计数器——链接计数（Link Count，在代码中为 i_nlink）：

  • 每次针对该 inode 成功创建一个新的硬链接，其 i_nlink 计数便加 1；
  • 当用户调用 unlink（即通常意义下的删除命令 rm）移除某个名称时，系统仅从目录中抹去该目录项，并将对应 inode 的 i_nlink 计数减 1；
  • 只有当 i_nlink 计数减为 0，并且当前系统中没有任何正在运行的进程保持着对该文件的打开句柄（Open File Descriptor）时，操作系统才会真正释放该 inode 及其占用的全部物理数据块。

硬链接通常有以下限制：

  1. 通常不能跨文件系统创建硬链接：目录项中的 inode 号由本文件系统解释，另一个文件系统可能有相同编号但对应不同对象。跨文件系统引用通常使用路径和符号链接等机制。
  2. 通常禁止普通用户为目录创建硬链接：这是一项为了保护文件系统免遭逻辑死锁的根本性设计限制。

目录硬链接形成环后，删除根目录到 a 的入口，inode 25 的链接计数仍为 1，会发生什么？为什么删除目录前需要处理其中的文件和子目录？

解答：

  1. 环与空间泄漏：任意目录硬链接可能让目录结构形成环。图中子目录通过链接指回祖先 inode 25，移除从根目录进入 a 的入口后，环内对象仍相互引用，计数无法归零，普通根路径却无法到达它们。只依赖引用计数时，这部分空间可能无法回收；递归遍历也需要检测环，避免无限循环。
  2. 预先清空目录的必要性：基于上述原则，操作系统系统调用 rmdir 强制要求目标目录必须处于空目录状态方可删除；高层删除命令必须先自底向上递归解绑所有子项，确保整棵子树上的所有引用计数能按拓扑顺序正确降为零。

图中的入口删除后，inode 25 仍被环内链接引用，计数为 1。可达性与引用计数因此不再一致：对象无法从根目录访问，却仍不能仅按零计数规则回收。这说明目录环需要额外限制或检测。

在标准 Unix 规范中，一个普通目录的初始默认链接计数通常为 2 + 直接子目录数量：

  • 父目录中指向它的目录项提供第 1 个引用；
  • 目录内部自带的自引用 . 项提供第 2 个引用；
  • 随后其下每新建一个子目录，子目录内部的 .. 项又会向父目录反向贡献一个链接计数。

重命名

文件重命名（Rename）常用于发布新版本。程序可以先将新内容写到临时文件，例如 .a.txt.swp，确认内容保存后，再用 rename 替换正式名称 a.txt。编辑器、构建工具等可以采用这类影子写入方式；实际文件名与保存流程因程序而异。

在支持原子替换的同一文件系统中，其他进程通过目标路径查找时，应取得替换前或替换后的对象，不应因替换过程看到目标名称暂时缺失。已经打开的旧描述符可以继续访问旧对象。故障后是否保留新名称，还要结合数据同步、目录同步和文件系统恢复保证判断。

保存时按下面的顺序替换正式文件名。

  1. UNLINK(to_name)
  2. LINK(from_name, to_name)
  3. UNLINK(from_name)

如果机器在第 1、2 步之间崩溃，原路径和临时文件可能各处于什么状态？需要什么保证才能让名称替换呈现完整结果？

解答：

如果机器在第 1 步完成、第 2 步尚未执行的夹缝中遭遇断电崩溃，那么正式的目标名称 to_name 已经在磁盘目录项中被永久抹除，而临时文件 from_name 尚未建立新的链接。重启之后，用户会惊恐地发现正式文件凭空失踪了，若此时临时文件所在目录未被正确同步或被垃圾清理，用户原有的宝贵数据就会发生不可逆的丢失。

把替换直接拆为多次普通名称操作，会暴露中间状态。rename 由内核协调相关目录修改，提供相应的运行时原子性；崩溃恢复还需要文件系统的日志或其他机制，并按要求同步目录。目录项与链接计数的恢复过程见改名故障。

a.txt 与 b.txt 起初是两份不同内容，将 a.txt 移到 b.txt 并覆盖目标。若先删除 b.txt，尚未建立新名称就发生故障，重启后看到了什么？完整旧状态和完整新状态分别是什么？

解答：

  1. 完整旧状态：系统中同时完好存在两个独立文件——a.txt 与 b.txt 分别保存着各自旧有的独立内容。
  2. 完整新状态：a.txt 的名称消失，仅保留 b.txt，但其内部的内容已经完整替换为原 a.txt 的内容。
  3. 中途崩溃状态：若先删除了目标 b.txt，在尚未完成新绑定时断电，重启后系统仅剩下 a.txt，而目标文件 b.txt 连同其原有内容已丢失。为了防范此风险，必须依赖内核级原子更新与日志回滚技术。

符号链接

符号链接（Symbolic Link，也称软链接）有自己的 inode，类型为 LNK，内容是目标路径字符串。路径可以保存在专用数据区，也可能按文件系统格式内联到 inode；解析时再根据这段字符串寻找目标。因此，链接对象和目标对象可以有各自独立的生命周期。

当用户程序访问一个符号链接时，内核检测到其文件类型为符号链接，会自动提取出内部保存的路径文本，并将该路径作为新的目标重新发起一轮路径解析。

  • 绝对目标路径：若软链接内部记录的是绝对路径（如 /etc/passwd），系统直接从全局根目录重新展开检索；
  • 相对目标路径：若记录的是相对路径（如 ../data/a.txt），系统将以该符号链接所在的物理目录作为基准起点展开次级检索。

  • 悬空链接（Dangling Link）：正是由于这种解耦设计，如果用户主动删除了原始的目标文件 myfile.txt，符号链接本身并不会随之消失，但其内部记录的路径已经失效，形成所谓的断链或悬空链接；如果后续在同一路径下重新创建了一个同名的新文件，该符号链接便会自动“复活”并指向新文件。
  • 跨界优势：由于符号链接仅仅是字符串路径的转发，因此它可以直接跨越不同的物理分区和挂载卷，也可以安全地指向目录。

执行 ln -s /tmp/abc s-link 后，ls -l 显示链接大小为 8。8 表示什么？目标文件暂时不存在时，readlink s-link 与 cat s-link 各返回什么？随后创建目标，原链接能否使用？

解答：

  1. 大小为 8 的含义：数字 8 代表该软链接自身所存储的目标路径字符串 /tmp/abc 占用的实际物理字节数（包含斜杠与字符共计 1+3+1+3=81 + 3 + 1 + 3 = 81+3+1+3=8 字节）。
  2. 不存在时的命令表现：
    • readlink s-link：专门用于读取软链接本身内容的系统工具，它不会去跟踪目标，因此会稳定原样打印出字符串 /tmp/abc。
    • cat s-link：常规文件查看工具，会主动请求内核跟随软链接解析目标；由于目标文件尚未创建，内核在解析终点返回错误，cat 会输出错误提示：No such file or directory。
  3. 延迟创建后的可用性：随后一旦在 /tmp/abc 处新建文件并写入数据，原软链接无需做任何改动即可立即正常解析并成功读取该内容。

此外在现代文件系统（如 ext4）中还存在一项经典的存储性能优化——内联快速符号链接（Fast Symlink）：当目标路径字符串非常短（例如在 ext4 中小于 60 字节）时，系统为了节省空间，会直接将这串路径文字塞进 inode 内部原本存放数据块指针的空闲数组空间（i_block）中，从而免去了在外部额外分配一个物理数据块的开销。

路径上下文

终端 Shell 是用户与操作系统交互的命令解析器环境。用户通过 cd 命令改变当前工作目录，通过 pwd 查看当前所在路径。然而当路径中穿插了符号链接时，就会产生一个经典的系统工程问题：逻辑路径与物理路径的二义性。

  • 逻辑路径（Logical Path）：记录用户在 Shell 命令行中按部就班键入的由各级名称拼接而成的语义路径，极力保留用户穿行过的符号链接名称。
  • 物理路径（Physical Path）：不采用符号链接的修饰名称，严格沿着文件系统底层真实的物理目录拓扑结构解析出来的真实根目录链。

根目录中的 /CSE-web 指向 /Scholarly/programs/www。从根目录开始，使用 bash 默认的逻辑路径处理，先执行 cd CSE-web，再执行 cd ..，当前目录是什么？若使用 cd -P ..，结果又是什么？

解答：

  1. 默认逻辑路径处理：bash 默认遵循逻辑路径上下文，在执行 cd CSE-web 后，Shell 环境变量中记录的逻辑路径为 /CSE-web。此时执行 cd ..，Shell 直接从逻辑字符串末端切除最后一部分，于是当前目录退回至系统的全局根目录 /。
  2. 物理路径处理（-P）：cd -P .. 按解析符号链接后的目录层次处理父目录。本例中真实目录为 /Scholarly/programs/www，其父目录是 /Scholarly/programs，因此进入该位置。逻辑与物理路径处理是 Shell 提供的两种规则。
工作模式与相关指令 经过软链接进入后显示的位置 随后执行退回父目录操作后的落脚点
逻辑路径模式（默认 pwd, 逻辑 cd） /CSE-web /（直接在逻辑字面上剪除一层）
物理路径模式（pwd -P, cd -P ..） /Scholarly/programs/www /Scholarly/programs（沿着物理目录真实的 .. 回溯）

为了支撑这套双轨机制，Shell 环境在底层长期默默维系着两个环境变量：

  • PWD：存储着当前激活的逻辑路径字符串；
  • OLDPWD：存储着上一次切换前的工作目录字符串，供用户随时使用便捷命令 cd - 在两个历史工作区间之间往返切换。

管理访问

文件属性

inode 除了记录内容位置，还保存所有者、权限模式和时间等属性。先看用于所有权与权限检查的字段：

  • 所有权标识：UID（User ID）标定文件法定拥有者的数字用户编号；GID（Group ID）标定文件所属的用户组编号。
  • 模式属性（Mode）：经典 16 位模式值中，高 4 位表示普通文件、目录、设备、套接字或符号链接等类型，低 9 位表示三组读写执行权限，中间另有 setuid、setgid 和 sticky 等特殊位。

经典 Unix 权限模型分别为文件所有者（User/Owner）、所属组（Group）和其他用户（Others）设置权限。每组由读（r=4）、写（w=2）、执行（x=1）三个位组成，以八进制表示。例如 755 的含义是：

  • 所有者拥有权限 4+2+1=74 + 2 + 1 = 74+2+1=7（可读、可写、可执行）；
  • 所属组成员与外部其他访客均拥有权限 4+0+1=54 + 0 + 1 = 54+0+1=5（可读、可执行，不可修改写入）。

相同权限位用于普通文件和目录时，含义不同：

  • 对普通文件：r 允许读取内部字节；w 允许修改或截断内容；x 允许将其交给操作系统作为二进制机器码或脚本程序启动执行。
  • 对目录：r 允许读取目录项名称，x 允许搜索目录并沿名称访问子项；创建、删除或重命名子项通常还需要目录的 w 与 x，并受 sticky、ACL 等规则约束。普通权限检查下，仅有 r 可以列出名称，但缺少 x 时无法正常进入目录或通过其中的名称访问文件。

时间属性

经典 Unix 文件属性包含三个常用时间戳：

时间戳字段 专有术语全称 核心追踪职责 系统典型的触发变更场景
atime Access Time 记录文件数据内容最近一次被主动读取的时间 程序调用 read 读取文件内容时按挂载策略触发刷新
mtime Modification Time 记录文件底层数据内容最近一次被修改写入的时间 程序调用 write 写入、追加数据或执行文件内容截断（truncate）时刷新
ctime Change Time 记录该文件自身的 inode 元数据状态最近一次发生变更的时间 执行 chmod 改权限、chown 改归属、增加硬链接，或修改文件内容导致 inode 属性变动时刷新

针对这三组时间，工程中存在一个常见的初学者误区：许多人常将 ctime 误解为文件的创建时间（Creation Time）。必须说明：在经典 Unix 体系中，ctime 专门指代状态变更时间（Change Time），任何对文件权限、所有权或链接计数的微调都会更新 ctime。如果底层文件系统需要准确记录真实的“出生创建时间”，必须依赖现代文件系统单独引入的扩展特性（如 ext4 中的 crtime 或 btime 字段）。

调用 open 成功仅仅代表系统完成了一次定位并创建了内核句柄，只有随后真正产生实质性的数据读取时，系统才会依照策略评估是否要重写 atime。即使用户仅以只读方式打开文件，内核也有可能在底层主动向该 inode 发起访问时间刷新。stat 手册给出了这些属性字段在系统结构体中的严格定义。

访问时间

读取内容也可能带来元数据写入：如果访问需要更新 atime，inode 会被标记为已修改，之后可能写回磁盘。频繁读取静态网页时，这些更新会增加写入量。是否每次更新、何时持久化，取决于挂载策略与缓存，不能把每次 read 都等同于一次同步磁盘写入。

系统通过挂载选项调整时间属性的更新与保存策略：

挂载调优策略 底层对于文件访问时间 (atime) 的实际处理哲学与机制
strictatime 按相应访问语义更新 atime，实际写回仍由持久化和缓存规则决定
noatime 禁止因普通文件访问更新 atime，减少相应元数据修改，应用不能再依赖它跟踪这些访问
relatime 现代 Linux 的默认智能折中策略：仅在旧的 atime 已经早于当前的 mtime/ctime，或者当前距离上一次记录更新已超过一定时间（如 24 小时）时，才触发一次 atime 刷新
lazytime 将 atime、mtime、ctime 更新暂留内存，在同步、其他 inode 修改、回收或达到规定时间等条件下写回

只读操作为什么也可能产生磁盘写入？把一万次访问时间更新合并后，还要考虑什么？

解答：

  1. 只读诱发写入的根源：应用程序调用 read 读取文件内容本身虽不修改数据块，但会触发内核将 inode 结构体内部的 atime 标记为“脏（Dirty）”。内核后台的脏页刷盘线程（Flusher Threads）稍后必须将这个变动过的 inode 重新写回磁盘介质，从而在底层引发出乎意料的物理写 I/O。
  2. 合并更新可以减少元数据写入，但需要说明故障后允许丢失哪些时间属性更新。noatime 不再记录相应访问时间，lazytime 则延后持久化，并按同步、回收和时间等规则保存。它们不能代替逐次访问审计日志。

打开记录

先用两个独立的 open 理解打开记录。进程 A 打开文件，读了 10 字节，它的游标移到 10。进程 B 独立打开同一文件，它的游标仍从 0 开始。两者指向同一个 inode，却有各自的打开记录。

  2. fork 派生，共享游标：
    • 随后，进程 B 调用了 fork() 派生出子进程 C。根据 POSIX 标准规范，子进程 C 会无损继承父进程 B 的整个文件描述符表。
    • 此时，子进程 C 中的 fd 3 将与父进程 B 中的 fd 3 共同无缝指向内核中同一条打开记录 116！
    • 该记录内部的引用计数递增为 2。这意味着父子两进程此时共享同一个底层读写游标！如果父进程 B 读取了 10 个字节，将游标推进到了 10；子进程 C 接着读取时，将从第 10 个字节开始接力向下读取，这一机制构成了 Unix 管道与多进程标准 I/O 协同的基石。fork 手册对此做出了硬性规定。

记录 115 与 116 的游标最初都为 0。按 A 读 10 B、B 读 10 B、C 读 5 B 的顺序执行，忽略错误与文件末尾，游标分别怎样变化？

解答：

  1. 初始状态：打开记录 115 的游标为 0；打开记录 116 的游标为 0。
  2. A 读 10 B：A 关联的打开记录 115 游标单向推进至 10；打开记录 116 全程不动，依然保持为 0。
  3. B 读 10 B：B 读取并推进其关联的打开记录 116，游标从 0 推进至 10。
  4. C 读 5 B：由于子进程 C 与父进程 B 共享打开记录 116，C 的读取操作直接基于该记录当前的游标 10 开始进行，读取 5 字节后将打开记录 116 的游标推进至 15。
  5. 最终结果：打开记录 115（A）的游标停留在 10；打开记录 116（由 B 与 C 共享）的游标最终停留在 15。同一进程内部使用 dup() 或 dup2() 复制描述符，亦会产生与此完全相同的共享游标效果。

必须将系统打开记录的“打开引用计数”与 Inode 结构体内部的“硬链接计数（i_nlink）”严格区分：

  • close() 的作用仅仅是递减系统打开记录的引用计数；
  • unlink() 的作用仅仅是移除目录项并递减 inode 的硬链接计数。
    只有当某文件的硬链接计数归零、且系统内指向该文件的全部打开记录也随进程退出或 close 释放时，文件系统才会启动底层扇区的空间回收。

如果多个并发进程需要向同一个共享日志文件末尾追写数据，不能依赖在用户态执行 lseek 后再调用 write，因为这非原子的两步操作极易引发严重的竞态条件；必须在打开时赋予 O_APPEND 标志，由操作系统内核在底层保证每一次写入前游标原子性地自动跃迁至物理末尾。

完成读写

读取文件

现在我们将前文所有孤立的技术机制进行全景贯通，以一个经典路径 /foo/bar 的打开与读取为例，还原 Linux 内核在执行用户态调用时的全生命周期行为。假设 foo 是中间目录，bar 是普通文件，程序以只读方式打开：

  1. 确定根起点：内核通过当前进程的根命名空间与挂载点记录锁定文件系统根目录，读取其 inode（如 inode 2）并加载其首个数据块。
  2. 逐级目录解析：
    • 在根目录数据块中扫描匹配字符串 "foo"，提取其对应的 inode 编号；
    • 校验当前进程是否具备对根目录的 x（检索）权限；权限通过后，读取 foo 的 inode；
    • 确认为目录类型后，读取 foo 的目录数据块，在其中扫描匹配目标文件名 "bar"，取得其实际的 inode 编号。
  3. 元数据鉴权与句柄生成：
    • 提取文件 bar 的 inode 元数据，检查文件的类型及本进程的只读权限；
    • 在内核系统级打开文件表中开辟一个空闲的打开文件记录（Open File Description），将文件内部游标（Offset）重置为 0，并将操作模式打上只读标志；
    • 在当前进程的文件描述符表中挑选编号最小的可用整数（如 3），建立从 fd 3 指向该系统级打开记录的指针，并将 3 作为系统调用返回值交给用户程序。
  4. 执行实际数据 I/O：
    • 应用程序后续调用 read(3, buf, count)；
    • 内核直接通过 fd 3 逆向寻回对应的打开记录，读取当前记录中的游标位置，并关联到文件的底层 inode；
    • 结合文件系统的块尺寸，利用取模和除法换算得出目标逻辑块号 qqq 与块内偏移 rrr；
    • 查阅 inode 中的多级指针表，将逻辑块号 qqq 转换为底层物理设备块号 bbb；
    • 检查该块的数据是否已经缓存在内存内核页缓存（Page Cache）中：若已命中缓存，则直接利用 CPU 将缓存字节拷贝至用户态内存 buf 中；若发生缓存缺失（Cache Miss），则向通用块层发起物理 I/O 请求，驱动机械硬盘或 SSD 读出扇区填补缓存，再行拷贝交付；
    • 本次实际读取的字节数累加至系统打开记录的游标字段中，以便为下一次顺序读取做好准备。

从性能角度审视，传统机械硬盘由于存在机械磁臂移动的寻道时间（Seek Time）与盘片高速自转的旋转延迟（Rotational Latency），频繁在磁盘头部的元数据区域与后部的数据区域之间往返跳跃会导致严重的 I/O 性能滑坡；固态硬盘（SSD）虽消除了机械运动，但由于其内部闪存颗粒独特的以页（Page）为单位读写、以块（Block）为单位擦除的物理特性，离散的小碎块读写同样会加剧写放大并降低总线带宽效率。因此，操作系统的页缓存机制、智能顺序预读算法（Readahead）以及局部块组物理布局优化，承担着弥补软硬件速度鸿沟的重任。

创建文件

创建 /foo/bar 这样的新文件，需要更新分配记录、inode 与父目录项，可能还要扩展父目录的数据块。这些修改共同建立“名称能够找到新对象”的状态；若要求跨故障可靠保存，还需要相应的持久化与恢复协议：

涉及的物理存储位置 操作系统必须严格协同完成的底层核心动作
父目录 foo 遍历解析出 foo 的 inode，校验当前进程对其是否拥有 w（创建）与 x（进入）权限，并确认同名文件 bar 尚不存在
inode 空闲位图 扫描搜索出一个值为 0 的空闲 bit，通过原子操作将其置为 1，正式锁定该新 inode 编号的分配合法权
inode 表对应槽位 将该新 inode 结构体初始化：文件长度清零、硬链接数设为 1、标记普通文件类型、写入当前进程的 UID/GID、配置初始权限掩码，并刷入纳秒级时间戳
foo 的目录数据块 在父目录的数据块中搜寻空闲槽位，写入一条崭新的目录项条目：建立从字符串 "bar" 到新分配 inode 编号的物理映射
foo 的自身 inode 更新父目录自身的元数据：递增其修改时间（mtime）与状态变更时间（ctime），若为容纳新条目导致目录扩容，还需同步更新父目录的大小字段

在初始阶段，新创建的空文件其真实长度为 0，并且尚未挂接任何实际的内容数据块；其初始硬链接计数为 1。如果父目录原先的数据块空间已经完全饱和、无法再塞入哪怕一条新的目录项，系统还必须在底层数据块位图中另外申请一个新的数据块挂接到父目录下，由此引发一系列连锁的块索引分配。

当应用程序随后向新文件 bar 写入第一批数据时，系统才正式触发实体数据块的分配流程：占用数据块位图、将数据写入物理扇区、将物理块号填入新 inode 的直接指针槽位中，并重新计算文件长度。

整块修改

下面按块设备模型分析局部修改：文件系统将数据组织为块，设备接口按逻辑扇区等单位读写。只修改块中的少量字节时，通常仍要保留同块其他内容，再按接口单位写回。传输单位、介质内部写入单位和断电原子性是不同概念，不能一概视为相同。

假设文件系统块为 4 KiB，一条 inode 为 256 B，一个块可容纳 16 条记录。修改其中一条时，需要保留另外 15 条，形成读改写（Read-Modify-Write，RMW）过程；若原块已在缓存中，可以直接使用缓存，无需再读设备：

  1. 读入内存：系统必须首先将包含该 inode 的整整 4 KiB 物理块从磁盘介质完整读入内核的内存缓冲区；
  2. 局部修改：在缓冲区中更新目标 inode 的相应字段，保留同块另外 15 条记录的内容。
  3. 整块写回：最后，再将这个已经包含新变动的完整 4 KiB 内存块重新写入磁盘介质。

位图也需要保留所在块的其他位。以 4 KiB 位图块为例，先取得原块或已有缓存，再通过按位或等操作改变目标 bit，随后按回写规则保存该块；它是否对应一个 4 KiB 设备扇区，取决于块与设备布局。

为什么新 inode 的初始化也可能先读后写？把空闲状态直接放在每条 inode 里，与单独位图相比，会怎样影响查找？

解答：

  1. 保留相邻记录：4 KiB 块可容纳 16 条 256 B 的 inode。更新其中一条前，需要取得原块或缓存，保留另外 15 条记录，再修改目标部分并写回。新 inode 的初始化也不能覆盖同块其他文件的元数据。
  2. 独立位图与内嵌标记的查找成本：
    • 独立位图方案：1 个 4 KiB 块可表示 4096×8=32,7684096 \times 8 = 32{,}7684096×8=32,768 个对象的分配状态，状态集中，便于按 64 bit 字批量扫描。命中缓存后可以减少设备读取，但具体时间与 I/O 量仍取决于缓存和空位分布。
    • 内嵌标记方案：状态分散在较大的 inode 记录中，缺少其他索引时，寻找空位可能需要读取更多 inode 表块。若已有缓存、空闲链表或额外索引，也可以减少扫描，因此需要按具体分配器比较。

写入顺序

本节的 B、D、I 分别表示位图、数据、inode。可以先问一句具体问题：读者什么时候会把新块当成文件内容？答案是 inode 已经指向它之后。因此，在发布这个指针前写好内容，可以避免读者顺着新指针读到旧字节。

另一方面，分配器依据位图判断空间是否空闲。如果指针已经建立，位图却仍标为空闲，同一块还可能分给别人。下面三种顺序，正是分别检查这两项依赖。

最后用追加文件分析崩溃一致性（Crash Consistency）与写入顺序（Write Ordering）：多项管理信息分别写入时，中途断电会留下哪些组合？

假设应用程序向一个已存在的文件末尾执行追加写（Append）操作，导致文件被迫向磁盘申请并写入一个新的数据块。为了将这一变更持久化，系统在物理底层必须协同写入三份各居一方的关键信息：

  1. 数据块位图（Bitmap，BBB）：将新选中的物理块标记为已占用（0 变 1）；
  2. 数据块实体内容（Data Block，DDD）：将用户实际写入的字节流写入该物理块；
  3. inode 元数据（Inode，III）：更新 inode 中的文件大小，并将该新块的物理块号写入指针索引树中。

操作系统回写和设备缓存可能改变实际持久化先后，源代码调用顺序并不足以保证落盘顺序。下面先假定各步确实按列出的顺序保存，再逐个分析步骤间断电的结果。

下面三种追加顺序中，故障后分别可能留下什么？假设各步确实按列出的顺序持久保存，且已通过分配协调取得目标块。

A. 占用位图 (BBB) ⟶\longrightarrow⟶ 写入新内容 (DDD) ⟶\longrightarrow⟶ 更新 inode 指针与大小 (III)

B. 占用位图 (BBB) ⟶\longrightarrow⟶ 更新 inode 指针与大小 (III) ⟶\longrightarrow⟶ 写入新内容 (DDD)

C. 更新 inode 指针与大小 (III) ⟶\longrightarrow⟶ 占用位图 (BBB) ⟶\longrightarrow⟶ 写入新内容 (DDD)

解答：

  • 时序 A 的故障后果：
    • 第 1 步完成、第 2 步尚未执行时断电：新块已经标为占用，却尚未被 inode 引用，造成空间泄漏（Space Leak）。在本例的分配与追加假设下，原文件的可见内容范围尚未改变。
    • 若在第 2 步完成、第 3 步未做时崩溃：同样仅仅表现为空间泄漏，原文件依然保持安全完好。
    • 三步全部完成后，inode 才引用已经写好的新内容。这种顺序减少了发布未初始化数据的风险，但仍需处理空间泄漏，可由符合格式与恢复条件的 fsck 或其他机制检查修复。
  • 时序 B 的故障后果（严重的内容与安全问题）：
    • inode（III）更新后、新内容（DDD）尚未保存时断电：恢复后的文件已经引用新块，读取可能得到该块此前遗留的旧字节，具体内容取决于初始化与恢复规则。
    • 这不仅直接导致文件内容严重损坏，在多用户操作系统中更构成信息泄漏风险（例如一个普通用户的文件通过这种漏洞意外读到了上一个被删除的系统密码 shadow 文件留下的物理残片）。
  • 时序 C 的故障后果（元数据双重分配问题）：
    • 最先更新 inode（III），位图（BBB）尚未更新就断电：文件已引用目标块，但位图仍把它记为空闲。
    • 如果恢复未修复这个不一致，分配器可能把同一块交给第二个文件，形成双重分配（Double Allocation），一个文件的后续写入便可能覆盖另一个文件的数据。

这组例子说明，程序中的逻辑顺序需要通过同步与恢复协议落实为持久化顺序，才能限制故障后可能出现的状态。

文件系统通过写入顺序约束、缓存刷新或相应存储接口协调持久化，具体机制取决于设备。ext4、XFS 等还使用日志（Journaling）记录相关元数据修改，日志有效提交后再写回原位置，故障时依据提交状态恢复。日志可以批量组织操作，数据与元数据的保护范围也因模式而异；完整过程见故障原子性。

另一种索引

FAT

前面用 inode 保存文件属性和块索引。课件还介绍了 FAT（File Allocation Table，文件分配表），可以用它检验自己是否理解“逻辑文件怎样由物理块组成”。

FAT 为存储单元保存一个表项，表项给出文件的下一个单元编号，或标记链已结束。设文件占用的单元依次为 4、9、2，目录项保存起点 4，FAT[4] 指向 9，FAT[9] 指向 2，FAT[2] 标记结束。读取时沿链取得内容，文件的逻辑顺序由这些链接决定，与编号大小无关。

追加内容时，可以分配一个新单元，把旧链尾改为指向它，再将新单元标为结束。查找文件中间位置时，则需要确定对应的链上节点。FAT 表常被缓存，以减少反复查询表项的设备访问。

问题 inode 索引 FAT 链
文件从哪里开始 目录项给出 inode 号 目录项给出起始单元
后续内容在哪里 从 inode 的块映射查找 沿 FAT 表中的链接查找
怎样定位中间位置 按逻辑块号查索引 沿链找到相应位置，缓存可加速
修改会涉及什么 数据、inode 索引与分配信息 数据、FAT 链与目录属性

两种布局都需要维护名称、内容位置与空闲空间，也都需要处理更新中途失败。学习重点是能沿各自的数据结构找到目标字节，而不是把某一种布局当作所有文件系统的共同格式。课件中的 FAT 图见 fs-api.pdf 第 7–8 个 PDF 页面。
