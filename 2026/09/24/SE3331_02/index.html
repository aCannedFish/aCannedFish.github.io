从磁盘到文件

大型网站要让文件服务器、数据库、缓存、应用服务器、负载均衡、CDN 和消息队列共同工作。这些分布式组件最终仍运行在单机的系统抽象之上。本讲先研究一个基于 inode 的单机文件系统：磁盘只认识编号的扇区，应用却希望操作有名字、可增长、断电后仍存在的文件。文件可以看成比原始内存更高层的字节序列抽象，名称和持久性是它区别于一段临时内存的重要性质。

磁盘驱动程序可简化为 Read(block_idx) 和 Write(block_idx, data)。其底层读写单位通常是扇区，常见大小有 512 B 或 4 KiB；一个文件却可能远大于一个扇区，还需要名称、权限、目录等功能。文件系统在硬件和应用之间建立多层映射，对上提供 open、read、write 等接口，对下把操作转换成块地址。

从接口形式也能看到抽象差别：设备接受“读第 bbb 个块”，文件系统对应用提供“读名称为 a.txt 的文件，从偏移 ooo 取 nnn 字节”。文件系统先用名称找到 inode，再把 ooo 换算成文件内块索引与块内位置，最终才得到设备块号。应用请求的长度可以跨越多个块，文件系统必须拼接结果。

Unix 文件系统接口还包括 append、seek、close、fsync，查询或修改元数据的 stat、chmod、chown，修改命名关系的 rename、link、unlink、symlink，以及目录和挂载相关的 mkdir、chdir、chroot、mount、umount。这些 API 分别解决数据访问、持久化、权限、命名和命名空间问题。

其中 seek 改变打开文件的当前偏移，stat 返回文件属性，chmod 和 chown 修改权限及所有者；fsync 则请求把相关待写数据和必要元数据推进到持久存储。link、unlink 改变名称与 inode 的绑定，rename 需要协调源和目标目录项。chroot 改变进程看到的路径根，mount 把另一个文件系统接入现有目录树。这些操作说明文件系统除保存字节外，还维护访问控制与全局命名关系。

从应用到磁盘的一次读取可拆成三步：应用把文件名和偏移交给文件系统；文件系统查元数据，算出要读的磁盘块；驱动程序再按块号从设备取回数据。课件的系统结构图还区分用户态应用、内核中的文件系统与磁盘驱动、以及硬件磁盘。文件系统负责解释“文件”，驱动负责执行设备 I/O。把这两个职责分开后，应用无需知道设备扇区号，文件系统也不必直接处理每种磁盘控制器的命令。

例如读取 report.txt 从第 5000 字节开始的 100 字节，驱动只会收到“读取某个块”这样的请求。文件系统必须先解析名字，找到文件元数据，再把文件内的第 5000 字节换算成块号和块内位置。后文将把这条链路逐层展开。

连续存储

一种朴素方案是每个文件占一段连续扇区，直接用起始扇区编号表示文件。它会遇到：

  • 磁盘上哪些位置空闲？每次全盘扫描代价太高。
  • 文件末尾后面的扇区已被别的文件使用时，扩容可能需要搬迁整个文件。
  • 扇区编号不能提供好记的字符串文件名。
  • 权限、所属用户等信息没有统一存放位置。

课件图中红色为已占用扇区，三个文件分别从 101、107、113 开始。文件 107 当前占用 107、108，后面的 109 至 112 可以用于追加；继续增长到 113 时就会撞上另一个文件。即使磁盘其他位置还有空闲扇区，要求文件必须连续也会迫使系统搬迁文件或改变布局。

起始扇区号还把“文件身份”绑在物理位置上：一旦移动文件，107 这个名字便失去原意。后续的 inode 层把文件身份与数据块位置分开，目录层再给文件提供人能记住的名称，逐层解决这里的限制。

inode 文件系统通过多层名字与地址映射逐步解决这些问题。

七层命名

课件以 Unix Version 6 的思路，把从磁盘到路径的映射分成七层。图中的层次是理解模型，并不表示所有现代文件系统都原样采用相同的磁盘布局。

层次 输入 输出 作用
1 块层 块号 磁盘块 找到物理存储单位
2 文件层 inode 与文件偏移 文件内容所在的块 组织可增长的文件
3 inode 编号层 inode 号 inode 给文件元数据稳定编号
4 文件名层 目录 inode 与文件名 子项 inode 号 提供人能阅读的名字
5 路径层 工作目录与相对路径 inode 号 逐级查找目录
6 绝对路径层 根目录与绝对路径 inode 号 统一所有用户的起点
7 符号链接层 链接中的路径字符串 目标路径 为另一条路径建立别名

“名字”在不同层有不同含义：物理块有块号，inode 有 inode 号，同一 inode 可以有多个目录项名字。理解每层输入和输出，才能看清一次路径查找到底做了哪些工作。

读这张课件图时可以从下往上看：驱动先识别磁盘块；inode 把一组块组织成文件；inode 号给元数据编号；目录把人类可读的名称连到 inode 号；路径把多个目录查找串起来；根目录为绝对路径提供共同起点；符号链接让一个路径再指向另一个路径。反过来，真正读取 /a/b.txt 时，系统从路径这一侧逐层向下转换，最终到达块号。图右侧标出的 machine-oriented names 与 user-oriented names，正是从机器编号过渡到用户名称的边界。

块与超级块

块层

文件系统通常按 块（block） 管理数据。块不小于设备的最小读写单位，可以由多个连续扇区组成。例如 1 KiB 扇区组成 4 KiB 文件系统块时，管理同样大小的文件所需记录的块号约减少到四分之一。块大一些能减少元数据与定位开销，但一个只占几字节的小文件也可能占用整块，造成块内碎片。因此块大小需要在效率与空间利用率之间权衡。

设磁盘有 4 TiB，文件系统采用 4 KiB 块，仅数据区就可能涉及约 2302^{30}230 个块。文件系统不可能每次访问都从头检查十亿个位置，必须长期保存块分配状态。若改用 1 KiB 块，块号数量会再增至四倍；若改用更大的块，小文件末块浪费的空间又会增加。块大小本质上同时决定索引粒度与分配粒度。

块号到内容的映射在教学模型中可写为 BLOCK_NUMBER_TO_BLOCK(b) = devices[b]。真正驱动程序还要把块号换算到设备地址，并处理 I/O 排队和错误。

超级块与位图

系统必须知道块大小、文件系统总规模、空闲块和 inode 的位置。超级块（superblock）保存这些文件系统级元数据；挂载时内核读取超级块，才能解释后续磁盘内容。课件示意的布局包含引导块、超级块、空闲块位图、inode 表与文件数据块。

空闲位图用每一位记录一个块是否可分配。一个字节可表示 8 个块，扫描位图可以寻找空闲块；分配时更新位，释放时清除相应状态。课件也提到超级块中的空闲块列表；这是不同实现或教学抽象中的组织方式，不必假定“列表”和“位图”在所有文件系统中同时以图示方式工作。

图把磁盘分成几类区域：引导块用于启动相关信息，超级块说明如何解释文件系统，位图记录块分配状态，后方的文件块保存内容。位图也占磁盘空间，但每个数据块只需要一个状态位；例如 2302^{30}230 个块的位图约占 230/8=1282^{30}/8=128230/8=128 MiB，远小于对应的数据容量。图没有指定 0、1 各表示空闲还是已用，实现中必须统一约定。

例如位图的第 42 位代表块 42。创建文件并分配此块时，分配器先确认它空闲，再修改位图并把块号记入文件索引。释放文件时顺序相反：先保证没有目录项或文件索引继续引用这个块，随后才能把它标为空闲。否则同一块可能被两个文件同时使用。超级块提供解释位图和 inode 表所需的总参数，位图负责逐块状态。

inode 与数据块

文件层

文件对应用表现为可随时间增长或缩小的字节序列。inode（index node）保存文件的元数据，例如大小、类型、权限、所有者、链接计数，以及定位数据块所需的索引。目录项中的文件名通常不在 inode 内。

读文件偏移 offset 时，先算出文件内逻辑块号 q=⌊offset/BLOCKSIZE⌋q=\lfloor offset / BLOCKSIZE\rfloorq=⌊offset/BLOCKSIZE⌋，再由 inode 的索引找到磁盘块号；块内字节位置是 r=offset mod BLOCKSIZEr=offset\bmod BLOCKSIZEr=offsetmodBLOCKSIZE。如果一次读取跨越块边界，就要重复定位后续逻辑块。文件长度与块号都必须检查，不能把未分配位置当作已有数据。

inode 内直接记录若干块号，能快速处理小文件；大文件还需要一级间接块、二级间接块甚至三级间接块。间接块不存普通文件内容，而是存下一层块号。若一个块能容纳 KKK 个块号，一项一级间接索引可覆盖 KKK 个数据块，一项二级间接索引可覆盖约 K2K^2K2 个数据块。代价是访问目标数据块前可能先读取一到数个索引块。

图左侧的长条是 inode，右侧的 Data 方框才存文件字节。最上方的直接指针从 inode 一步到 Data；浅橙色的一级间接指针先到一个索引块，再到 Data；粉色和深红色的指针分别多经过一层、两层索引块。箭头增加的是查找层数，换来的是可表示的文件大小。

假设块长 4 KiB、一个块号占 4 B，则一个间接块能存 K=4096/4=1024K=4096/4=1024K=4096/4=1024 个块号。一个一级间接入口可覆盖 4 MiB 数据；一个二级间接入口可覆盖 4 GiB 数据。这里只计算该入口能寻址的数据，不含 inode 中其他直接入口和其他元数据。读小文件常能直接定位；读落在二级间接范围内的数据，若相关索引块未缓存，就需要先读两级索引，再读最终数据块。

inode 编号层

inode 本身也要存放在磁盘上。课件的简单模型把 inode 表放在固定区域，inode 号就是表中的索引。文件系统还要记录哪些 inode 号已经使用，可通过空闲列表或位图实现。布局也可以不同，课程后续实验会讨论替代设计。

有了 inode 号，系统已经能定位文件内容，但普通用户不会愿意记住一个数字。因此下一步要在目录里保存“名字到 inode 号”的映射。

inode 号与磁盘块号不能混用。inode 号定位的是一条文件元数据记录；这条记录中的索引才给出数据块号。课件的 INODE_NUMBER_TO_BLOCK(offset, inode_number) 正是先查 inode 表，再根据 offset 查文件内逻辑块，最后把块号交给块层读取。拆成多个函数，是为了让每一层只负责一个映射。

目录与路径

文件名层

目录本身也是文件：其数据由多个目录项组成，每项把一个名称映射到 inode 号，inode 的类型字段则区分普通文件、目录等。查找 notes.md 时，系统先拿到当前工作目录的 inode，读出目录数据，再比较各目录项的名称；匹配后返回对应 inode 号。如果目录特别大，逐项线性比较会变慢，现代文件系统可使用索引等更高效的组织方式。目录项只负责命名，读取文件前还需检查 inode 中记录的权限；chmod 与 chown 分别修改权限和所有者。

课件中的 LOOKUP(dir, filename) 可按以下顺序理解：检查 dir 对应 inode 的类型确为目录；从该 inode 定位目录数据块；逐个取出目录项，把保存的名字与 filename 比较；找到后返回目录项中的 inode 号，直到目录末尾仍未找到则返回失败。示意伪代码省略了跨块读取、目录项边界和错误处理，不能直接照搬为实现。

目录 inode 的数据存的是索引项，而普通文件 inode 的数据存的是用户字节。文件系统复用“inode + 块”的存储机制来保存两类内容，差别由 inode 类型与读写规则决定。

图中的目录保存两条映射：helloworld.txt → 12、cse2021.md → 73。查找 cse2021.md 时，系统从给定目录 inode 读取这些目录项，字符串比较命中后返回 73；下一层再用 73 查 inode 表，取得文件大小与块索引。目录项里的 73 是 inode 号，不是该文件第一个数据块的块号。

查找还依赖目录上下文。在另一个目录里，cse2021.md 可以指向完全不同的 inode。函数的两个输入“目录 inode 号”和“名称”共同决定结果；路径解析就是不断把上一轮找到的目录 inode 当作下一轮上下文。

Unix V6 的目录项使用固定长度名称字段，课件指出其文件名最多 14 字节。这里的限制是字节数，多字节编码的字符可能占不止一个字节。不要把这一历史限制套用到现代 ext4。

路径层

相对路径 projects/paper 从当前工作目录开始：先在当前目录查 projects，确认找到的是目录，再在其中查 paper。绝对路径以根目录 / 开始；课件示例把根目录 inode 号设为 1，路径 /programs/pong.c 的查找过程如下：

  1. 从根目录 inode 1 读取其目录块。
  2. 在根目录中找到名称 programs，得到 inode 号 7。
  3. 读取 inode 7 指向的目录数据，找到 pong.c 对应 inode 号 9。
  4. 读取 inode 9 中的块索引，找到文件数据块 61、44、15，再按文件偏移读取其中字节。

图中从左到右依次是 inode 表、由块号定位的内容、根目录项、/programs 目录项以及 pong.c 文件。虚线表示“名字或编号对应到下一层”，实线框中可看到根 inode 1、目录 inode 7、文件 inode 9。最右边的数据块 61 只是文件的第一个磁盘块；同一 inode 还列出了块 44、15，说明文件逻辑上连续的字节不要求物理块号连续。

假定图中的文件系统块长为 4096 B，读取 /programs/pong.c 的偏移 5000 时，文件内逻辑块号为 ⌊5000/4096⌋=1\lfloor5000/4096\rfloor=1⌊5000/4096⌋=1，块内位置为 5000−4096=9045000-4096=9045000−4096=904。inode 9 的第二个数据块号是 44，因此驱动读取磁盘块 44，并从该块第 904 字节开始取数据。这里的 4096 B 是为了演示换算选定的块长，并非课件图上给出的设备参数。

工作目录只决定相对路径的查找起点；绝对路径从 / 查起。用户登录后通常有默认的 HOME 目录，根目录则让不同用户的路径进入同一个命名空间。根目录中的 . 和 .. 都指向根目录自身。课件示例的根 inode 号属于其教学模型，其他文件系统的编号可能不同。

查看目录数据

课件用 ls -ai 查目录项名称和 inode 号，再用 debugfs 导出 ext4 目录内容，最后用 xxd 查看原始字节，证明目录确实保存“名称到 inode 号”的映射。ext4 目录项示例包含：

字段 大小 含义
inode_number 4 B 目标 inode 号
dir_entry_length 2 B 当前目录项占用的总字节数
file_name_length 1 B 名称长度
file_type 1 B 文件类型
name 可变 名称字节

图中的首个目录项开头为 0d 01 73 00 0c 00 01 02 2e 00 00 00。小端序下，前四字节的 inode 号是 0x0073010d，0c 00 表示目录项长度为 12 字节，01 表示名称长 1 字节，02 表示目录，2e 对应字符 .。随后 .. 对应父目录。课件图中一处文字把 . 项的类型写成 regular file，与其原始字节 02 不符，这里按字节值解释。

第一个目录项占用 12 字节，故第二个目录项从十六进制偏移 0x0c 开始。第二项的名称长度是 2，对应 ..。这说明 dir_entry_length 用于跳到下一项，file_name_length 只说明名字本身有几个字节；两者并不相同。课件还列出 ext4 文件类型码：0x1 是普通文件、0x2 是目录、0x7 是符号链接，其他值可表示字符设备、块设备、FIFO 或 socket。

这张图展示的是 ext4 目录项格式，前面的 14 字节名称限制来自 Unix V6。两者都支持“目录项指向 inode”的概念，具体字段布局不同。

硬链接

link(old, new) 在目录中增加另一个名字，使两个名字指向同一个 inode。没有哪一个天生是“原名”，它们都是平等的硬链接。inode 中的链接计数随新目录项增加而加一；unlink(path) 删除一个名称映射，并使计数减一。最后一个硬链接被删除时，文件不再能通过名称访问；实际释放时机还受已打开文件句柄等因素影响。

假设 a.txt 指向 inode 25，当前链接计数为 1。执行 link("a.txt", "b.txt") 后，两项都记录 inode 25，计数变成 2。修改 a.txt 的内容，随后从 b.txt 读取会看到同样的改动，因为两者定位到同一个 inode 和同一组数据块。删除 a.txt 只移去一个目录项，计数回到 1，b.txt 仍可使用。硬链接不保存“目标路径字符串”，所以把 a.txt 改名或删除也不会使 b.txt 失效。

硬链接直接引用同一文件系统内的 inode，因此不能跨文件系统。硬链接把严格树形的路径关系变成图。若允许普通用户随意给目录添加硬链接，就可能形成环：删除入口后，环内目录还相互引用，引用计数无法降到零，却又无法从根目录到达。课件因此限制普通硬链接指向目录；. 和 .. 是文件系统管理的特殊目录项。删除非空目录通常也会受限制，因为其中仍有要处理的子项。

图按三个状态展示问题：起初根路径可进入目录 a，其 inode 25 的计数为 1；若允许再把内部目录的某项连回 a，计数升为 2，并形成环；随后从根目录移除 a，计数只降到 1。剩下的引用困在已从根断开的环内，用户既无法沿根路径进入，也无法靠简单计数回收。限制目录硬链接，是为了让命名图保持可管理的树形结构。

重命名

文本编辑器常先写临时文件，再把临时文件改成正式名称。若用 unlink(to_name)、link(from_name, to_name)、unlink(from_name) 三步模拟替换，第一步和第二步之间崩溃会让目标名称暂时消失。重命名需要比这种简单组合更强的原子性保证。

图中 from_name 可以理解为已经写好的临时文件 .a.txt.swp，to_name 是用户熟悉的 a.txt。第一步删去 a.txt，第二步才把这个名字连到新 inode。若恰好在两步之间断电，临时文件可能还在，但用户原来访问的 a.txt 已经不存在。对用户而言，保存操作把一个可见文件变成了缺失文件，因此这个中间状态不可接受。

课件随后给出较弱的方案：先让目标名称指向源 inode，再删除源名称；若中途崩溃，要在恢复阶段修正 inode 的链接计数。若目标名称原本就存在，这个顺序至少避免了先删目标造成的名字空窗。它仍没有完整解决崩溃恢复和所有观察者看到的原子性，现代文件系统要用日志等机制处理这些边界。

第二张图把目标名字先改为指向临时文件的 inode，再移除临时名字。两步之间崩溃时，新 inode 可能同时有两个名字，恢复过程要让目录项与链接计数一致。图里的 LINK(from_name, to_name) 表达“建立或更新目标绑定”的教学步骤；真实 POSIX link 在目标已经存在时会失败，因此不能把这两行直接作为可运行的 rename 实现。图比较的是更新顺序与中间状态，完整的原子性仍由文件系统协议保证。

可以把断电点列出来检查：

写入顺序 断电位置 可能看到的名称
先删目标，再加新目标 删除目标后 旧目标已不见，新目标尚未出现
先加新目标，再删源 两步之间 两个名称可能同时指向源 inode
完成所有步骤 最后 只保留目标名称

这个表格讨论课件的分步模拟，不等于断言真实 rename 系统调用就是按这些 API 逐个执行。真实实现需要明确崩溃前后允许的结果，并保证目录项与 inode 计数恢复后相符。

符号链接

符号链接（symlink）是一种单独的 inode 类型，其内容保存目标的路径字符串。访问链接时，系统按该路径继续解析。硬链接直接指向 inode；符号链接通过名字重新查找，因此可跨文件系统，也可能在目标被删后成为悬空链接。

例如 ln -s /tmp/abc s-link 把 /tmp/abc 写入链接。readlink s-link 可读出该字符串；cat s-link 会尝试访问目标。若目标不存在，读取失败；创建目标后，再读链接便能得到文件内容。ls -l 中此符号链接显示大小 8，是目标路径 /tmp/abc 的字节长度，不是目标文件内容的大小。

按图中的命令顺序，可以观察“链接自身”与“解析后的目标”：

操作 观察结果 原因
创建 s-link 链接创建成功 创建链接只需保存目标路径，目标可以尚不存在
readlink s-link 返回 /tmp/abc 读取链接自身保存的路径字符串
第一次 cat s-link 报目标不存在 cat 跟随路径去读目标文件
创建 /tmp/abc 并写入文本 目标开始存在 原链接内容无需修改
再次 cat s-link 读到 hello, world 同一目标路径现在能解析成功

图中大小 8 的计算是 1 个斜杠、3 个字符 tmp、另一个斜杠和 3 个字符 abc，合计 8 B。后来目标文件内容变长，也不会自动改变链接里这 8 B 的路径字符串。

比较点 硬链接 符号链接
目录项最终指向 目标文件的 inode 链接自身的 inode
链接内容 不单独保存目标路径 保存目标路径字符串
目标被删除 只要还有硬链接，文件仍可访问 链接可能悬空
跨文件系统 不可直接跨越 可指向已挂载文件系统中的路径

课件“Two Types of Links”图中，myfile.txt 与 my-hard-link 的箭头都直接抵达同一 inode；my-soft-link 的箭头先到 myfile.txt 这个名字，再由名字解析到 inode。符号链接还可能指向另一个符号链接，因此路径解析要防止循环。

符号链接可以指向已挂载的另一文件系统中的路径。挂载是把一个文件系统接入现有目录树；符号链接只保存并引用一个路径，两者的作用不同。

符号链接也改变路径解释的上下文。若 /CSE-web 指向 /Scholarly/programs/www，shell 逻辑路径下执行 cd /CSE-web 再 cd ..，通常回到 /；按真实目录层次解析时，父目录是 /Scholarly/programs。cd -P .. 使用物理路径，pwd -P 可查看物理位置。shell 通过逻辑工作目录记录用户输入的路径；课件把这一行为简化描述为记住先前位置，应以逻辑路径与物理路径的区别来理解。

核心关系

文件名是目录的数据，也属于文件系统的命名元数据；它通常不存放在普通文件 inode 里。同一 inode 可以由多个硬链接命名，目录项只需记录名称和 inode 号，所以“文件夹”并不是一个装满文件内容的容器。沿着“路径名 → 目录项 → inode 号 → inode → 块号 → 数据块”逐层追踪，就能解释文件打开、读取、链接与删除的大部分基本行为。
