系统目标

计算机系统工程关注程序怎样在真实设备上提供服务。系统规模可以从一台机器扩到许多机器，但扩容后仍需要保存正确结果、处理故障，并在约定时间内完成请求。

设计通常从需求开始，再把需求写成可以检查的规格（specification）。例如“做一个可靠的文件服务”还缺少具体条件，需要继续说明文件怎样读写、成功回复代表什么、允许哪些设备失效，以及需要支持多少并发请求。

项目 需要说明的条件
功能 提供哪些接口，参数和返回值是什么
正确性 转账总额、文件内容和操作顺序要满足什么规则
故障 需要承受断电、节点宕机、网络中断中的哪些情况
性能 在什么数据量与请求量下，测量延迟、吞吐和资源占用
扩展 增加设备后，容量与处理能力能增长多少，搬迁要做哪些工作

接下来才是实现和验证。实现可以由人编写，也可以借助编程工具；验证需要依据已经写清楚的规格，检查实现是否满足条件。设计判断要联系具体用途：训练数据读取、银行转账和聊天同步的访问方式与故障要求各有特点。

思考题：一个并行程序在两台机器上运行会出错。修改测试，让它只使用一台机器后通过测试，能否说明问题已经解决？

解答：

原要求包含并行执行。单机测试没有触发原来的并发场景，因此还需要在规定的机器数、数据量和交错顺序下验证。测试条件、预期结果和必须保留的功能，都应作为规格的一部分。

检查性能优化时也要这样做：固定输入与正确性标准，再测优化前后的时间。删掉计算、缩小问题或减少并发，都会改变被测任务。

规模增长

计算机把数据表示成二进制的 0、1。一个二进制位称为 bit，8 bit 组成一个字节，记为 B。文件大小表示存了多少字节，计算量表示处理这些数据需要做多少运算，用户请求数表示同时有多少人让系统做事。这三种规模可以分别增长。

思考题：把模型写成 action=F(input)action=F(input)action=F(input) 时，F、input、action 分别表示什么？为什么常用语言表示输入和输出？扩大模型、数据和计算规模可以带来什么作用？

解答：

F 是模型的计算过程，input 是输入和当前上下文，action 是模型给出的下一步输出。语言可以描述任务、背景和结果，也有大量文本可用于训练。增加参数能提高模型表示复杂规律的能力，增加数据和计算为学习提供条件；能改善多少，仍要通过具体训练和评测判断。

token 可以是一个词、词的一部分或一个符号，由文本编码方式决定。模型为候选 token 给出原始分数 logits，再把分数换成概率；采样表示按这些概率抽取下一项，抽到后继续生成后面的内容。

文本先被分词器转换成 token 编号，再由模型转换成数值向量进行计算。图像也能数字化：像素保存颜色数值，多模态模型通过图像编码器取得数值表示。程序代码、工具调用与机器人动作同样可以用约定格式记录。数字化提供了可保存、传输和计算的输入，具体表示还要适合所使用的模型。

把模型写成 action=F(input)action=F(input)action=F(input) 时，可以把一次执行理解为“读取当前输入，计算输出，再按应用规则使用输出”。例如编程助手读到用户要求和工作区文件，生成修改建议或工具调用；工具执行后的结果又成为下一次输入。文件系统负责保存工作区，推理程序负责计算输出，应用负责协调二者。

数据变多、计算量增加、用户请求增多时，存储和计算系统也要扩展。语言模型生成文本时反复计算下一个 token，使用更多参数、处理更长文本或同时服务更多请求，都会增加计算和存储工作。

编程助手、客户服务等应用需要读取数据、运行模型，并保存用户请求和结果。使用规模增加后，这些工作会给计算设备、网络和存储带来更多负担。

练习：初始值为 1，每天比前一天增长 1%，连续 365 天后是多少？写出计算式。

解答：

每天乘以 1.01，连续乘 365 次，得到 1×1.01365≈37.781\times1.01^{365}\approx37.781×1.01365≈37.78。因此一年后的值约为 37.78，是初始值的 37.78 倍。

初始值为 1、每天增长 1% 时，每天把已有结果乘以 1.01，365 次相乘得到 1.01365≈37.81.01^{365}\approx37.81.01365≈37.8。要在计算系统中获得持续增长的收益，算法也得能用好增加的资源。

搜索和学习

搜索从候选方案中寻找较好的结果，例如尝试棋盘上的不同着法。学习用已有数据调整模型中的数值参数，例如看过很多带标签的图片后，调整判断图片类别的规则。训练是调整参数的过程，推理是用已经训练好的参数处理新输入。

思考题：增加计算量为什么可能改善模型或搜索结果？这种推理需要对算法作什么假设？

解答：

搜索可以利用额外计算探索更多着法、看得更深；学习可以利用额外计算处理更多样本、完成更多参数更新。前提是所选方法能有效使用新增资源，数据和训练安排也适合任务。单纯增加无效或重复的计算，收益需要另行评测。

Rich Sutton 在《苦涩的教训》中总结，长期来看，能持续利用计算资源的方法往往更有效。搜索和学习都可以利用更多计算资源，分别探索更多候选方案、从更多数据中调整模型。具体任务能提高多少，仍取决于算法、数据和训练方式。

程序员设计搜索或学习过程，让程序从计算和反馈中找出具体策略。系统负责保存数据、执行计算、传递结果，并处理运行中的故障。

棋类搜索

搜索树的每个节点代表一个局面，每条边代表一步着法，叶子是暂时停止搜索的位置。分数越大，表示对己方越有利。在自己的回合，从子节点中取最大分数；在对手回合，从子节点中取最小分数，模拟对手会选对己方最不利的一步。这样逐层算回根节点，就能比较当前可选的着法。

棋类程序包含评估函数和搜索。评估函数 f(s)f(s)f(s) 给未结束局面打分，搜索展开未来着法。Minimax 假设己方选最大收益、对手选最小收益；alpha-beta 剪枝根据已知上下界跳过不会改变选择的分支。

更多算力可以让程序在同一时间内检查更多节点。专用硬件、并行搜索、棋局知识及已有局面资料共同帮助实现这件事；搜索时间、局面评估和数据访问仍需要配合。IBM 的 Deep Blue 介绍说明了其并行计算设计。

图像特征

图像由像素组成，每个像素保存亮度或颜色数值。特征是从这些数值中提取的有用表示，例如边缘方向、角点或某种纹理。SIFT 寻找在缩放、旋转后仍较稳定的关键点，并为附近图案计算描述向量。CNN（卷积神经网络）让小滤波器在图像上移动，对附近像素做加权计算，再把多层结果交给分类器。

SIFT 由人设计关键点、尺度、方向和描述子规则；CNN 在规定网络结构后训练滤波器等权重。两者都需要方法设计，区别在于哪些表示可随训练调整。

这些滤波器能识别不同方向的边缘和颜色变化，参数通过训练得到，网络结构和训练条件由开发者选择。2012 年 ImageNet 比赛中，AlexNet 的 top-5 错误率为 15.3%，第二名为 26.2%。top-5 错误率指模型给出的前五个候选类别都未命中正确类别的比例。

算力和数据

CPU、GPU 执行计算，内存保存正在处理的数据，磁盘或 SSD 长期保存训练资料。网络把不同机器上的数据送到需要它的位置。某个设备的运算速度增加后，其他部分也要及时提供数据，否则计算设备就会等待。

思考题：单芯片受到功耗、散热和制造条件限制时，怎样从系统层面增加可用计算量？增加机器后又要处理哪些工作？

解答：

可以增加处理器核心、GPU 或机器数量，把独立任务或可拆分的计算同时执行。机器增加后，要安排任务和数据位置，传输中间结果，协调共同修改，并处理机器与网络故障。共享网络、存储或串行步骤的耗时还要计入总时间。

单位计算成本长期下降，使更多搜索与学习成为可能。单芯片仍受功耗、散热和制造约束，多芯片、多机能扩大总计算量，但通信、调度和故障会增加系统工作。

互联网和代码仓库积累了大量文本，为语言模型提供了训练数据。存储系统保存这些内容，让训练程序反复读取；计算设备和网络则负责处理并传递数据。

思考题：语言模型可以从哪些地方取得大量训练数据？存储容量和读取速度对训练有什么影响？

解答：

通用文本来自互联网等资料，程序与说明可以来自代码仓库。容量决定能保留多少训练资料；读取速度决定计算设备能否及时取得下一批输入。若输入供应较慢，GPU 会等待，因此还要组织文件、安排读取和传输，并检查数据质量。

训练计算量

模型参数是训练过程中调整的数值，常用“权重”表示。一次浮点加法或乘法各计为一次 FLOP，FLOPs 表示运算总数，FLOP/s 表示每秒完成多少运算。批次是一次交给模型的一组样本；序列长度是每个样本包含多少 token。Transformer 是处理序列的网络结构，其中的注意力计算用于结合不同 token 的信息。

思考题：B 条序列、平均每条 S 个 token、参数量为 W 的模型，一步训练大约需要多少浮点运算？公式中的系数 6 怎样得到？同一近似下，一个 token 的前向计算和训练分别约需多少运算？

解答：

一步处理 BS 个 token。一次乘法和一次加法约计两次运算，所以每个 token 的前向计算约为 2W2W2W；计算输入梯度和权重梯度约再需 4W4W4W，训练合计约为 6W6W6W。因此一步训练约需 6BWS6BWS6BWS 次运算。这是简化估算，注意力等具体计算还会带来额外开销。

一批 Transformer 训练的计算量可以用下面的简化公式估算：

F≈6BWSF\approx6BWS F≈6BWS

B 表示这一步处理多少条序列，W 表示模型参数量，S 表示每条序列的平均 token 数。前向计算中，每个权重对一个 token 做一次乘法和一次加法，约计两次浮点操作。反向计算输入和权重的梯度约再需四次，合起来得到系数 6。这是近似估算，注意力计算和优化器更新等还会增加开销。

思考题：B、W、S 分别提供了哪些扩展方向？单步批次大小与整次训练使用的数据总量有什么关系？

解答：

B 是每步处理的序列数，W 是参数量，S 是平均序列长度。增大 B 能在一步中处理更多输入，增大 W 扩大模型，增大 S 处理更长上下文。整次训练处理的 token 总数要把所有步骤相加：D=∑tBtStD=\sum_t B_tS_tD=∑t​Bt​St​；只改变一次批次的大小，还要结合训练步数才能确定总处理量。

BSBSBS 是这一步处理的 token 数。把所有训练步的 token 数相加，才得到总训练数据量。模型可以增加参数、读取更多训练数据，或处理更长的上下文；这些变化都会增加计算和存储需求。

缩放定律

损失是衡量预测误差的数值，通常越小越好。例如，模型给正确答案很低的概率时，损失就较大。训练通过计算参数变化会怎样影响损失，再据此调整参数。图中的测试损失在未直接用于训练的数据上计算，用来观察模型处理新输入的效果。幂律形如 L=aN−bL=aN^{-b}L=aN−b：N 增加一倍时，这一项损失乘上 2−b2^{-b}2−b。

思考题：训练预算固定时，应怎样安排模型参数量和训练数据量？为什么需要寻找二者的配比？

解答：

设参数量为 N、总训练 token 数为 D，总计算量近似为 6ND6ND6ND。预算固定时，增加参数会挤占可用于处理数据的计算，增加数据也会占用同一预算。可以用较小实验拟合损失，再在预算约束下寻找损失最低的配比。图中每条固定预算曲线的最低点，就是相应实验的较合适配置。

Chinchilla 进一步研究固定训练预算如何分配参数 N 和数据 D，得到下面的拟合公式：

L^(N,D)=E+ANα+BDβ\hat L(N,D)=E+\frac{A}{N^\alpha}+\frac{B}{D^\beta} L^(N,D)=E+NαA​+DβB​

E 是公式中与 N、D 无关的常数项。E、A、B 等系数由实验拟合得到。这里的 B 是拟合系数，训练计算量公式中的 B 表示批次大小，两处符号按所在公式解释。

每条曲线对应一个固定计算预算。模型较小时，增加参数能降低损失。继续增加参数，会减少同一预算下可处理的训练数据，损失可能回升。曲线最低点表示这次实验中较合适的参数和数据配比。

右侧两图分别给出不同预算下较合适的参数量和 token 数。在这项研究的训练条件下，两者都接近按计算量的平方根增长。预算增加时，需要一起增加参数和训练数据。实际选模型大小时，还要考虑推理成本、数据质量和网络结构。

选择训练配置可以按下面的步骤进行：

  1. 固定数据处理方法、训练方法和验证集，使不同实验的损失具有可比性。
  2. 先训练几组较小模型，改变参数量与训练 token 数，记录计算量和验证损失。
  3. 用这些结果拟合损失与规模的关系，在预算约束 C≈6NDC\approx6NDC≈6ND 下寻找较合适的配比。
  4. 用更大的中间实验检查预测，再决定是否投入完整训练预算。

例如预算固定时，模型参数量 N 增加一倍，按这一近似，能够处理的 token 数 D 就要减少一半。大模型可能有更强的表达能力，也需要足够数据完成训练，因此需要同时评估两项。小规模实验形成的逐级验证过程，常称为 scaling ladder。

拟合是对实验范围内趋势的估计。模型结构、数据分布和训练方式变化后，需要重新检查趋势；少数实验点也可能无法可靠确定最低点。Chinchilla 论文给出了固定预算下参数量与数据量的实验研究。

工作区示例

一个贯穿多个系统问题的例子是带远程工作区的编程助手。用户在笔记本上提出要求，助手运行工具读写文件，模型服务生成下一步输出。工作区放在远端后，更换笔记本也可以重新连接到原来的文件；正在进行的修改和回复仍需要由服务记录。

推理实验可以使用较小模型，例如 Qwen3-0.6B。B 表示十亿，0.6B 对应约六亿这个量级的参数。若只按六亿个 32 bit 权重估算，权重内容约占 6×108×4=2.4×1096\times10^8\times4=2.4\times10^96×108×4=2.4×109 字节；实际运行还需要缓存、中间结果和程序内存，具体参数数目与格式以模型文件为准。

优化这类程序时，先确认输出符合要求，再固定硬件、输入长度、输出长度和并发量测量。相同工作量的执行时间从 10 秒降到 5 秒，才得到两倍加速；还可以分别检查模型加载、计算、文件读取和网络等待占了多少时间。

应用和存储

应用是实现聊天、购物或生成文本等功能的程序。用户操作产生请求，应用根据请求读取或修改保存的数据，再返回页面或结果。文件系统按文件名访问字节；数据库按表、行和字段组织数据。接口规定调用方要传什么参数、能得到什么结果，让应用可以逐步请求底层完成工作。

思考题：一个应用同时提供社交、购物交易和模型服务，后台需要哪些组件？一次用户请求怎样经过这些组件？

解答：

需要请求入口、业务程序、文件与数据库存储，以及模型计算服务。LAMP 中，Linux 管理资源，Apache 等服务器接收请求，PHP 等业务代码读取或修改 MySQL 和文件系统中的记录，再生成响应；模型请求还会送到计算服务。一次购物请求可依次经过入口、业务判断、商品查询或交易提交，最后返回页面。

一个应用可以同时提供社交、交易和模型服务。LAMP 中 Linux 管理系统资源，Apache 一类服务器处理 Web 请求，MySQL 与文件系统保存表和文件，PHP 等业务层生成响应。

思考题：应用使用文件名和字节偏移，磁盘使用块号。谁负责记录文件对应哪些块？断电后，系统怎样重新找到这些记录？

解答：

文件系统通过目录项找到 inode，再由 inode 和索引块找到文件的数据块。名称、大小、索引和分配记录也需要可靠保存。重新挂载时，系统读取超级块等布局信息，从根目录逐级查找路径，再沿 inode 和块索引读取内容；故障恢复按已保存的日志或其他恢复记录处理未完成更新。

应用通过文件路径、键值和表访问数据。文件系统记录 chat.log 的名字、大小和数据块位置，数据库处理表和查询。应用调用这些接口后，由相应系统完成底层读写。

存储扩展

容量表示能保存的数据总量。例如 40 TB 是全部可用空间，每天新增 8.6 TB 是增长速度；容量除以每天增长量，得到能使用的天数。保留三份副本时，同一份新照片会占三份空间，因此每天实际新增占用量也乘以三。

练习：每周新增约 60 TB 数据，按平均每天 8.6 TB 计算，40 TB 空间能使用多少天？保存三份副本时又能使用多少天？

解答：

按题目给出的每天 8.6 TB 计算，一份数据占用时，40/8.6≈4.6540/8.6\approx4.6540/8.6≈4.65 天，约为 4.7 天。三份副本每天占用 3×8.6=25.83\times8.6=25.83×8.6=25.8 TB，40/25.8≈1.5540/25.8\approx1.5540/25.8≈1.55 天，约为 1.6 天。这里把 40 TB 全部看作可用于新增内容的空间。

Facebook 2010 年的一组上传数据为：每周约十亿张照片，产生约 60 TB 新数据，平均每天约 8.6 TB。按 40 TB 存储容量估算，约 40/8.6=4.740/8.6=4.740/8.6=4.7 天装满；若数据保留三份，约 40/(3×8.6)=1.640/(3\times8.6)=1.640/(3×8.6)=1.6 天就用完容量。

分布式存储把多个磁盘接入网络，应用通过 RPC 使用统一接口；增加磁盘或阵列可扩容量。从一块本机磁盘扩展到多个远端磁盘阵列后，系统要记录每条数据所在的节点，并安排扩容时的数据迁移。

这里有两份规模不同的信息：实际文件内容可能很大，定位它们的管理记录也会随文件数增长。记录每个文件的位置是一种方法；根据键计算归属可以减少逐文件查表的工作，但仍需要知道当前有哪些节点、这些节点在映射中的位置，以及失效后怎样找到其他副本。

数据分片

键是用于寻找一条数据的标识，例如照片 ID。哈希函数把键转换成整数，再用这个整数选择存储节点。取模 a % N 表示 a 除以 N 后的余数：21 除以 3 余 0，除以 4 余 1，所以节点数从三变四时，这条数据的归属会变化。分片就是把不同键分配给不同节点，每个节点保存全部数据中的一部分。

思考题：数据原来按 hash(key) % N 分配，节点数增加到 N+1 后，旧数据的归属会怎样变化？图中的哈希值 21、39、28、34、44、26 从模 3 改成模 4 时，有几项需要迁移？

解答：

取模的除数变化后，旧键的余数也可能变化，所以已有数据需要重新定位并迁移。六个值的变化为：21 从 0 到 1，39 从 0 到 3，28 从 1 到 0，34 从 1 到 2，44 从 2 到 0，26 仍为 2。因此有五项迁移，一项留在原节点。

哈希取模使用 hash(key) % N。固定 N 时可散布键；节点数变化会改变许多余数，均衡程度还取决于哈希与键分布。

一致性哈希把节点和键映到环，键交给顺时针遇到的第一个节点。

这个方法增加了一层间接映射：键先进入固定的逻辑空间，再由这个空间上的区间找到物理节点。节点数变化时，逻辑空间保持不变，只调整有关区间的归属。名称中的“一致性”描述这种映射随节点增减的变化性质，副本读写是否一致还需要单独的协议。Dynamo 论文介绍了这种分片方法及虚拟节点。

扩容前，k3、k4 顺时针找到的第一个节点都是 B。D 插入 A 与 B 之间后，k3 先遇到 D，因此从 B 移到 D；k4 位于 D 之后，仍归 B。均匀分布的情况下，新节点平均接收约 1/(N+1)1/(N+1)1/(N+1) 的数据。实际结果还受节点位置和数据分布影响。一个物理节点可以在环上对应多个虚拟节点，帮助分散负载。

移动范围变小后，搬迁仍要处理并发读写。一个简化的在线搬迁流程是：先从旧节点复制区间内容，记录复制期间的新修改；新节点追上更新后，发布新的归属版本；仍使用旧映射的请求由旧节点转发或要求重新查询。确认旧访问路径已退出后，才回收旧内容。实际系统按自己的协议实现这些步骤。

均匀散布键也需要结合请求分布检查。如果一个热门文件承担了大部分请求，即使每台保存的字节数接近，该文件所在节点仍可能过载。容量均衡、请求均衡和节点处理能力需要分别测量。

延迟和缓存

命中表示所需数据已经在缓存中，未命中时需要继续访问较慢的存储。假设一次命中用 1 ms，未命中的完整请求用 10 ms，100 次请求有 80 次命中，则平均耗时为 (80×1+20×10)/100=2.8(80\times1+20\times10)/100=2.8(80×1+20×10)/100=2.8 ms。缓存有效程度同时取决于命中比例和两条访问路径的耗时。

延迟是一次请求从发送到收到回复的时间，吞吐量是每秒完成的请求数或数据量。远端读取要经过网络传输、服务器排队、磁盘读取和回复传输。增加机器可以分担请求，减少排队；网络传播时间还受距离影响。

图中的示例值包括：内存访问约 100 ns，SSD 随机读 4 KB 约 150 μs，同一数据中心的网络往返约 500 μs，磁盘寻道约 10 ms。150 μs 等于 150000 ns，能看出这些操作的时间差距。图中数字来自不同年代和条件，分析自己的程序时需要实际测量。

思考题：速度快的存储容量有限，为什么较小的缓存仍可能改善很多请求的耗时？应观察哪些访问统计？

解答：

访问通常集中在一部分热门数据上，缓存这部分内容就能覆盖许多请求。可以统计各键的访问频率，确定热点；再测量命中率、命中和未命中时的完整请求耗时，计算平均等待时间。效果取决于缓存覆盖了多少访问，以及两条访问路径的速度。

缓存把常用数据放到速度更快的位置。如果少量数据承担了大部分访问，小容量缓存也能减少很多等待。是否有效，可以通过命中率和请求耗时来测量。

延迟表示一次请求从发出到取得结果用了多久，吞吐表示单位时间完成多少请求或传输多少数据。远端访问会经过编码、发送、排队、处理和回复，计算时需要把这些部分都算进去。

网络传播还有物理限制。若两点直线距离为 d，传播速度至多为光速 c，单程传播时间至少为 d/cd/cd/c。距离约 1000 km 时，这一下界约为 3.3 ms，实际路径和设备处理还会增加时间。减少往返次数、在近处缓存数据，可以减少请求经过长路径的次数。

缓存收益可以用平均时间估算。假设命中耗时 1 ms，未命中耗时 20 ms，命中率为 80%，忽略其他开销，平均访问时间为 0.8×1+0.2×20=4.80.8\times1+0.2\times20=4.80.8×1+0.2×20=4.8 ms。常说的“少量数据承担多数访问”是负载的一种可能特征，需要用真实访问记录确认。

缓存更新

先看写缓存带来的确认问题。A 的请求由服务器 1 处理，B 的请求由服务器 2 处理，两台各有缓存，共同访问后面的存储服务。

步骤 状态
① A 写入 X 新内容先进入服务器 1 的缓存
② 返回成功 后端存储尚未接收到新内容
③ A 告诉 B 已完成 B 向服务器 2 请求 X
④ B 查询后端 服务器 2 缓存未命中，后端仍返回旧内容或不存在

如果接口承诺“写成功后其他用户能读到新值”，步骤②就需要等待满足这一承诺的条件。可以先把内容提交到后端，再回复，并使其他缓存失效或重新验证；若接口允许暂时读取旧值，也要明确这种范围。写入确认、持久保存和其他读者可见分别需要检查。

读取结果也包含“查无此项”。把这个结果缓存起来后，后续查询可以很快返回，但创建文件时也要处理这份旧记录。版本号是每次修改后推进的编号；客户端发现版本变化，就重新取得内容。一致性模型进一步规定：更新传播过程中，返回旧值、新值或暂时等待，哪些行为符合接口约定。

思考题：B 已把“X 不存在”存入缓存，A 随后创建 X。B 再次查询会发生什么？系统可以怎样让它取得新结果？

解答：

B 若直接使用旧缓存，仍会返回“X 不存在”。A 创建 X 后，可以通知 B 清除该记录；也可以让缓存按 TTL 过期，或让 B 查询修改时间、版本号后重新读取。缓存失效后，B 再到服务器查找，才能取得新文件的信息。

B 先查询 X，得到“文件不存在”，并把这个结果存入缓存。A 随后写入 X。B 再次查询时直接返回缓存中的 X:none，因此仍看不到新文件。系统可以在写入时通知 B 清除旧缓存，也可以让 B 定期检查修改时间或版本。TTL 是缓存的有效时长，超过这个时间后要重新查询。采用这些办法时，需要说明更新后多久能读到新内容。

一致性模型说明多次读写可以出现什么结果。最终一致性允许副本暂时不同，更新停止且通信恢复后，各副本最终一致。因果一致性要求有前后依赖的操作按同一顺序被看到。顺序一致性要求所有操作能排成一个共同顺序，并保留各进程的执行顺序。线性一致性还要保留实际时间上的先后关系。图中的 strict 表示更严格的理想时间要求。

为了满足更多顺序要求，节点通常需要交换更多消息。选择哪种模型，要看业务能接受哪些读取结果和等待时间。

机器故障

平均故障间隔描述长期统计。单台机器平均一万天故障一次，可以估算每天产生 1/100001/100001/10000 次故障；一万台的预期次数相加，得到平均每天一次。某天可能没有故障，也可能多台同时出问题。设备增加后，维护和恢复需要成为日常流程。

故障可能来自硬件损坏、配置错误、软件 bug、内存泄漏、网络中断和电力问题。还需要考虑暂时停顿：例如 Java 垃圾回收的某些阶段会暂停应用线程，服务器稍后恢复，但客户端在等待期间可能已经超时。垃圾回收是程序运行中的常规内存管理活动，暂停方式取决于收集器。Oracle 的 G1 文档介绍了暂停与并发执行的关系。

没有回复时，客户端通常只能确认“等待已经超出限制”。服务器可能已经宕机，也可能仍在处理，或者处理完成但回复被网络延迟。时间限制帮助系统安排重试、切换和错误返回，操作最终有没有执行，还需要依据请求身份与服务端记录判断。

静默错误

有些故障会停止程序，有些会让程序继续运行并产生错误数据。后者称为静默数据损坏（silent data corruption，SDC）。例如内存中的 00000010 表示 2，一个 bit 变化后成为 00000011，程序读到的数值就变为 3，却可能没有收到异常。

在模型训练中，一个错误数值可能进入后续梯度与参数更新，影响许多步骤。大量设备长时间工作，会增加遇到低概率错误的机会；具体风险还取决于硬件、运行环境和软件检查。

处理时需要同时考虑发现与恢复。校验和可以检查保存或传输的内容是否变化；ECC 内存能够检测、纠正其设计范围内的部分错误；关键计算还可以进行有规则的结果检查或重复计算。发现错误后，可以隔离相应设备，从此前确认可靠的检查点恢复，再重算受影响步骤。

检查点也需要验证完整性，复制错误数据可能把同一错误传播到多个副本。不同检查手段保护的对象和错误范围需要写清楚。Silent Data Corruptions at Scale给出了大规模系统中这类问题的实际案例。

写入和恢复

原子更新需要对外呈现完整结果。例如同时修改账户 A、B 时，可以先保存一份记录，注明这笔转账要修改哪些值；恢复程序读取记录后，判断应完成两边修改还是撤销。日志保存修改过程，写时复制先写入另一份完整内容，再更新所使用的版本。持久性还要求相应记录在规定的故障后能读回来。

持久性说明成功写入的数据在系统规定的故障情况下能继续保存。原子性说明一组更新要么全部完成，要么全部撤销。系统需要分别说明能承受哪些故障，以及哪些操作共同完成。

思考题：写整个文件时，只写完一部分机器就崩溃。恢复后可能读到什么？成功写入的持久性与整份更新的原子性分别要求什么？

解答：

如果只完成部分块的更新，恢复后可能出现一部分新内容、一部分旧内容。持久性要求已报告成功的数据在规定故障后仍可恢复；原子性要求整份替换对外呈现完整旧版本或完整新版本。若需要整份原子替换，可以用包含相应数据的日志或写时复制，配合提交记录决定恢复哪一版本。

图中只写入了一部分新数据，应用读到一半新、一半旧的内容。如果需要整份文件同时更新，系统要安排日志、写时复制或其他保存流程，在恢复时选出完整旧版本或新版本。

原本 A=100、B=0。B 加上 100 后，A 的扣款还没完成，机器就崩溃了，随后读到 A+B=200。转账需要把两次修改放在同一事务中，并在故障恢复时一起完成或撤销。

服务和副本

可用性表示某段时间内服务能正常响应的比例。不可用概率 p 表示在所选时间窗口里，一个副本无法服务的机会。独立故障时，要让三个副本同时失效，需要三个事件共同发生，所以概率相乘得到 p3p^3p3。共享电源或网络会让故障彼此相关，部署时应把这种共同依赖算进去。

思考题：什么是分布式系统？为什么一台应用没有直接访问过的机器发生故障，也可能让应用无法继续工作？

解答：

分布式系统由多台联网机器上的组件共同提供服务。应用可能先调用数据库，数据库再依赖另一台存储机器，因此间接依赖的故障也会影响请求。系统需要识别故障，保存可恢复的记录，再为相关请求安排其他访问路径、重试或错误返回。

思考题：保存多份数据和失败后重试怎样帮助系统继续工作？多个副本的更新顺序需要怎样协调？

解答：

重试也会消耗容量。先向一台发送请求，等待 50 ms 后再联系其他副本，增加的是时间上的尝试；同时向多台发出请求，增加的是空间上的尝试。两种方式都会让服务收到重复请求，修改数据时需要识别同一逻辑操作，读取时也要检查结果是否符合版本要求。

排队时间

在一台机器上增加可用核心、线程、内存或更强设备，称为纵向扩展（scale up）；增加机器并分配任务，称为横向扩展（scale out）。多线程能利用多个核心，也能让部分线程等待 I/O 时由其他线程继续工作，实际收益取决于可用资源与共享瓶颈。

增加处理能力还可以减少排队。假设六个请求同时到来，每个实际处理时间为 100 ms，一台工作线程依次处理时，它们分别在 100、200、300、400、500、600 ms 完成。后来的请求虽然同样只计算了 100 ms，却在前面等待。

两个互不争用资源的工作线程同时处理时，每轮完成两个请求，完成时间成为 100、100、200、200、300、300 ms。请求内部的计算量保持不变，等待时间缩短，所以平均响应时间从 350 ms 降为 200 ms。

长期到达速率超过系统处理能力时，积压会持续增长。到达速率较低时，突发请求仍可能排队；设计需要保留容量余地，并测量负载高时的响应时间。

并行计算

向量是一列数，矩阵是按行和列排列的数。矩阵与向量相乘时，每个输出项由一行矩阵与整个输入向量计算得到。例如一行是 [2,3]、输入向量是 [4,5]，输出为 2×4+3×5=232\times4+3\times5=232×4+3×5=23。各输出行可以分给不同计算单元处理，最后拼成完整输出向量。

一个线程等待 I/O 时，其他线程可以继续处理请求。增加机器也能同时处理更多任务。如果它们共用的网络或存储已经忙满，继续加机器的收益就会减小。

模型并行

网络层接收上一层的输出并计算下一组数值。把不同层放在不同 GPU 上称为模型并行，前一层的结果要通过网络或设备间链路送给后一层。训练的前向传播计算预测，反向传播计算损失对各权重的梯度，优化器再按梯度更新权重。梯度描述权重稍微变化时损失怎样变化，这些前后依赖决定了可同时执行哪些工作。

layer 1 把计算结果传给 layer 2，layer 2 再传给 layer 3。处理一批数据时，图中很多时间都在等待，这些空闲时段称为流水线气泡。交错处理多个小批次可以减少等待，调度时仍要安排好各层的数据依赖。

分层还可以解决容量问题：一个模型的权重和中间状态放不进单块 GPU 时，把不同层交给不同设备共同保存和计算。不过，一批数据必须先经过第 1 层再进入第 2 层，各层之间仍有顺序。

以三层、每层耗时 T 的纯前向例子说明流水线。只有一个请求时，总耗时为 3T，每块 GPU 只工作 T，平均利用率约为三分之一。若把四个独立请求交错送入三层，忽略传输，总耗时约为 (4+3−1)T=6T(4+3-1)T=6T(4+3−1)T=6T；每块工作 4T，利用率升到三分之二。每个请求仍需依次经过三层，收益来自让不同请求同时占用不同层。

真实训练还包含反向传播、参数更新与缓存容量限制，需要额外调度。长时间租用大量 GPU 时，空闲资源也有成本。例如按每天 90 万美元计费、平均三分之一资源空闲的假设，约 30 万美元对应空闲资源；这个计算用于理解利用率，具体费用与设备和计费条件有关。

一个训练步先做前向传播，再计算梯度，最后更新参数。反向传播要用前向结果，更新要等梯度完成。满足这些条件后，独立的子任务可以同时执行。

并发读写

先区分两种执行中的依赖。矩阵乘法各层的输入来自前一层输出，这个顺序在开始前就能确定。购票、改文件等操作是否访问同一记录，则可能要运行到选定对象之后才能知道。前一类可以按已知依赖调度，后一类还需要在执行中检查数据冲突。

并发表示两次操作的执行时间重叠，线程在一个核心上交错执行也可以形成并发。并行表示多个计算单元在同一时刻工作。下面的购票错误只需要交错顺序，就有机会发生。

事务把一组相关操作作为一个整体处理。购票事务可以包含查库存、确认余票、扣库存和建立订单。隔离性规定同时进行的事务怎样影响彼此。锁可以让访问同一数据的事务依次进入；乐观并发控制先计算，提交时再检查读取过的数据是否已被其他事务修改，发生冲突的一方重新执行。

思考题：两个用户都请求“购买任意一张票”，为什么请求开始时很难知道二者是否冲突？如果它们都读到余票为 1，怎样协调扣票和建订单？

解答：

请求开始时尚未选定票号，两次请求后来可能选中同一张票，冲突因此在执行中才出现。要把查库存、判断、扣票和建订单作为受协调的一组操作：用锁依次处理时，后一事务读到 0 就停止；用乐观控制时，第一笔提交后，第二笔发现旧读取已失效，重新读取后停止购买。

T1 和 T2 都先读到 left=1。T1 把库存写成 0，建立 Alice 的订单；T2 也根据刚才读到的 1，把库存写成 0，建立 Bob 的订单。于是只有一张票，两人却都下单成功。按顺序处理时，第二个人会看到库存已经为 0，购买就会停止。为保证这一结果，系统需要把查询库存、判断余票、扣票和建立订单一起协调。

隔离性用于控制事务之间的相互影响。系统可以用两阶段锁（2PL）或乐观并发控制（OCC）处理冲突。上面的购票例子希望得到与串行执行相同的结果；使用数据库时，还要查看所选隔离级别提供的保证。

锁方法可以让第一笔事务在读取余票之前取得保护，完成判断、扣票和建单后再让第二笔进入。两阶段锁要求一个事务先取得所需锁，开始释放锁后停止取得新锁；严格的做法还会将有关写锁保留到事务结束。多个事务等待彼此的锁时，也需要检测死锁或安排重试。

乐观方法在读取时记录数据版本，例如读到 left=1,version=7，先计算自己的结果。提交时检查版本仍为 7，并在同一受保护的提交过程里完成版本推进与数据更新。一方成功后版本变为 8，另一方检查失败，重新读取后发现没有余票。版本检查和更新需要共同协调，才能避免两方都通过旧版本检查。

例如，两个人都请求“购买任意一张票”，开始时还没选定具体票号。如果后来选中了同一张票，系统就要协调这两次购买。为此，需要记录每个事务访问了哪些数据。

学习率决定沿梯度方向走多大一步。以损失 w2w^2w2 为例，在 w=1w=1w=1 附近，w 增加 0.01，损失约增加 0.02，局部变化率约为 2；这就是该位置的梯度。学习率取 0.6 时，更新量为 −0.6×2=−1.2-0.6\times2=-1.2−0.6×2=−1.2。更新后 w=−0.2w=-0.2w=−0.2，损失为 0.04；再次使用旧更新量得到 w=−1.4w=-1.4w=−1.4，损失变为 1.96。更新所依据的参数版本因此会影响训练结果。

两个 GPU 都读到 w=1w=1w=1，各自算出更新量 Δw=−1.2\Delta w=-1.2Δw=−1.2。同步训练先把两份更新取平均，再执行一次，得到 w=−0.2w=-0.2w=−0.2。异步训练收到第一份更新后得到 -0.2，收到第二份后继续加上 -1.2，得到 -1.4。第二份更新是根据旧的 w=1w=1w=1 算出的。图中的损失为 w2w^2w2，从 -0.2 变成 -1.4 会让损失增大。同步训练需要等待较慢的工作节点；异步训练则需要控制旧参数算出的更新对结果的影响。

横轴是 worker 数，蓝线是同步训练，绿线是异步训练。在这次实验中，蓝线的测试精度更高；worker 较多时，绿线达到收敛所需的训练量也更大。比较训练总时间，还要结合每步耗时。

性能目标通常是达到某个质量所需的总时间。可以估算为“每步时间 × 达到目标所需步数”，再计入读取、通信和保存检查点的时间。减少单步等待后，如果需要更多步骤才能达到目标，仍要用完整训练过程判断收益。

请求调度

在一个请求内部划分计算，称为任务内划分（intra-task）；把多个请求分给不同实例，称为任务间调度（inter-task）。前者检查子任务的依赖与通信，后者还要检查每台实例已有的缓存和等待队列。

语言模型逐个生成 token 时，可以保存前面 token 的注意力键 K 与值 V，形成 KV cache，后续生成便能继续使用已经算好的结果。相同模型版本、相同前缀及相关计算条件下，请求还可能复用已有前缀缓存。缓存占用内存，转移请求时也可能需要重新计算或传输它。PagedAttention 论文讨论了 KV cache 的管理与共享。

因此，一个请求在缓存命中的实例上计算更快，也可能因为该实例排队较长而更晚完成。估算时要把排队、准备数据或缓存、实际计算共同相加，再决定放到哪台。

扩展限制

扩展后的总耗时由计算、数据读取、通信、排队和协调共同组成。安排任务时，可以先列出每一步依赖哪份数据、由哪台机器执行，再计算最慢的一条依赖路径。新增设备能承担的独立工作越多，等待公共资源的时间越少，扩展收益通常越大。

系统扩展会受到芯片算力、功耗、网络延迟和带宽限制。CAP 定理讨论网络分区时的读写服务：如果节点间无法通信，系统要在保持线性一致性和继续回答所有未故障节点的请求之间作选择。实际服务还要规定请求最多等待多久。

事务、故障恢复、副本协调、安全和网络都会影响扩展结果。系统规模增加后，仍要保证读写结果正确，故障后能恢复数据，并满足请求的完成时间和处理量要求。

思考题：两个副本之间发生网络分区时，能让每一侧持续完成读写，同时让读取保留全局实时顺序吗？CAP 定理说明了什么约束？

解答：

在允许网络分区的读写模型中，这一保证组合无法同时成立。C 要求线性一致性，A 要求非故障节点收到的操作最终得到符合接口的响应，P 表示系统需要面对节点间长期无法通信。
若一侧已经完成写入，另一侧随后读取，它需要知道那次更新才能保留实时顺序。通信持续中断时，可以等待或暂停部分操作来保留 C；若两侧继续独立完成操作，某些读取就可能缺少已完成的更新。约束针对这种分区条件下的保证。CAP 原论文
