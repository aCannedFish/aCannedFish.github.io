计算机系统工程-04：NFS、GFS 与 3FS

发表于2026-09-29|更新于2026-11-02|Note计算机系统工程
|浏览量:

远程访问

远程文件

本地文件系统把路径和字节偏移转换成设备访问。文件放到远端后，还需要通过网络找到保存它的服务器，再把数据传回来。多个节点保存内容或副本时，又需要记录位置并协调更新。

FTP、网盘让用户显式上传下载，挂载后的 NFS 则让普通文件路径指向远端内容，GFS 使用专门客户端库。这些接口不同，都要面对网络等待、重试和节点故障。

共享工作文件就是一个例子：源文件留在工作机器，其他机器从挂载路径读取，省去手工搬运与核对副本。服务仍需管理访问权限、连接和新版本发布。下面分别比较工作站共享、大文件批处理与训练样本访问。

把本地 inode 文件系统的 open、read、write 等接口逐一改成 RPC，远端文件服务还需要处理哪些状态、故障和读写规则？

解答：

需要重新安排文件标识、打开记录和读写位置，并定义缓存、重试和故障恢复的行为。例如 NFSv2/v3 用 LOOKUP 取得句柄，由客户端保存 fd 与游标，READ、WRITE 带上句柄、偏移和长度；目录修改还要保持名称关系的原子更新。请求超时、重复执行与服务器恢复，都需要相应协议处理。

分层接口

应用调用文件接口，NFS 客户端把操作转换成协议请求，RPC 层传输并匹配回复，服务端执行本地文件操作。每层只需要理解相邻接口，而不直接管理所有底层细节。

十个模块若都依赖其他九个，最多有 90 条有向依赖；严格排成十层、只依赖下一层时，只有九条相邻依赖。这个算例说明限制连接能减少共同检查的关系，实际复杂度还取决于接口状态。

错误与完成条件仍要贯通。RPC 超时时，远端文件操作可能已经执行；文件系统恢复了目录关系，也不一定意味着应用的一整笔业务完成。

共享文件

NFS

挂载为远端目录设置本地入口。把服务器目录接到 /home/paul 后，程序打开该路径下的 a.txt，内核识别挂载点，再交给 NFS 客户端构造请求、接收数据和维护本地打开记录。

NFS 是 Network File System，Sun 在 1980 年代为不同硬件和系统的工作站共享文件设计，也支持无本地磁盘工作站。它通过缓存、预读减少远端访问。

经典 NFSv2/v3 将打开记录和游标放在客户端，请求携带访问所需信息。服务器仍保存文件、元数据及部分辅助状态，锁服务与回复缓存也有自己的记录。NFSv4 又增加了打开和缓存管理状态，不能把各版本混为一套协议。

接口和请求

fd 是进程内的描述符，fh 是服务器解释的文件句柄。客户端先由 fd 找到 fh 和当前游标，再把 fh、offset、count 放入 READ。服务器因此不需要记住这个客户端上次读到哪里。

LOOKUP 根据父目录句柄与名称找子项，GETATTR 查询属性，MKDIR、REMOVE、RENAME 修改名称关系。lseek 只改本地游标，经典版本没有独立 CLOSE RPC；close 仍可能先触发 WRITE 或 COMMIT，再释放本地记录。创建文件也需要额外的创建请求。

本地操作 典型 NFS RPC 转换
open(path,flags) LOOKUP(dirfh,name) 逐级找对象，客户端建立打开记录
read(fd,buf,n) READ(fh,offset,count) 显式发句柄与偏移
write(fd,buf,n) WRITE(fh,offset,count,data) 发位置、长度和数据
lseek 无对应 RPC 修改本地游标
close 无独立 CLOSE RPC 释放本地记录，必要时先写回
stat GETATTR(fh) 查询远端属性
mkdir MKDIR(dirfh,name,attr) 创建目录项
unlink REMOVE(dirfh,name) 删除名称
rename RENAME(dirfh,name,tofh,toname) 指定源、目标目录与名称

挂载和读取

服务器先配置导出目录与权限。客户端执行 mount 192.168.1.100:/users/paul /home/paul，取得导出目录句柄并建立挂载关系。VFS 根据这个关系分派后续路径访问。

图中 OPEN 先变成 LOOKUP，服务器返回 fh 与属性，客户端建立 fd 到 fh 的映射并将游标设为 0。READ 再携带 fh、0、n，服务器返回内容，客户端按实际字节数推进游标。读了 100 B，下一次顺序读就带 offset=100。

CLOSE 释放引用并按需写回。缓存有效的路径或属性可减少 LOOKUP 等往返，但权限与认证仍按所用协议检查。

打开状态

如果服务器保存每个客户端的打开表，就要记住它打开了哪个文件、读写方式和游标，还要在重启后恢复、失联后清理。长时间打开却没有请求的客户端也会持续占用这些记录。

经典 NFS 把 fd、fh 和游标留在客户端，每条请求显式给位置。服务器恢复文件系统后，可直接依据请求定位对象。这里的“无状态”只限定这类打开会话，文件内容、inode、目录、锁服务和回复缓存并没有消失。

文本生成接口也可以让客户端每次带完整上下文，或者只带会话 ID，由服务端查历史。前者重复传输更多内容，后者需要保存、恢复和鉴权会话。共享网络出口不妨碍按用户与会话身份区分请求。

WRITE 重试仍需考虑重复与并发。A 的旧写 a、B 的新写 b 之间若发生重启，丢失去重记录后再执行 A，可能把 b 覆盖回 a。相同写入连续执行的幂等性，不会自动保护中间插入的新更新。

A、B 两个客户端都得到 fd=3，分别打开 f、g。若服务器保存打开文件表，应怎样区分它们？服务器重启、表中记录丢失后，READ(3,...) 又怎样找到文件？NFSv2/v3 把游标保存在哪里？

解答：

fd 属于各自进程，A 的 3 指向 f，B 的 3 指向 g。服务器若保存打开表，就要结合客户端身份和 fd 定位记录，表中还包含文件与游标；重启后只有数值 3，需先恢复或重新建立这种对应关系。NFSv2/v3 让客户端保存 fd、fh 和游标，每条 READ 带 fh、offset、count，服务器据此访问文件。

A 写入 a 后回复丢失，B 随后写入 b 并成功。服务器重启丢失回复缓存，A 的旧请求又被执行，最后是什么？同一个 WRITE 重复设置相同内容，为什么还要检查并发与去重？

解答：

最后可能重新变为 a，覆盖 B 已完成的 b。同一个值连续重复写入时效果可以相同，中间插入其他写入后，旧请求又可能覆盖新结果。

可以按协议保留可靠请求完成记录、检查数据版本，或协调写入顺序。需要跨重启去重时，相应记录也要持久保存，并与业务修改共同生效。

文件句柄

fh 是服务器给客户端的不透明标识，客户端通常原样带回。服务器可以在其中编码文件系统身份、对象编号和分配代次。

它需要在名称变化后继续识别原对象，并在编号被新对象复用时识别旧请求。下面两个图分别检查这两类情况。

名称变化

程序 1 打开 dir1/f 后，程序 2 把 dir1 改成 dir2，再把另一个 dir3 改成 dir1。程序 1 随后的读取应继续访问原来的文件，即现在的 dir2/f。

如果句柄只保存路径字符串 dir1/f，再次解析会进入新改名来的目录，找到另一个对象。因此，打开后的请求需要稳定对象身份，而不能仅凭原路径重新查找。

程序 1 进入 dir1 并打开 f；程序 2 把 dir1 改为 dir2，再把 dir3 改为 dir1。程序 1 随后的 READ 应访问哪个文件？文件句柄若只保存 dir1/f，会发生什么？

解答：

程序 1 已打开的是原来的 f，它现在位于 dir2/f。目录改名只改变名称关系，打开引用仍指向原对象。若句柄保存 dir1/f 字符串，下次解析可能进入由原 dir3 改名形成的另一目录。稳定对象标识让请求继续找到原文件。

编号复用

旧文件使用 inode 7、代次 1，删除回收后，新文件可能再次取得 inode 7，但代次变为 2。旧句柄仍带 (7,1)，服务器比较发现代次不同，就能返回失效句柄错误，避免误读新对象。

generation number 跟踪编号的分配，内容修改则使用修改时间或数据版本。它们分别回答“还是不是原对象”和“原对象的内容有没有变化”。本地 Unix 的打开引用可以延后 unlink 后的回收，经典 NFS 缺少完整服务端打开会话时，跨客户端删除可能使旧句柄失效，部分客户端用临时改名帮助保留对象。

旧文件使用 inode 7，打开后被删除，编号 7 又分给同名新文件。旧读请求怎样识别自己打开的是哪一个对象？generation number 如何参与检查？

解答：

句柄同时保存 inode 号和 generation number。旧文件取得 (7,1)，编号 7 分给新文件后，当前代次为 2。旧请求仍带 1，服务器检查出与当前代次不匹配，返回句柄失效错误，防止旧请求读到新文件。

缓存更新

客户端可以缓存内容、属性和名称查找结果，减少 READ、GETATTR、LOOKUP、READLINK、READDIR。服务器的页缓存又能减少设备读取。节省了哪一段工作，要沿实际访问路径测量。

图中服务器最初为 v1，客户端 1 将 v2 留在本地，客户端 2 此时仍取得 v1。客户端 1 关闭并写回后，服务器才有 v2；客户端 2 再次打开并检查属性，才重新取得新内容。

close-to-open consistency 围绕这两个时刻安排同步：关闭方完成所需写回，打开方验证缓存。长期同时打开的两个进程还需额外同步。修改时间、版本号或缓存期限用于判断何时重查，例如文件 3 s、目录 30 s 是一种配置示例，而非通用时限。写入尚未发布或网络断开时，单靠 TTL 不能决定所有读取结果。

远端读取的耗时由哪些部分组成？服务器设备、网络和缓存条件改变后，远端访问与本地访问的速度应怎样评估？

解答：

总耗时包含客户端处理、请求传输、服务器排队、查找与存储读取、回复传输及结果交付。服务器采用更快设备或命中缓存时，可能减少实际 I/O；较慢网络或排队则增加等待。应对相同读取范围测量实际路径，并结合缓存命中、设备速度和网络负载评估。

顺序预读

一次远端读取除了数据发送，还要经过请求构造、排队和回复处理。应用连续做 64 次 64 B 读取，总量只有 4 KiB；若客户端先取连续 4 KiB，后续就能从缓存交付，减少独立往返。

收益取决于预取的字节是否真正被使用。网络还有 MTU、协议头和最小帧等条件，大请求与小请求的成本并不严格按字节同比变化。预读过多会占带宽和缓存，随机访问需要按命中情况选择。

非易失内存

NVRAM 指能在规定断电条件下保留内容的随机访问存储。它可以使用非易失介质，也可以通过电池保护内存、闪存备份等方式实现。UPS 则是在断电时继续供电的设备。

服务器可以先在可靠存储中记下待完成写入，再按协议回复，随后整理到磁盘。重启后根据记录继续。这个确认依赖真实的保护范围、记录完整性和恢复过程，不能仅凭设备名称判断。

NFS 版本

NFSv3 支持更大的文件范围、TCP 与较大传输，并通过 WRITE 的稳定性状态和 COMMIT 协调可靠保存。稳定存储承诺在协议规定的故障后保留结果。

NFSv4 增加打开与缓存管理状态，并提供统一命名空间、复合 RPC、ACL 与安全等机制。复合请求把多个相继操作放进一次交互，减少往返；额外状态则让系统能做更多协调，同时增加恢复工作。表中还列出相关实现的锁、缓存和重试机制。

方向 主要变化
NFSv3 64 位文件大小、TCP、大块传输、COMMIT
相关实现机制 锁管理、非易失存储、动态重试、客户端磁盘缓存
NFSv4 更多打开与缓存状态、变化通知、统一导出命名空间、复合 RPC、扩展属性、ACL 和安全机制

分块存储

GFS 用途

GFS 面向网页归档、索引构建和 MapReduce 一类批处理。文件常有多个 GB，读取较连续，新记录经常追加到末尾，因此系统关注持续吞吐与大容量。

单服务器文件服务仍受本机容量和失效影响。GFS 把文件分块并复制到普通硬件节点，分担容量与请求，并提供故障后的其他数据来源。其 2003 年设计使用客户端库，提供 create、delete、open、close、read、write，还增加 snapshot 与 record append。

接口支持原子重命名，应用可写完临时文件后发布正式名称。它没有提供 Unix 文件接口的全部功能，例如硬链接和符号链接，需要依据实际 API 编写应用。

网页归档这类负载为什么经常读取大文件、在末尾追加新记录？单服务器 NFS 模型在文件容量与服务器失效时遇到什么限制？

解答：

归档把新抓取的网页等记录加入末尾，保存后又经常成批顺序读取，所以大文件、连续读取和追加很常见。单服务器 NFS 可以保存大文件，但大小仍受协议、配置和本机存储容量限制；服务器失效时，该访问路径暂停。GFS 通过跨节点分块扩展容量，通过副本提供其他读取路径。

文件分块

文件被切成 chunk，每块有唯一的 64 位 handle，chunkserver 保存块内容，master 保存文件到块以及块到副本位置的关系。图中 C0 分布在节点 1、2、3，C1 分布在 2、3、4，客户端取得位置后直接传输数据。

经典块大小为 64 MB，默认三副本。chunk 在节点上保存为 Linux 文件，内部每 64 KB 单元有 32 位校验和，读取时用于发现损坏。热门内容可以增加副本，分担读请求。

大块减少元数据条目和重复定位，也让同一块上的多次读取复用连接。图中连续读 3 MB、每次读 1 MB：按 1 MB 分块时跨三个块，按 64 MB 分块时可以继续访问同一个 chunk。小文件或热点集中在一个块时，则需要注意空间及负载分布。

采用大 chunk 对元数据条目、master 查询和连接复用有什么作用？图中读取 3 MB、每次 1 MB，小块分布在三台服务器且每次新建连接时需要几次握手？三段数据在同一大块且复用连接时又需要几次？

解答：

大 chunk 减少同一文件所需的块条目，连续访问时可复用位置记录，减少 master 查询，并反复使用同一服务器连接。按题中图示，小块位于三台服务器且每次新建连接，需要 3 次握手；三段数据位于同一大块并复用连接时，只需 1 次握手。

恢复信息

master 内存中的元数据不能在崩溃后全部丢失。名称、目录关系和文件到 chunk 的映射，通过操作日志与检查点恢复；chunk 副本位置则可以在启动时向 chunkserver 查询，再结合心跳更新。

集中管理便于协调跨目录改名，但单 master 的内存和处理能力也会限制规模。复制同一份管理状态、把不同元数据分片、增加前端实例，是三种不同扩展方式。

客户端通常缓存 chunk handle 与副本列表。大文件顺序读一次时，内容复用较少，缓存定位信息更有价值；chunkserver 的 Linux 页缓存仍可服务常用内容。

一个 master 统一管理元数据有哪些便利？文件到 chunk 的映射为何要可靠保存，chunk 的副本位置又怎样在启动时重建？

解答：

一个 master 统一处理名称和块映射，较易安排元数据修改顺序，内存记录也便于查询。文件名到 chunk 的关系要通过日志、检查点等可靠保存，才能恢复原路径及文件组成。副本位置从 chunkserver 的块清单重建，运行时再通过心跳更新哪些节点保存了相应块。

元数据 处理方式
命名空间、文件到 chunk 的映射 在内存中查询，通过操作日志等材料持久化
chunk 的副本位置 启动时向 chunkserver 查询，运行时结合心跳更新

大文件经常连续读取一遍时，客户端缓存哪些信息最有帮助？文件内容还可以在哪一层获得缓存？

解答：

客户端主要缓存文件到 chunk 的编号及副本位置，后续访问同一块就可直接联系 chunkserver。大文件只连续读过一次时，文件内容的再次利用较少。chunkserver 上的操作系统页缓存仍可保存常用内容，减少重复磁盘读取；缓存和映射失效时再按协议重新检查。

读取文件

客户端用偏移除以块长 C，商为 chunk 编号，余数为块内位置。按 64 MiB 计算，70 MiB 位于 C1 内偏移 6 MiB。

图中客户端向 master 请求文件名和块编号对应的信息，得到 handle 与副本列表，再选择一个可用 chunkserver 请求字节范围。chunkserver 2 直接返回内容，数据不经 master 转发。

缓存的定位信息有效时，后续读取跳过 master，也可一次取得多块信息。副本失效、布局变化或缓存过期后再查询。选择时可以考虑网络距离、负载和有效版本；额外并行读或延迟重试，也会占用更多带宽。

写入文件

同一位置先写 A、再写 B，最后为 B；顺序反过来，最后为 A。第一张图中不同副本按不同到达顺序写入，因而分叉。GFS 用 primary 为同一 chunk 的修改排序，secondary 跟随该顺序。

master 给 primary 发放租约，示例有效期为 60 s，可通过心跳续期。一次写入先取得 primary 与 secondary 的位置，再推送数据。数据可以从一个 secondary 沿链经过 primary 到另一个 secondary，节点先缓冲并确认收到。

数据到齐后，客户端向 primary 发控制请求。primary 分配顺序、执行修改并通知 secondary，汇总结果后回复客户端。数据流路径按网络效率安排，修改顺序由控制消息确定，两者不必相同。后面的图将 A、B 都先缓冲，再统一按 A 后 B 应用。

中途失败可能只修改部分副本。chunk version number 帮助识别落后副本，系统排除无效读取来源，再恢复或重新复制。

顺序条件

副本从相同状态出发，按相同顺序完整执行确定的操作，才能得到相同结果。收到数据、开始修改和完成修改是三个时刻，ACK 必须说明确认了哪一步。

例如 A 的序号为 11，B 为 12，副本先收到 12 也要等 11 按协议处理。GFS 对同一 chunk 排序，跨 chunk 业务还需相应接口语义。失败时部分修改可能已经发生，客户端应按恢复与重试规则处理。

主副本切换

primary 失联后，master 要同时确认有效数据和有效授权。旧节点可能只是暂时断网，不能让它与新主继续各自确认写入。等待旧租约到期、更新版本与重新查询位置，都是相关协议的一部分。

新主选出来后，还要处理旧请求和落后副本，确定从哪份状态继续。节点名字的变化本身不等于完成安全接管。

流水传输

若完整传完 S 字节再发给下一节点，h 段链路依次花费约 h(α+S/B)。其中 B 为每段速率，α 为启动等待。

流水方式把内容拆成 q 字节的小段，第一段到达后立即继续转发，后续段同时沿不同链路前进。公式中 S/B 是整份数据通过一段的主要时间，(h−1)q/B 是最后小段穿过剩余阶段的时间，hα 是启动开销。

64 MiB 经三段独立 1 Gbit/s 链路，整份串行约为 1.6106 s；按 1 KiB 分段，理想流水约为 0.5369 s。网络仍运送了三份数据，只是传输重叠，转发能力与共享链路仍会限制收益。

T≈SB+(h−1)qB+hαT\approx\frac{S}{B}+(h-1)\frac{q}{B}+h\alpha T≈BS​+(h−1)Bq​+hα

把 64 MiB 数据依次送到三份副本，三段独立链路均为 1 Gbit/s。忽略启动时间，整份串行转发约多久？按 1 KiB 分段流水转发，理想值约多久？

解答：

一份数据的发送时间为 64×220/(109/8)≈0.536964\times2^{20}/(10^9/8)\approx0.536964×220/(109/8)≈0.5369 s，三段依次完成约为 1.6106 s。

流水转发约需 (64 MiB+2 KiB)/(1.25×108)≈0.5369(64\ \text{MiB}+2\ \text{KiB})/(1.25\times10^8)\approx0.5369(64 MiB+2 KiB)/(1.25×108)≈0.5369 s。这个估算要求各段能够同时传输，转发处理足够快，且没有共享带宽瓶颈。

64 MiB 是本例数据量，1 KiB 是网络流水的分段大小，两者与文件系统逻辑 chunk 的职责分别理解。

追加记录

record append 让服务器选择末尾位置并完整追加一条记录。若第一次成功但回复丢失，客户端重试仍可能追加另一份，因此记录完整与只出现一次是两个要求。应用可以为记录分配 ID，在后续处理中识别重复。

snapshot 保存某个时刻的文件或目录树版本。GFS 与作业调度器配合，为任务提供输入与结果。原部署例子包括 200 多个集群，许多有上千台机器与客户端，总容量超过 4 PB，读写负载约 40 GB/s；这些数值描述该历史部署。

HDFS

HDFS 受到 GFS 启发，用多个普通硬件节点保存大文件和副本。NameNode 管理名称与块元数据，DataNode 保存数据，block 对应 GFS 的 chunk。图中的 FSImage 与 EditLog 用于保存元数据状态和变化。

组件相似不表示接口相同。HDFS 通常按一个文件一个写入者及数据流水线组织写入，不能从架构图推导它具有 GFS record append 的全部语义。

训练存储

3FS 用途

训练会读取样本、保存检查点，推理也可能读写可复用的 KV cache。样本分散在许多文件中，客户端频繁打开文件并读小段内容，元数据查找、复制与队列开销会累积。

3FS 由 DeepSeek 开发，用文件与目录接口组织这些数据。图中四类负载分别是数据准备、随机取训练样本、集中写检查点和访问 KV cache。样本请求可能从几 KB 到数 MB，示例检查点超过每节点 10 GiB/s，KV cache 读取峰值为 40 GiB/s。GiB 按 2^30 B 计算。

训练顺序是清洗与转换数据、dataloader 取下一批、计算更新参数、定期保存参数和优化器等状态，故障后从有效检查点继续。样本打乱与实际 I/O 顺序可以通过批量、预读和缓冲协调。KV 复用还需匹配模型、前缀和计算条件，并计入取回成本。

硬件对照图给出 GFS 每节点两块 80 GB 磁盘、100 Mbps 网络，3FS 每节点 16 块 NVMe SSD、两条 200 Gbps RDMA，名义带宽相差 4000 倍。硬件变快后，CPU、复制和软件路径可能成为限制。

从大文件顺序读取变为大量样本随机读取，配合 NVMe SSD 和高速 RDMA 网络后，元数据查询与 I/O 软件路径需要怎样调整？

解答：

大量小文件随机读会提高打开、查属性和寻找块的频率。3FS 让多个元数据服务共享事务存储，打开时缓存布局，后续按公式计算 chunk 和复制链，减少逐块查询；native I/O 通过共享请求环和数据缓冲区减少内核队列与复制工作。这样能把较快硬件用于更多实际读写。

服务分工

客户端接收应用文件操作，元数据服务处理目录、inode、属性与布局，存储服务处理 SSD 和数据块，集群管理器维护成员、配置与存活状态。心跳用于了解节点状况，再按协议处理失联。

图上方是管理请求，下方是内容访问。多个元数据前端共享 FoundationDB，前端失效后，其他实例可以读取同一权威记录继续处理。提交结果不明的请求仍要确认原事务状态。

对照图中的历史 GFS 单 master 每秒几千次元数据操作只是特定实现的示意。多前端分担接入工作，后端状态仍要按自身分片、复制与事务规则管理。

3FS 的元数据保存在哪里？多个元数据服务怎样共享记录？单个服务失效后，其他服务继续处理请求需要哪些条件？

解答：

权威元数据保存在 FoundationDB 中，多个元数据服务从同一份事务键值存储读取和修改记录。一个实例失效后，其他实例需能访问共享存储及集群配置，按事务规则处理请求。进行中的事务还要确认是否提交，避免把结果不明的修改当作全新操作重复处理。

键值存储

键值接口按键取得记录，例如“文件 7”对应一份属性。分布式键值存储还要处理记录放置、复制和故障。事务接口把相关读取、检查和修改放在同一提交决定中。

3FS 元数据前端将文件操作转换成 FoundationDB 事务。多个前端可以访问同一组键，冲突由事务机制处理。增加前端不等于自动增加全部后端能力，后端或网络不可用时仍可能等待、重试或查询提交结果。

修改目录

目录项键可以写成 DENT|父目录inode|名称，值为子项 inode；INOD|inode号 保存属性和布局。移动 /x/a.txt 到 /y/a.txt 时，文件对象不变，删除旧目录项并建立新目录项即可。

图中两个名称分别位于目录 2、5，目标 inode 为 7。事务先检查源、目标及权限，再共同修改两个键。并发 unlink 若改变了相关记录，另一事务需要根据冲突结果重新读取。实际 rename 还要处理覆盖、目录环等条件。

重试重新执行事务过程，外部通知和普通内存副作用需要额外安排。回复丢失也可能发生在已经提交之后，因此应按同一操作身份确认结果。

记录 键的组成 值
目录项 DENT 前缀、父目录 inode、名称 子项 inode
inode INOD 前缀、inode 号 属性与文件布局

/x/a.txt 对应 inode 7，要移动到 /y/a.txt，其中目录 inode 分别为 2、5。键值存储要修改哪两个目录项？为什么要放在同一事务中？若另一个服务同时 unlink 源名称，怎样处理冲突？

解答：

在简化模型中，先读取并检查源、目标目录项，再删除 DENT|2|a.txt，建立 DENT|5|a.txt → 7。文件 inode 仍为 7，两次名称修改在一个事务中共同提交或撤销。并发 unlink 访问相关记录时，事务存储检查读写冲突，一方提交后，另一方重新读取最新状态，再决定继续处理或报告源名称已变化。

打开文件

3FS 跟踪写打开会话，使删除过程知道还有写入者可能产生数据。只读打开主要在客户端保存 fd 与布局，省去大量只读会话的管理写入。

图中训练样本通常稳定，减少只读会话成本有利于大量打开。但样本被删除后，已打开读者的后续远端访问可能失效。正在写的检查点需要延后回收，直到写会话关闭或按失联清理规则处理。

若删除先回收旧块，写入者随后又产生新块，可能留下无法从名称找到的空间。因此，会话、客户端存活判断和删除流程必须共同协调。共享后端保存会话状态，也使前端更换后能够继续处理。

训练启动时打开很多样本，记录所有只读会话会增加什么工作？3FS 跟踪哪些打开会话？样本文件与正在写的检查点被删除时，分别怎样处理？

解答：

记录每个只读打开会产生大量会话写入与清理工作。3FS 由客户端保存只读 fd 和布局，服务器跟踪写打开。样本没有需要保留的写会话时可被删除，已打开读者的后续远端读取可能失效；正在写的检查点则延后回收，等写会话关闭或失联会话被清理。

查找数据块

打开文件时取得块大小 C、条带宽度 stripe 和链列表。偏移决定块编号 i 与块内位置，chunk ID 为 (inode,i)，再用 i 对 stripe 取余选择 chains 中的项。复制链描述保存同一块的节点。

图中 inode 7、链列表为 1、2、3，块 3 余数 0 选择 chain 1，块 4 余数 1 选择 chain 2。C=4096 B、偏移 13000 B 时，i=3，块内偏移为 712 B，随后访问相应链上的 (inode,3)。

布局回答选哪条链，集群配置回答链上节点及地址。两者有效时可直接计算访问目标，变化后要更新，并处理旧配置下仍在进行的请求。

计算和存储

数据就近调度把任务放在已有输入的节点，减少网络传输。图左侧 MapReduce 在保存 C2 的机器处理 C2；右侧 3FS 让独立 GPU 节点通过 RDMA 取数据，优先按计算资源安排任务，称为 locality-oblivious。

分离后 GPU 与存储可分别扩容，但网络必须供应总输入量。例如 100 台各需 2 GB/s，聚合需求为 200 GB/s，存储、链路与交换路径都要承受。full bisection 描述相应的跨两组节点传输能力目标。

随机样本来自许多节点，把计算靠近某一份数据未必能靠近后续所有输入。可以通过多链路并行取数分担，但仍要检查热点、排队与实际拓扑。

locality-oblivious 的任务访问方式怎样安排计算和存储？它对网络带宽有什么要求，为什么计算节点和存储节点可以分别扩容？

解答：

GPU 与存储节点分开部署，任务主要依据计算资源安排，输入通过网络从相应存储节点取得。网络需要支撑跨节点的总数据需求，减少 GPU 等待输入。GPU 数量和存储容量可以按各自需求增长；实际效果还取决于存储服务、链路容量、排队和数据分布。

访问文件

普通应用调用 read 进入 VFS，FUSE 将请求转交用户态文件服务 daemon，daemon 访问远端存储后再返回。共享队列需要同步，数据经过 daemon、内核与应用时也可能复制。

图示测试环境中，FUSE 路径约每秒处理 40 万次 4 KiB 读取。高速硬件下，共享队列、调度与复制会占据更多时间。

native I/O 让应用先经 FUSE 打开并注册 fd，随后通过 Ior 请求环提交操作，通过 Iov 共享缓冲保存内容。客户端批量取请求并通过 RDMA 访问存储，减少每次经过 FUSE 队列的工作。初始化、注册及共享结构同步仍需要正确执行。

普通应用怎样通过 FUSE 访问 3FS？一次 read 从应用到存储服务，要经过哪些队列、程序和数据复制？

解答：

普通应用调用 read，进入 VFS，再由 FUSE 模块放入共享请求队列。用户态 daemon 取出请求并访问存储服务，数据沿返回路径交给应用。图中队列的多线程取放需要同步，数据在 daemon、内核和应用之间传递时存在复制，因而占用 CPU 与内存带宽。

高速存储和网络下，FUSE 路径可能在哪些环节等待？native client 的 Ior、Iov 分别传什么，怎样减少每次 I/O 的队列与复制工作？

解答：

FUSE 可能等待共享队列的锁、请求调度及内核与用户态之间的数据复制。Ior 保存读写请求，Iov 保存待写内容或读取结果。应用先打开文件并完成所需注册，随后通过共享内存提交请求，由 native client 批量处理并访问存储，减少每次经过 FUSE 队列和复制数据的工作；共享结构仍按接口同步使用。

结构 作用
Iov 共享数据缓冲区，读取结果进入其中，写入数据先放入其中
Ior 应用与 native client 间的请求环，用于异步提交与处理

共享缓冲

共享内存可以让应用地址 0x1000 与客户端地址 0x8000 映射同一物理页 P。地址不同，使用的字节相同，因此应用把内容放进 Iov 后，客户端无需再复制成另一份进程缓冲。

一次异步写先完成打开与注册，再填写数据、偏移、长度和缓冲位置，将请求发布到 Ior。客户端执行后返回完成状态，应用收到结果才能按规则复用缓冲。提交请求与 I/O 完成是两个时刻，期间仍需保留数据。

这种请求环借鉴 io_uring 的异步方式。open、close、stat 等管理操作继续使用相应文件接口，采用 native 数据路径需要应用明确管理异步完成和缓冲生命周期。

系统对照

三种系统

比较文件系统时，可以沿一次读追踪名称、对象、块与节点，再沿一次写追踪排序者、确认者及恢复记录。

NFS 让客户端携带远端句柄与游标，适合共享文件；GFS 将大文件分块，通过主副本安排修改顺序；3FS 为样本随机读提供共享元数据后端、布局计算和较短的数据路径。下面按负载、接口与定位方式对照，理解设计为什么随需求和硬件变化。
